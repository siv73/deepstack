The system so far, and what this page adds to it

Gateway v4 from Part 3 answers seller-b at 1,199 in 250 ms, reports seller-e as timed out, caps seller calls with one Semaphore shared by every request, and leaves nothing running. Its tests pass. Yet six small mistakes, each legal Python that raises no error where it is written, can still make it answer late, answer wrong, or fail without anyone noticing. This page makes each mistake on purpose.

Introduction

This is Part 4 of a ten-part series. Every part works on the same system: a price-comparison gateway that asks five sellers for a price and must answer within a budget of 250 ms. Parts 1 to 3 are the prerequisites for this page. This part recaps them in one screen; if any line below is unfamiliar, read that part first.

What Parts 1 to 3 built

  1. The five sellers: seller-a (80 ms, 1,249), seller-b (120 ms, 1,199), seller-c (150 ms, 1,229), seller-d (200 ms, 1,215) and seller-e (900 ms, 1,149). The right answer within 250 ms is seller-b at 1,199, with seller-e missing.
  2. Part 1: asked one after another, the waits add up to 1,450 ms; overlapped on one thread with a toy event loop, 900 ms. Part 1 also showed, on the toy loop, that one blocking call delays every task and that a forgotten await raises nothing.
  3. Part 2: the sellers became real TCP servers. asyncio's loop runs ready callbacks, sleeps in select() until a socket or a timer is due, and hands results over in Futures. A Task drives a coroutine step by step and stores its result or exception. Loop lag, measured with a timer, shows when something holds the loop.
  4. Part 3: a TaskGroup runs the five calls and cancels the rest on an unexpected failure; a Semaphore caps calls in flight; asyncio.timeout_at gives each request one deadline, entered before the wait for a slot. Expected seller failures and timeouts are returned as values. That is gateway v4.

What was still broken

  • Blocking calls: a synchronous call in a seller coroutine still freezes every Task.
  • Swallowed cancellation: a broad except in the wrong place can break the deadline and the TaskGroup.
  • Lost tasks and silent timeouts: Tasks created outside a group, forgotten awaits, and timeouts that nobody counts.

Why the traps exist: five promises the loop takes on trust

Last part: gateway v4 works, and this page breaks it six ways. Still unsolved: why are these mistakes possible at all, and why does none of them raise an error where it is made?

A thread pool protects itself: if one thread blocks, the operating system runs another. asyncio's loop cannot. It runs every request of the gateway on one thread and believes what each coroutine tells it. If a coroutine never hands back the thread, or quietly ignores a request to stop, the loop has no way to notice, let alone object.

Introduction

Parts 1 to 3 built the gateway on a small number of rules that the code must follow for the loop to work. Nothing in Python enforces them. This part names them, because each trap on this page is one of them broken, and the signal for each trap is whatever trace the broken rule happens to leave.

Comparison

Consider a shared office kitchen with one cook and a rota on the wall. The cook does whatever ticket is at the front, and trusts every ticket to say honestly what it needs. A ticket written but never handed in is never cooked. A ticket that says "stir for 10 seconds" but means "stir for 10 minutes" holds the cook while every other order goes cold. An order nobody collects is thrown away without anyone hearing about it.

  • The cook = the loop's one thread.
  • A ticket never handed in = a coroutine that is never awaited or turned into a Task.
  • A ticket that holds the cook = code that blocks instead of awaiting.
  • An order nobody collects = a Task whose result or error nobody reads.

The comparison stops working here: a cook can be interrupted. The loop cannot interrupt a coroutine at all; it can only throw an exception in at the next await, and the coroutine decides what to do with it.

Definition

An async trap is a mistake in asyncio code that the language accepts, that raises no error at the line where it is made, and that breaks one of the promises below, so the damage appears somewhere else: in another request, at another time, or only under load.

Working: the five promises

  1. Every coroutine is handed to someone who runs it. It is awaited, or wrapped in a Task. A coroutine object on its own does nothing (Part 1).
  2. Every step gives the thread back quickly. Code runs between awaits without waiting on the network, the disk or a long computation. The loop can only switch at an await (Parts 1 and 2).
  3. Every Task has an owner who reads its outcome. Someone keeps a reference to it and reads its result or its exception. A Task stores its failure; it does not announce it (Part 2).
  4. Cancellation always travels out. When a Task is cancelled, the CancelledError thrown in at its await is allowed to leave the coroutine, after any clean-up. Deadlines and TaskGroups are built on it (Part 3).
  5. Every missing answer is counted. A seller that timed out or failed is reported as such, so a partial answer is visible. This one is the gateway's promise, not the loop's.

Why each promise is needed

  • Promise 1: the loop only runs what is in its ready queue or parked on a Future; a coroutine object nobody hands over is in neither.
  • Promise 2: the loop is one thread; while a step runs, nothing else does, including the timer that enforces the deadline.
  • Promise 3: a Task keeps its exception until someone asks for it; with no owner, nobody asks.
  • Promise 4: timeout, timeout_at and TaskGroup stop work by cancelling it; if the cancellation is caught and dropped, the work goes on.
  • Promise 5: a partial answer looks like a normal answer; only a count makes the difference visible.

Wrong belief: "If something goes wrong in async code, an exception will tell me."

Why people hold it: in ordinary synchronous code, a mistake usually raises at the line that made it.

Why it is wrong: in four of the six traps nothing is raised anywhere the caller can see: a forgotten await only warns, a blocking call only makes things late, a lost Task keeps its exception to itself, and a swallowed cancellation makes a deadline quietly not fire. The fifth, gather, raises the first failure and drops the next ones. The signals are warnings, logs, late timers and counts, not exceptions.

  • The loop trusts five promises: hand over every coroutine, give the thread back, own every Task, let cancellation out, count every missing answer.
  • Each trap breaks one promise and raises no error where it is written.
  • The damage appears elsewhere: other requests, later, or under load.

The loop runs on trust: each trap is one broken promise whose damage shows up somewhere other than the line that broke it.

Introduction

Part 2 opened asyncio's loop: a ready queue of callbacks, a timer heap, a selector, Futures that hand results over, and Tasks that step coroutines. This part walks the six traps through those same pieces, using CPython 3.14's source. Each trap gets its own part later; here the aim is the map.

Working: the six hiding places

  1. Forgotten await: before the loop ever sees it. Calling an async function only builds a coroutine object. Without await or a Task, it never reaches the ready queue. The docs say that when a coroutine function is called but not awaited, or not scheduled with create_task(), asyncio emits a RuntimeWarning. The warning is issued when the dropped object is cleaned up, not where it was dropped.
  2. Blocking call: inside one callback of one iteration. In CPython 3.14's base_events.py, each loop iteration counts the callbacks in the ready queue and calls them one after another; each call returns before the next starts. A Task step is one such callback. If it blocks for 900 ms, the next select() and every due timer, including the deadline's, wait 900 ms.
  3. Lost Task: in a reference the loop does not keep. The docs warn that the event loop only keeps weak references to tasks, so a task that isn't referenced elsewhere may get garbage collected at any time, even before it is done. In CPython 3.14's futures.py, a Future whose exception was set but never retrieved reports "exception was never retrieved" from its __del__ method, that is, only when the object is destroyed.
  4. gather: in a done callback that has stopped listening. In CPython 3.14's tasks.py, once gather()'s outer Future is done, its done callback marks the exception of each child that finishes later as retrieved and returns without passing it on.
  5. Swallowed cancellation: at the await where CancelledError arrives. Task.cancel() arranges for a CancelledError to be thrown into the wrapped coroutine on the next cycle of the event loop, and the coroutine then has a chance to clean up or even deny the request by suppressing the exception. In CPython 3.14's timeouts.py, the timeout's exit turns a CancelledError into TimeoutError only when that CancelledError is leaving the block; if the block ends without an exception, nothing is raised.
  6. Silent timeout: in an except clause that is too wide. TimeoutError is one of the built-in subclasses of OSError. So except OSError, meant for refused or reset connections, also catches the deadline's TimeoutError, and so does except Exception.

The detector: asyncio's debug mode

Introduction

asyncio has a debug mode built for exactly this. It does not change what the program computes. It adds checks and timings to the loop and records where objects were created, so the warnings and logs of traps 1 to 3 name the line that caused them. This part shows how to turn it on, what it reports, and how to make a test suite fail on what it finds.

Definition

Debug mode is asyncio's development setting. The docs list four ways to enable it: the PYTHONASYNCIODEBUG environment variable set to 1, the Python Development Mode, debug=True passed to asyncio.run(), or loop.set_debug().

What it reports

  1. Slow steps. In debug mode, callbacks taking longer than 100 milliseconds are logged, and loop.slow_callback_duration sets the minimum duration, in seconds, that counts as slow. In CPython 3.14's base_events.py, the loop times each ready callback in debug mode and logs a warning "Executing … took … seconds" when it took at least slow_callback_duration. A Task step is a callback, so a blocking call shows up here with the Task's coroutine named.
  2. Where a never-awaited coroutine was created. In debug mode, the never-awaited RuntimeWarning adds a "Coroutine created at" traceback that ends at the line that called the coroutine function. In CPython 3.14, turning debug mode on also turns on coroutine origin tracking with sys.set_coroutine_origin_tracking_depth().
  3. Where an unread Task was created. With debug mode on, the "Task exception was never retrieved" message also shows the traceback where the task was created.
  4. Calls from the wrong thread. In debug mode, many non-threadsafe asyncio APIs, such as loop.call_soon() and loop.call_at(), raise an exception if they are called from a wrong thread. Part 2 measured this one.
  5. Slow I/O polls. The execution time of the I/O selector is logged if it takes too long to perform an I/O operation.

Why each report is needed

  • Report 1 is the only runtime signal for trap 2 that names the code; loop lag (Part 2) says that something blocked, not what.
  • Reports 2 and 3 turn traps 1 and 3 from "somewhere in the program" into one file and one line.
  • Report 4 catches the cross-thread mistake Part 2 showed, which otherwise only makes callbacks late.

Introduction

Static checks read the source without running it. They are cheap and run on every change, so they are worth having; but they can only recognise patterns they were written for. This part runs one linter, Ruff, over seven small trap examples, shows exactly which ones it flags, and names a type-checker rule for the most common trap it misses.

Definition

A static check reads source code without running it and reports patterns known to be mistakes. A linter checks patterns; a type checker checks types, and can see that a value is a coroutine that nobody uses.

The rules used

  • Ruff's rule RUF006 checks for asyncio.create_task and asyncio.ensure_future calls that do not store a reference to the returned result.
  • Ruff's rule ASYNC251 checks that async functions do not call time.sleep. Ruff's rule ASYNC210 checks that async functions do not contain blocking HTTP calls.
  • Ruff's rule BLE001 checks for except clauses that catch all exceptions, including except BaseException and except Exception; clauses that re-raise, or that log the exception with exc_info enabled, are not flagged.
  • mypy's unused-coroutine check, one of its error codes enabled by default, reports an async def function whose return value is ignored, because the coroutine won't be executed at the call site.

Trap 2a: a sync SDK that freezes every request

Last part: a forgotten await skips work silently. Still unsolved: the opposite mistake, code that does its work but will not give the thread back while it waits.

seller-e's vendor stops supporting its HTTP API and ships a Python SDK instead, built on blocking sockets. A developer calls sdk.get_price(item) inside the seller coroutine, the way the README shows. The next request answers after 900 ms, and the cheapest offer is now seller-e at 1,149, while the four fast sellers are all reported as timed out.

Introduction

Part 1 showed a blocking call on the toy loop, where it could only be faked with time.sleep. Here it is the real thing: a library that waits on a socket without ever awaiting. The docs say blocking (CPU-bound) code should not be called directly: if a function performs a CPU-intensive calculation for 1 second, all concurrent asyncio Tasks and IO operations would be delayed by 1 second. A blocking network call does the same, and the result on the gateway is stranger than "slow": the answer is wrong in a way that looks plausible.

What the user sees

Every request takes 900 ms instead of 250 ms, and every request names seller-e as the cheapest, with seller-a to seller-d "timed out". A dashboard would show the four fastest sellers failing and the slowest one perfect: exactly backwards.

Root cause

  1. The TaskGroup creates five Tasks. Their first steps run one after another in one loop iteration (Part 2).
  2. Sellers a to d each run until await asyncio.open_connection(...) and park on a Future. Their requests are not sent yet.
  3. seller-e's step calls sdk.get_price(). It connects, sends and waits for the answer inside the call, holding the loop's only thread for 900 ms. The step then returns the Offer, so seller-e's Task finishes within that same step, and its timeout's exit cancels its own timer.
  4. Only now does the iteration end. The next one finds sellers a to d's connections ready and the 250 ms deadline timers 650 ms overdue. The timers cancel sellers a to d before they can send a byte.
  5. The group ends with four TimeoutErrors and one offer: seller-e at 1,149, after 900 ms.

Why each step matters

  • Step 3: the deadline cannot cut seller-e, because cutting is a timer callback and callbacks need the thread seller-e is holding (Part 1 showed the same on the toy loop).
  • Step 4: the healthy sellers are punished for the slow one; their timers fire late, all at once.

Program

SyncSellerClient stands in for the vendor's SDK: plain blocking sockets to seller-e's server. Blocking is gateway v4 with seller-e called through it directly. InAThread makes the same call in a thread of seller-e's own pool with loop.run_in_executor().

Explanation of the program

  1. Called directly, the SDK produces the backwards answer from the root cause: seller-e at 1,149 after about 900 ms, sellers a to d timed out. No seller line is printed for a to d, because none of them ever sent its request.
  2. In a thread, seller-e's call waits in another OS thread, the loop stays free, sellers a to d answer at 80 to 200 ms, and the deadline cuts seller-e at 250 ms: gateway v4's answer again.
  3. After the answer, one SDK call is still running in its thread. It finishes at about 900 ms with nobody waiting for it. The deadline stopped the gateway's wait, not the thread.

Why the thread keeps running

loop.run_in_executor() arranges for a function to be called in the given executor; if the executor is None, the default executor is used, which, unless set with set_default_executor(), is a ThreadPoolExecutor created the first time it is needed. It returns an asyncio Future linked to the executor's own future. In CPython 3.14's futures.py, when the asyncio Future is cancelled, the linked executor future's cancel() is called. But a concurrent.futures Future cannot be cancelled once its call is being executed: cancel() then returns False. So the deadline cancels the gateway's wait at 250 ms, and the thread runs to 900 ms regardless. A call still waiting in the pool's queue, by contrast, is cancelled before it starts; gateway v5's part uses that.

to_thread or run_in_executor

asyncio.to_thread() runs a function in a separate thread, propagates the current contextvars context to it, and is primarily intended for IO-bound functions that would otherwise block the event loop. In CPython 3.14's threads.py, to_thread() is loop.run_in_executor(None, …) around a copy of the current context, so it always uses the loop's default executor. That is fine for an occasional call. For a dependency every request uses, the gateway passes its own pool to run_in_executor; gateway v5's part measures why.

Probing question: "A vendor only ships a sync SDK, and your service is asyncio. What are your options, and what does each cost?"

What a strong senior answer contains: first, look for an async client or call the vendor's HTTP API directly with an async client. If the SDK is the only option, run it with run_in_executor in a thread pool of its own, sized from the call rate and how long each call holds a thread, with a deadline around the await. The candidate says plainly that the deadline frees the request, not the thread: a call that runs on after its deadline still occupies a thread, so the pool's size, not the deadline, bounds the cost. If the calls are slow and frequent, moving them off the request path (a cache refreshed in the background) can beat any pool size.

Wrong belief: "The deadline will cut the slow sync call at 250 ms, like any other seller call."

Why it is wrong: a deadline is a timer callback on the loop. While the sync call holds the thread, no callback runs; the deadline fires only after the call returns, and by then it can only cut the calls that were waiting behind it.

  • A blocking call in a coroutine holds the loop: every other Task and every timer waits, including the deadline.
  • On the gateway, the slowest seller "wins" at 900 ms and the four fast ones time out.
  • Fix: run_in_executor (or to_thread); the deadline then frees the request, but the running thread continues to the end.

A sync call in a coroutine freezes every request and even the deadline, so it belongs in a thread, where the deadline can free the request though not the thread.

This needs Parts 2 and 3. Suppose seller-b (120 ms), not seller-e, is the one called through a sync SDK directly. With gateway v4's 250 ms deadline, which sellers answer and what is the cheapest offer?

The deadline cuts seller-c, seller-d and seller-e at 250 ms. The answer is still seller-b at 1,199, but with seller-c and seller-d timed out: one 120 ms block cost two healthy sellers.

Trap 2b: CPU work, where a thread does not help

Last part: a sync SDK belongs in a thread, which waits on its socket without the loop. Still unsolved: work that does not wait at all, but computes. Does a thread fix that too?

The gateway adds a ranking step: a pure-Python model scores the offers before the cheapest is returned. It costs about 100 ms of CPU per request. Six requests arrive together. On the loop, the last of them waits behind the other five's ranking; a timer that should fire every 10 ms fires several hundred ms late.

Introduction

Part 1 separated waiting (I/O-bound) from computing (CPU-bound) and noted that, in CPython, only one thread runs Python code at a time. That rule decides this trap. A thread fixed seller-e's SDK because the SDK mostly waits. A ranking step never waits; moving it to a thread only moves it to a different place in the same single queue for the interpreter.

Definition

A process pool is a set of worker processes that run submitted functions. ProcessPoolExecutor uses the multiprocessing module, which allows it to side-step the Global Interpreter Lock, but also means that only picklable objects can be executed and returned.

What the user sees

Latency rises for every request, not only the ones that rank, and it rises with load: each ranking adds about 100 ms to every request whose turn on the loop comes after it. Loop lag shows the same numbers.

Root cause

  1. On the loop: the ranking runs inside a Task step, so it holds the iteration for its whole 100 ms, exactly like the sync SDK, but with the CPU busy instead of idle.
  2. In a thread: the loop thread is free between the GIL switches, so timers still fire, but the six rankings still run one at a time on the interpreter. The docs say that, due to the GIL, asyncio.to_thread() can typically only be used to make IO-bound functions non-blocking, unless an extension module releases the GIL or the Python implementation has none.
  3. In a process pool: each ranking runs in another process with its own interpreter, on another core. The loop only sends the offers and receives the result.

Program

score_offers() is the ranking step. The program calibrates it to about 100 ms of CPU on the machine running it, then runs six rankings three ways while a 10 ms heartbeat timer measures how late the loop is.

Explanation of the program

  1. On the loop, the six rankings run back to back inside one iteration, and the heartbeat's worst lag is almost the whole run: the loop was frozen.
  2. With two threads, the total is no shorter than on the loop, because the interpreter runs one ranking at a time; the heartbeat's lag drops to tens of milliseconds, because the loop thread gets the interpreter between switches.
  3. With two processes, the total drops to well under the thread version's on two cores, and the heartbeat is on time.
  4. Exact times vary with the machine and its other work; the test checks the relationships: the loop frozen, threads no faster, processes faster with the loop free.

Trap 3: background Tasks that vanish or fail silently

Last part: CPU work goes to processes. Still unsolved: work that runs on the loop but belongs to no request at all, such as sending the per-seller counts to the metrics service. Who owns it, and who hears when it fails?

The gateway starts its metrics flusher with self.flusher = asyncio.create_task(flush_every(...)) and never looks at it again. One night the metrics service refuses connections. The flusher's first send fails, the Task ends with ConnectionRefusedError, and the dashboard stays flat for three days. No error appears in any log.

Introduction

Part 2 showed that a Task stores its coroutine's exception instead of raising it into the loop, and warned that the loop keeps only weak references to Tasks. Part 3 gave every request's Tasks an owner, the TaskGroup. A background job outlives any request, so it has no group. This part shows the two ways such a Task is lost (collected while still waiting, or ended by an error nobody reads) and a small helper that fixes both.

What the user sees

Nothing, until someone needs the background job's work: a flat dashboard, a cache that stopped refreshing, an audit trail with gaps. At best a single "Task exception was never retrieved" line, far from the cause and with no request attached.

Root cause, part 1: which Tasks can disappear

The docs warn that the event loop only keeps weak references to tasks, so a task that isn't referenced elsewhere may get garbage collected at any time, even before it is done. In practice, in CPython 3.14, a waiting Task is also referenced by whatever will wake it: a timer's callback, a socket's callback, or a Future someone else holds (Part 2's done callbacks). It is collected only when nothing that can wake it is reachable either. In CPython 3.14's tasks.py, a Task destroyed while still pending reports "Task was destroyed but it is pending!" from its __del__ method.

Explanation of the program

  1. Three Tasks are created and no reference to any of them is kept.
  2. The timer Task is reachable through the timer heap; the Event Task through the Event, which main() keeps. Both survive gc.collect() and finish.
  3. The third Task waits on a Future that only it can reach. gc.collect() destroys it while it is pending: asyncio reports it, and its finally runs at that moment, inside the garbage collector, not at any point the code chose.
  4. The docs' warning is a promise not made, not a description of when collection happens: keep the reference whatever the Task waits on.

Root cause, part 2: who reads the failure

For reliable fire-and-forget tasks, the docs recommend keeping them in a collection such as a set, and having each task remove itself on completion with add_done_callback(background_tasks.discard). The docs add that this approach never awaits the tasks, so if a task fails, its exception is never retrieved and asyncio logs a "Task exception was never retrieved" message when the task is garbage collected. The gateway's version of the trap is worse still: a reference kept in an attribute and never read means the Task is never collected, so even that message never appears.

Explanation of the program

  1. Kept in self.flusher and never read: the Task is done with ConnectionRefusedError, and the failure is reported nowhere. It would surface only when the gateway object itself is destroyed.
  2. With no reference: the Task is collected after it ends, and asyncio's exception handler receives "Task exception was never retrieved", with no name and no request.
  3. With spawn(): the set keeps the Task alive while it runs; the done callback reads the exception at once, logs it with the Task's name, and counts it in failures, which can feed an alert.

The signal

  • "Task was destroyed but it is pending!" and "Task exception was never retrieved" in the asyncio logger; with debug mode on, each names the line that created the Task.
  • A background job's own output stops (a counter that stops moving), with no matching error.
  • RUF006 at review time, for a create_task whose result is not stored.

In February 2023, a post by Will McGugan on the blog of the Textual project warned that a task created with asyncio.create_task may disappear without warning when Python runs garbage collection if no reference to it is held, a bug it called almost impossible to reproduce, and recommended keeping a reference for as long as the task must live, or using TaskGroups.

In-process background work dies with the process. Even a perfectly owned Task is lost on a deploy or a crash, and Part 2 showed that asyncio.run cancels whatever is still running when main() returns. Counts lost on a restart are acceptable for a metrics flush. Work that must happen, such as an order confirmation, belongs in a durable queue or an outbox table, not in a Task.

Wrong belief: "Storing the Task in an attribute is enough; it cannot be lost now."

Why it is wrong: it can no longer be collected, but its failure is still never read, and now not even the "never retrieved" message will appear while the object lives. Ownership means both: a reference, and someone who reads the outcome as soon as the Task ends.

  • A Task with no reference may be collected when nothing can wake it; its finally then runs inside the garbage collector.
  • A Task nobody reads keeps its failure: reported late ("never retrieved"), or never if a reference is held.
  • Fix: a set for the reference plus a done callback that reads, logs and counts the exception; a TaskGroup when the work belongs to a request.

A background Task needs an owner that keeps it alive and reads its outcome the moment it ends; without one it can vanish, and its failure can go unheard.

A team adopts the docs' recipe exactly: a module-level set, and task.add_done_callback(background_tasks.discard). One background job raises an exception. When do they hear about it?

  1. Immediately, from the done callback
  2. Never, because the set keeps the Task alive
  3. Only when the Task is garbage-collected after the set drops it, as a "Task exception was never retrieved" log line

The docs say this recipe never awaits the tasks, so the exception is never retrieved and is logged only at garbage collection. A done callback that calls task.exception() itself, as spawn() does, reports it at once.

Trap 4: gather keeps running after it fails, and drops what comes next

Last part: a background Task needs an owner who reads its outcome. Still unsolved: gather looks like an owner of the Tasks it runs. When does it stop being one?

An older part of the gateway still uses asyncio.gather(). seller-c fails at 150 ms, gather raises, and the request returns an error. At 200 ms seller-d fails too. That second failure, which may be the real cause of an incident, appears in no log and no metric. And in another path, a request crashes with AttributeError: 'CancelledError' object has no attribute 'price'.

Introduction

Part 3 measured gather's best-known problem: when one call fails, the others keep running, holding connections, until they finish. This part adds two less obvious failures that make no sound: what gather does with the second failure, and what return_exceptions=True puts in the result list when a call is cancelled.

Recap from Part 3

With return_exceptions=False, the default, the first raised exception is immediately propagated to the task that awaits gather(), and the other awaitables won't be cancelled and will continue to run. The docs note that TaskGroup provides stronger safety guarantees than gather: if a task raises, TaskGroup cancels the remaining tasks and gather does not.

What the user sees

For the first failure: a request that failed, with only half of the story in the logs. For the second: an occasional crash with a confusing message about CancelledError, in code that "handles all exceptions".

Root cause

  1. Later failures are dropped. gather's outer Future is done once it has raised. In CPython 3.14's tasks.py, once gather()'s outer Future is done, its done callback marks the exception of each child that finishes later as retrieved and returns without passing it on. Marked as retrieved, the exception is never logged, not even as "never retrieved".
  2. A cancelled child becomes a CancelledError in the list. If a Task or Future passed to gather() is cancelled, it is treated as if it raised CancelledError, and the gather() call itself is not cancelled. With return_exceptions=True, exceptions are treated the same as successful results and aggregated in the result list. So a cancelled seller call shows up as a CancelledError object among the offers.
  3. And CancelledError is not an Exception. Since Python 3.8, asyncio.CancelledError is a subclass of BaseException rather than Exception. Code that filters the list with isinstance(r, Exception) keeps it as if it were an offer.

Program

The first half fails seller-c and seller-d and checks, after garbage collection, whether asyncio reported seller-d's failure; a plain Task with the same failure, nobody reading it, is the control.   2. After every Task is garbage-collected, asyncio has reported nothing. The control, the same seller-d failure in a Task nobody reads, is reported as "Task exception was never retrieved". gather did not lose the failure by accident; it marked it as read.

Trap 5: one broad except that breaks every deadline

Last part: gather drops failures and hides cancellations. Still unsolved: what if the code inside a call is the one hiding the cancellation, so that the deadline itself stops working?

Someone adds a retry wrapper around each seller call: "on any failure, wait 50 ms and try once more". It is written with except BaseException so that "nothing can crash a seller call". From then on, requests take 1,200 ms, the cheapest offer is seller-e at 1,149, and the timeout counter shows zero. The deadline is still in the code; it has simply stopped working.

Introduction

Part 3 built the deadline from asyncio.timeout_at, and showed that a timeout is a timer that calls Task.cancel(). Cancelling works by throwing CancelledError into the coroutine at its current await. This part shows what happens when the coroutine catches that exception and carries on. It stays at the surface: how to recognise the trap and fix it. Part 5 goes inside cancellation itself.

Definition

To swallow a cancellation is to catch CancelledError and not raise it again, so the coroutine continues as if it had not been cancelled. The docs warn that TaskGroup and asyncio.timeout() are implemented using cancellation internally and might misbehave if a coroutine swallows CancelledError.

What the user sees

Requests that ignore their budget: 1,200 ms instead of 250 ms. Their answers often look better (seller-e's cheaper price arrives), so the bug can even look like an improvement in a dashboard of prices.

Root cause

  1. At 250 ms the deadline's timer calls cancel() on seller-e's Task. In the next step, CancelledError is thrown in at the await inside the first attempt.
  2. except BaseException matches it, because CancelledError is a BaseException. The wrapper sleeps 50 ms and starts a second attempt.
  3. The second attempt is not cancelled again: the cancel request was delivered once, and it was caught. seller-e answers 900 ms later, at about 1,200 ms.
  4. The async with asyncio.timeout_at(...) block ends normally, with a value. In CPython 3.14's timeouts.py, the timeout's exit turns a CancelledError into TimeoutError only when that CancelledError is leaving the block; if the block ends without an exception, nothing is raised. No TimeoutError is raised, yet the timeout's expired() method returns whether the context manager has exceeded its deadline, and here it returns True.
  5. The TaskGroup waits for every Task, so the whole request waits for seller-e.

Program

Explanation of the program

  1. retry_anything catches BaseException. seller-e's first attempt is cancelled at 250 ms, the wrapper retries, and seller-e answers at about 1,200 ms. The report says "cheapest: seller-e at 1,149 after 1200 ms" with no timeout listed, and expired() is True.
  2. retry_errors catches only SellerError and ConnectionError, the failures a retry can fix. CancelledError passes through, the timeout turns it into TimeoutError, and the answer is gateway v4's again.
  3. Both versions print expired() = True: the deadline fired in both. Only the first one let the request ignore it.

The rule, and the fix

The docs recommend try/finally blocks for clean-up, and say that if CancelledError is explicitly caught, it should generally be propagated when clean-up is complete; because it directly subclasses BaseException, most code will not need to be aware of it. The exceptions reference adds that in almost all situations a caught CancelledError must be re-raised. In practice:

  • Catch the exceptions you can handle, by name. except Exception already lets CancelledError through.
  • Put clean-up in finally, which runs on cancellation too.
  • If you must catch BaseException (to log everything), end the handler with a bare raise.
  • For the rare case where suppressing cancellation is truly intended, the docs say Task.uncancel() must also be called, and that user code should not generally call it. That is Part 5's subject.

Which retry wrapper is safe under gateway v4's deadline?

  1. A bare except: that waits and retries
  2. An except asyncio.CancelledError: that logs "cancelled, retrying" and loops again
  3. An except (SellerError, ConnectionError): that waits and retries, with clean-up in finally

Only the named exceptions are retried; CancelledError, a BaseException, passes through, so the deadline still ends the call and finally still cleans up.

In your own words: why does an except BaseException in a retry wrapper make gateway v4 answer at 1,200 ms with no timeout reported?

At 250 ms the deadline cancels seller-e's Task, which throws CancelledError in at the await inside the first attempt. The wrapper's except BaseException catches it, so the coroutine carries on and retries; the second attempt is not cancelled again. The timeout only turns a CancelledError into TimeoutError if it leaves the block, so the block ends normally with seller-e's offer. The TaskGroup waits for that Task, so the request answers at about 1,200 ms, with seller-e as the cheapest and no timeout recorded.

Introduction

What the user sees

Root cause: three ways a timeout goes missing

  1. Relabelled. asyncio.timeout() turns the resulting CancelledError into a TimeoutError, which can only be caught outside the async with block. Outside the block, it is a TimeoutError, and TimeoutError is one of the built-in subclasses of OSError. So an except OSError written for refused connections catches it too. If that handler wraps everything as one "seller failed" error, the timeout is counted as a failure, with an empty message, because a TimeoutError raised by a timeout has no text.
  2. Not counted. The answer lists seller-e as timed out, the response is a normal 200, and nothing aggregates that list. One request's partial answer is invisible among thousands.
  3. Never fired. A timeout around a blocking call cannot fire during the call (trap 2), and when the call returns the block exits without an exception. Part 3's asyncio.wait(timeout=...) is the other silent form: wait() does not raise TimeoutError; futures that are not done when the timeout occurs are returned in the second set, and unlike wait_for(), wait() does not cancel them.

Program

Explanation of the program

  4. Never rely on a timeout around blocking code; move the code to a thread first (trap 2).

A handler around a seller call has except OSError: return Failure(name) and then except TimeoutError: return Timeout(name), in that order. The try sits outside an async with asyncio.timeout(...) block. The deadline fires. What is recorded?

Solved example: sizing v5 for 2,000 requests per second

Given: 2,000 requests per second (10 times Part 1's 200). seller-e's sync call holds a thread for 900 ms and cannot be stopped once running. Ranking costs about 1 ms of CPU per request here. Each request records 5 outcomes; the metrics client sends a batch every 100 records.

Step 1. seller-e's threads if every call ran. Threads busy = calls per second × seconds each holds a thread = 2,000 × 0.9 = 1,800 threads. And every one of those calls answers after the 250 ms deadline, so all 1,800 threads would produce nothing anyone reads.

Step 2. With a pool of 4. At most 4 threads are busy. A call that has not started when its deadline fires is cancelled in the queue (the trap 2a part: a waiting executor call can be cancelled, a running one cannot). So the pool's size is the amount of waste the gateway accepts, here 4 threads, not a capacity to fill. For a dependency that does answer in time, the same arithmetic sets the size the other way: a 100 ms sync call at 2,000 per second needs about 2,000 × 0.1 = 200 threads.

Step 3. Ranking. CPU needed = 2,000 × 1 ms = 2,000 ms of CPU per second: two cores' worth, in addition to the loop's own work. A gateway process with a pool of 2 workers is at its limit; at 10 times the load, run several gateway processes (Part 1's one loop per core), each with its own small pool.

Step 4. Metrics. Records per second = 2,000 × 5 = 10,000, so 100 batches per second. Each full batch is sent inside the record() call that filled it, so 1 request in 20 waits for one send (5 records per request, 100 per batch). The background flusher only sends what is left each second.

Result: the scarce resources at 10 times the load are threads for seller-e and cores for ranking; the pool sizes cap both, and the deadline keeps unanswerable seller-e calls from ever starting.

Why seller-e must not use the loop's default pool

The docs note that loop.getaddrinfo() and getnameinfo() use their synchronous versions through the loop's default thread pool executor, so when that executor is saturated these methods may be delayed, which higher-level networking libraries may report as increased timeouts. In CPython 3.14's base_events.py, a connection to a host name that is not already an IP address is resolved with loop.getaddrinfo(), which runs socket.getaddrinfo() with run_in_executor(None, …). Real sellers are reached by name, so with to_thread() seller-e's 900 ms calls and every seller's name lookups wait in the same queue.

Probing question: "How do you size a thread pool for a blocking dependency in an async service?"

What a strong senior answer contains: Little's law: threads ≈ calls per second × seconds each call holds a thread, using the dependency's real latency, not the request deadline, because a call that outlives its deadline keeps its thread. Then the ceiling: the dependency's own capacity, memory per thread, and the fact that a waiting call can be cancelled before it starts but a running one cannot. The pool is a separate bulkhead per dependency, never the shared default, which also serves name lookups. And if the dependency rarely answers within the budget, the right size is small, or the call belongs off the request path.

Wrong belief: "A bigger thread pool for seller-e means more of its answers get through."

Why it is wrong: seller-e takes 900 ms and the budget is 250 ms; no pool size changes that. A bigger pool only means more threads busy on answers nobody will read. The small pool is the better design: it drops the calls that cannot help before they start.

Introduction

Three prompts follow. Each draws on this page and at least one earlier part. Try each before opening the reference answer.

Prompt 1: "Every endpoint got slow at once, and CPU is low"

The service fans out to five downstreams per request. After a release, p99 is 900 ms on every endpoint, including the health check. CPU is 15%. What is your hypothesis, how do you confirm it, and what is the fix and its cost?

Every endpoint at once points at the shared loop; low CPU means it is waiting, not computing: a blocking call in a coroutine, probably a sync client added in the release. Confirm with loop lag (a periodic timer firing late) and then name the coroutine with debug mode on a canary: "Executing … took 0.900 seconds". Fix: an async client, or run_in_executor with a pool of its own sized as rate × seconds held. The cost: threads that keep running after the request's deadline, so the pool size, not the deadline, bounds the waste; and if the dependency is slower than the budget, no pool makes it useful.

Prompt 2: "Our timeouts don't seem to work"

The service wraps each downstream call in asyncio.timeout(0.25). Some requests take over 1 s, and the timeout metric is flat. Name the two most likely causes and how you tell them apart.

Either the deadline fires and is swallowed (a retry or "never crash" handler catching BaseException, so the CancelledError never leaves the block and no TimeoutError is raised; expired() is True), or it cannot fire because a blocking call holds the loop until the call ends and the block finishes without awaiting again (expired() is False and loop lag spikes). Fix the first by catching exceptions by name and re-raising CancelledError after clean-up; fix the second by moving the call to a thread. A senior answer adds the TaskGroup consequence: a swallowed cancellation also stops the group from ending, so it can hang shutdowns too.

Prompt 3: "Design background work for an async API"

The API must send per-dependency metrics every second and must also send an order confirmation after each purchase. Design both, and say what each design gives up.

The metrics flush is a long-lived background Task started with a helper that keeps a strong reference in a set and adds a done callback that reads the exception, logs it with the Task's name and increments a failure counter that pages someone; losing a few seconds of counts on a deploy is acceptable. The order confirmation must not be lost, so it is not a Task at all: it is written to an outbox table in the same transaction as the order, and a worker sends it with retries; that costs a table and a worker, and gives at-least-once delivery. Any work that belongs to one request runs in that request's TaskGroup, so it is awaited and its errors are raised.

What separates a senior answer here: it goes from symptom to mechanism (one thread, cancellation as an exception, Tasks that store their errors) instead of from tool to tool; it uses numbers (900 ms, 250 ms, rate × seconds held); and it states the cost of each fix: threads that outlive deadlines, partial answers that must be counted, work that dies with the process unless it is made durable.

Wrong belief: "Turning on debug mode in production is the fastest way to find these bugs."

Why it is wrong: The docs describe the Python Development Mode as additional runtime checks that are too expensive to be enabled by default. In CPython 3.14's futures.py, every Future, and so every Task, created while the loop is in debug mode records the stack where it was created. Use it in tests, staging or a canary; in production, use loop lag and outcome counts, which cost almost nothing.

  • Symptom → mechanism → signal → fix → cost, in that order.
  • Over budget with flat timeouts: swallowed (expired True) or blocked (expired False).
  • Background work: owned and watched if it may be lost; durable if it must happen.
