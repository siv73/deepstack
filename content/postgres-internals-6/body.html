Two buyers, one unit left

A flash sale has one pair of headphones left. Two checkout requests arrive a few milliseconds apart. Both read stock = 1, both write stock = 0, and both customers get a confirmation email. Nothing errored, yet you sold two units you didn't have.

Think of two cashiers sharing one paper stock sheet. Each glances at the sheet, walks to the shelf, sells the item, and comes back to write the new count. If both glance before either writes, both see "1", both sell, and both write "0". The second write silently wipes out the first.

That silent overwrite has a name: a lost update. It isn't a bug in PostgreSQL. Both transactions did exactly what they were told; the problem is what each was allowed to see and when it was allowed to write.

How much one running transaction is shielded from others is set by its isolation level. The SQL standard defines four isolation levels; PostgreSQL accepts all four but implements three, because its Read Uncommitted behaves like Read Committed. Read Committed is the default isolation level in PostgreSQL.

Part 2 of this series showed how each row version carries the transaction that made it, and how a snapshot decides which versions you see. This part answers the two questions left open: when is the snapshot taken, and what happens when two transactions want to change the same row? Then it covers locks, the other half of concurrency: who waits for whom, and what goes wrong when the wait never ends.

Concurrency bugs happen when transactions act on what they read earlier; the isolation level decides what they could see and what happens when their writes collide.

In the diagram, which change alone would stop the oversell?

  1. Make the SELECT faster
  2. Add an index on product id
  3. Stop B from writing a value it computed from a read that is now out of date

The bug is B acting on a stale read. The rest of this part shows three ways PostgreSQL can stop that: do the arithmetic inside the UPDATE, lock the row before reading it, or make B fail and retry.

Read Committed: a fresh view for every statement

Last part: the lost update comes from acting on a stale read. Still unsolved: what exactly does each statement see, and what does an UPDATE do when the row changed under it?

Your checkout code runs at Read Committed. You want to know which of your three statements can see a sale that another request committed half a second ago.

Back to the cashiers. Read Committed is a cashier who looks at the sheet again before every single action. Each look shows the latest committed count, but nothing stops the count changing between two looks.

  1. In Read Committed, a SELECT sees only data committed before the query began, plus its own transaction's earlier changes.
  2. Read Committed starts each command with a new snapshot, so two SELECTs in one transaction can see different data.
  3. If an UPDATE finds a row that another transaction is updating, it waits for that transaction to commit or roll back.
  4. If the first updater commits, the waiting UPDATE re-checks its WHERE clause against the updated version of the row and, if it still matches, applies its change to that version.

Step 4 is why arithmetic inside SQL is safe here. UPDATE products SET stock = stock - 1 WHERE id = 42 AND stock >= 1 reads stock at the moment of writing, after any wait. B's UPDATE waits for A, re-checks stock >= 1 against A's committed 0, finds no match, and changes nothing. The docs show a transfer written as UPDATE ... SET balance = balance + 100.00 working correctly in Read Committed, because each command affects only a predetermined row.

The trouble in the last part was different: the app read 1 in one statement and wrote a constant in a later one. Nothing ties those two statements together. The docs call Read Committed unsuitable for commands with complex search conditions, while adequate for many applications.

The comparison breaks down in one place: a real cashier would notice the count changed. PostgreSQL only re-checks the row a waiting write touches; it never re-checks what your earlier SELECT saw.

Stock is 1, at Read Committed. A runs UPDATE ... SET stock = stock - 1 WHERE id = 42 AND stock >= 1 and hasn't committed. B runs the same statement. What happens to B, and what does it return once A commits?

B waits on the row A is changing. When A commits, B re-checks its WHERE clause against A's version, where stock is 0. The condition fails, so B updates 0 rows, and your code can tell the customer it sold out. No error, no oversell.

Read Committed gives each statement a fresh snapshot and re-checks a waiting UPDATE's WHERE clause against the newest row, so put the read and the write in one statement.

Inside one Read Committed transaction you run SELECT count(*) FROM orders twice, a second apart. Another session commits 10 new orders in between. What do you see?

  1. The same count both times
  2. The second count is 10 higher
  3. An error, because the data changed

Each statement takes a new snapshot, so the second count includes everything committed before it started.

Repeatable Read: one view, and an error when it's stale

Last part: Read Committed re-reads before every statement. Still unsolved: a report or a read-then-decide flow that needs the whole transaction to see one consistent picture.

A month-end report runs 40 queries over several minutes. Orders keep arriving. With a fresh snapshot per query, the totals page and the detail page disagree by the orders that landed in between.

This cashier photographs the sheet once and works only from the photo. Every look shows the same numbers, however long the shift. The risk moves: the photo can be out of date when the cashier finally writes.

  1. In Repeatable Read, every query sees a snapshot taken at the start of the first non-transaction-control statement of the transaction. BEGIN alone doesn't take it; your first real query does.
  2. If a Repeatable Read transaction tries to update a row that another transaction updated or deleted and committed after its snapshot, it is rolled back with ERROR: could not serialize access due to concurrent update.
  3. The docs say to abort and retry the whole transaction from the beginning; the retry sees the committed change in its new snapshot.

That error is a serialization failure. It turns the silent lost update into a loud one: B's stale write is refused, B retries, sees stock 0, and doesn't sell. Only updating transactions might need to be retried; read-only transactions never have serialization conflicts at Repeatable Read. So the month-end report gets its stable picture for free.

Repeatable Read freezes one snapshot for the transaction and refuses a write to a row changed since then, so the app must retry instead of losing an update.

Two Repeatable Read transactions both read stock 1. A updates it to 0 and commits. B then runs UPDATE products SET stock = 0 WHERE id = 42. What should the application do?

  1. Catch the serialization failure and rerun the whole transaction, including the SELECT
  2. Rerun just the failed UPDATE
  3. Nothing; B waits and then succeeds

The retry takes a new snapshot, sees stock 0, and decides not to sell. Repeating only the UPDATE would repeat the stale decision.

Serializable: catching what snapshots miss

Last part: Repeatable Read catches two writes to the same row. Still unsolved: two transactions that each read what the other writes, but never write the same row.

A hospital rule says at least one doctor must be on call. Two doctors, both on call, ask to go off call at the same moment. Each checks "is anyone else on call?", sees yes, and removes only their own row. Both commit. Nobody is on call.

The photographs don't help: each cashier changed a different line of the sheet, so no line was written twice. The error is in the combination. This pattern is called write skew.

  1. Serializable works exactly like Repeatable Read, and also watches for patterns that no one-at-a-time order of the transactions could produce; when it finds one, it raises a serialization failure.
  2. Serializable uses predicate locks, shown in pg_locks with mode SIReadLock; they never block and cannot cause a deadlock. They only record what each transaction read.
  3. Serialization failures always return SQLSTATE 40001.

The docs' own example: transaction A sums class 1 rows (30) and inserts the sum as a class 2 row, while B sums class 2 rows (300) and inserts it as a class 1 row; at Repeatable Read both commit, at Serializable one is rolled back. Run one after the other, the second sum would have been 330 or the first would have changed. The rolled-back transaction gets ERROR: could not serialize access due to read/write dependencies among transactions.

PostgreSQL's Serializable is implemented with Serializable Snapshot Isolation, which adds checks for serialization anomalies on top of Snapshot Isolation. The payoff: if a transaction is correct when run alone, it stays correct in any mix of Serializable transactions, or it fails with 40001.

Cashiers notice each other; transactions don't. Every guarantee in this part comes from snapshots plus, at Serializable, a record of reads. Nothing waits for the other to finish thinking.

Serializable catches write skew by tracking reads without blocking, and turns any result no serial order could produce into a 40001 retry.

The on-call bug: two transactions each delete their own row after checking the other is still on call. Which is the lowest level that stops it without explicit locks?

  1. Read Committed
  2. Repeatable Read
  3. Serializable

No single row is written twice, so only read tracking can see that the two checks and deletes can't be put in any serial order.

In your own words: what does each of PostgreSQL's three levels do when two transactions collide?

Read Committed gives every statement a fresh snapshot. If an UPDATE hits a row another transaction is changing, it waits and then re-checks its WHERE clause on the new version. Repeatable Read keeps one snapshot for the whole transaction, and if you try to change a row someone else changed and committed since then, you get a serialization failure. Serializable does the same and also tracks what you read, failing one transaction when the combination couldn't happen in any one-at-a-time order. At both higher levels the application retries the whole transaction.

Table locks: what each command waits for

Last part: isolation levels decide what you see. Still unsolved: why a harmless-looking command can freeze every query on a table.

At peak hour you run CREATE INDEX on a 200-gigabyte orders table. Checkout traffic is 400 writes a second. Reads keep working, but every INSERT hangs until the 25-minute build finishes.

Most PostgreSQL commands take table-level locks automatically, so a table can't be dropped or changed in an incompatible way while a command runs. Each lock has a lock mode. Two transactions cannot hold locks of conflicting modes on the same table at the same time, though a transaction never conflicts with itself.

How long do you hold it? A lock is normally held until the end of the transaction; one taken after a savepoint is released if you roll back to that savepoint. A fast DDL inside a slow transaction holds its lock for the whole slow transaction.

"Is it safe to add an index to a busy table?" A strong answer names the lock: plain CREATE INDEX takes SHARE, which blocks every write for the whole build; CONCURRENTLY takes SHARE UPDATE EXCLUSIVE, which blocks neither reads nor writes but builds more slowly and can leave an invalid index if it fails (Part 4). A command's lock mode, not how much work it does, decides what it blocks, and it holds that lock until its transaction ends.

A VACUUM is running on orders. Which of these has to wait for it?

  1. A SELECT on orders
  2. A CREATE INDEX on orders
  3. An INSERT into orders

CREATE INDEX takes SHARE, and SHARE UPDATE EXCLUSIVE conflicts with SHARE. Reads and writes don't conflict with it.

Row locks: making the read count

Last part: table locks keep commands from tripping over each other. Still unsolved: making the read-then-decide flow from the first part safe at Read Committed.

Seat booking: the app must read the seat, run 30 lines of business rules in code, then write. The rules can't be squeezed into one UPDATE, and you'd rather not handle retries.

Lock the row as you read it. SELECT ... FOR UPDATE reads and takes a row lock in one step. FOR UPDATE stops other transactions from locking, updating or deleting the row until the current transaction ends. The second buyer's FOR UPDATE waits. In Read Committed, once the first transaction commits, a waiting SELECT FOR UPDATE re-checks its WHERE clause and, if the row still matches, locks and returns the updated version of the row. So the second buyer reads stock 0 after the wait, and the business rules decide on real data.

Row-level locks don't affect reading; they block only writers and lockers of the same row. There are four strengths, and plain writes take them too:

  • DELETE takes FOR UPDATE, as does an UPDATE that changes columns with a unique index usable by a foreign key; any other UPDATE takes the weaker FOR NO KEY UPDATE.
  • FOR KEY SHARE conflicts only with FOR UPDATE, so it doesn't block an UPDATE that leaves key columns alone.
  • FOR SHARE and FOR NO KEY UPDATE conflict with each other and with FOR UPDATE, but FOR SHARE doesn't conflict with FOR SHARE.

The model below replays the first part's race under three fixes. Its tests show the read-then-write version overselling at Read Committed, the guarded UPDATE selling once, and Repeatable Read refusing the stale write.

FOR UPDATE at a higher level behaves differently. In Repeatable Read or Serializable, SELECT FOR UPDATE throws an error if the row changed after the transaction started. Code that never retried at Read Committed starts failing the day someone raises the level.

"Pessimistic or optimistic locking for this flow?" A strong answer picks by contention and cost of a retry. FOR UPDATE suits a hot row with expensive side effects (charging a card), since only one transaction proceeds at a time. A version column checked in the UPDATE, or Repeatable Read with a retry, suits rare conflicts, since nothing waits. It names the cost of each: waiting and deadlock risk versus wasted work on retry.

SELECT ... FOR UPDATE turns a read-then-decide flow into one where the second transaction waits and then decides on the committed row.

Transaction A holds FOR UPDATE on seat 14C for 2 seconds. During that time, a plain SELECT * FROM seats WHERE id = '14C' runs. What happens?

  1. It returns immediately with the last committed version
  2. It waits 2 seconds for A to finish
  3. It fails with a lock error

Readers never wait for row locks; they see the committed version their snapshot allows.

A job queue that doesn't serialize its workers

Last part: FOR UPDATE makes the next transaction wait for the row. Still unsolved: 20 workers all wanting "the next job" would all wait on the same row.

An email table works as a queue. 20 workers each run SELECT ... ORDER BY id LIMIT 1 FOR UPDATE. All 20 pick the same oldest row; 19 wait in line behind one worker, and throughput is that of a single worker.

Two options change what a locking SELECT does when a row is taken. With NOWAIT, a locking SELECT reports an error instead of waiting if a selected row can't be locked immediately. With SKIP LOCKED, rows that can't be locked immediately are skipped; the docs warn this gives an inconsistent view, usable for queue-like tables with multiple consumers but not for general-purpose work.

BEGIN;
SELECT id, payload
FROM email_jobs
WHERE status = 'pending'
ORDER BY id
LIMIT 10
FOR UPDATE SKIP LOCKED;     -- each worker gets 10 rows nobody else holds
-- send the emails, then:
UPDATE email_jobs SET status = 'sent' WHERE id = ANY($1);
COMMIT;                     -- row locks are released here

Each worker gets a different batch, and a worker that crashes rolls back, so its rows become claimable again. NOWAIT and SKIP LOCKED apply only to row-level locks; the ROW SHARE table lock is still taken the ordinary way. A pending ACCESS EXCLUSIVE on the table still stops the whole queue.

Sometimes the thing to lock isn't a row at all: "only one nightly billing run per tenant". Advisory locks have meanings the application defines; the system doesn't enforce their use. A session-level advisory lock is held until it is released or the session ends, even if the transaction that took it rolls back; a transaction-level one is released automatically at transaction end. Prefer the transaction-level form (pg_advisory_xact_lock) unless you need the lock to outlive a transaction; the part on ten times the load shows why.

"Why not use Kafka or SQS for this queue?" A strong answer says a Postgres queue with SKIP LOCKED is fine at modest volume and gives you the job and the business write in one transaction. It names the limits: every claimed or finished job leaves dead row versions for VACUUM (Part 3), and polling adds load. Past those limits, or when many consumers need the same events, a log or broker fits better.

FOR UPDATE SKIP LOCKED lets many workers claim different rows at once; advisory locks cover things that aren't rows.

Where would SKIP LOCKED give a wrong answer?

  1. Workers claiming jobs from a queue table
  2. A balance report that sums every row of an accounts table
  3. Picking 10 unassigned support tickets for an agent

Skipping rows another transaction holds means the sum silently leaves them out: the inconsistent view the docs warn about.

The retry loop every higher level needs

Last part: locks that let workers avoid waiting. Still unsolved: Repeatable Read and Serializable promise to fail, not to succeed. Who handles the failure?

You switch payments to Serializable. Under load, about 1 in 100 transactions now fails with 40001, and each failure becomes an HTTP 500 for a customer who did nothing wrong.

  1. Both Repeatable Read and Serializable can raise serialization failures, and applications using them must be ready to retry.
  2. The docs say deadlock failures, SQLSTATE 40P01, may also be worth retrying.
  3. The complete transaction must be retried, including the logic that decides what SQL to run and with which values; for that reason PostgreSQL has no automatic retry.

So the retry belongs in your code, around the whole unit of work: the reads, the decisions in code, and the writes. A wrapper that resends only the last statement repeats the stale decision.

Three details carry the weight. work(conn) holds the reads and decisions, so a retry re-decides. Commit is inside the try. And other errors are not retried: unique-key failures (23505) are sometimes worth retrying, but they may be persistent errors, so they need more care. Side effects outside the database, like charging a card or sending an email, must not run inside work, or a retry repeats them.

A retry isn't guaranteed to succeed; under very high contention a transaction may need many attempts. Hence the attempt limit, and the backoff with random jitter so colliding transactions don't collide again in lockstep.

"You're getting serialization failures. Do you lower the isolation level?" A strong answer first measures the retry rate and finds the hot rows or relation-level predicate locks causing it. Retries are the expected cost of Serializable; the fix is usually a smaller transaction, a READ ONLY declaration, or an index that turns a sequential scan into narrower locks. Lowering the level trades a visible retry for a silent anomaly.

At Repeatable Read and Serializable, wrap the whole transaction, decisions included, in a bounded retry on 40001 and 40P01, and keep outside side effects out of it.

A colleague's ORM retries just the statement that failed with 40001. What's wrong?

  1. Serialization failures should never be retried
  2. Nothing, if the statement is idempotent
  3. The values in that statement came from reads in the failed transaction; the whole transaction must rerun

The failed transaction's snapshot is gone. Only a full rerun takes a new snapshot and makes new decisions from it.

In your own words: list the tools from this rung for the "last unit" problem and when you'd reach for each.

If the change fits in one statement, I put the arithmetic and a guard in the UPDATE; at Read Committed a waiting UPDATE re-checks its WHERE on the committed row, so it can't oversell. If the decision needs code between read and write, I read with FOR UPDATE so the next transaction waits and then sees the real value. For many workers taking jobs I use FOR UPDATE SKIP LOCKED, or NOWAIT when I'd rather fail than wait. At Repeatable Read or Serializable I wrap the whole transaction in a bounded retry on 40001 and 40P01.

Deadlocks: two transactions waiting for each other

Last part: retries for failures the database raises on purpose. Still unsolved: the failure you cause yourself by locking rows in the wrong order.

Money transfers between two wallets. At 10 transfers a second, deadlock errors are rare. At 100 a second, with a few busy merchant wallets, you see dozens of 40P01 errors a minute, and each one stalls a request for a second first.

In the docs' example, transaction one updates account 11111, transaction two updates 22222 and then waits for 11111, and transaction one then waits for 22222: a deadlock. Deadlocks can happen through row-level locks alone, without any explicit locking.

PostgreSQL detects deadlocks and aborts one of the transactions; which one is hard to predict and should not be relied on. deadlock_timeout is how long a session waits on a lock before checking for a deadlock; the check is relatively expensive, and the default is one second. That second is the stall in the problem: every deadlock costs a full wait before anyone notices.

The fix is ordering, not detection. The docs' best defence is to make every application take locks on multiple objects in a consistent order, and, for each object, to take the most restrictive mode it will need with the first lock rather than upgrading later. For transfers: always lock the lower account id first, whichever way the money moves. Then the second transfer queues behind the first instead of forming a cycle.

Its tests run both transfers side by side: opposite order produces a cycle; sorted ids produce one transaction waiting and none deadlocked. At ten times the load, more transfers overlap in time, so the chance two of them touch the same pair in opposite order grows faster than traffic; ordering makes it zero instead of smaller. Detect it from 40P01 counts in your error metrics and the deadlock errors in the server log.

Deadlocks come from taking the same locks in different orders; detection costs a timeout and an aborted transaction, while a fixed lock order removes them.

You raise deadlock_timeout from one second to ten, hoping for fewer deadlocks. What changes?

The number of deadlocks doesn't change: the cycles still form. Each one is just found later, so the stuck transactions block for ten seconds instead of one before one is aborted. A higher value saves needless checks on a busy server whose lock waits are usually short; it never prevents a deadlock.

The migration that took the site down while waiting

Last part: two transactions waiting on each other. Still unsolved: a migration that does no work at all yet stalls every query.

A deploy runs ALTER TABLE orders ADD COLUMN note text, instant by itself. An analytics query has been reading orders for eight minutes. The ALTER waits, and within seconds every API request touching orders is waiting too.

The ALTER needs ACCESS EXCLUSIVE, which conflicts with the report's ACCESS SHARE, so it waits. New SELECTs arrive behind it, and the definition of blocking covers that: pg_blocking_pids returns the sessions blocking a given session: those holding a conflicting lock (hard block) and those waiting for a conflicting lock ahead of it in the wait queue (soft block). API queries are soft-blocked by the ALTER, itself hard-blocked by the report.

The tests replay it: readers queue behind the ALTER, and cancelling it frees them. ADD FOREIGN KEY lets readers through but queues writers.

GoCardless describes a migration that dropped and recreated foreign-key constraints: its exclusive lock request queued behind a long-running read query, API reads and writes piled up behind it, and the result was about 15 seconds of API downtime. GoCardless's post recommends setting lock_timeout in migration scripts.

The fix is to bound the wait. lock_timeout aborts any statement that waits longer than the limit for a lock; the limit applies to each lock attempt separately, and 0, the default, disables it. Set it only in the migration session, to a few seconds, and retry later. The docs recommend against setting lock_timeout in postgresql.conf, because it would affect all sessions.

Then shrink what needs the strong lock. ADD CONSTRAINT ... NOT VALID skips the scan of existing rows and can commit immediately; a later VALIDATE CONSTRAINT checks them while holding only SHARE UPDATE EXCLUSIVE, plus ROW SHARE on the referenced table for a foreign key. Adding an ordinary column with a non-volatile DEFAULT stores the value in the table's metadata, so no table rewrite is needed; a volatile default, a stored generated or identity column, or a domain type with constraints rewrites the table.

Diagnose with pg_blocking_pids(pid), starting from the waiting ALTER: its blocker is the culprit. The docs caution that calling pg_blocking_pids frequently can affect database performance.

"How do you run schema changes on a table taking 5,000 queries a second?" A strong answer sets lock_timeout and retries, checks for long transactions first, splits risky changes (NOT VALID then VALIDATE; CREATE INDEX CONCURRENTLY), and knows which ALTER forms rewrite the table.

A waiting ACCESS EXCLUSIVE request blocks everything queued behind it, so migrations need lock_timeout plus retry, and changes split so the strong lock is held briefly.

Put the safe migration routine in order.

  1. Check for long-running transactions on the table
  2. SET lock_timeout to a few seconds in the migration session
  3. Run the ALTER
  4. If it timed out, wait and retry, rather than waiting longer

Clear the hard blockers first, cap how long the request can sit in the queue, run it, and treat a timeout as "try again", never "wait harder".

What breaks first at ten times the load

Last part: a queued lock request that froze a table. Still unsolved: the slower failures that grow with traffic, and how to see them coming.

Traffic grows 10 times. Nothing was changed, yet p99 latency triples, serialization failures go from rare to constant, and one tenant's billing job sometimes runs twice.

Idle transactions first. A request that opens a transaction, then calls a slow HTTP API, holds every lock it took. Without a deadlock, a transaction waiting for a lock waits indefinitely, so holding transactions open for long periods is a bad idea. idle_in_transaction_session_timeout ends sessions that sit idle inside an open transaction for longer than the limit; it is disabled (0) by default. An idle open transaction can hold locks, and it also stops VACUUM from removing recently dead rows, which can add to table bloat.

Serializable next. When the predicate lock table runs short of memory, page-level predicate locks are combined into a relation-level lock, which can raise the serialization failure rate. A sequential scan always needs a relation-level predicate lock. So one query that loses its index plan (Part 5) can make every writer of that table conflict. In PostgreSQL 18, max_pred_locks_per_transaction and max_locks_per_transaction both default to 64; the PostgreSQL 19 release notes raise max_locks_per_transaction to 128. For busy Serializable workloads the docs recommend declaring READ ONLY transactions, limiting active connections with a pool, keeping transactions small, and not leaving connections idle in transaction.

Then the pooler. PgBouncer's transaction pooling assigns a server connection to a client only during a transaction, and its feature table lists session-level advisory locks as never working in that mode. The lock lands on a server connection that the next transaction, from another client, may get, while the client that took it may find it gone. That's the billing job running twice.

The docs warn that pg_advisory_lock(id) in a query with LIMIT may take locks the application didn't expect, because LIMIT isn't guaranteed to apply before the locking function runs. Those locks stay until the session ends. Pick the ids in a subquery, then lock.

Detect it. log_lock_waits logs a message when a session waits longer than deadlock_timeout for a lock; it is off by default in PostgreSQL 18. The PostgreSQL 19 release notes, not final at the time of writing, enable log_lock_waits by default. Alert on the rate of 40001 and 40P01 errors, on sessions idle in transaction for longer than a few seconds, and on lock-wait log lines.

At scale the first failures are long or idle transactions holding locks, coarse predicate locks raising retry rates, and session-level state lost behind a transaction pooler.

Behind PgBouncer in transaction mode, which way of ensuring "one billing run per tenant" works?

  1. pg_advisory_lock at the start, pg_advisory_unlock at the end, across several transactions
  2. pg_advisory_xact_lock inside the single transaction that does the billing run
  3. A session variable that marks the tenant as busy

A transaction-level advisory lock lives and dies with one transaction, which is exactly the unit transaction pooling keeps on one server connection.

In your own words: name the lock failures from this rung, how you'd detect each, and the fix.

Deadlocks come from two transactions locking the same rows in opposite order; I'd see 40P01 errors and log entries, and fix it by always locking in id order. A migration waiting for ACCESS EXCLUSIVE queues every later query behind it; pg_blocking_pids shows the chain, and lock_timeout with a retry bounds it. Idle or long transactions hold locks and stop VACUUM removing dead rows; I'd alert on idle-in-transaction sessions and set idle_in_transaction_session_timeout. Session-level advisory locks don't survive transaction pooling, so I'd use transaction-level ones.

Three prompts that come up in product-company rounds. For each, commit to an answer before opening the reference.

For every prompt, say four things: the anomaly or lock risk, the mechanism you'd use, how you'd detect it failing, and what the choice costs.

1. Movie seat booking. 500 people try to book the last 10 seats of a premiere in the same minute. A booking holds a seat for 5 minutes while the user pays. Design it.

Don't hold a database transaction open for the 5 minutes: idle transactions hold locks and stop VACUUM removing dead rows. Make the hold a row: UPDATE seats SET held_by = $user, held_until = now() + interval '5 min' WHERE id = $seat AND (held_by IS NULL OR held_until < now()). At Read Committed a waiting UPDATE re-checks that guard on the committed row, so exactly one user gets each seat; the rest see 0 rows and get "taken". Payment confirmation is a second short transaction checking the hold is still yours. Detect problems via conflict rate and expired holds. Cost: expired holds need clean-up, and users can lose a seat if payment runs past the hold.

2. Wallet transfers at 2,000 a second, with a few merchant wallets receiving most of the money. Deadlocks and lock waits are rising. Fix it.

Lock both wallets in a fixed order, lowest id first, removing the deadlocks; add a bounded retry on 40P01 and 40001 for safety. The rising waits come from hot merchant rows: every transfer to them serializes on one row. Options, with costs: append transfers to a ledger table and update the merchant balance in batches (balance is briefly stale); split a hot wallet into several sub-balance rows and sum them (reads get more expensive). Detect with lock-wait logs and per-row wait sampling via pg_locks during incidents. State that Serializable alone doesn't fix hot-row contention: writers still wait on the row lock, and then some also fail and retry.

3. Add a NOT NULL foreign key from orders (800 million rows, 3,000 writes a second) to a new customers_v2 table without downtime.

Every step runs with a short lock_timeout and a retry, after checking for long transactions. Add the nullable column (no rewrite, brief ACCESS EXCLUSIVE). Backfill in small batches, each its own short transaction, so no long transaction holds row locks or stops VACUUM removing dead rows. Add the foreign key NOT VALID: no scan, brief SHARE ROW EXCLUSIVE on both tables, which pauses writes only for that moment. VALIDATE CONSTRAINT under SHARE UPDATE EXCLUSIVE while traffic flows. For NOT NULL, add the not-null constraint NOT VALID as well and validate it later; on PostgreSQL 18 NOT VALID works for not-null constraints, and a validated CHECK (col IS NOT NULL) would also let SET NOT NULL skip its scan. Cost: a multi-step, multi-deploy migration and app code that tolerates NULLs during the backfill.

"Read Committed or Serializable as the starting level for a new service?" A strong answer gives a position and its cost: Serializable makes every transaction correct in isolation and needs a retry wrapper everywhere; Read Committed is faster to start but needs every cross-row rule found and locked by hand. It notes the deciding question: how many rules span rows, and whether the team will reliably spot them.

Rows carry versions, snapshots choose among them, VACUUM clears the dead ones, indexes find them, the planner picks the route, and locks plus isolation decide who sees and changes what.
