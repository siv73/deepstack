How a 10-minute report and 2,000 payments a second share one table

Finance runs a 10-minute month-end report over the payments table. During those 10 minutes, the app writes 2,000 payments a second to the same table. If the report locked the table, 1.2 million payments would queue behind it. If it didn't, it could add up half-written totals.

PostgreSQL avoids both. Each SQL statement sees a snapshot of the data as it was at some earlier moment, regardless of the current state of the underlying rows. The approach is called MVCC.

Think of a shared document with version history. When you open it, you see it as of that moment. Others keep editing, and their edits become new versions. You keep reading your version until you reopen it. Nobody waits for anybody to finish reading.

  1. Writers never overwrite a row. They add a new version (part 2).
  2. Each version is stamped with the transaction that created it and the one that replaced it (parts 2 and 3).
  3. Each reader carries a list of which transactions had finished when it started (part 4).
  4. A version is shown only if its stamps say it existed at the reader's moment (part 5).

In MVCC, locks taken for reading don't conflict with locks taken for writing, so reading never blocks writing and writing never blocks reading. PostgreSQL keeps this guarantee even at the strictest isolation level, Serializable, through Serializable Snapshot Isolation (SSI).

The price: old versions pile up and must be cleaned up later. That cost drives most of parts 8 to 10, and all of part 3 of this series.

PostgreSQL lets readers and writers run at the same time by keeping old row versions, so each reader sees one consistent moment.

The 10-minute report is halfway through when a payment of ₹5,000 commits. Does the report's total include it?

  1. Yes, because the row is committed before the report finishes
  2. No: the report reads from its snapshot, taken before that payment committed
  3. The payment waits until the report finishes, then commits

The report sees the table as of its snapshot. The payment commits normally; it becomes visible to statements that start later.

In your own words: how does PostgreSQL let a long report and heavy writes run at the same time, and what does it cost?

Writers don't overwrite rows; they add new versions. Each statement reads a snapshot of an earlier moment and only sees versions that existed then. So the report gets a consistent total and the writes don't wait for it. The cost is that old versions stay in the table until they are cleaned up, which uses disk and cleanup work.

An UPDATE never changes a row: it adds one

Last part: readers see a past moment. Still unsolved: where does the past version physically live?

You run UPDATE acct SET bal = 50 WHERE id = 1 on a one-row table. Afterwards the table's page holds two rows. Where did the second one come from?

A row version is one state of a row, and each update of a row creates a new row version for the same logical row. From part 1: every row version has a header. Two header fields do the work:

  1. xmin is the ID of the transaction that inserted this row version.
  2. xmax is the ID of the transaction that deleted it, or zero; it can be nonzero in a visible version, usually because the deleting transaction hasn't committed yet or was rolled back.
  3. An UPDATE sets xmax on the old version and inserts a new version whose xmin is the updating transaction. Each version's header has a t_ctid field: the ctid of this version or of a newer one. So the old version points forward to the new one.
  4. A DELETE only sets xmax. Nothing is removed yet. An UPDATE or DELETE does not immediately remove the old version: it must stay while other transactions might still see it, and VACUUM reclaims its space later.

These IDs are real: they came from running this exact UPDATE and reading the page with pageinspect (part 6). You can see the same fields yourself: SELECT xmin, xmax, ctid, * FROM acct. A row's ctid changes when it is updated or moved by VACUUM FULL, so the docs say to identify rows by primary key, not ctid.

An UPDATE marks the old version with its transaction ID in xmax and writes a new version with that ID in xmin.

Transaction 930 runs DELETE FROM acct WHERE id = 1 and commits. What is on the page right after the commit?

The deleted version is still there, with xmax set to 930. Earlier versions that nobody can see any more are also still there. Nothing is physically removed until cleanup (VACUUM) runs and finds no transaction that could still see them.

Transaction IDs, and where "committed" is written down

Last part: versions are stamped with transaction IDs in xmin and xmax. Still unsolved: where do those IDs come from, and how does anyone know whether 927 committed?

Your app sends COMMIT, and the network drops before the reply arrives. Did the ₹12,000 transfer happen or not?

  1. A transaction gets a real transaction ID (xid) only when it first writes to the database; xids come from one global counter shared by every database in the cluster.
  2. Every transaction also has a virtual transaction ID, and read-only transactions have a virtual ID but no real xid. Reading costs no xid.
  3. When a top-level transaction with an xid commits, it is marked as committed in the pg_xact directory. This is the commit log.
  4. A ROLLBACK marks the transaction as aborted. The versions it wrote stay in the table; they are simply never shown.

That last point is why rollback is cheap: nothing is undone row by row. The aborted version (0,2) from part 2 sits on the page until cleanup, and its xmin, 927, is listed as aborted.

Back to the dropped COMMIT. pg_xact_status reports whether a recent transaction is in progress, committed or aborted, and the docs suggest it for checking whether a COMMIT went through after the connection dropped. Record pg_current_xact_id() before committing, and ask after reconnecting.

xid numbers have a size limit. The xid type is 32 bits wide and wraps around every 4 billion transactions; the 64-bit xid8 type adds an epoch and doesn't wrap. Wraparound is part 3's topic.

Writers get an xid on first write, and pg_xact records whether each xid committed or aborted; rollback just marks it aborted.

A reporting service runs 50 million read-only queries a day. How many transaction IDs does it use up?

  1. 50 million, one per query
  2. One per snapshot taken
  3. None: read-only transactions only get virtual IDs

xids are assigned on first write. Pure reads use virtual transaction IDs, which don't draw from the global counter.

A snapshot is a list of who had finished

Last part: pg_xact records who committed. Still unsolved: how does a reader ignore transactions that committed after it started?

A report starts while transactions 14 and 15 are still writing. Both commit a second later. The report must keep ignoring them for its whole run.

The reader keeps a snapshot. A snapshot records xmin, the lowest transaction ID still active; xmax, one past the highest completed ID; and xip_list, the IDs in progress; its text form is xmin:xmax:xip_list.

  1. IDs below xmin had finished; IDs at or above xmax had not finished and are invisible; IDs in between had finished unless they are in xip_list.
  2. "Finished" is not enough to be visible. The reader also checks pg_xact: finished and committed means visible, finished and aborted means never visible.
  3. pg_current_snapshot() returns the current snapshot, and only top-level transaction IDs appear in it. The docs' example is 10:20:10,14,15.

When is the snapshot taken? That depends on the isolation level:

  1. In Read Committed, the default level, a SELECT sees a snapshot as of the instant the query begins, so two SELECTs in one transaction can see different data.
  2. In Repeatable Read, every query in the transaction sees a snapshot as of the start of its first non-transaction-control statement.
  3. Either way, a query sees the effects of earlier updates made inside its own transaction, even before they commit.

A snapshot says which transaction IDs had finished; Read Committed takes a new one per statement, Repeatable Read keeps one for the whole transaction.

A snapshot is 100:110:103,107. Which of these transactions' committed rows can it see?

  1. 98, 103 and 105
  2. 98 and 105
  3. 98, 105 and 110
  4. 98, 103, 105 and 107

98 is below xmin: finished. 105 is between xmin and xmax and not in the list: finished. 103 and 107 were running; 110 is at xmax. Each finished one is visible only if pg_xact says committed.

Explain how PostgreSQL decides whether a report sees a row written by another transaction.

Every row version carries xmin, the transaction that wrote it, and xmax, the one that deleted or replaced it. The report holds a snapshot: xmin, xmax and a list of transactions in progress. An ID counts as finished if it is below xmin, or below xmax and not in the list. The version is visible if its xmin finished and committed, and its xmax is zero or didn't finish-and-commit. Read Committed takes a fresh snapshot per statement; Repeatable Read keeps the first one.

Looking at versions and snapshots on a live database

Last part: the rule in code. Still unsolved: how do you see these fields on a real server?

A table has 2 million live rows but 9 GB on disk. You suspect old versions. You want to see them, and find who is keeping them.

Three views, from the rows up:

  1. System columns on any table: SELECT xmin, xmax, ctid, * FROM t. These show only versions your snapshot can see.
  2. pageinspect's heap_page_items shows every line pointer on a heap page, whether or not the row versions are visible to an MVCC snapshot. All pageinspect functions may be used only by superusers. Use it on a copy or in staging.
  3. pg_stat_activity shows each backend's top-level transaction ID in backend_xid and its xmin horizon in backend_xmin. The xmin horizon is how far back that session might still need to see.
SELECT pid, usename, state,
       now() - xact_start     AS open_for,
       age(backend_xid)       AS xid_age,
       age(backend_xmin)      AS xmin_age,
       left(query, 60)        AS last_query
FROM pg_stat_activity
WHERE backend_xid IS NOT NULL OR backend_xmin IS NOT NULL
ORDER BY greatest(age(backend_xid), age(backend_xmin)) DESC
LIMIT 10;

The docs tell you to find long-running open transactions by checking pg_stat_activity for rows where age(backend_xid) or age(backend_xmin) is large. age() returns how many transactions ago that ID was.

The usual culprit is not a slow query. It is a session in state idle in transaction: an app that ran BEGIN, did a read, then waited on an HTTP call or crashed without closing. It holds its snapshot, and every version deleted since then must be kept.

System columns show your visible versions, pageinspect shows all of them, and pg_stat_activity shows which session is holding old ones.

You want to count dead versions on page 0 of acct, including ones no snapshot can see. Which tool shows them?

  1. pageinspect's heap_page_items, reading page 0 of acct with get_raw_page
  2. SELECT xmin, xmax, ctid FROM acct
  3. pg_stat_activity

Only a raw page read shows every line pointer, visible or not. Normal queries apply the visibility rule first.

Production settings that keep transactions short

Last part: finding sessions that hold old versions. Still unsolved: how do you stop them happening in the first place?

A payment service opens a transaction, reads the order, calls the bank API (P99 of 8 seconds, sometimes 5 minutes on outages), then writes. During an outage, bloat on the busiest table grows by 20 GB.

The timeouts PostgreSQL gives you:

  1. idle_in_transaction_session_timeout terminates a session that has been idle inside an open transaction for longer than the set time; 0, the default, disables it.
  2. An open transaction prevents vacuuming away recently-dead tuples that may be visible only to it, so a session that stays idle for long can contribute to table bloat.
  3. transaction_timeout terminates any session that spends longer than the set time in a transaction; it is 0 (off) by default, and the docs advise against setting it in postgresql.conf because it would affect all sessions. Set it per role or per session instead.
ALTER ROLE payments_app SET idle_in_transaction_session_timeout = '30s';
ALTER ROLE payments_app SET transaction_timeout = '60s';

The design fix matters more than the timeout: never hold a transaction open across a network call. Read, commit, call the bank, then open a new short transaction to write the result, using an idempotency key so a retry is safe.

"Why not wrap the whole request, including the external API call, in one transaction?" A strong answer: under MVCC an open transaction pins its snapshot, so cleanup stalls for the whole database while you wait on the network, and locks you took are held too. Keep transactions to database work only, and make the external step idempotent.

Never keep a transaction open across a network call, and set idle-in-transaction and transaction timeouts per application role.

Which setting would have ended the stuck payment sessions during the bank outage?

  1. statement_timeout = '5s'
  2. Leaving idle_in_transaction_session_timeout at its default
  3. idle_in_transaction_session_timeout = '30s' for the app's role

The sessions sat idle inside open transactions while waiting on the bank. That is exactly what idle_in_transaction_session_timeout ends.

One forgotten transaction slows every table

Last part: timeouts and short transactions. Still unsolved: what actually breaks when one session holds an old snapshot, and what else can hold one?

An analyst opens a Repeatable Read transaction in a SQL client on Friday and goes home. By Monday, the orders table is 3 times its size and queries that took 5 ms take 80 ms.

What happens at 10 times the write rate: every UPDATE leaves a dead version. Cleanup can only remove versions that no snapshot anywhere can still see. One old snapshot sets that line for the whole database, so dead versions pile up in every busy table. Scans and index lookups wade through them, and the first thing users notice is latency on the most-updated tables.

Things that hold the line back:

  1. Long or idle-in-transaction sessions (part 6).
  2. hot_standby_feedback lets a standby tell the primary about queries running on it; this avoids query cancels on the standby but can cause bloat on the primary. A 2-hour report on a replica then holds cleanup back on the primary.
  3. The docs' list of things to fix also names old prepared transactions and old replication slots, found through pg_prepared_xacts and pg_replication_slots.

How to detect it: alert on the oldest age(backend_xmin) in pg_stat_activity, on replication slot and prepared transaction ages, and on dead-row counts per table. The fix is to end the holder; the cleanup that follows is part 3's topic.

"Reads never block writes. So why can a read-only report on a replica hurt the primary?" Strong answer: it blocks nothing directly, but with hot_standby_feedback on, its snapshot holds back cleanup on the primary, so dead versions pile up there. Trade-off: turn feedback off and the replica's long queries may be cancelled instead. Many teams send such reports to a separate replica with feedback off and a long delay allowance.

The oldest open snapshot anywhere, including replicas, slots and prepared transactions, decides what cleanup may remove everywhere.

You kill the analyst's session on Monday. Predict what happens to table size and latency in the next hour.

Cleanup can now remove the dead versions, so latency recovers as autovacuum works through the tables. The files usually don't shrink: standard VACUUM marks the space of dead versions as reusable but does not return it to the operating system, except when whole pages at the end of the table become free. Part 3 covers what to do about it.

Explain to an on-call engineer why one idle session can make unrelated tables slow, and how to find it.

Every UPDATE and DELETE leaves an old version. Cleanup may only remove versions that no open snapshot could still need. A session idle in an old transaction keeps its snapshot, so dead versions pile up in every busy table and queries slow down. Standbys with hot_standby_feedback, old prepared transactions and stale replication slots do the same. Find the holder by the age of backend_xmin in pg_stat_activity and the ages in pg_prepared_xacts and pg_replication_slots, then end it.

Why a SELECT can write to disk

Last part: old snapshots hold back cleanup. Still unsolved: why does reading freshly loaded data sometimes cause heavy writes?

You bulk-load 50 million rows at night. The first morning report on them runs twice as slow as the second, and disk writes spike during a read-only query.

Looking up pg_xact for every version on every read would be slow. So PostgreSQL caches the answer in the row itself:

  1. Visibility checks set hint bits on a row version once they see that its inserting or deleting transaction has committed or aborted, and then mark the page as dirty. A hint bit is that cached answer.
  2. The first reader after a bulk load sets hint bits on every row, dirtying every page. Those pages must be written back to disk.
  3. Hint bits set on the primary are not WAL-logged, so a standby writes them again itself and performs disk writes even when all its users only read.
  4. If data checksums are enabled, hint bit updates are always WAL-logged. Then the first read after a load also generates WAL.

A read-only replica is not write-free, and the first scan after a big load is not a fair benchmark. Measure the second run, and expect the first scan after a large load to pay this cost.

The first reader of new rows records their commit status in the rows, so a SELECT after a bulk load can write every page.

A replica serving only reads shows steady disk writes after the primary loads a big batch. Why?

  1. Replication is writing duplicate rows
  2. Its reads set hint bits on the new rows, which aren't in the WAL, so it writes those pages itself
  3. Every query writes its snapshot to disk

Hint bits set on the primary are not sent through the WAL, so the standby discovers commit status itself and dirties the pages.

SAVEPOINT: the MVCC feature that took down replicas

Last part: reads can write. Still unsolved: which innocent-looking feature has caused whole-cluster slowdowns?

An ORM wraps each "find or create" in a nested transaction. Each request opens 70 of them inside one outer transaction. Nothing fails, but the database slows sharply under load.

  1. Subtransactions are started with SAVEPOINT, and also in other ways such as a PL/pgSQL EXCEPTION clause. A subtransaction can roll back alone.
  2. A read-only subtransaction gets no ID, but once it writes, it and all its parents get transaction IDs.
  3. Up to 64 open subtransaction IDs are cached in shared memory per backend; beyond that, storage I/O rises significantly because of extra lookups in pg_subtrans.

In a post from 29 September 2021, GitLab described stalls in which queries on its replicas waited on SubtransControlLock. They traced it to SAVEPOINTs run on the primary while a long-running transaction was open, and fixed it by removing SAVEPOINT use from the application.

How you detect it: waits on the subtransaction cache appear in pg_stat_activity as the wait events SubtransSLRU and SubtransBuffer. Also count SAVEPOINT statements in your query logs. Check whether your ORM's nested-transaction helper issues SAVEPOINT.

"When would you avoid savepoints?" Strong answer: on hot paths and in loops, because each writing subtransaction takes an ID and more than 64 open per transaction means disk lookups. Replace "try insert, catch, retry" with INSERT ... ON CONFLICT, which needs no savepoint.

Subtransactions look free but cost IDs and, past 64 per transaction, extra pg_subtrans lookups; prefer ON CONFLICT on hot paths.

Which pattern risks going past the subtransaction cache?

  1. A loop that inserts 200 rows, each in its own SAVEPOINT that is kept open
  2. 200 SAVEPOINTs that only run SELECTs
  3. 200 rows inserted with one INSERT ... ON CONFLICT DO NOTHING

Writing subtransactions get IDs, and more than 64 open in one backend spill to pg_subtrans lookups.

PostgreSQL's MVCC against the alternatives

Last part: subtransactions. Still unsolved: how does this design compare with other databases, and when does it hurt you?

An architect says MySQL handles your update-heavy wallet_balances table better "because it updates in place". Is that true, and what would you trade?

InnoDB, MySQL's storage engine, also uses MVCC, with old versions in a different place. InnoDB keeps old versions of changed rows in undo tablespaces, in a structure called a rollback segment. InnoDB updates records in its clustered index in place. Long-running transactions, even read-only ones, stop InnoDB discarding undo logs, which can grow until they fill the undo tablespace.

DesignWhere old versions livePick it whenYou give up
PostgreSQL: new version in the tableIn the table itself, cleaned by VACUUMMixed read/write workloads, long reads next to writes, cheap rollbackDead versions in the table and indexes; cleanup must keep up
InnoDB: update in place plus undoUndo tablespaces, as aboveWorkloads dominated by small updates to the same rows, if you watch undo growthOld snapshots read through undo; long transactions grow undo instead of the table
Lock-based reads (no MVCC)Nowhere: readers lockAlmost never for OLTP todayReaders and writers block each other

Notice the shared failure: in InnoDB long transactions grow undo logs, and in PostgreSQL they grow dead versions. Neither design forgives long transactions. The answer to the architect: "in place" moves the cost, it doesn't remove it. For a hot balance row in PostgreSQL, keep the row narrow and its indexes few, so updates stay cheap (part 3 covers how).

"What's the downside of PostgreSQL's MVCC?" Strong answer: every update writes a whole new version, possibly with new index entries; dead versions stay until VACUUM; one old snapshot holds cleanup back everywhere; and xids are 32-bit, so they need regular maintenance. Then say how you'd limit each: short transactions, narrow hot rows, autovacuum tuning, monitoring the xmin horizon.

Every MVCC design stores old versions somewhere; PostgreSQL keeps them in the table, so its costs are dead versions and cleanup.

A team moves to MySQL to "fix bloat" but keeps a 6-hour read-only export transaction on the primary. What happens?

  1. Nothing: read-only transactions don't matter in InnoDB
  2. The InnoDB table itself fills with dead rows
  3. Undo logs grow for 6 hours, because old versions can't be discarded

Both engines must keep versions an open snapshot might need. InnoDB keeps them in undo, so undo grows.

Interview drill: MVCC questions at the senior bar

Last part: MVCC designs compared. Still unsolved: can you answer under pressure?

A fintech interviewer takes your wallet design and asks three MVCC questions. Commit to an answer before opening each reference.

1. "Your balance report runs 20 queries. Finance says totals don't add up between the summary and the detail sections. Why, and how do you fix it?"

Under Read Committed each query takes its own snapshot, so payments committing between queries appear in later sections only. Run the report in one Repeatable Read transaction so all 20 queries share one snapshot. Trade-off: that transaction holds its snapshot for the report's duration, so run it on a replica or keep it short, and watch the xmin horizon.

2. "Our checkout holds a transaction open while calling the payment gateway. What can go wrong under load, and what would you change?"

Each open transaction pins a snapshot and any locks it took. During a gateway slowdown, hundreds of them stay open, cleanup stalls across the database, dead versions pile up and connections run out. Split it: commit the order as pending, call the gateway outside any transaction with an idempotency key, then update the status in a new short transaction. Add idle-in-transaction and transaction timeouts per role. Trade-off: you now handle a pending state and reconciliation.

3. "Reads never block writes in PostgreSQL. So how can a read-only replica hurt the primary?"

With hot_standby_feedback on, the replica reports its oldest snapshot to the primary, and the primary keeps dead versions that snapshot might need. A long report on the replica therefore causes bloat on the primary. Turning feedback off moves the pain: long replica queries may be cancelled. Choose per replica, and alert on the oldest xmin age.

Staff-level versions add setting organisation-wide limits on transaction length, and choosing which replicas get feedback across many services. This page stops at one service.

Senior MVCC answers tie each symptom to snapshots and old versions, then state what the fix costs.
