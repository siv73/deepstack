The system so far, and what this page adds to it

Gateway v7 from Part 6 answers seller-b at 1,199 in 250 ms for every request it admits, refuses the rest with busy in about 0 ms, skips a seller whose limits are full, and keeps its audit writes bounded. Every request still asks all five sellers for itself. seller-e's 1,149, the best price of all, never reaches a shopper, because seller-e takes 900 ms and every request stops waiting at 250 ms.

This is Part 7 of a ten-part series. Every part works on the same system: a price-comparison gateway that asks five sellers for a price and must answer within a budget of 250 ms. What this page adds

Introduction

Part 1 showed that the loop can switch Tasks only at an await. That is usually told as good news: code between two awaits is never interrupted. The other side of the same rule is this part's subject. Code that reads shared state, then awaits, then writes based on what it read, is interrupted at exactly the worst moment. This part measures two forms of the mistake on the gateway: a counter, and a price cache.

Comparison

Two clerks share one whiteboard that shows how many tickets are left. Each clerk reads the number, walks to the phone to confirm a sale with the customer, comes back and writes the number minus one. If both read "10" before either comes back, both write "9", and one sale has vanished from the board.

  • The whiteboard = shared state, such as self.calls.
  • Walking to the phone = the await.
  • Writing "9" twice = a lost update.

The comparison stops working here: two clerks really act at the same time. On an event loop, only one Task runs at any moment; the damage comes entirely from the pause in the middle, not from two things running at once.

Definitions

  1. A race condition is a bug whose result depends on the order in which concurrent Tasks happen to run.
  2. Check-then-act is code that tests shared state and then acts on what it found: "if the price is not cached, fetch it and store it".
  3. A lost update is a write overwritten by another Task that read the same old value, so its effect disappears.
  4. A critical section is a stretch of code that must run as one step with respect to other Tasks, because it reads and then writes shared state.

Working: how 3 calls become 1

  1. task-1 reads self.calls: 0. It reaches the await and gives up the thread.
  2. task-2 runs and reads 0, because task-1 has not written yet. It awaits too. task-3 does the same.
  3. task-1 resumes and writes 0 + 1 = 1.
  4. task-2 and task-3 resume and each writes 0 + 1 = 1, the value computed from what they read before their await.

Why each step matters

  • Step 1: the read is correct when it happens. What makes it wrong is the time that passes before the write.
  • Step 2: every Task that runs during the gap reads the same old value. The longer the await, the more Tasks fit in the gap.
  • Step 4: no write fails and no exception is raised. The result is simply wrong.

Solved example: the gap, at the gateway's numbers

Given: 2,000 requests a second for one item; a miss is filled by seller-c, 150 ms.

Step 1. The gap is the 150 ms between the check and the store.

Step 2. Requests that arrive during the gap: 2,000 × 0.15 = 300, by Little's law (Part 6). Each finds the cache empty.

Step 3. So one miss costs 300 calls to seller-c instead of 1. For seller-e's 900 ms it would be 2,000 × 0.9 = 1,800 calls, against a thread pool of 4 (Part 4).

Result: a check-then-act cache sends one call per request that arrives while the first call is in flight. That burst has a name, a cache stampede: many requests miss the same key at once and all call the source behind it. Rung 3 builds the fix.

Wrong belief: "There is only one thread, so races cannot happen in asyncio code."

Why people hold it: with threads, a race needs two threads running the same code at the same time; asyncio has one.

Why it is wrong: asyncio needs no second thread, only a second Task and a pause. Any await between a read of shared state and a write that depends on it is a gap other Tasks can use. The programs above lose 9 of 10 updates and make 100 calls instead of 1 on a single thread.

  • Code between two awaits runs as one step; an await between a read and a dependent write is a race window.
  • Read, await, write lost 9 of 10 counts; the same with no await lost none.
  • A cache that checks, awaits the seller and stores makes one call per request that arrives during the call: a cache stampede.

On one event loop a race needs no second thread: any await between reading shared state and the write that depends on it lets other Tasks act on the same old value.

The counter's await asyncio.sleep(0.001) is moved to before the read: await, then read, then write with no await in between. 10 Tasks record a call at once. What does the counter end at?

10. Each Task now awaits first and then reads and writes with nothing in between, so the read and the write run as one step. When a Task resumes after its sleep, it reads the latest value, adds one and stores it before any other Task can run. The await still exists; it just no longer sits inside the critical section.

Log lines that carry another request's id

Last part: an await between a read and a dependent write is a race window. Still unsolved: the same window hides in code that does not look like shared state at all, such as the value a logger stamps on every line.

An on-call engineer searches the logs for shopper-1's slow request and finds the line "seller-b answered 1,199" tagged with shopper-2's id. Under load, about one line in fifty carries the wrong id, so the logs cannot be trusted exactly when they are needed.

Introduction

A gateway wants every log line to say which request it belongs to. The quick way is a module-level variable, set when a request starts and read by the logging code. With threads, people reach for thread-local storage. With asyncio, many requests share one thread, and a module variable is shared by all of them. This part reproduces the wrong tag and names what was missing.

Definition

Request-scoped data is data that belongs to one request, such as its id, and must be visible to all code that runs for that request, including the Tasks it starts, and to no other request.

A module variable has the opposite scope: the whole process. Setting it at the start of a request only works until the request's first await, when another request can set it again.

Working

  1. 0 ms: shopper-1's handler sets current_request = "shopper-1", logs "asking seller-b" and awaits seller-b.
  2. 50 ms: shopper-2's handler sets current_request = "shopper-2" and awaits seller-b too.
  3. 120 ms: shopper-1's handler resumes and logs "seller-b answered". The logger reads current_request: "shopper-2".

Program

Explanation of the program

Solved example: how often the tag is wrong

Given: each request logs once at its start and once after its 250 ms of seller calls; requests arrive at 2,000 a second.

Step 1. The start line is always right: it is written in the same step as the set.

Wrong belief: "threading.local() fixes this, as it does for threaded servers."

Why it is wrong: thread-local storage gives each thread its own value. Every request on the event loop runs on the same thread, so they all share one thread-local value, exactly like the module variable. The scope needed is "this request and the Tasks it starts", which the next rung provides.

  • A module variable, or a thread-local, is shared by every request on the loop.
  • Its value is right only until the request's first await.
  • Request-scoped data needs storage scoped to the request and the Tasks it starts.

A request id kept in a module variable is overwritten by whichever request ran last, so after any await a log line can carry another request's id.

In your own words: how can a gateway that runs on one thread lose 9 of 10 counter updates, ask seller-c 100 times for one price, and stamp the wrong request id on a log line?

The loop runs one piece of code at a time, but it switches Tasks at every await. The counter code reads the count, awaits a write, then stores what it read plus one; all ten Tasks read 0 during the first Task's await, so all write 1. The one rule: code between two awaits runs as one step

Introduction

Every tool in this rung exists to stretch one guarantee the loop already gives. Before using any of them, it pays to know that guarantee exactly, because most shared state in an asyncio service needs no tool at all, and adding a lock where none is needed only adds waiting.

Definition

On one event loop, the code a Task runs between two awaits is an atomic step with respect to other Tasks: no other Task's code can run in the middle of it, because the loop switches only when the running Task awaits something that is not ready (Parts 1 and 2). Shared state is safe without a tool if every critical section that touches it fits inside one atomic step.

Working: checking one piece of state

  1. Find every read of the shared value whose result decides a later write (a check, a computation, a "seen" copy).
  2. Find the write that depends on it.
  3. Look between them for an await, an async with or an async for: each can give up the thread. Calls to plain functions cannot.
  4. No await in between: safe as written. An await in between: a race window; close it with a tool, or move the await out of the window.

Why each step is needed

  • Step 1: a read whose result is thrown away, or only logged, cannot cause a wrong write.
  • Step 3: async with and async for hide awaits in their setup and teardown, so they count. An await on something already finished does not give up the thread, but code should not rely on that, because the same line gives it up whenever the awaited thing is not ready.

asyncio.Lock: one Task at a time through a critical section

Introduction

A lock turns a critical section that contains awaits into one step for every Task that uses the same lock. A Task that finds the lock taken waits in line, parked on a Future, the same way Part 3's Semaphore and Part 6's full queue park their waiters.

Comparison

A single-person changing room with a "occupied" sign. Whoever goes in turns the sign; everyone else queues outside in the order they arrived; the person coming out turns it back, and the first in the queue goes in.

  • The sign = the lock's locked flag.
  • The queue outside = the lock's waiters, each parked on a Future.
  • Turning the sign back = release(), which wakes the first in line.

The comparison stops working here: a changing room knows who is inside. An asyncio Lock does not: any Task may release it, as the second program shows.

Definition

An asyncio.Lock lets one Task at a time through a block of code. An asyncio lock can be used to guarantee exclusive access to a shared resource, and the preferred way to use one is an async with statement, which is equivalent to await lock.acquire() followed by the block in a try with lock.release() in its finally. Acquiring a lock is fair: the coroutine that proceeds is the first coroutine that started waiting on the lock.

Working: one acquire and one release, in CPython 3.14's locks.py

  1. Fast path. In CPython 3.14's locks.py, Lock.acquire() takes the lock at once if it is unlocked and every waiter in line, if any, has been cancelled; otherwise it appends a new Future to a deque of waiters and awaits it, and release() sets the result of the first waiter's Future.
  2. Waiting. The Task that cannot take the lock is parked on its Future and uses no CPU (Part 2).
  3. Release. The holder's async with exit calls release(); the first waiter's Future is filled and its Task is scheduled with call_soon.
  4. Hand-over. That Task resumes in a later iteration, marks the lock taken and runs its critical section.

Why each step is needed

  • Step 1: the fast path makes an uncontended lock cost almost nothing: no Future, no wait.
  • Step 1, the cancelled-waiter rule: a newcomer may not overtake a waiter that is still in line, which is what makes the lock fair.
  • Step 3: waking only the first waiter, instead of all of them, means one Task proceeds and the rest stay parked.

  • async with lock: makes the block, awaits included, one step for every Task using that lock.

An asyncio.Lock makes a critical section that contains awaits run as one step for every Task that shares the lock, at the cost of those Tasks taking turns.

Three Tasks call async with lock on a free lock in the same loop iteration. Put what happens in order.

  1. task-1 finds the lock free with nobody in line and takes it without waiting
  2. task-2 and task-3 each append a Future to the waiters and park on it
  3. task-1 leaves its block; release() fills the first waiter's Future
  4. task-2 resumes, takes the lock and runs its critical section
  5. task-2 leaves its block, and task-3 is woken next

Waiters are woken one at a time, in the order they started waiting, by the release of the Task before them.

asyncio.Event: many Tasks wait for one thing to happen

Last part: a Lock lets one Task at a time through. Still unsolved: sometimes no Task should go through until something has happened, and then all of them at once, such as "the cache is warm".

After a deploy the gateway loads seller-e's prices into its cache, which takes 100 ms. Requests that arrive in those 100 ms should wait for the load and then all go ahead. Part 2's busy-loop part showed the wrong way: each request polling a flag with await asyncio.sleep(0), keeping a core at 100%.

Introduction

An Event is a flag that Tasks can wait on. It is the right tool when the thing being waited for happens once (or once per phase) and every waiter should wake when it does.

Definition

An asyncio.Event is a flag Tasks can wait for. An Event manages an internal flag, false initially, that set() sets to true and clear() resets to false; wait() returns True immediately if the flag is set and otherwise blocks until another task calls set(). When an Event is set, all tasks waiting for it are awakened.

Working

  1. Not set: each wait() creates a Future, adds it to the Event's waiters and parks the Task on it.
  2. set(): In CPython 3.14's locks.py, Event.set() sets the result of every waiting Future, while Lock.release() wakes only the first.
  3. Set: a later wait() returns at once, with no Future.
  4. clear(): the flag goes back to false; Tasks already woken are not affected; new wait() calls park again.

Program

Explanation of the program

  1. shopper-1 to shopper-3 arrive at 0, 20 and 40 ms and park in wait(). Nothing runs for them until 100 ms.
  2. At 100 ms set() wakes all three in the same iteration.
  3. shopper-4 arrives at 150 ms, while the flag is set, and is served at once.
  4. At 200 ms clear() resets the flag, so shopper-5 at 250 ms parks until the second set() at 300 ms.

Solved example

Given: 2,000 requests a second arrive during a 100 ms warm-up.

Step 1. Requests parked when set() runs: 2,000 × 0.1 = 200, each one Future in the Event's waiters.

Step 2. set() fills 200 Futures in one call, and their 200 Tasks run in the next iteration.

Result: 200 Tasks wake together, which is the point, and also a burst: if each then calls a seller, the warm-up has moved a stampede rather than removed it. An Event says "go"; it does not decide how many may go.

Wrong belief: "set() then clear() straight away is a pulse that wakes the current waiters and leaves the flag clear."

Why it is wrong: it does both: the waiters' Futures were filled by set(), so they still wake, and new waiters park. But a Task that was about to call wait() a moment later misses the pulse entirely. If waiters must not miss a change, they need state they can check, which is what a Condition adds.

  • Event: a flag; wait() parks until set(); set() wakes every waiter.
  • Once set, wait() returns at once; clear() makes later waits park again.
  • Use it for "happened / not yet"; it limits nothing about what the woken Tasks do next.

An Event lets any number of Tasks wait, without polling, for one thing to happen, and wakes all of them together when it does.

An Event is set at 100 ms and never cleared. A Task calls await event.wait() at 500 ms. What happens?

  1. It returns True at once, without parking
  2. It parks until the next set()
  3. It raises, because the event was already consumed

wait() returns True immediately when the flag is set; set() keeps it set until someone calls clear().

asyncio.Condition: wait, under a lock, until the state you need

A product manager wants a "quick quote": answer as soon as any three sellers have answered, with the best of those three. The offers go into a shared list from five Tasks. The quote Task must wait until the list holds three, then read it while no seller Task is changing it.

Introduction

A Condition is a Lock with a waiting room attached. A Task takes the lock, checks the shared state, and if it is not ready, waits; waiting gives the lock up so others can change the state. Whoever changes it notifies the waiters, which take the lock back and check again.

Definitions

An asyncio.Condition lets Tasks wait for shared state to change while holding a lock around it. A Condition combines the functionality of an Event and a Lock, and several Condition objects can share one Lock.

  1. Condition.wait() raises RuntimeError if the calling task has not acquired the lock; otherwise it releases the lock, blocks until it is awakened by notify() or notify_all(), re-acquires the lock and returns True.
  2. notify() and notify_all() must be called with the lock acquired, and released shortly after; called with an unlocked lock, they raise RuntimeError.
  3. A task may return from Condition.wait() spuriously, so the caller should re-check the state; wait_for(predicate) waits repeatedly until the predicate is true and returns its final value.

Working: the quick quote

  1. The quote Task enters async with cond and calls wait_for(lambda: len(offers) >= 3). The predicate is false, so it waits, and the lock is released.
  2. A seller Task enters async with cond, appends its offer and calls notify_all().
  3. The quote Task wakes, takes the lock back once the seller Task leaves its block, and checks the predicate again: 1 offer, not yet; it waits again.
  4. At the third offer the predicate is true: the quote Task reads the list, still holding the lock, and answers.

Why each step is needed

  • Step 1: releasing the lock while waiting is what lets the seller Tasks get in to change the list.
  • Step 3: re-checking after every wake is what makes a spurious or premature wake harmless.
  • Step 4: reading under the lock means no seller Task can append in the middle of the read, even if the read contained an await.

asyncio.Barrier: N Tasks go on together once all N have arrived

Last part: a Condition waits for any predicate over shared state. Still unsolved: one common predicate, "all N of us are here", has its own tool since Python 3.11.

The load test for gateway v8 must send 100 requests at the same instant, to reproduce a stampede. Opening 100 connections takes tens of milliseconds, and requests sent as each connection opens arrive spread out. The test needs every shopper to wait until all 100 are connected, then fire together.

Introduction

A barrier is a meeting point for a fixed number of Tasks. Each waits there; when the last one arrives, all of them go on. It is the tool for phases, where no Task may start phase 2 until every Task has finished phase 1.

Definition

An asyncio.Barrier holds Tasks until a set number have arrived. Barrier(parties) blocks Tasks in wait() until parties tasks are waiting, then unblocks them all simultaneously; it can be reused any number of times, and it was added in Python 3.11. The docs say Barrier.wait() returns an integer from 0 to parties − 1, different for each task, and a waiting task that is cancelled exits the barrier, which stays in the same state.

abort() puts the barrier into a broken state, so that active and future calls to wait() fail with BrokenBarrierError, a subclass of RuntimeError; reset() returns the barrier to its empty state, and tasks waiting on it receive BrokenBarrierError.

Working

  1. Filling. Each wait() before the last one parks; the barrier counts it.
  2. The last arrival releases all of them: the barrier enters its draining state and every waiter wakes, each with its own position number.
  3. Reuse. When all have left, the barrier is back to filling, with 0 waiting, for the next phase.
  4. Failure. If one party cannot arrive, abort() breaks the barrier, so the others get BrokenBarrierError instead of waiting forever.

Program

Explanation of the program

  1. shopper-1 and shopper-2 connect at 0 and 30 ms and park; at 50 ms the barrier shows 2 of 3 waiting.
  2. shopper-3 connects at 70 ms; all three send at 70 ms, with positions 0, 1 and 2.
  3. Afterwards the barrier is filling again with 0 waiting: ready for another round.
  4. With abort(), both waiting shoppers get BrokenBarrierError and the barrier stays broken.

Gateway v8's load test in rung 3 uses exactly this: 100 shoppers connect, meet at a Barrier(100), and send together.

Python 3.10 and older: no asyncio.Barrier. There, the same meeting point is built from a counter and an Event: each arrival adds one, and the arrival that reaches N sets the Event everyone waits on. It serves one phase; a second phase needs a new Event. On 3.11 and later, use asyncio.Barrier, which is reusable and handles cancelled waiters.

Wrong belief: "gather() or a TaskGroup already does what a Barrier does."

Why it is wrong: a TaskGroup waits, from outside, until the Tasks have finished. A Barrier makes running Tasks wait for each other in the middle of their work, and then lets them all go on. The load test cannot use a TaskGroup for that: the shoppers must still send and read after the meeting point.

  • Barrier(n): each wait() parks until n are waiting, then all go on; reusable.
  • wait() returns a position, 0 to n − 1, to each Task; after a cancelled waiter two Tasks can get the same number (measured on 3.11 to 3.14), so do not use it as an id.
  • If a party cannot come, abort(): everyone else gets BrokenBarrierError.

A Barrier makes a fixed number of Tasks wait for each other at one point in their work and releases them together, which is what phases and true-simultaneity load tests need.

A Barrier(3) has 2 Tasks waiting. One of them is cancelled by its request's deadline. Then 2 more Tasks call wait(). What happens?

  1. All three get BrokenBarrierError
  2. The cancelled Task leaves, so 1 is waiting; the next 2 arrivals make 3, and those three go on together
  3. The first new arrival releases the barrier, because the cancelled Task still counts

contextvars: a value that belongs to the current context, not to the module

Last part: a Barrier makes Tasks wait for each other. Still unsolved: the wrong request id from rung 1. A module variable is shared by every request; what kind of variable belongs to one request?

Passing it through every function signature in the codebase would touch hundreds of functions. A module variable is wrong after the first await.

Introduction

The contextvars module, added in Python 3.7, provides APIs to manage, store and access context-local state, and its docs say that context managers that have state should use context variables instead of threading.local, to keep that state from bleeding into other code when used in concurrent code. A context variable's value depends on the current context, a mapping that asyncio swaps in and out as it switches between Tasks. This part covers the variable and the context on their own, with no asyncio. The next part adds the Tasks.

Comparison

A hotel gives each guest a key card. The card reader on a door does not ask the guest's name; it reads whatever card is presented and opens the right room. Two guests using the same door at different times get different rooms.

  • The key card = the current context.
  • The door's card reader = request_id.get(): the same code, a different answer per context.
  • Copying a card for a family member = copy_context().

The comparison stops working here: a copied card opens the same room. A copied context is a separate mapping: changes made under the copy do not appear in the original.

Definitions

  1. A ContextVar is a variable whose value is looked up in the current context. ContextVar.get() returns the variable's value in the current context; if there is none, it returns the get() call's default argument if one was given, else the variable's own default if it was created with one, else it raises LookupError.
  2. ContextVar.set() sets a new value in the current context and returns a Token, which ContextVar.reset() uses to restore the value the variable had before that set(); the same token cannot be used twice.
  3. A Context is the mapping from variables to values. copy_context() returns a copy of the current Context, and Context.run() enters the context, calls the function, then exits; changes made with ContextVar.set() while it runs are recorded in that context.
  4. Context variables should be created at the top module level and never in closures, because Context objects hold strong references to them, which prevents them from being garbage collected.

Working

  1. Declare once, at module level: request_id = ContextVar("request_id", default="-").
  2. Set at the edge, when a request starts: request_id.set("shopper-1"). The value goes into the current context, not into the variable.
  3. Read anywhere: request_id.get() looks in whatever context is current when it runs.
  4. Run code in another context with ctx.run(f); its sets stay in ctx.

Program

Explanation of the program

  2. shopper_tier has no default and no value, so get() raises LookupError.
  3. Inside ctx.run(inside), the set to "shopper-2" goes into ctx. Outside, the current context never changed: still "-". ctx[request_id] shows the value kept in the snapshot.
  4. The last block uses the Token as a context manager, new in 3.14.

Python 3.11 to 3.13: no with var.set(...). Support for using a Token as a context manager, which resets the variable when the block exits, was added in Python 3.14. On older versions the program stops at that line with TypeError; write token = var.set(...) and var.reset(token) in a finally instead.

Each Task gets a copy of the context, taken when it is created

Last part: a ContextVar's value lives in the current context. Still unsolved: on an event loop, what is "the current context" while 200 requests take turns on one thread?

The gateway sets request_id in each request's handler. The handler then starts five seller Tasks in a TaskGroup. Each seller Task must log with its own request's id, and a seller Task that changes the value, by accident or on purpose, must not change it for its request or its siblings.

Introduction

asyncio answers the question with one rule, applied at one moment: when a Task is created, it takes a copy of the context current at that moment, and every step of the Task runs inside that copy. Callbacks get the same treatment when they are scheduled. Everything about request ids, and every bug in rung 4, follows from that one rule.

Definition

If no context is provided, a Task copies the current context and later runs its coroutine in the copied context; asyncio.create_task() and the Task constructor accept a context argument to use a given Context instead, added in Python 3.11. Context variables are natively supported in asyncio and are ready to be used without any extra configuration.

loop.call_soon() accepts an optional context argument for the callback to run in, and callbacks use the current context when none is provided. In CPython 3.14's events.py, a Handle created without a context takes a copy of the current context when it is created, and futures.py's add_done_callback() likewise copies the context current when the callback is added.

Working

  1. The handler sets request_id in its own Task's context.
  2. It creates child Tasks. Each takes a copy of the handler's context at that moment, value included.
  3. Each step of each Task runs inside that Task's own copy: get() sees the value, and set() changes only that copy.
  4. A callback scheduled with call_soon or added as a done callback runs in a copy taken when it was scheduled or added.

Why each step is needed

  • Step 2: copying at creation is what makes the id follow the request into every Task it starts.
  • Step 3: a separate copy per Task is what keeps one Task's set() from leaking into its parent, its siblings, or another request.
  • Step 4: callbacks need a context too, and they get the one in force when they were scheduled, not when they run.

A single-flight price cache: one seller call, however many requests ask

Last part: each Task gets a copy of the context at creation. Still unsolved: rung 1's stampede. 100 requests for one item asked seller-c 100 times. How does the gateway make them share one call?

A sale starts at 10:00 and 100 shoppers ask for kettle-1l in the same instant, with an empty cache. The gateway should ask each seller once and give all 100 shoppers the answer. And seller-e, which answers at 900 ms, long after every request's 250 ms deadline, should still end up in the cache, so the shoppers who come next get its 1,149.

Introduction

A Lock around the check, the call and the store would stop the duplicate calls, but rung 4 measures what it does to every other item. The pattern that fits is older than asyncio and has a name. This part builds it in about 25 lines and measures it against the naive cache.

Comparison

An office of 100 people wants coffee from the shop downstairs. The first person to ask writes "going for coffee, back at 10:15" on the board and goes; everyone who asks after that adds their name to the board and waits; the one runner brings back enough for all. If someone stops waiting and leaves for a meeting, the runner still comes back, and the coffee is there for whoever asks next.

  • The note on the board = the in-flight entry for the key.
  • The one runner = the one fill Task.
  • Someone leaving for a meeting = a request whose deadline or hang-up stops its wait.

The comparison stops working here: the office runner is a person with a name. The fill Task belongs to no request, which decides whose deadline, cancellation and request id it carries.

Definitions

  1. Single-flight: at most one call per key is in flight, and callers who ask for the same key meanwhile wait for that call and share its result. Go's golang.org/x/sync/singleflight package provides a duplicate function call suppression mechanism: its Do method makes sure that only one execution is in flight for a given key at a time, and a duplicate caller waits for the original to complete and receives the same results.
  2. A fill: the one call that loads a missing or expired entry. In the gateway it is an owned Task, started with Part 4's spawn().
  3. The TTL (time to live): how long a cached price is used before it is fetched again.

Working: one fill for 100 requests

  1. Check the cache. A fresh price is returned at once.
  2. On a miss, look for a fill in flight for (seller, item). If there is none, start one and record it. There is no await between the lookup and the record, so by the one-step rule no other request can slip in between: the first request starts the fill, and the other 99 find it.
  3. Wait for the fill through shield(), under the request's own deadline. The deadline or a hang-up ends that request's wait; the fill goes on (Part 5's shield, for the same reason as the audit row).
  4. The fill stores the price and finishes. Its done callback removes the in-flight entry, so the next miss, after the TTL, starts a new fill.
  5. A failure is returned, not stored. Every waiter gets the same error value; nothing is cached, so the next request tries again.

Why each step is needed

  • Step 2: the check and the record must be one step; that is what a Lock would buy, and the loop gives it free when there is no await between them.
  • Step 3: without the shield, the first request's 250 ms deadline would cancel the fill for all 100, and seller-e's 900 ms price would never be stored. The naive cache in the program below has exactly that problem.
  • Step 3, ownership: the fill is created with spawn(), outside any request's TaskGroup, in a fresh context. Rung 4 shows what goes wrong in logs when it inherits the first request's context instead.
  • Step 5: caching a failure would make one bad answer from a seller stick for the whole TTL.

Explanation of the diagram

  1. Steps 1 to 3 are the one-step rule at work: whichever request runs first records the fill before any other request can look.
  2. Steps 4 and 5 separate the fill's lifetime from the requests'. The requests keep their 250 ms promise; the fill keeps going.

Solved example: the calls saved at the sale's numbers

Given: 2,000 requests a second for one item; TTL 30 s; five sellers.

Facebook's NSDI 2013 paper on scaling memcache describes leases against thundering herds: a lease is a 64-bit token bound to the key a client asked for, servers by default return a token only once every 10 seconds per key, and in their measurement the peak database query rate was 17K/s without leases and 1.3K/s with them. Probing question: "Your cache sits in front of a slow API. Traffic spikes after every deploy and every expiry. What is happening and what do you change?"

What a strong senior answer contains: a cache stampede: every request that misses during the refill calls the API.   • Single-flight: one fill per key; others wait for it; the entry is removed when it finishes.

  • Failures are returned, not cached. 100 requests: 5 seller calls instead of 500, and seller-e's price finally cached.

Crossing between threads and the loop: three bridges

Last part: copy_context().run carries the request id into seller-e's SDK thread. Still unsolved: that crossing went from the loop into a thread. seller-e's SDK also calls the gateway back, from a thread of its own. Which way across fits which job?

seller-e's vendor adds a price feed to its SDK: feed.subscribe(callback), and the SDK calls callback(item, offer) on its own thread whenever a price changes. The callback must update the gateway's cache, which lives on the loop, and the vendor wants a reply only once the change is applied and audited.

Introduction

Part 2 showed that only call_soon_threadsafe both queues work safely and wakes the loop, and Part 4 put seller-e's SDK in a thread pool with run_in_executor. This part puts all the crossings side by side. There are three directions a gateway needs, and one tool for each.

Definitions

  1. The asyncio docs say almost all asyncio objects are not thread safe; code outside a Task or callback that needs a low-level asyncio API should use loop.call_soon_threadsafe(), and run_coroutine_threadsafe() should be used to schedule a coroutine object from a different OS thread.
  2. call_soon_threadsafe() must be used when scheduling callbacks from another thread, because call_soon() is not thread-safe, and it raises RuntimeError if called on a loop that has been closed, which can happen on a secondary thread while the application shuts down.
  3. run_coroutine_threadsafe(coro, loop) submits a coroutine to the given event loop, is thread-safe, returns a concurrent.futures.Future for waiting on the result from another OS thread, and is meant to be called from a different OS thread than the one running the loop. If the coroutine raises, the returned Future is notified, and the Future can be used to cancel the task in the event loop, for example after result(timeout) raises TimeoutError.
  4. In CPython 3.14's threads.py, to_thread() copies the current context and runs the function through ctx.run with loop.run_in_executor(None, ...), so it always uses the loop's default executor.

Working: one bridge per direction

  1. Loop → thread, wait for the result. A coroutine needs a blocking call. await asyncio.to_thread(f) uses the default pool and carries the context. For a dependency with its own pool (Part 4), await loop.run_in_executor(pool, ctx.run, f) with ctx = copy_context() does the same in that pool.
  2. Thread → loop, fire and forget. A thread has a small piece of work for the loop and does not need a reply: loop.call_soon_threadsafe(callback). The callback runs on the loop's thread in a later iteration.
  3. Thread → loop, wait for a coroutine's result. A thread needs async work done and must know how it went: asyncio.run_coroutine_threadsafe(coro, loop).result(timeout). The thread blocks; the loop does not.
  4. Get the loop first. A foreign thread has no running loop: get_running_loop() returns the running event loop in the current OS thread and raises RuntimeError if there is none. So the loop is captured on the loop's thread, at start-up, and handed to whoever will cross.

In CPython 3.14's tasks.py, run_coroutine_threadsafe() creates a concurrent.futures.Future and uses loop.call_soon_threadsafe() to schedule a callback that wraps the coroutine in a Task on the loop and chains that Task's outcome to the Future. So bridge 3 is bridge 2 plus a Task and a Future: the same wake-up, with a result attached.

Free-threaded Python 3.14: what changes for this gateway

Last part: three bridges cross between threads and the loop. Still unsolved: those threads are about to run Python code truly in parallel on the free-threaded build. What does that change for a service built on one event loop?

Introduction

Part 1 noted that the free-threaded build exists and argued it does not make an I/O-bound gateway faster. This part looks at it from this page's side, shared state, and answers with the docs and with one measurement that differs between the builds.

Definitions

  1. Python 3.14's release notes say the free-threaded build is now supported and no longer experimental, the start of phase II, in which it is officially supported but still optional; whether it becomes the default build is still undecided.
  2. In 3.14 the performance penalty on single-threaded code in free-threaded mode is roughly 5 to 10%, depending on the platform and C compiler.
  3. A free-threaded build can run with the GIL enabled at runtime through the PYTHON_GIL environment variable or the -X gil option, sys._is_gil_enabled() reports whether the GIL is actually disabled in the running process, and importing an extension module not marked as supporting free threading can enable the GIL automatically, with a warning.
  4. In 3.14 asyncio has first class support for free-threading builds, which enables parallel execution of multiple event loops in different threads, scaling linearly with the number of threads.

Working: what changes, piece by piece

  1. Code on one event loop: unchanged. One loop is one thread; the one-step rule and every tool in rung 2 work exactly as before, because they never relied on the GIL.
  2. asyncio objects touched from other threads: still forbidden. Lock, Event, Queue and the loop's own methods were never thread-safe; the bridges of the last part are still the only way in.
  3. Plain Python state shared with threads (the SDK's counters, a dict a feed thread writes): the free-threaded build aims to provide thread-safety at the Python level similar to the default build, with built-in types such as dict, list and set using internal locks, and the docs recommend threading.Lock or other synchronization primitives instead of relying on those internal locks. A read-modify-write such as count += 1 from several threads needs a threading.Lock on either build, as seller-e's SDK already uses; on the free-threaded build the threads really run at the same time, so a missing lock shows up sooner.
  4. Context in new threads: different. The thread-context flag from the last part defaults to true here, so a pool thread starts with a copy of whatever context was current when the pool started it.

A lock held across a slow call: every cached item waits for one miss

Last part: gateway v8 shares one fill per key. Still unsolved: the obvious alternative, one Lock around the whole cache, also stops duplicate calls. What does it cost?

Introduction

A lock makes its critical section one step for every Task that uses it, and that is the whole problem when the section contains a 900 ms await and the lock covers more than the one key the await is about. This part measures it and shows how to tell it from other slowness.

Working

  1. shopper-1 asks for toaster-2s, which is not cached. It takes the cache's one lock and awaits seller-e: 900 ms with the lock held.
  2. shopper-2 asks for kettle-1l at 10 ms. kettle-1l is cached, but checking the cache needs the lock, so shopper-2 parks in the lock's waiters.
  3. At 900 ms shopper-1 stores and releases; shopper-2 takes the lock, finds kettle-1l at once and answers, 890 ms late.

Program

Explanation of the program

  1. OneLock: the cached kettle-1l is answered at 900 ms, together with the miss it had nothing to do with.
  2. PerKey: single-flight per item. kettle-1l is answered at 10 ms, when it was asked; toaster-2s at 900 ms, as it must be.

Solved example: at the sale's load

Step 1. The lock is held 900 ms of every 1,000 ms by fills.

Step 2. Requests arriving during a fill: 2,000 × 0.9 = 1,800 a second wait for the lock; their 250 ms deadlines cut most of them, as cache misses for prices the cache already had.

A deadlock from lock order: two Tasks that wait for each other forever

Last part: a lock's scope decides who waits behind it. Still unsolved: once code holds one lock and needs another, two Tasks can each hold what the other needs.

Introduction

A deadlock needs two locks, two Tasks and two different orders. It is a classic of threaded code, and an event loop does not prevent it: an await while holding a lock is all it takes.

Definition

A deadlock is two or more Tasks each waiting for a lock that another of them holds, so none can ever go on. On an event loop the Tasks are parked on Futures that nobody will fill: no CPU is used and nothing is reported.

Working

  1. refill takes cache_lock and awaits seller-d.
  2. report runs during that await, takes quota_lock and awaits the metrics store.
  3. refill resumes and asks for quota_lock: held by report, so it parks.
  4. report resumes and asks for cache_lock: held by refill, so it parks. Neither will ever release.

Program

Explanation of the program

  1. Opposite orders: after 1 s neither Task has finished, the log is empty, and each lock is held with one waiter. Without the 1 s limit in asyncio.wait(), the program would wait forever.
  2. The program cancels both; each lock's async with releases what it held.
  3. Same order: report waits for refill to release cache_lock, then both finish.

  3. Relying on asyncio.Lock being fair

What breaks first at 10 times the load: herds, hot keys and ten caches

Introduction

Single-flight fixed the stampede for one key in one process. At 10 times the load three new things break first, all of them about scope and timing rather than correctness: entries that expire together, a cache per process, and a cache with no size limit.

Program: a model of seller calls after a deploy

Working: the order things break

  1. Synchronized expiry. A deploy starts all 10 processes with empty caches; every item is filled in the first second, so every entry expires in the same second, 30 s later, and every 30 s after that. Each of those seconds sends one call per item per process: 10 × 5,000 = 50,000 calls to each seller.
  2. Ten caches. Single-flight works per process, so each item is filled once per process per TTL: 10 × 5,000 ÷ 30 ≈ 1,667 calls a second to each seller in the long run, above seller-d's contract of 1,500 a second (Part 6), however the expiries are spread.
  3. Hot keys. One item that everybody wants is still one fill per process, but while seller-e's 900 ms fill runs, every request for it waits on that fill until its own deadline: at 2,000 requests a second per process, 2,000 × 0.25 = 500 Tasks parked on one fill at any moment, each answering without seller-e for most of every refill.
  4. Memory. The dict never forgets: expired entries stay until overwritten, and items that are never asked for again stay forever.

Solved example: the fixes, with numbers

Step 1. Jitter. A TTL of 30 s ± 10% spreads each round of expiries over 6 s. The model's worst second falls from 50,000 calls to 8,449, the same long-run rate.

Step 2. Share the cache. One cache for all 10 processes, with single-flight across them (a lease, as in Facebook's memcache), refills each item once per TTL: about 167 calls a second, and the model's worst second is 901. That is below seller-d's 1,500 a second; the cost is a network hop per lookup and a shared store that can fail.

Step 3. Refresh before expiry. Hot items can be refreshed in the background a few seconds before they expire, while the old price is still served, so no request ever waits on a hot key's refill. The cost is calls for items nobody asks for again.

Step 4. Bound the memory. A size limit with eviction of the least recently used entries, and removal of expired ones.

Result: what broke first was not the cache's correctness but its timing and scope: entries filled together expire together, and caches per process multiply every seller's load by the process count.

Lock, single-flight, an owner Task or an immutable snapshot: which to pick

Last part: at 10 times the load, cache timing and scope break first. Still unsolved: this page used several ways to keep shared state correct. Faced with a new piece of shared state, which should a team reach for?

Four pieces of shared state land on the gateway team: seller-d's daily call counter, the price cache, a per-seller "health" record that several jobs update, and the list of sellers and their settings, which changes a few times a day. Each needs protecting. They do not all need the same protection.

Introduction

There are four ways to keep shared state correct in an asyncio service. Two of them, a lock and single-flight, came up on this page already. The other two avoid sharing altogether: give the state to one owner Task that everybody messages, or never change the state in place and replace it whole. The program puts all four on the same burst.

Definitions

  1. An owner Task is the only Task that reads and writes a piece of state; others send it requests through a queue and wait for its replies. No two Tasks touch the state, so there is nothing to race.
  2. An immutable snapshot is state that is never changed in place: a writer builds a complete new copy and swaps it in with one assignment, and readers use whichever version they read.

Program: the same burst, four ways

90 requests at once, 30 for each of three items; each miss is a 150 ms call to seller-c.

Explanation of the program

  1. OneLock and OwnerTask both make 3 calls and both serialise them: the third item waits for the first two, 450 ms. They are the same design in two shapes; an owner that handles one message at a time is a lock.
  2. PerKeyFlight makes the same 3 calls at the same time: 150 ms.
  3. Snapshot makes no calls during the burst and nobody waits: the refresher filled it before the burst and will replace it on its own schedule. The price is staleness, up to one refresh interval.

Decision rules

  • Can the critical section avoid awaits? Then no tool: keep the read and write in one step (the one-step rule).
  • Is it one expensive load per key? Single-flight, with the fill owned and shielded.
  • Is it read on every request and changed rarely? An immutable snapshot, swapped in one assignment.
  • Is it a short read-await-write? A Lock, scoped as narrowly as the state.
  • Is it a rich object several jobs change, where order matters? An owner Task, which also gives each change a place in one sequence.
  • Does more than one process share it? None of these is enough; the state, or a lease on it, must live in a shared store.

Probing question: "In an asyncio service, when would you use a lock, and when would you design the lock away?"

What a strong senior answer contains: first, most shared state needs nothing: on one loop, code without an await between read and write is already one step. A lock is for a short critical section that must await, scoped to the state it protects, never held across a slow call or while taking another lock. It is designed away by single-flight for keyed loads, by one owner Task for state with many rules, and by immutable snapshots for read-mostly data; each has a cost, waiting, an owner to supervise, or staleness. And none of them works across processes.

Wrong belief: "An owner Task (actor) avoids locks, so it avoids lock contention."

Why it is wrong: it avoids the lock object, not the waiting. A single owner that awaits inside a message handler serialises every caller behind that await, exactly like a lock held across it: the program's OwnerTask waits 450 ms, the same as OneLock. An owner is fast only if its handlers do not await slow work, or hand it to single-flight fills.

  • No await between read and write: no tool needed.
  • Keyed expensive loads: single-flight. Read-mostly data: an immutable snapshot. Short read-await-write: a narrow Lock. Rich state with rules: an owner Task.
  • Across processes: a shared store with a lease; none of the in-process tools reach that far.

Pick the protection by the shape of the access: nothing for one-step updates, single-flight for keyed loads, a snapshot for read-mostly data, a narrow lock for short read-await-writes, and an owner Task for rich state, and none of them across processes.

The gateway's seller settings (caps, lines, rates, TTLs for five sellers) are read by every request and changed by an admin a few times a day. Which design fits best?

  1. A Lock around every read and write of the settings dict
  2. An owner Task that answers every request's "what are seller-c's settings?" message

Prompt 1: "Our cache makes the backend fall over after every deploy"

An asyncio API with a 300 ms budget caches product data from a backend that takes 1.2 s. After each deploy of its 8 processes the backend is overloaded for a minute, and products from the backend are almost never in the cache. The cache code is: if not cached, await the backend, store, return. What is going on, and what do you change?

Two things. First, a stampede: every request that misses during the 1.2 s load calls the backend itself, because the check, the await and the store are not one step, and after a deploy every key misses at once in all 8 processes. Second, the slow backend is never cached: each request's own 300 ms deadline cancels its own call, so no call ever completes to store anything. Fix both with single-flight per key: one fill per key, an owned Task in a fresh context with its own deadline longer than 1.2 s, awaited through shield() under each request's deadline, failures not cached. Then the deploy herd: jitter TTLs, refresh hot keys ahead of expiry, and, because single-flight is per process, a shared cache with a lease so 8 processes make one call per key instead of 8. Prompt 2: "Our logs show the wrong user"

An asyncio service tags log lines with the current user from a module-level variable set in middleware. Under load, lines show the wrong user, and lines from a sync SDK called through a thread pool show none. Design the fix and say what remains to watch.

The module variable is shared by every request on the loop's one thread, so another request overwrites it during any await. Move the user into a ContextVar set in middleware before the handler starts any Task; each Task copies the context at creation, so the value follows the request into all of them, and a logging filter reads it for every record, including library records. The thread pool runs in its own context, so wrap each call with copy_context().run, or use to_thread() where the default pool is acceptable. Callbacks from foreign threads run in that thread's context and must set their own value. Shared work started on behalf of many requests, such as a cache fill, gets a fresh context and its own id, or its lines carry whichever request started it. On the free-threaded build new threads copy their starter's context, so a missing wrap shows a wrong user rather than none; carrying the context explicitly avoids depending on the build.

Prompt 3: "A vendor SDK calls us back on its own thread"

A payment provider's SDK delivers status updates by calling your function on its own thread, and redelivers any update your function does not return from within 5 s. Each update must update an in-memory order status (used by asyncio handlers) and write an audit row through an async client. Design the callback.

Capture the loop at start-up. In the callback, run_coroutine_threadsafe(apply(update), loop) and wait with result(timeout=4) before returning, so the SDK learns about failures (an exception from result()) and timeouts (redelivery), and so the SDK's thread is held to the loop's pace. apply() runs on the loop: it updates the status dict in one step, with no await between its read and write, and awaits the audit write. If redelivery can repeat an update, apply() is idempotent by update id. Never touch the dict or any asyncio object from the SDK thread directly; call_soon_threadsafe would do for fire-and-forget, but here the SDK must know the outcome. The callback sets its own context id, since it runs in the SDK thread's context. On shutdown, stop the SDK before closing the loop, because calls into a closed loop raise RuntimeError. Trade-off: the SDK thread blocks up to 4 s per update, so its delivery rate is bounded by the loop's handling time.

Wrong belief: "In an interview, 'asyncio is single-threaded, so no race conditions' is a safe simplification."
