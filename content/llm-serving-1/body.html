Why a chat reply can leave a top-end GPU almost idle

Your team puts an 8-billion-parameter chat model on one H100 behind a FastAPI endpoint. A typical answer of 300 tokens streams back in about one and a half seconds. The GPU dashboard says it is busy the whole time. By the end of part 6 you will see that its arithmetic units are doing useful work well under 1% of that time.

That gap is not a bug in your code. It comes from how a language model writes text: one small piece at a time, and every piece needs the entire model read out of GPU memory again. Reading, not calculating, sets the pace.

Think of a bank clerk who, for each word of a letter, must walk to the archive, carry back all 16 binders of the rulebook, and then write a single word. The writing takes a second; the walk takes a minute. A faster pen changes nothing. Carrying the binders once for twenty customers at the same desk changes everything.

  1. What the model reads and writes: tokens, and the loop that produces them one by one (part 2).
  2. The two phases of every request: prefill and decode, and what each one costs (parts 3 to 6).
  3. Using it: a calculator, the latency metrics, and a script that estimates both phases (parts 7 to 10).
  4. Breaking it and choosing: why one-request-at-a-time serving collapses under load, and how to reason about hardware and metrics in interviews (parts 11 to 14).

This is Part 1 of a seven-part series on how LLM inference servers work inside. It sets up the problem the rest of the series solves. Batching, memory management and scheduling come in later parts.

Generating text is limited mostly by how fast the GPU can read the model's weights, not by how fast it can calculate.

In the bank clerk story, which change would speed up the clerk the most?

  1. A faster pen
  2. Serving many customers per trip to the archive
  3. Asking customers for shorter letters

The walk dominates. Sharing each walk across many customers spreads its cost. On a GPU that idea is called batching, and Parts 3 and 4 of the series are about doing it well.

The model writes one token, then starts over

Last part: reading the model, not calculating, sets the pace. Still unsolved: why does it have to read the model again for every piece of output?

A user asks for a 300-word summary. You might expect the model to produce the summary in one shot, the way a database returns a result set. Instead it runs a few hundred times in a row, and you cannot run those passes in parallel.

A model does not see characters or words. It sees tokens. Hugging Face's tokenizer guide describes subword tokenization: common words stay whole as one token, and rare words are split into smaller pieces.

  1. The prompt is turned into a list of token IDs.
  2. The model runs once over that list and scores every possible next token.
  3. The server picks one token and appends it to the list.
  4. The model runs again over the longer list to pick the token after that.
  5. This repeats until a stop condition.

A language model generates the next token from the prompt plus everything it has generated so far, and stops at a length limit or when it produces an end-of-sequence token. Each output becomes part of the next input. That is called autoregressive generation. The original Transformer paper describes its decoder this way: it emits output one symbol at a time, feeding earlier outputs back in as extra input for the next step.

As a backend engineer, picture a chain of database queries where each query needs the previous query's result in its WHERE clause. You cannot fire them in parallel, however many connections you have. Token 101 cannot start until token 100 exists.

Output is produced one token per model run, and each run needs the token before it, so the runs form a strict sequence.

A product manager asks: "We have spare GPUs. Can we generate tokens 1 to 150 on one GPU and 151 to 300 on another, at the same time?" What is the problem?

  1. The second GPU would run out of memory
  2. The two GPUs would tokenize the prompt differently
  3. Token 151 depends on tokens 1 to 150, which do not exist yet

Generation is autoregressive: each token is computed from all earlier tokens, including the model's own outputs. The second half cannot start before the first half is finished.

In your own words: why can't one request's output be generated all at once?

The model reads and writes tokens, small chunks of text with integer IDs. Each run of the model produces just one next token, which is appended to the input for the following run. Because every token depends on all the tokens before it, the runs for one request must happen in order. It stops when it writes an end-of-sequence token or hits a length limit.

One request, step by step: prefill, then decode

Last part: output comes one token per model run. Still unsolved: is every run the same, or is the first one special?

A 2,000-token prompt asks for a 300-token answer. The model runs about 300 times. The first run takes in 2,000 tokens; every later run adds just one. Those are very different jobs.

Before you look at the diagram: for a 2,000-token prompt and a 300-token answer, how many runs of the model are there, and how many tokens does each one take in that the model has not seen before?

300 runs. The first run takes in all 2,000 prompt tokens at once and produces output token 1. Each of the remaining 299 runs takes in one new token, the one produced just before, and produces the next. The first run is prefill; the other 299 are decode steps.

One run of the model over some tokens is a forward pass. A request has two phases of forward passes.

  1. Prefill: the server runs the whole prompt through the model in one step, processing all prompt tokens in parallel, and that step produces the first output token.
  2. Decode: the server generates the remaining tokens one per step, over many steps.
  3. Reuse: the model stores per-token attention state (the KV cache) as it processes tokens, so later steps reuse it instead of recomputing it. That is why a decode step only needs the newest token. Part 2 of the series covers how big this state gets.

In backend terms, prefill is a batch job: all the input is known up front and processed in one go. Decode is a streaming response: small pieces, one after another, each waiting on the last.

Every request runs one big parallel prefill pass that yields the first token, then many one-token decode passes.

Put one streamed request in order.

  1. The server tokenizes the prompt
  2. Prefill runs one forward pass over every prompt token
  3. The first output token is streamed back
  4. Decode steps each feed in the newest token and produce one more
  5. The model emits an end-of-sequence token and the stream closes

Tokenize, prefill (which yields token 1), then the decode loop until a stop condition. Only prefill sees the prompt tokens as new input.

What each phase actually costs: arithmetic and reading

Last part: prefill takes in the whole prompt once; each decode step takes in one token. Still unsolved: why would one-token steps be slow?

Prefill over 2,000 tokens does 2,000 times more arithmetic than one decode step. Yet on an H100 that prefill takes only about 7 times as long as a decode step. Something other than arithmetic is setting the decode time.

Any forward pass has two costs. One is arithmetic. A FLOP is one multiply or one add. A forward pass costs about 2 FLOPs per model parameter per token, one multiply and one add, plus an attention term that grows with context length and stays a small share while the model width exceeds the context length divided by 12.

The other cost is reading the weights from GPU memory into the chips that do the arithmetic. How fast that happens is the memory bandwidth. In BF16 each parameter takes 2 bytes, so loading an X-billion-parameter model takes about 2X GB of GPU memory.

The key asymmetry: one forward pass reads the weights once, however many tokens go through it. So the reading cost is fixed per pass, while the arithmetic grows with the tokens in the pass.

8B model in BF16Tokens in the passArithmeticWeights read
Prefill, 2,000-token prompt2,0002 × 8 billion × 2,000 = 32 trillion FLOPs16 GB, once
One decode step12 × 8 billion = 16 billion FLOPs16 GB, again

Hugging Face's docs state that every active parameter must be read from memory for every generated token, and call this a bottleneck for text generation. For a 300-token answer, that is 300 full reads of 16 GB: about 4.8 TB moved to write a few paragraphs.

Every forward pass reads all the weights once; prefill spreads that read over thousands of tokens, decode spends it on one.

A 13-billion-parameter model in BF16 writes a 100-token answer. Roughly how many bytes of weights does decode read in total?

  1. About 2.6 TB: 26 GB of weights, read about 100 times
  2. About 26 GB: the weights are read once
  3. About 1.3 TB: 13 GB read 100 times

13 billion parameters × 2 bytes = 26 GB. Each decode step reads all of it, and there is roughly one step per output token, so about 100 × 26 GB.

FLOPs per byte: the number that decides who waits

Last part: each pass reads all the weights once, and the arithmetic grows with the tokens in it. Still unsolved: how do you tell which of the two costs wins?

Two services run on the same server. One resizes images; adding CPU cores makes it faster. The other proxies calls to a slow storage API; adding cores does nothing. You already know these as CPU-bound and I/O-bound. A GPU has the same split.

The deciding number is how much arithmetic you do per byte you read. Call it arithmetic intensity. The Roofline paper (Williams, Waterman and Patterson) calls this ratio operational intensity: operations performed per byte of traffic to main memory.

For a dense model in BF16 the weights-only intensity falls straight out of part 4. Each token costs 2 FLOPs per parameter, and each pass reads 2 bytes per parameter. So the intensity equals the number of tokens in the pass.

  1. Prefill of a 2,000-token prompt: about 2,000 FLOPs per byte.
  2. One decode step for one request: about 1 FLOP per byte.

Work with high intensity is compute-bound: it finishes when the arithmetic is done. Work with low intensity is memory-bound: the arithmetic units sit waiting for bytes.

Backend idea you knowGPU equivalentWhat helps
CPU-bound batch job (resize 10,000 images)Prefill: compute-boundMore arithmetic speed
I/O-bound streaming endpoint (each chunk waits on storage)Decode: memory-boundMore bandwidth, or fewer bytes per useful result
Serving many callers from one disk read (a shared cache fill)Batching decode steps of many requestsRaises FLOPs per byte read

The comparison has a limit. An I/O-bound web service waits on something outside the machine, and async code lets it serve others while it waits. A memory-bound decode step waits on the GPU's own memory, and nothing else runs on those arithmetic units unless you put more work into the same pass.

Weights-only intensity equals tokens per pass: thousands for prefill, one for a single request's decode step.

A server runs one decode step for 32 requests together in a single pass. What is the weights-only arithmetic intensity of that pass?

  1. About 1 FLOP per byte, same as one request
  2. About 32 FLOPs per byte
  3. About 2,000 FLOPs per byte, like a prefill

The pass reads the weights once (2 bytes per parameter) but does 2 FLOPs per parameter for each of 32 tokens. 64 ÷ 2 = 32 FLOPs per byte.

The roofline: a GPU's two speed limits on one chart

Last part: prefill does about 2,000 FLOPs per byte, single-request decode about 1. Still unsolved: where is the line between compute-bound and memory-bound on a real GPU?

You need a number for the H100: below how many FLOPs per byte does it stop being limited by arithmetic? Without it, "memory-bound" is just a feeling.

The Roofline model says reachable performance is the lower of two ceilings: peak compute, and memory bandwidth multiplied by the intensity. The ridge point is where the two ceilings meet: the lowest intensity at which a kernel can reach peak compute. The ridge point is peak FLOPs per second divided by bytes per second.

Now the H100. NVIDIA lists the H100 SXM at 1,979 teraFLOPS of BF16 Tensor Core throughput with sparsity, 3.35 TB/s of memory bandwidth and 80 GB of memory. NVIDIA's with-sparsity figures are twice the dense ones; for example, the A100 lists 312 teraFLOPS of BF16 dense and 624 with sparsity. An ordinary model is dense, so its usable peak on the H100 is about 989 teraFLOPS.

  1. Ridge: 989 trillion FLOP/s ÷ 3.35 trillion bytes/s ≈ 295 FLOPs per byte.
  2. Decode, one request (about 1 FLOP per byte): at most 3.35 teraFLOPS, about 0.34% of peak.
  3. Prefill, 2,000 tokens (about 2,000 FLOPs per byte): past the ridge, so it can use the full 989.

So the clerk from part 1 is real: an H100 decoding one request spends over 99% of each step waiting for weights.

On an H100 anything below about 295 FLOPs per byte is memory-bound; single-request decode sits near 1.

A colleague says: "Decode is slow, so let's turn on the sparse Tensor Core mode; NVIDIA says it doubles BF16 throughput." What is wrong with the plan for single-request decode?

  1. The sparse figure is only marketing and does not exist
  2. It would double decode speed only for large models
  3. Decode is far below the ridge, so a higher compute ceiling does not change its speed; only bandwidth or more tokens per pass does

Reachable performance is the lower of the two ceilings. At about 1 FLOP per byte the memory ceiling is the binding one, so raising the compute ceiling changes nothing. You need more bandwidth or a higher intensity.

In your own words: why is prefill compute-bound while decode is memory-bandwidth-bound? Use the H100's numbers.

Each forward pass reads all the weights once and does about 2 FLOPs per parameter for each token in the pass. Prefill pushes thousands of prompt tokens through one read, so it does thousands of FLOPs per byte, well past the H100's ridge of about 295, which is 989 teraFLOPS of dense BF16 divided by 3.35 TB/s. Decode for one request pushes one token through a full read, about 1 FLOP per byte, so the arithmetic units wait on memory. The way out is to put more tokens into each pass.

TTFT and TPOT: the two numbers a user actually feels

Last part: more bandwidth speeds up decode, more FLOPs speed up prefill. Still unsolved: how do those show up in what users see and what you put on a dashboard?

Support tickets say "the bot thinks for four seconds before it starts typing, then types fast." Another team says "it starts instantly but types like a snail." Those are two different metrics, driven by two different phases.

TTFT is how long a user waits before anything appears. vLLM's benchmark docs define TTFT as the time from sending a request to receiving its first streamed output.

TPOT is how fast text flows once it starts. vLLM computes TPOT per request as (end-to-end latency minus TTFT) divided by (output tokens minus 1).

The DistServe paper treats TTFT as the duration of the prefill phase and TPOT as the measure of the decoding phase. In a real server TTFT also includes time spent queued before prefill starts.

  1. TTFT ≈ queue wait + prefill. Long prompts and busy servers raise it.
  2. TPOT ≈ one decode step. Model size, bandwidth and whatever else shares the pass raise it.
  3. End-to-end ≈ TTFT + TPOT × (output tokens − 1). This is the TPOT formula rearranged.

Worked example, 8B model on an H100 SXM, best case, empty queue, 2,000-token prompt, 300-token answer: TTFT about 32 ms, TPOT about 4.8 ms, end-to-end about 32 + 299 × 4.8 ≈ 1,460 ms. Decode is about 98% of the total. For long answers, end-to-end latency is a decode story.

TTFT is queue plus prefill; TPOT is the decode step; long answers make end-to-end mostly decode.

"Thinks for four seconds, then types fast." The model and prompt sizes have not changed this week. Which is the most likely cause?

  1. Requests are waiting in the queue before prefill starts, which inflates TTFT
  2. Decode steps got slower
  3. Answers got longer

TTFT is queue wait plus prefill. Prefill cost depends on prompt length, which has not changed. Fast typing means TPOT is fine. That leaves the queue, which grows when traffic outruns capacity.

ITL, throughput, and what vLLM actually exports

Last part: TTFT is queue plus prefill, TPOT is the decode step. Still unsolved: what do you put on the dashboard, and what do the metric names mean in a real server?

Your Grafana panel shows mean TPOT of 20 ms, but users complain about stutters. An average per request hides the one 900 ms pause in the middle of a stream.

ITL keeps every gap. vLLM's benchmark docs define inter-token latency (ITL) as the time between consecutive streamed outputs. With standard decoding each streamed output usually holds one token, so ITL and TPOT are usually close. Their percentiles are not: a p99 of ITL catches stutters that mean TPOT smooths away.

Throughput is the server's view. vLLM's benchmark reports request throughput (requests per second), output token throughput and total token throughput (tokens per second).

This page follows vLLM v0.31.0, the newest non-preview release tag when it was written. vLLM exports these as Prometheus histograms named vllm:time_to_first_token_seconds, vllm:inter_token_latency_seconds, vllm:request_time_per_output_token_seconds and vllm:e2e_request_latency_seconds.

It also splits each request's time into a queue interval, a prefill interval (from being scheduled to the first new tokens) and a decode interval (first to last new tokens), exported as vllm:request_queue_time_seconds, vllm:request_prefill_time_seconds and vllm:request_decode_time_seconds. Those three map straight onto this page's phases.

vLLM's docs warn that ITL and TPOT diverge when one streamed output bundles several tokens, as with speculative decoding. They also warn that metric names are not standardized across benchmarking tools, so compare measurement points and formulas, not names. The Splitwise paper, for example, reports TTFT, time between tokens (TBT) and end-to-end latency.

"Which latency SLOs would you set for a chat product, and why not just end-to-end?" A strong answer sets TTFT p95/p99 (perceived responsiveness, driven by queue and prefill) and ITL p99 (stream smoothness, driven by decode and interference). End-to-end mixes both and scales with answer length, so it cannot tell you which phase to fix. Throughput is a capacity target, tracked separately.

Watch TTFT and ITL percentiles for users, the queue/prefill/decode split for diagnosis, and tokens per second for capacity.

Mean TPOT is a steady 20 ms but users report the stream "freezing" mid-answer now and then. Which metric would show it?

  1. Mean end-to-end latency
  2. p99 TTFT
  3. p99 inter-token latency

ITL records every gap between streamed outputs, so one long pause lands in its tail. TPOT averages the gaps within each request, which hides the pause.

One request at a time: what breaks at 10 times the load

Last part: per pass, time is the larger of arithmetic and reading. Still unsolved: what happens to a server that runs one request at a time when real traffic arrives?

Your 8B model on one H100 handles one request at a time. Each 300-token answer takes about 1.46 s at best, so the GPU completes at most about 0.7 requests per second. Launch day brings 7 requests per second, ten times that.

The papers agree on the cause. The vLLM paper (SOSP 2023) notes that the prompt phase uses the GPU's parallelism well, while the token-by-token generation phase is limited by memory access and leaves GPU compute underused. DistServe (OSDI 2024) describes prefill as tending to be compute-bound and a single decoding job as heavily bandwidth-bound.

  1. What breaks first: the queue. Requests arrive ten times faster than they finish, so the backlog grows every second.
  2. What users see: TTFT climbs from tens of milliseconds to minutes, then client timeouts. Once a request starts, TPOT stays at about 4.8 ms, so streams look normal.
  3. A bad client: one caller sending a huge prompt or asking for thousands of output tokens holds the only slot, and everyone waits behind it.
  4. How you detect it: queue time and waiting requests rising while ITL stays flat.
  5. The fix: put many requests in each pass. The vLLM paper explains why batching helps: requests in a batch share the same weights, so the cost of moving them is spread across the batch.

vLLM's reference Grafana dashboard tracks queue time and the number of running and waiting requests alongside TTFT and inter-token latency. Alert on queue time and waiting requests, not only on latency.

"GPU utilization is 100%, so we are at capacity." NVML reports GPU utilization as the percent of time over the sample period during which one or more kernels was executing on the GPU. nvidia-smi is built on top of NVML. A single-request decode loop keeps a kernel running nearly all the time, so it reads close to 100% while using well under 1% of the arithmetic. Judge headroom by tokens per second against the roofline, not by this number.

Same GPU and model, but now the server runs one decode pass for 64 requests at a time. By the weights-only roofline, roughly what happens to the step time and to total tokens per second?

At 64 tokens per pass the intensity is about 64 FLOPs per byte, still under the ridge near 295, so the step is still set by the 16 GB weight read: about 4.8 ms. But it now produces 64 tokens, so the ceiling rises from about 209 to about 13,400 tokens per second. In practice attention's per-request reads (Part 2) cut into this, which is why the rest of the series exists.

Serving one request at a time caps an H100 at about 209 tokens per second for an 8B model, so extra load turns into queueing and exploding TTFT.

During the launch-day incident, which pair of signals best confirms "one-request-at-a-time capacity, not slow hardware"?

  1. GPU utilization at 100% and high end-to-end latency
  2. Queue time and waiting requests climbing while ITL stays flat
  3. TPOT rising steadily with load

Flat ITL says each step is as fast as before. Growing queue time says requests wait for the single slot. NVML's utilization only measures time with a kernel running, so it reads high either way.

When one long prompt freezes everyone else's stream

Last part: batching decode steps is the fix for one-at-a-time serving. Still unsolved: what goes wrong when prefill and decode share the same GPU?

You batch decode for 64 chat users. A customer uploads a 100,000-token contract. By the weights-only estimate its prefill alone takes at least 1.6 s on an H100, more once attention over that long a context is counted, and 64 people watch their streams stop for that long.

Prefill and decode want opposite things. Prefill is compute-bound and long. Decode is memory-bound and needs to run every few milliseconds. DistServe reports that mixing them slows both: prefill steps delay the decoding steps they share a batch with, which lengthens TPOT. Hugging Face's continuous batching docs likewise note that processing a long prompt in a single step blocks other requests from generating.

  1. What breaks at 10 times the load: more arrivals mean more prefills cutting into decode, so ITL p99 rises for everyone even when average TPOT looks fine.
  2. Misuse: a client sending maximum-length prompts in a loop can stall every other user's stream; cap prompt and output tokens per tenant.
  3. Detection: ITL p99 spikes that line up with large values of vllm:request_prompt_tokens.
  4. The fixes, later in the series: splitting long prefills into chunks, and running prefill and decode on separate GPUs.

"Users say streams stutter when someone pastes a big document. Why, and what are your options?" A strong answer names prefill-decode interference: the compute-bound prefill occupies the GPU while memory-bound decode steps wait, so ITL spikes. Options: cap prompt length, split prefill into chunks interleaved with decode, or separate prefill and decode onto different machines. Each trades something: chunking adds a little to the long request's TTFT; separation costs extra hardware and moving attention state between machines.

A long prefill on a shared GPU pauses every decode stream batched with it, which shows up as ITL tail spikes.

Average TPOT is fine, but ITL p99 jumps every few minutes. Prompt-length histograms show occasional 80,000-token prompts at the same moments. Best explanation?

  1. Long prefills are blocking the decode steps of the requests batched with them
  2. The GPU is slowly running out of memory
  3. The tokenizer is slow on long documents

The spikes line up with long prompts, and long prefills delay the decode steps that share the GPU with them. Averages hide it; the ITL tail shows it.

In your own words: what fails first when an LLM server takes ten times its load, and how would you see it on a dashboard?

With one request at a time, the GPU can only produce about bandwidth divided by weight bytes tokens per second, so extra traffic piles up in the queue and TTFT explodes while each stream still types normally. You see it as queue time and waiting requests climbing with flat ITL; GPU utilization reads high either way because it only measures time with a kernel running. Batching fixes it by sharing each weight read. Once batched, long prefills sharing the GPU stall everyone's decode steps, which shows up as ITL p99 spikes.

Interview drill and final check

Last part: match the hardware lever and the metric to the dominant phase. Still unsolved: can you put it all together under interview pressure?

Three prompts an interviewer could open with. Commit to an answer before revealing each one; each reference answer names the trade-off.

Prompt 1: "Design an endpoint that serves an 8B model to 50 concurrent chat users on one H100. Estimate whether one GPU is enough."

Set assumptions: 2,000-token prompts, 300-token answers, target ITL under 50 ms. Weights are 16 GB, so it fits. One at a time, the ceiling is about 209 tokens per second, which serves under one request per second: not enough. Decoding all 50 together, the weight read is still about 4.8 ms per step, well inside the ITL budget, so weights-only it fits easily. The trade-off: bigger batches raise throughput but add attention reads per request and make prefill interference more likely, so verify with a load test and watch ITL p99.

Prompt 2: "TTFT p99 tripled after we launched a 'summarise this file' feature. Walk me through your diagnosis."

Split TTFT into queue and prefill using the queue and prefill interval metrics. If prefill time rose, long prompts are the cause: prefill is compute-bound, so time scales with prompt tokens. If queue time rose, long prefills are holding the GPU and others wait. Then check ITL p99 for interference. Fixes trade off: capping file size limits the product; chunked prefill protects other users at the cost of the long request's own TTFT; separate prefill machines cost hardware.

Prompt 3: "Why can't we make decode faster by buying GPUs with more FLOPs?"

Single-request decode does about 1 FLOP per byte of weights read, far below a ridge of hundreds, so it is memory-bound: it waits for weights, not arithmetic. The levers are more bandwidth, fewer bytes per parameter, or more tokens per pass through batching. The trade-off with batching is per-request latency and memory for each request's attention state, which Part 2 sizes.

Final check. A 30B dense BF16 model on an H100 SXM decodes 16 requests per pass. Which statement is right by the weights-only roofline?

  1. The model does not fit in 80 GB
  2. The pass is compute-bound because 16 requests share it
  3. Each step takes 16 times longer than for one request
  4. The pass is memory-bound at about 16 FLOPs per byte, takes about 18 ms, and yields about 890 tokens per second in total

Weights: 60 GB, fits. Intensity equals tokens per pass, 16, below the ridge of about 295, so the step is set by the read: 60 GB ÷ 3.35 TB/s ≈ 18 ms. Sixteen tokens per step gives about 16 ÷ 0.018 ≈ 890 tokens per second.

Explain back the whole page: what are prefill and decode, why does each hit a different limit, which metrics do they drive, and why does naive serving waste the GPU?

An LLM writes one token per forward pass, each depending on the ones before. Prefill is the first pass: all prompt tokens at once, thousands of FLOPs per byte of weights read, so it is compute-bound and sets TTFT along with queue time. Decode is every later pass: one new token per request, about 1 FLOP per byte when serving a single request, far below an H100's ridge near 295, so it is memory-bound and sets TPOT and ITL. Serving one request at a time leaves almost all of the arithmetic idle and caps throughput at bandwidth divided by weight bytes. Putting many requests in each pass shares the weight read, which is where the rest of the series picks up.
