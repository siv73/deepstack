Why a backend engineer should care where a row lives

Two teams create a payments table with the same six columns in a different order. At 120 million rows, one table is about 1.3 times the size of the other. A third team stores user profiles as one big JSON document, and a counter update on it fills the disk far faster than the row count suggests.

None of this shows up in the SQL. It shows up in how PostgreSQL lays bytes on disk. Once you know the layout, table sizes, cache hit rates and slow updates stop being surprises you debug at 2 a.m.

Think of a warehouse. Stock is kept in identical boxes. Each box has a packing list glued inside the lid, and goods are packed from the far end. Anything too big for a box goes to a separate overflow room, and the box keeps a slip saying where it went.

  1. The boxes: fixed-size pages, and how rows are placed in them (part 2).
  2. What is in each item: the row header, the null bitmap and the padding between columns (part 3).
  3. The overflow room: TOAST, where large values go (part 4).
  4. Using it: measuring real sizes, ordering columns, tuning TOAST (parts 5 to 7).
  5. Breaking it and choosing: what fails at 10 times the load, and how to design tables and answer interview questions (parts 8 to 12).

PostgreSQL 18, first released on 25 September 2025, is the newest supported major version, and this page follows its documentation. The storage layout it describes has been stable for many releases, so it also applies to the versions you run at work.

Table size, cache behaviour and update cost all follow from how PostgreSQL packs rows into fixed-size pages.

A table grows 30% bigger than expected, but the row count and the data are identical to a sister table. Where would you look first?

  1. A hidden batch job inserting extra rows
  2. The compression setting of the database
  3. How the bytes of each row are laid out, for example the order of the columns

Same data and same row count means the difference is in how each row is packed. Column order is one of the causes; you will see exactly why in part 6.

In your own words: why does the on-disk layout matter to someone who only writes SQL?

PostgreSQL stores every table as fixed-size pages, and rows are packed into those pages with headers and padding. Large values are moved to a separate overflow store. How much fits in a page decides how big the table is, how many rows the cache can hold, and how much work an update does. So two tables with the same data can behave very differently.

A table is a stack of 8 kB boxes

Last part: layout decides size and speed. Still unsolved: what does one of those boxes look like inside?

Your orders table is 40 GB. When PostgreSQL reads "one row", how much does it actually read from disk into memory?

It reads a whole box. Every table and index is stored as an array of fixed-size pages, usually 8 kB. A page is the unit PostgreSQL reads, caches and writes. So one small row costs one 8 kB read, and the more rows fit in a page, the fewer pages a query touches.

  1. Every page starts with a 24-byte header that holds, among other things, pd_lower and pd_upper: the offsets where free space starts and ends.
  2. After the header comes an array of item identifiers, 4 bytes each, holding the offset and length of each row. Call each one a line pointer: it is the packing list in the lid.
  3. New item identifiers are taken from the start of the free space, and new rows are placed at its end, so the two grow toward each other.
  4. Ordinary tables leave the special space at the end of the page empty; B-tree indexes use it for links to neighbouring pages.

Why two ends? Line pointers have a fixed size and rows don't. Growing them toward each other lets a page hold many small rows or a few big ones without wasting a fixed split.

A page is a header, a list of 4-byte line pointers growing forward, and rows growing backward from the end, with free space in between.

A page has room left in the middle. You insert one more row of 60 bytes. Which way do pd_lower and pd_upper move, and by how much at least?

pd_lower moves forward by 4 bytes, because a new line pointer is added after the existing ones. pd_upper moves backward by at least 60 bytes, because the row is placed at the end of the free space. The free space shrinks from both sides. (Part 5 shows why the row's slot is usually a bit bigger than 60.)

What one row costs before your data even starts

Last part: rows sit at the end of a page, pointed at by line pointers. Still unsolved: what is inside a row, and how does anything point at it?

A table of three boolean flags stores 3 bytes of data per row. Yet each row uses 36 bytes of its page. Where do the other 33 go?

PostgreSQL calls a stored row a tuple. Each one looks like this:

  1. Every row starts with a fixed header of 23 bytes on most machines, then an optional null bitmap, then the column data.
  2. The header holds t_xmin and t_xmax, the IDs of the transactions that inserted and deleted this row version. Part 2 of this series is built on these two fields.
  3. The null bitmap exists only if the row has at least one NULL, and has one bit per column.
  4. Column data begins at offset t_hoff, which is always a multiple of the platform's MAXALIGN distance. MAXALIGN was 8 on the 64-bit x86 server used to test this page, so data started at byte 24. Every byte count on this page assumes that; the tests in part 6 pin them.

How does an index find this row later? A ctid, the pointer to a row, is a page number plus the index of an item identifier on that page. A ctid such as (0,3) means page 0, line pointer 3. An item identifier is never moved until it is freed, so it stays valid even when the row it points to is moved within the page to compact free space.

Every row pays a 23-byte header, rounded to 24, before its first column, and each column may add padding to reach its boundary.

A row has 5 columns and one of them is NULL. How much extra space does the null bitmap cost compared with the same row with no NULLs?

  1. 5 bytes
  2. Nothing: 5 bits fit in 1 byte, and byte 23 was going to be padding before the data starts at 24
  3. 8 bytes, because the data start moves to the next 8-byte boundary

23 bytes of header plus 1 byte of bitmap is exactly 24, the same start as without a bitmap. From the 9th column on, the bitmap needs a second byte and the data start jumps to 32.

Where a 50 kB value goes when the box is 8 kB

Last part: a row is a header, a bitmap and aligned columns. Still unsolved: what happens when one column is bigger than a page?

You store a 50 kB JSON document per customer. A page is 8 kB. Yet the insert works, and SELECT id, status on that table is still fast.

PostgreSQL does not let a row span pages, so large values are compressed and/or split into multiple rows in a separate TOAST table. TOAST is the overflow room from part 1. Only variable-length (varlena) types can be TOASTed, and any such value is limited to 1 GB. A varlena is a value with a length header, like text or jsonb.

  1. TOAST kicks in only when a row is wider than TOAST_TUPLE_THRESHOLD, normally 2 kB; it then compresses or moves values out until the row is under TOAST_TUPLE_TARGET, also normally 2 kB, or nothing more can be gained.
  2. With EXTENDED, compression is tried first, then out-of-line storage if the row is still too big. EXTENDED is the usual setting (part 7).
  3. Out-of-line values are cut into chunks of about 2000 bytes, each stored as its own row in the TOAST table with chunk_id, chunk_seq and chunk_data.
  4. For a value moved out of line, the main row keeps only an 18-byte TOAST pointer, whatever the size of the value.

Small strings get a discount too. Strings up to 126 bytes are stored with a 1-byte header; longer ones have a 4-byte header. Values with a 1-byte header are not aligned, while values with a 4-byte header are aligned on at least a 4-byte boundary.

Rows over about 2 kB get their big values compressed, then moved to a TOAST table as ~2000-byte chunks, leaving an 18-byte pointer behind.

You insert two 3,000-byte text values: one is the letter "a" repeated, the other is random hex digits. Predict how each one is stored.

Both rows are over 2 kB, so TOAST runs. The repeated letters compress to a few dozen bytes, the row drops under 2 kB, and the value stays inline, compressed. The random hex compresses poorly, so it is moved out of line in two chunks, and the row keeps only the 18-byte pointer. Same length, very different storage.

Explain how PostgreSQL stores a row with an id, a flag and a 20 kB text, from the page down to the bytes.

The row goes into an 8 kB page. A 4-byte line pointer is added after the page header and the row is written at the end of the free space. The row starts with a 23-byte header, then the columns, each padded to its alignment. The 20 kB text makes the row wider than 2 kB, so TOAST compresses it and, if it is still too big, splits it into ~2000-byte chunks in the TOAST table. The row keeps an 18-byte pointer. Indexes find the row by its ctid, the page number plus line pointer number.

Measuring what a table really costs

Last part: big values move to TOAST. Still unsolved: how do you see any of this on a real database?

An alert says the events database grew 200 GB this month. The row count only grew 5%. You need to know which table, and whether the growth is rows, indexes or TOAST.

First, where the bytes live. Each table and index is stored in its own file, named after its filenode number from pg_class.relfilenode. When a table or index grows past 1 GB, it is split into 1 GB segment files named filenode, filenode.1, filenode.2 and so on.

Besides the main fork, each table has a free space map (suffix _fsm) and a visibility map (suffix _vm); unlogged tables also have an initialization fork (_init). A fork is one of these files. The visibility map keeps two bits per heap page: all-visible and all-frozen. A table with columns that can hold large values has a TOAST table, linked from pg_class.reltoastrelid.

The functions that add these up:

  1. pg_relation_size returns the size of one fork (main by default; also fsm, vm or init).
  2. pg_table_size counts the table without indexes but with its TOAST table, free space map and visibility map; pg_total_relation_size adds the indexes.
  3. pg_column_size shows the bytes used to store a value, including any compression. pg_column_compression returns the compression method used for a value, or NULL if it isn't compressed.
SELECT c.relname,
       pg_size_pretty(pg_relation_size(c.oid))                 AS rows_main,
       pg_size_pretty(pg_table_size(c.oid) - pg_relation_size(c.oid)) AS toast_fsm_vm,
       pg_size_pretty(pg_total_relation_size(c.oid) - pg_table_size(c.oid)) AS indexes
FROM pg_class c
WHERE c.relkind = 'r'
ORDER BY pg_total_relation_size(c.oid) DESC
LIMIT 10;

The middle column is mostly TOAST: the free space map and visibility map are tiny next to it. If that column grew, big values grew. If the first grew faster than the row count, rows got wider or pages hold dead versions (part 3 of the series).

"A table doubled in size but the row count didn't. How do you investigate?" A strong answer splits the size first: main fork, TOAST and indexes, using the functions above. Then it samples pg_column_size on the widest columns, checks for dead row versions, and only then proposes a fix. Guessing "add an index" or "vacuum it" before measuring is the weak answer.

Split every size question into main fork, TOAST and indexes before you guess at a cause.

pg_table_size('events') grew by 150 GB, but pg_relation_size('events') grew by only 2 GB. What grew?

  1. Mostly the TOAST table: large values, not rows
  2. The indexes on events
  3. The number of rows

pg_table_size is main fork plus TOAST plus the two small maps. The main fork barely grew, and the maps are tiny, so the growth is in TOAST.

Column order: free space savings with one migration

Last part: how to measure a table. Still unsolved: how do you make rows smaller without dropping data?

The payments table from part 1 has columns (paid boolean, user_id bigint, refunded boolean, amount_paise bigint, gift boolean, created_at timestamptz). It will hold 120 million rows.

The cause is alignment padding. Each type has an alignment: c needs none, s is 2 bytes and i is 4 bytes on most machines, and d is 8 bytes on many machines; padding is inserted before a value so it starts on its boundary. bigint and timestamptz take 8 bytes, integer and date take 4, smallint takes 2 and boolean takes 1.

Each boolean followed by a bigint wastes 7 bytes. Put the 8-byte columns first and the booleans last, and the padding disappears. The estimator below applies the rules from parts 2 to 4; its tests pin every number on this page.

Results: the original order is a 72-byte row and 107 rows per page. The packed order is 51 bytes and 136 rows per page. The packed table needs about a fifth fewer pages. When PostgreSQL adds a row to a page, it reserves the row's length rounded up to MAXALIGN. That is why the estimator rounds 51 up to 56 before adding the 4-byte line pointer.

GitLab's development guidelines require new tables to order columns by size, largest first, with variable-length types at the end. Their example: reordering the events table cut the fixed part of each row from 48 to 40 bytes, which they estimate saves at least 610 MB across 80 million rows.

"Would you reorder columns on an existing 2 TB table?" Changing the order of an existing table means creating a new table in the new order and copying the data into it. A strong answer weighs a one-off rewrite of 2 TB against a saving of maybe 10 to 25%, and usually says: bake the rule into new-table reviews, and reorder existing tables only when you are rewriting them anyway (a partition migration, a big schema change).

Order columns by alignment, 8-byte types first and variable-length types last, and the padding goes away.

Which order wastes the least space for (a smallint, b bigint, c integer, d boolean)?

  1. a, b, c, d
  2. d, b, c, a
  3. b, c, a, d
  4. b, c, d, a

bigint at 24 to 32, integer to 36, smallint to 38, boolean to 39: no padding at all. Descending alignment always packs tightest.

A teammate asks why the order of columns in CREATE TABLE changes the table size. Explain it, and say how you would prove it on a real database.

Each fixed-size type must start at a multiple of its alignment: 8 bytes for bigint and timestamptz, 4 for integer. If a 1-byte boolean sits in front of a bigint, PostgreSQL pads 7 bytes so the bigint starts on an 8-byte boundary. Putting the widest-aligned columns first and variable-length ones last removes most padding. To prove it, create both orders, load the same rows, and compare pg_column_size of a row and pg_relation_size of each table.

The TOAST settings worth knowing in production

Last part: column order removes padding. Still unsolved: what can you tune for the large values?

A document service stores 30 kB JSON blobs and reads a slice of a 5 MB log text column. CPU is high on compression, and slice reads are slow.

The four storage strategies are PLAIN (no compression, no out-of-line), EXTENDED (both; the default for most TOAST-able types), EXTERNAL (out-of-line, not compressed) and MAIN (compressed, out-of-line only as a last resort). EXTERNAL makes substring operations on large text and bytea columns faster, at the cost of more storage, because only the needed part of an uncompressed out-of-line value is fetched.

The supported compression methods are pglz and lz4; lz4 is available only if PostgreSQL was built with --with-lz4. In PostgreSQL 18, default_toast_compression defaults to pglz.

-- slices of a huge log column: skip compression
ALTER TABLE jobs ALTER COLUMN log SET STORAGE EXTERNAL;
-- faster compression for JSON blobs
ALTER TABLE docs ALTER COLUMN body SET COMPRESSION lz4;
-- check what existing values actually use
SELECT pg_column_compression(body), count(*) FROM docs GROUP BY 1;

Neither command touches existing data. ALTER TABLE ... SET STORAGE doesn't change existing rows; it only sets the strategy for future updates. SET COMPRESSION doesn't rewrite the table, so existing values may stay compressed with the old method. Teams switch to lz4, see no change in CPU, and conclude lz4 doesn't help. Check with pg_column_compression first.

PostgreSQL 19, not yet released at the time of writing, changes the default TOAST compression method from pglz to lz4. Code that relies on pglz being the default should set it explicitly.

toast_tuple_target defaults to 2040 bytes on 8 kB pages, can be set between 128 and 8160 bytes, applies only to new rows, and cannot be set on TOAST tables. The docs note that the default is often close to optimal and that changing it can hurt in some cases. Leave it alone unless you measured a reason.

"Your service reads the first 1 kB of 5 MB text values. What would you change?" Strong answer: EXTERNAL storage on that column, because slices of uncompressed out-of-line values fetch only the needed chunks; accept the extra disk; note that it applies to new writes only, so plan a backfill. Better still, question whether the 5 MB value belongs in PostgreSQL at all (part 11).

Choose storage and compression per column, and remember both settings only affect values written afterwards.

You ran SET COMPRESSION lz4 on a 500 GB table yesterday. pg_column_compression shows 99% pglz today. What happened?

  1. lz4 isn't compiled in, so PostgreSQL silently fell back
  2. Nothing is wrong: the setting only applies to values written after it; existing values keep pglz
  3. The background recompression job hasn't reached those rows yet

SET COMPRESSION doesn't rewrite the table. Only new or changed values use lz4. A full rewrite, or a dump and restore, converts the rest.

What breaks first at 10 times the data

Last part: per-column TOAST settings. Still unsolved: what goes wrong as the table grows 10 times?

The payments table goes from 120 million to 1.2 billion rows. The server's cache stays at 80 GB. P99 latency on "recent payments for a user" triples.

First to break is the cache. Rows per page fixes how many rows 80 GB of cache can hold. At 107 rows per page, 1.2 billion rows need about 11.2 million pages, or 92 GB. At 136 rows per page they need about 8.8 million pages, or 72 GB. The padded table falls out of cache first, and queries start reading from disk. Wider rows mean the same failure arrives sooner.

Next are the hard limits:

  1. A single relation can hold at most 32 TB with the default 8 kB block size. Partition long before that.
  2. A table can have at most 1,600 columns, and fewer in practice because a row must fit on one 8 kB page: 1,600 integer columns fit, 1,600 bigint columns don't.
  3. The source defines the most rows a heap page can hold, MaxHeapTuplesPerPage, as the space after the page header divided by the smallest aligned row header plus one line pointer. With 8 kB pages that is 8168 ÷ 28 = 291 rows, however narrow they are.

How you see it coming: track pg_relation_size and pg_table_size per table daily, divide by row count, and alert when bytes per row move. Then compare the table's hot part with the cache size.

"What happens to this table at 10 times the rows?" A senior answer does the arithmetic: bytes per row, rows per page, pages versus cache. It names the first thing to break (the working set falls out of cache), the signal (cache hit ratio and disk reads rising), and the fix (narrower rows, splitting cold columns, partitioning by time).

At 10 times the rows, the first failure is usually the working set outgrowing the cache, and wider rows make it come sooner.

You add a 200-byte metadata text column to the 72-byte payments row. Predict what happens to rows per page and to the cache-fit problem.

The row grows to 276 bytes, which is still under the 2 kB TOAST threshold, so it all stays inline. Rows per page drop from 107 to 28. The same cache now holds under a third of the rows it did. Moving rarely-read columns out of the hot table is the fix (part 11).

Explain to an interviewer how row width turns into latency at 10 times the data, and how you'd catch it before users do.

PostgreSQL caches whole 8 kB pages. Bytes per row decides rows per page, and so how many rows fit in the cache. When the frequently-read part of a table outgrows the cache, queries go to disk and latency jumps. Wider or padded rows get there sooner. I would track size per table and bytes per row over time, watch the cache hit ratio, and fix with narrower rows, a hot/cold split, or time partitioning. Hard limits such as 32 TB per relation come much later.

How TOAST quietly multiplies your writes

Last part: row width decides when the cache runs out. Still unsolved: what goes wrong with the large values themselves?

A profiles table keeps a 30 kB JSONB document per user and stores a last_seen timestamp inside it. It is updated on every login, 2 million times a day. The TOAST table grows by tens of GB a day.

The rule that saves you: An UPDATE that doesn't change any out-of-line values incurs no TOAST cost. The rule that bites: When a changed value is TOASTed again, PostgreSQL normally picks a new unused OID for it and writes its chunks as new rows. TOAST stores whole values, not edits. Change one key and all 30 kB is written again.

  1. User logs in; jsonb_set(doc, '{last_seen}', ...) produces a new 30 kB value.
  2. It is compressed and chunked into the TOAST table under a new chunk_id.
  3. The previous version's chunks are no longer used; how that space is cleaned up is part 3 of this series. Meanwhile, 2 million logins a day means tens of GB of new TOAST writes a day.

The fix is design, not tuning: move the fast-changing field into its own column (last_seen timestamptz). Updating a plain column leaves the TOASTed document untouched, so it costs one small new row version instead of 30 kB.

A second limit hides in TOAST. Each table can hold at most 2^32 out-of-line values because each is identified by a 32-bit OID; as the OID space fills up, finding a free one gets slow, slowing INSERT and UPDATE. The docs suggest partitioning as a workaround and say this usually matters only for tables with many terabytes of data. Each partition has its own TOAST table, so each gets its own OID space.

How you detect both: TOAST size growing much faster than row count (part 5's query), and write-ahead log volume rising with no rise in rows.

"Why not store the whole user profile as one JSONB column?" A strong answer: fine for data read and written as a whole; bad for fields updated independently and often, because each update rewrites the whole TOASTed value. Keep hot fields and anything you filter or join on as real columns; keep the rarely-changed rest in JSONB.

Changing any part of a TOASTed value rewrites all of it, so keep frequently updated fields out of big documents.

The profiles table has (id, login_count int, doc jsonb 30 kB). Which update writes new TOAST chunks?

  1. UPDATE profiles SET doc = jsonb_set(doc, '{theme}', '"dark"')
  2. UPDATE profiles SET login_count = login_count + 1
  3. SELECT doc FROM profiles WHERE id = 7

Changing any key produces a new document value, which is TOASTed again under a new chunk_id. Updating another column keeps the existing pointer.

Three storage assumptions that break real code

Last part: big-document updates rewrite the whole value. Still unsolved: which everyday assumptions about storage are wrong?

A deduplication script uses ctid as a row id across two queries a minute apart and deletes the wrong 40 rows.

  1. ctid is not an id. An UPDATE adds a new version of the row to the table rather than changing it in place. Each row version's header has a t_ctid field: the ctid of this version or of a newer one. The new version has a new ctid, and vacuum can reuse the old line pointer for another row. Use ctid only within one statement; use the primary key everywhere else.
  2. SELECT * is not free. Wide TOASTed values are only fetched, if selected at all, when the result is sent to the client; so the main table stays small and more rows fit in the buffer cache. Selecting a TOASTed column you don't use makes PostgreSQL read and decompress every chunk for every row.
  3. The file name is not the table OID. TRUNCATE, REINDEX, CLUSTER and some forms of ALTER TABLE can change the filenode while keeping the table's OID. pg_relation_filepath() shows the path of a relation's first main-fork segment, relative to the data directory. Use it instead of assuming.

One more: Dropped columns still count toward the 1,600-column limit, and their slots still take space in the null bitmap. A table that adds and drops columns for years can hit the column limit with 200 visible columns.

An ORM that loads whole rows by default turns point 2 into a production problem: a list page showing 50 titles pulls 50 full documents. Select the columns you render.

ctid changes on update, unused TOASTed columns still cost reads, and file names don't follow table OIDs.

A job reads rows by ctid, sleeps, then deletes by those ctids. Meanwhile other sessions update some of those rows. What can happen?

  1. Nothing: ctids never change for a row
  2. The delete fails with an error for every updated row
  3. Updated rows are missed, and a reused slot can point at a different row

Each update writes a new row version with a new ctid. The old ctid points at a dead version, which vacuum can remove, freeing the slot for an unrelated row.

Choosing a table layout for wide or changing data

Last part: storage assumptions that break code. Still unsolved: how do you design the table in the first place?

You are designing a merchants table: 12 fixed fields read on every payment, 40 rarely-read KYC fields, a 20 kB settings document, and a last_payout_at updated every hour for each of 5 million merchants.

One more mechanism helps you decide. An UPDATE can skip creating new index entries (a heap-only tuple, HOT) only if it changes no indexed columns and the new version fits on the same page. fillfactor is a percentage between 10 and 100, 100 by default; lower values leave room on each page so an UPDATE can put the new row version on the same page. The pg_stat_all_tables view lets you monitor how often updates are HOT and how often they are not. Narrow rows make HOT updates more likely, because more new versions fit in the space left on each page.

For the merchants table: a narrow hot table with the 12 fields and last_payout_at, ordered by alignment; a 1:1 cold table with KYC fields and the settings document. The hourly update touches a small row, doesn't rewrite 20 kB, and has a good chance of being HOT.

"When is a JSONB column the wrong choice?" When a field inside it is updated often, when you filter or join on it, or when you need constraints on it. Say the cost: every update of the document writes the whole value again.

Keep hot, frequently updated fields in narrow, aligned rows, and push large or rarely-read data to a cold table, a document column, or object storage.

An orders table has a 15 kB line_items JSONB and a status updated 6 times per order. Which change cuts write volume the most?

  1. Switch line_items to lz4 compression
  2. Keep status as its own column and never write it inside line_items
  3. Set fillfactor to 70 on orders

If status lives in its own column, its 6 updates leave the TOASTed line_items untouched. If status is inside the JSON, each update rewrites 15 kB.

Interview drill: storage questions at the senior bar

Last part: choosing a layout. Still unsolved: can you defend these choices under questioning?

In a design round at a payments company, the interviewer stops you on the data model and asks three storage questions in a row. Commit to an answer before opening each reference.

1. "You store a 5 kB risk-score explanation JSON on every payment row. Reads are mostly lists of recent payments. What do you expect, and would you change it?"

At 5 kB the row is over the 2 kB threshold, so the document is compressed and, if still large, moved to TOAST. The main rows stay narrow, so list queries that don't select it are fine. The risks are ORMs selecting it anyway, and any update to the explanation rewriting it whole. I would keep it only if it is written once; if it is recomputed often, it goes to a separate table keyed by payment id. Trade-off: one extra lookup when someone opens the details view.

2. "Your ledger table will hit 5 billion rows in two years. What would you do with its column layout now, and why?"

Order the fixed columns by alignment, 8-byte first, variable-length last, and keep rarely-read fields out of the hot table. Estimate bytes per row and rows per page, then pages times 8 kB, and compare the recent working set with memory. Partition by time so old data leaves the hot set and each partition has its own TOAST OID space. Trade-off: cross-partition queries and extra operational work for partition management.

3. "Disk use doubled in a month, but the row count grew 10%. Walk me through the investigation."

Split each large table into main fork, TOAST and indexes. If TOAST grew, look for big documents being updated often. If the main fork grew faster than rows, check for wider rows or dead row versions not being cleaned up. If indexes grew, check for new or bloated indexes. Fix the cause, then reclaim space. Trade-off: reclaiming space usually needs a table rewrite with locks or an online tool, so it is scheduled, not done in panic.

Staff-level versions of these questions add rolling a column-order or hot/cold split migration across many teams' tables, and setting organisation-wide schema review rules. This page stops at the single-service level.

Senior storage answers do the arithmetic, name the first failure and its signal, and state what the fix costs.

Pick one of the three prompts and answer it out loud as you would in the interview, in under two minutes.

A strong answer starts from the numbers: bytes per row, rows per page, pages against memory. It says which fields are hot and keeps them in narrow, aligned rows, with large or rarely-read data in TOAST, a side table or object storage. It names what breaks first as data grows, how you would see it in metrics, and what the fix costs in joins, migrations or locking.
