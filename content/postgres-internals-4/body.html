Why "just add an index" is only half an answer

A payments table holds 200 million rows. The merchant dashboard runs WHERE merchant_id = 42 AND status = 'pending' ORDER BY created_at DESC LIMIT 50 and takes several seconds, because it reads the whole table. Someone adds an index and it returns almost instantly. Six months later the table has 11 indexes and every payment insert is slower.

Think of the index at the back of a textbook. It is a sorted list of terms, each with page numbers. You find the term fast, then turn to those pages. The index is printed separately from the chapters, and every edit to the book means updating it too.

  1. The term list maps to the indexed column values. The page numbers map to ctids, the row addresses from part 1 of this series. All PostgreSQL indexes are secondary indexes: each is stored separately from the table's main data area, which PostgreSQL calls the heap.
  2. An index pays for itself three ways: finding a few rows without reading the table, handing rows back already sorted, and enforcing uniqueness. With ORDER BY plus LIMIT n, an index that matches the sort order can return the first n rows directly, while a sort would have to process all the data.
  3. The price: PostgreSQL keeps every index synchronized with the table, which adds overhead to data changes; indexes can also prevent heap-only tuple (HOT) updates, so indexes that are seldom or never used should be removed.
  4. PostgreSQL ships B-tree, Hash, GiST, SP-GiST, GIN and BRIN index types, plus the bloom extension, and CREATE INDEX builds a B-tree unless USING names another type.

Each index type answers a different question shape. "Equal to, or between these values?" is a B-tree question. "Which documents contain this key?" is an inverted-index question. "Which bookings overlap this hour?" and "which part of a 5-terabyte log could hold yesterday?" are different again. This page goes through how the standard B-tree works on disk, the ways to shape an index, the other five types, and what breaks when you have too many.

An index is a separate structure of column values pointing at row addresses; every query it speeds up is paid for by every write to the table.

The payments table goes from 3 indexes to 11. Reads that use the new indexes got faster. What happened to a plain INSERT INTO payments?

  1. Nothing: indexes only matter for reads
  2. It now writes the row plus an entry in each of the 11 indexes
  3. It writes only to the indexes whose columns are used in WHERE clauses

Every index is a separate structure that PostgreSQL keeps in step with the table, so each new row needs one new entry per index.

What a B-tree looks like on disk

Last part: an index is a separate structure pointing at row addresses. Still unsolved: what is inside the standard one, and how does a lookup walk it?

An index on payments(merchant_id) covers 200 million rows. Finding merchant 42 reads only a handful of pages. Which pages, and why so few?

A B-tree is a library's catalogue cabinet: a sign on the wall says which cabinet, the cabinet's drawers are labelled with ranges, and the cards inside point at shelf locations.

  1. A B-tree index uses standard pages: one metapage at a fixed position at the start, then internal pages and leaf pages, and typically over 99 percent of the pages are leaves. The metapage is the sign on the wall. The metapage records the location of the root page, and each backend caches a copy so it doesn't read the metapage on every search.
  2. Internal pages hold entries pointing to the next level down; leaf pages hold entries pointing to table rows, and each level can be walked as a doubly-linked list of pages. A leaf page is the drawer of cards.
  3. B-tree entries are kept in ascending order with nulls last, and the table row's TID breaks ties between equal keys. TID is the general name for the ctid from part 1.
  4. When a leaf page can't fit a new entry, it splits: some entries move to a new page and the parent gets a pointer to it, which can split the parent in turn; when the root splits, the tree gains a level.

Repeated keys used to cost one full entry each. With deduplication, a group of entries with the same key is stored as the key once followed by a sorted array of TIDs, and it is on by default. Deduplication arrived in PostgreSQL 13; an index carried over by pg_upgrade needs a REINDEX to use it. Deduplication is never used for indexes with INCLUDE columns, nor for numeric, jsonb, float4 or float8 keys.

A lookup reads the cached root location, walks internal pages down to one leaf, and follows each matching entry's ctid to a heap page.

Put the pages a lookup of merchant_id = 42 touches in order.

  1. The root location, from the backend's cached copy of the metapage
  2. The root page
  3. Any internal pages on the way down
  4. The leaf page holding the entries for 42
  5. The heap pages named by those entries' ctids

The tree is walked top-down to a single leaf; only then are the rows themselves fetched from the heap, one heap page per distinct ctid page.

After an upgrade from PostgreSQL 12 by dump and restore, a B-tree on payments(status) (4 distinct values, 200 million rows) shrinks a lot. A B-tree on payments(amount numeric) does not. Why?

  1. Deduplication only applies to unique indexes
  2. The amount index wasn't rebuilt
  3. Repeated status values are stored once with a list of TIDs, but deduplication is never used for numeric keys

Deduplication stores a repeated key once per group, followed by a list of TIDs, which shrinks an index with 4 distinct values a lot. numeric keys are excluded, so the amount index keeps one full entry per row.

Why entries point at row addresses, and what an UPDATE costs

Last part: leaf entries hold a key and a ctid. Still unsolved: what happens to every index when a row changes?

Payments move from pending to captured 3,000 times a second. status is indexed, and the table has 9 indexes.

Pointing at a physical address makes a read one hop: entry, then heap page. In an ordinary index scan every row needs a fetch from the index and from the heap, and the matching rows can be anywhere in the heap, so that part is mostly random reads.

The cost is on writes. Part 2 of this series showed that an UPDATE writes a new row version, usually at a new ctid. Part 3 showed the escape hatch: an update can be HOT only when it changes no column used by the table's indexes (summarizing indexes such as BRIN don't count) and the new version fits on the same page. Otherwise:

  1. An UPDATE that can't use HOT needs a new entry in every index on the table, including indexes whose columns didn't change.
  2. The old entries stay until cleaned up. B-trees remove such obsolete version entries in bottom-up deletion passes, triggered when a leaf page is about to split from version churn in an index the UPDATEs don't logically modify; before PostgreSQL 14 only simpler, opportunistic deletion existed.
  3. So for the problem above: every status change is non-HOT, and each one writes a row version plus 9 index entries, about 30,000 writes a second.

Other databases chose differently. In MySQL's InnoDB, rows live inside the primary key index, and each secondary index record stores the primary key columns, which a lookup then uses to search the primary key index. That means two tree walks per secondary lookup, but a row moving on disk doesn't change any secondary entry.

Uber's 2016 engineering post on leaving PostgreSQL (its analysis mainly based on PostgreSQL 9.2) described an update to one indexed column of a row with three indexes needing at least four physical writes: the new row version plus one entry per index. The fix inside PostgreSQL is fewer indexes and HOT-friendly updates, not a different database for every case.

Pointing at ctids makes index reads one hop, but any update that can't be HOT writes a new entry into every index on the table.

The team drops the index on status. No other index uses status in any way: not as a column, not in an expression, not in a partial-index WHERE clause. Predict what happens to the 3,000 status updates a second.

They can now be HOT, as long as the new version fits on the same page. A HOT update writes the new row version and no B-tree entries (only BRIN summaries, if any, still update), so about 27,000 index writes a second disappear. If pages are full, updates still go non-HOT; that is part 3's fillfactor lesson.

Index-only scans: when the table is skipped, and when it isn't

Last part: entries point at ctids, so most index reads also visit the heap. Still unsolved: can a query skip the heap entirely?

SELECT created_at FROM payments WHERE merchant_id = 42 uses an index on (merchant_id, created_at). The plan says Index Only Scan, yet it reads 9,800 heap pages for 10,000 rows.

  1. An index-only scan is possible only when the index type supports it and the query uses only columns stored in the index. B-tree always supports it, GiST and SP-GiST do for some operator classes, and GIN can't, because its entries usually hold only part of each value.
  2. Index entries carry no visibility information, so for each entry the scan checks the heap page's all-visible bit in the visibility map, and visits the heap only when that bit is not set.
  3. The visibility map is four orders of magnitude smaller than the heap and usually stays cached, so an index-only scan pays off only when a large share of the table's pages are marked all-visible.
  4. EXPLAIN ANALYZE shows the heap visits of an Index Only Scan node on a Heap Fetches line. Part 3 explained who sets the all-visible bit: VACUUM.

The problem's table is busy: recent pages change all day, so their bits are clear and the scan visits them. More frequent vacuuming of that table, not a new index, is the fix.

To make more queries index-only, add the columns they return. INCLUDE adds payload columns that can't be searched on but are stored in the index, so a query needing them can still run as an index-only scan. That is a covering index.

CREATE INDEX payments_merchant_created
  ON payments (merchant_id, created_at)
  INCLUDE (amount, status);

INCLUDE columns sit only in leaf entries, not in the upper levels used to walk the tree, and only B-tree, GiST and SP-GiST support INCLUDE. Payload columns make the index bigger and potentially slower to search, and an entry that exceeds the index type's maximum size makes the insert fail, so add wide columns sparingly.

An index-only scan skips the heap only for pages the visibility map marks all-visible; on recently changed pages it is an ordinary index scan.

An append-only events table: an Index Only Scan on yesterday's rows shows Heap Fetches close to the row count. What helps most?

  1. Getting VACUUM to visit the new pages sooner, so their all-visible bits get set
  2. Adding the selected columns with INCLUDE
  3. Switching to a GIN index

The heap visits come from pages whose all-visible bit isn't set yet. On PostgreSQL 18, visibility map bits are set only by VACUUM or COPY ... FREEZE, and cleared by any change to the page. Making autovacuum reach the table sooner is the fix.

Explain to a teammate why adding an index can make reads faster and writes slower, and why an "Index Only Scan" can still read the table.

A B-tree entry holds the key and the row's ctid, so a lookup walks a few index pages and then reads the heap page the ctid names. Because entries point at physical addresses, any update that can't be HOT gives the row a new ctid and needs a new entry in every index. Index entries carry no visibility information, so an index-only scan checks the visibility map for each heap page and still reads pages that aren't marked all-visible.

Column order in a multicolumn index

Last part: an index-only scan needs every column in the index. Still unsolved: once an index has several columns, which queries can use it?

An index on payments(merchant_id, status). WHERE merchant_id = 2 is fast. WHERE status = 'pending' across all 50,000 merchants is not.

A phone book is sorted by surname, then first name. Finding every "Sharma" is one slice of the book. Finding every "Priya" means reading every page, because Priyas sit inside every surname.

  1. Only B-tree, GiST, GIN and BRIN support multicolumn indexes, with up to 32 columns including INCLUDE columns.
  2. In a multicolumn B-tree, equality conditions on the leading columns, plus a range condition on the first column without an equality condition, limit how much of the index is scanned; conditions on later columns are checked inside the index, saving heap visits, but may not shrink the scan. This is the leftmost-prefix rule.
  3. Skip scan lets a B-tree on (x, y) serve WHERE y = 7700 by repeating the search for each value of x; the planner usually chooses it only when x has few distinct values, because with many the whole index must be read, and in most cases a sequential scan is then preferred. Skip scan for B-tree indexes is new in PostgreSQL 18.
  4. EXPLAIN ANALYZE prints an Index Searches line on index scan nodes with the total number of index searches, which is how skip scan shows up in a plan.

The model below sorts entries the same way. Its tests show the slice sizes and the cost of skip scan with many leading values.

Rule of thumb: equality columns first, then the one range or sort column. The docs warn that indexes with more than three columns are unlikely to help unless the table's usage is extremely stylized. PostgreSQL can also combine separate indexes by building an in-memory bitmap of matching rows from each and ANDing or ORing them, though this loses index order, so an ORDER BY then needs a sort.

"Design the index for WHERE merchant_id = ? AND created_at > ? ORDER BY created_at DESC LIMIT 50." A strong answer puts the equality column first and the range-and-sort column second: (merchant_id, created_at). It explains that the range then narrows one slice, the order comes free, and LIMIT stops after 50 entries. It also says why (created_at, merchant_id) is worse: the range on the first column makes the scan read every merchant's rows in that window.

A multicolumn B-tree is a sort by its first column, then the next; conditions narrow the scan only from the left, and skip scan helps only when the skipped column has few values.

Index on (merchant_id, created_at, status). Query: merchant_id = 42 AND status = 'failed' AND created_at > now() - interval '7 days'. Which conditions limit the part of the index that is scanned?

  1. All three, because they are all in the WHERE clause
  2. merchant_id and created_at; status is checked on the entries read and doesn't necessarily narrow the scan
  3. Only merchant_id

Equality on the leading column, then a range on the first column without equality, bound the scan. status comes after the range column, so it filters entries inside that slice; with nearly unique created_at values, skip scan can't use it to jump ahead either.

Partial, expression and unique indexes

Last part: column order decides which queries an index serves. Still unsolved: what if you only care about some rows, or about a computed value?

Workers poll status = 'pending', which is 1 in 200 of the 200 million payments. A full index on status holds 200 million entries to find 1 million. Login looks up lower(email), and a plain index on email can't help.

  1. A partial index holds entries only for rows that satisfy its WHERE predicate, which makes it smaller and means many updates don't need to touch it.
  2. The planner uses a partial index only if it can prove, at planning time, that the query's WHERE condition implies the index predicate; beyond simple inequalities, the predicate must match part of the query's WHERE condition exactly. Because the match happens at planning time, a parameterized clause doesn't work with a partial index: x < $1 can't imply x < 2 for every value of the parameter.
  3. An expression index such as one on lower(email) serves queries that write the same expression; the expression is computed at each insert and non-HOT update, not during the search. Functions used in an index expression or partial-index predicate must be marked immutable.
  4. Only B-tree indexes can be unique; by default nulls count as distinct, so a unique column can hold many nulls, and NULLS NOT DISTINCT makes them equal. NULLS NOT DISTINCT arrived in PostgreSQL 15.
-- only the rows workers poll
CREATE INDEX payments_pending ON payments (created_at)
  WHERE status = 'pending';
-- case-insensitive lookup that also rejects duplicates
CREATE UNIQUE INDEX merchants_email_lower ON merchants (lower(email));
-- at most one open refund per payment
CREATE UNIQUE INDEX refunds_one_open ON refunds (payment_id)
  WHERE state = 'open';
-- one row per (merchant, external_ref), even when external_ref is NULL
CREATE UNIQUE INDEX payments_ext_ref ON payments (merchant_id, external_ref)
  NULLS NOT DISTINCT;

A unique expression index can enforce rules a plain unique constraint can't, such as rejecting values that differ only in case. A unique partial index enforces uniqueness only among the rows that satisfy its predicate. A primary key or unique constraint already creates a unique index, so a manual index on the same columns only duplicates it.

A new expression index has no statistics until ANALYZE runs on the table, by hand or by autovacuum. Until then the planner guesses how selective lower(email) is, so run ANALYZE right after creating one.

Many partial indexes split by a category value are not a substitute for partitioning; one index with the category column first is almost always better, because the planner must test each partial index separately.

A partial index shrinks the index to the rows you query, an expression index stores a computed value, and both are used only when the query repeats the predicate or expression in a form the planner can match.

The app runs SELECT ... WHERE status = $1 AND created_at < now() - interval '5 minutes' as a prepared statement, with $1 = 'pending'. After a few runs the driver switches to a generic plan. Does it keep using payments_pending?

Not with the generic plan. Partial-index matching happens at planning time, and a plan built for any value of $1 can't prove status = 'pending'. It falls back to another index or a sequential scan. Write the literal status = 'pending' into the query text for this one.

GIN and operator classes: searching inside values

Last part: partial and expression indexes. Still unsolved: a B-tree compares whole values, so how do you find rows by something inside a value?

Each payment carries a metadata jsonb document from one of 40 integrations. Support staff search for {"order_ref": "A-991"} inside it, and the query reads all 200 million rows.

  1. A GIN index stores each key once with a list of the rows that contain it, and one row can appear under many keys, which suits arrays, jsonb documents and text search. GIN means generalized inverted index.
  2. Which keys it extracts, and which operators it serves, is decided by an operator class. An operator class identifies the operators an index can use for a column, and the default class for the column's type is usually enough.
  3. jsonb has two GIN operator classes: the default jsonb_ops supports the key-exists operators ?, ?| and ?& as well as @>, @? and @@, while jsonb_path_ops supports only @>, @? and @@.
  4. A jsonb_path_ops index is usually much smaller than a jsonb_ops index on the same data and searches more precisely, because each of its entries is a hash of a value together with the keys leading to it.
  5. GIN is the preferred index type for full-text search; GiST also works there but is lossy, so false matches have to be rechecked against the table rows.
-- containment searches anywhere in the document
CREATE INDEX payments_meta ON payments USING GIN (metadata jsonb_path_ops);
SELECT id FROM payments WHERE metadata @> '{"order_ref": "A-991"}';
-- only one key is ever searched: index just that key
CREATE INDEX payments_order_ref ON payments ((metadata ->> 'order_ref'));
-- prefix search on a text column when the database locale isn't C
CREATE INDEX merchants_name_prefix ON merchants (name text_pattern_ops);
SELECT id FROM merchants WHERE name LIKE 'Raz%';

An expression index on the part of the document you search is likely smaller and faster than a GIN index on the whole column, but serves only queries on that part. The second index above is a plain B-tree on one extracted value: the ->> operator extracts one field of a JSON object as text. That is the cheapest option when one key carries most searches.

text_pattern_ops compares strings character by character instead of by the locale's collation rules, so a B-tree with it can serve LIKE 'abc%' when the database doesn't use the C locale; ordinary <, <=, > and >= comparisons then need a second index with the default class. A B-tree serves LIKE only when the pattern is a constant anchored at the start, such as LIKE 'foo%', never LIKE '%bar'.

"Support wants to search any field in a payment's JSON metadata. What index?" A strong answer first asks which operators the queries use. Containment only: jsonb_path_ops. Key-exists with ?: jsonb_ops. One or two hot keys: B-tree expression indexes. Then it names GIN's write cost.

GIN indexes the pieces inside a value, and the operator class decides which pieces and which operators; pick the class from the operators your queries actually use.

The table has GIN (metadata jsonb_path_ops). Which query can't use it?

  1. metadata @> '{"gateway": "upi"}'
  2. metadata @? '$.items[*] ? (@.sku == "X1")'
  3. metadata ? 'refund_id'

The key-exists operator ? is supported only by the default jsonb_ops class. jsonb_path_ops hashes values with their key paths, so it can't answer "does this key exist".

Overlaps, huge logs and pure equality: GiST, SP-GiST, BRIN and Hash

Last part: GIN for values with many pieces. Still unsolved: values that overlap rather than equal, tables too big for any tree, and lookups that only ever ask "equal?".

A booking service must never double-book a room. An event log grows by 2 billion rows a month and is queried by time. A token table is only ever looked up by exact match.

  1. GiST. GiST is a balanced, tree-structured framework in which B-trees, R-trees and many other indexing schemes can be implemented. GiST and SP-GiST indexes on range columns speed up operators such as && (overlaps), @> and <@. With the btree_gist extension, EXCLUDE USING GIST (room WITH =, during WITH &&) rejects a booking whose time range overlaps another booking for the same room. PostgreSQL 18 adds PRIMARY KEY and UNIQUE constraints with WITHOUT OVERLAPS, which are enforced like such a GiST exclusion constraint.
  2. SP-GiST. SP-GiST supports non-balanced trees that repeatedly split the search space into parts that need not be of equal size, such as quad-trees, k-d trees and radix trees; its built-in text_ops class also supports the ^@ starts-with operator.
  3. BRIN. A BRIN index stores a summary, such as the minimum and maximum value, for each block range of physically adjacent table pages, so it suits columns whose values follow the table's physical order. The pages_per_range storage parameter sets the size of a block range, 128 pages unless you change it. BRIN is lossy: every row in a matching range is returned and rechecked, but the index is so small that reading it adds little to a scan.
  4. Hash. A hash index stores only a 4-byte hash of each value and may be much smaller than a B-tree on long values such as URLs; it supports only the = operator, on a single column, without uniqueness.

The BRIN model below shows why physical order is everything. On an append-only log one hour falls in one range out of 100; shuffle the same rows and every range matches.

Smaller block ranges make a BRIN index bigger but its summaries more precise, so more pages can be skipped. Hash indexes suit unique or nearly unique data: many rows in one hash bucket create overflow pages that every lookup in that bucket must read.

PostgreSQL 10 added write-ahead logging to hash indexes, making them crash-safe and replicated, and removed the old warning against using them. Advice to avoid them predates that. They are safe now; they are still equality-only.

GiST answers overlap and nearness questions and powers exclusion constraints, BRIN trades precision for a tiny index on physically ordered data, and Hash is a smaller equality-only index.

A 5-terabyte events table is append-only and queried by created_at ranges. A B-tree on created_at would be about 150 gigabytes. Why does BRIN fit, and when would it stop fitting?

  1. Rows arrive in time order, so each block range covers a narrow time window; it stops fitting if rows land out of time order, for example from backfills or updates moving rows
  2. BRIN fits because queries are equality checks; it stops fitting for range queries
  3. BRIN fits only until the table is too big, because it is lossy

BRIN's min and max per range are narrow only when values follow physical order. Out-of-order rows widen every range's min-to-max span until most ranges match every query.

You are reviewing a migration that adds six indexes. Explain the questions you'd ask about each one before approving it.

For a multicolumn B-tree: are equality columns first and the range or sort column last, and is there already an index with the same leading columns? For partial and expression indexes: do the queries repeat the same predicate or expression, as literals rather than parameters? For GIN: which operators do the queries use, so the right operator class is chosen? For BRIN: does the column follow the table's physical order? For Hash: is it really equality-only on nearly unique values?

Adding an index to a live table without an outage

Last part: what each index type answers. Still unsolved: creating or rebuilding one on a table that takes writes all day.

Building an index on the 200-million-row payments table takes most of an hour, and a plain CREATE INDEX makes every payment insert wait that long.

  1. A plain CREATE INDEX blocks inserts, updates and deletes on the table until the build finishes, but not reads. A plain CREATE INDEX takes a SHARE lock, while CREATE INDEX CONCURRENTLY and REINDEX CONCURRENTLY take SHARE UPDATE EXCLUSIVE, which doesn't conflict with the ROW EXCLUSIVE lock that writes take.
  2. CREATE INDEX CONCURRENTLY scans the table twice and waits for existing transactions that could modify or use the index, so it does more work and takes significantly longer. CREATE INDEX CONCURRENTLY can't run inside a transaction block, and only one concurrent index build can run on a table at a time.
  3. If it fails, for example on a deadlock or a uniqueness violation, it leaves an INVALID index that queries ignore but that still consumes update overhead; drop it and try again, or rebuild it with REINDEX INDEX CONCURRENTLY.
  4. Plain REINDEX blocks writes and also takes an ACCESS EXCLUSIVE lock on the index, which blocks nearly every query on the table, because the planner tries to lock every index of the table. REINDEX CONCURRENTLY builds a replacement with a _ccnew suffix and swaps it in; after a failure, drop an invalid _ccnew index and retry, or drop an invalid _ccold index because the rebuild itself succeeded.
-- outside any transaction block
CREATE INDEX CONCURRENTLY payments_merchant_created
  ON payments (merchant_id, created_at);
-- any index a failed concurrent build left behind
SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;

pg_index.indisvalid marks whether an index is valid for queries; a concurrent rebuild flips it to true for the new index and false for the old one. For a unique index built concurrently, the constraint is enforced against other transactions from the start of the second scan, and an index left invalid by a failure in that scan keeps enforcing it.

CREATE INDEX CONCURRENTLY doesn't support partitioned tables: build each partition's index concurrently, then create the parent index non-concurrently, which is then only a metadata change.

In PostgreSQL 14 before 14.4, CREATE INDEX CONCURRENTLY and REINDEX CONCURRENTLY could silently leave out index entries, so queries missed rows; the fix was to upgrade, then rebuild affected indexes, and pg_amcheck --heapallindexed detects the damage in B-trees.

"Add an index to a 2-terabyte table with no downtime." A strong answer uses CREATE INDEX CONCURRENTLY, ends long transactions first because the build waits for them, watches progress (each backend running CREATE INDEX reports its progress in the pg_stat_progress_create_index view), and checks indisvalid afterwards.

Use CONCURRENTLY on live tables, end long transactions first, and check for INVALID indexes afterwards.

CREATE UNIQUE INDEX CONCURRENTLY on payments(gateway_ref) fails halfway with a duplicate key error. The deploy moves on. What is the state an hour later?

  1. No index exists; the failure rolled it back
  2. An INVALID index remains: no query uses it, and depending on which phase failed, writes may still maintain it and it may still reject duplicates
  3. The index works for queries but isn't enforced

The failed build leaves an INVALID index behind. The docs say it still consumes update overhead, and if it failed in the second scan it keeps enforcing uniqueness. Find it with indisvalid and drop it.

Too many indexes at ten times the write rate

Last part: building indexes safely. Still unsolved: what does each index cost once it exists, and how do you find the ones not worth it?

A sale brings 10 times the usual traffic: 30,000 payment status changes a second on a table with 11 indexes. Commit latency triples, WAL volume and replica lag climb, and nothing in the queries changed.

  1. Each non-HOT update writes a row version plus one entry per index: 12 writes per status change, about 360,000 a second. Every index multiplies the write rate.
  2. HOT is the escape, but more columns block it than people expect. For non-summarizing indexes, columns used in an index's expressions, in a partial index's WHERE clause, or as INCLUDE columns also count as indexed for HOT, so changing them makes an update non-HOT. The covering index with INCLUDE (amount, status) from earlier, or a partial index WHERE status = 'pending', makes every status change non-HOT.
  3. Find the indexes that don't pay. The pg_stat_user_indexes view has one row per index, with relname, indexrelname, idx_scan (the number of index scans started) and last_idx_scan (the time of the last scan).
  4. Read the counters with care. Statistics counters survive a clean shutdown, but all of them are reset after an unclean shutdown, a crash, a start from a base backup, or point-in-time recovery. Cumulative statistics are collected in shared memory, and a physical replica keeps its own copy of them across clean restarts. So a primary's idx_scan of 0 says nothing about reads served by replicas.
SELECT indexrelname, idx_scan, last_idx_scan
FROM pg_stat_user_indexes
WHERE relname = 'payments'
ORDER BY idx_scan;

The audit below turns those rows into verdicts: never-scanned indexes, and indexes whose columns are the leading columns of a wider one. It skips unique indexes, which enforce rules even with zero scans.

Indexes also bloat. Part 3 showed how to measure a B-tree with pgstatindex and rebuild it with REINDEX CONCURRENTLY; the next part covers the types that bloat or slow down differently.

"Write throughput dropped after we added a few indexes. How do you investigate?" A strong answer checks the HOT ratio first (part 3's n_tup_hot_upd), then which new index columns the hot UPDATEs change, including INCLUDE and partial-index predicate columns. It lists unused and prefix-duplicate indexes from pg_stat_user_indexes, confirms on every replica and over a full business cycle, and drops them concurrently: a normal DROP INDEX takes an ACCESS EXCLUSIVE lock on the table, while DROP INDEX CONCURRENTLY waits for conflicting transactions instead of locking out reads and writes.

Every index multiplies writes for any update that can't be HOT; find the ones nobody scans on any server, and keep hot-updated columns out of indexes, INCLUDE lists and predicates.

Last week the primary crashed and was restarted. Today payments_old_report shows idx_scan = 0 on the primary. What do you do?

  1. Drop it now: zero scans means unused
  2. Never trust idx_scan; keep every index
  3. Wait until counters cover a full business cycle, check the replicas' own counters too, then drop it if still unused

A crash resets all counters, and each server counts only its own scans. A monthly report on a replica would be invisible on the primary.

GIN's pending list, and the upkeep each index type needs

Last part: the write cost every index adds. Still unsolved: GIN, Hash and BRIN each fail in their own way. What does each need?

Most updates to a table with a GIN index finish in a few milliseconds. Every few minutes one unlucky UPDATE takes several seconds and holds its row locks the whole time.

  1. Inserting one row can add many GIN entries, so GIN's fast update technique puts new entries in an unsorted pending list and moves them into the main index in bulk later. That list is the pending list.
  2. The pending list is flushed when the table is vacuumed or autoanalyzed, when gin_clean_pending_list is called, or when the list grows past gin_pending_list_limit; that last case happens inside the statement that crossed the limit, which makes that statement much slower than the rest.
  3. Searches must scan the pending list too, so a large list slows them significantly. gin_pending_list_limit is 4 megabytes unless changed, and each GIN index can override it as a storage parameter.
  4. Fixes, from the docs: if steady response time matters more than update speed, turn fastupdate off; otherwise avoid foreground flushes by raising the limit or making autovacuum more aggressive, knowing a foreground flush will then take even longer. Turning fastupdate off with ALTER INDEX doesn't flush entries already pending, so run VACUUM or gin_clean_pending_list afterwards.

GitLab's issue 336930 investigated multi-second merge request updates and pointed to pending-list cleanup of a trigram GIN index on the description column; manual cleanups in that investigation took between 465 and 3,155 milliseconds.

Two other types have their own upkeep:

  • Hash. A hash index never shrinks on its own: emptied overflow pages are reused but not returned to the operating system, the number of buckets never goes down, and only rebuilding it, for example with REINDEX, makes it smaller.
  • BRIN. New block ranges at the end of the table stay unsummarized until VACUUM runs, autosummarize (off unless enabled) queues them, or brin_summarize_new_values is called. A BRIN scan returns every page of an unsummarized range, as if it matched. On a busy log, the newest data, usually the most queried, is the part BRIN can't skip until summarization catches up.
-- steady latency over insert speed for the trigram index
ALTER INDEX merge_requests_description_trgm SET (fastupdate = off);
SELECT gin_clean_pending_list('merge_requests_description_trgm');
-- summarize each full block range soon after it fills
CREATE INDEX events_created_brin ON events USING brin (created_at)
  WITH (pages_per_range = 64, autosummarize = on);

autosummarize queues a summarization run for the previous block range whenever an insert is detected on the next one.

GIN's fast updates trade a steady write cost for occasional big flushes inside unlucky statements; Hash never shrinks without REINDEX, and BRIN can't skip ranges it hasn't summarized.

You raise gin_pending_list_limit on that GIN index from 4 to 64 megabytes and change nothing else. Predict p50 and p99.9 UPDATE latency a week later.

p50 stays about the same and foreground flushes become rarer, so fewer statements are hit. But a flush can now move up to 16 times as much data, so the statements that do hit one get even slower: the extreme tail and the maximum get worse, even if p99.9 happens to improve. The steady fix is fastupdate off, or more aggressive autovacuum on that table so flushes happen in the background.

The index the planner won't use

Last part: upkeep each index type needs. Still unsolved: the index exists, it's valid, and EXPLAIN still shows a sequential scan. Why?

An engineer adds an index for a slow query, deploys, and sees no change. The index has idx_scan = 0 a day later.

Go through the reasons in this order. The first group means the query can't use the index; the second means the planner thinks it shouldn't.

  1. The query doesn't match the index. No condition on the leading column; LIKE '%bar'; an expression written differently from the indexed one; a partial-index predicate passed as a parameter; ? against jsonb_path_ops; a locale that needs text_pattern_ops. An index supports one collation per column, so a comparison with a different COLLATE can't use it. And an INVALID index is never used.
  2. The query reads too much. A query for a value that covers more than a few percent of the table won't use an index anyway. For a query that reads a large fraction of the table, an explicit sort after a sequential read is likely faster than using an index, because it reads sequentially.
  3. The statistics are wrong or missing. Without ANALYZE, the planner uses default estimates that are almost certainly inaccurate, so examining index usage before running ANALYZE is a lost cause.
  4. The test data is too small. Very small test tables mislead: 100 rows probably fit in one page, and no plan beats reading one page sequentially.

To tell the groups apart: turn off enable_seqscan in a session to force another plan; if the index still isn't used, there is probably a more basic reason, such as the query condition not matching the index; if it is used, either the planner was right or its cost estimates are off, so time the query with and without the index, for example with EXPLAIN ANALYZE.

ANALYZE payments;
SET enable_seqscan = off;   -- this session only, for diagnosis
EXPLAIN ANALYZE SELECT id FROM payments WHERE merchant_id = 42;
RESET enable_seqscan;

Never leave enable_seqscan = off in a role or server setting to "fix" a plan. It hides the real cause, and it pushes every other query toward index plans, including the ones that read half the table.

"The planner ignores my index. What do you check?" A strong answer separates "can't" from "won't": first whether the query's form matches the index (leading column, expression, operator class, collation, partial predicate, validity), then selectivity and statistics with ANALYZE and an enable_seqscan test. It doesn't jump to hints or disabling scans in production.

If forcing the index doesn't use it, the query's form doesn't match; if forcing works, compare real timings, because the planner may be right.

Which of these queries can't use a B-tree index on lower(email), even with enable_seqscan off?

  1. WHERE lower(email) = 'a@b.com'
  2. WHERE email = 'A@b.com'
  3. WHERE lower(email) LIKE 'a%' in a database using the C locale

An expression index is used only by queries that write the same expression. A condition on plain email needs its own index.

A payments service doubles its traffic and p99 write latency jumps. Explain the index-related causes you'd look for and how you'd confirm each one.

First, write amplification: each non-HOT update writes every index, so check the HOT ratio and whether hot-updated columns appear in any index, INCLUDE list or partial-index predicate. Second, unused or duplicate indexes, confirmed with pg_stat_user_indexes over a full cycle and on every replica before dropping them concurrently. Third, GIN pending-list flushes inside unlucky statements, fixed with fastupdate off or tuned autovacuum. Finally, any INVALID index left from a failed concurrent build, which costs writes and serves no reads.

Choosing the index type

Last part: why a valid index can still go unused. Still unsolved: given a query shape, which of the six types should you reach for?

Six types, dozens of operator classes, and every index costs writes. You need a short rule that picks the right one in a design review.

Start from the question the query asks, then check the cost column. B-tree is the answer unless the question is one it can't express.

Two more decisions sit on top of the type: the shape (partial, expression, INCLUDE, unique) and whether the index earns its write cost at all. A query run once a day by a batch job rarely does.

The draft PostgreSQL 19 release notes list table scans that can mark pages all-visible, which only VACUUM and COPY ... FREEZE could do before, and parallel autovacuum workers for a table's indexes. The first should mean fewer Heap Fetches for index-only scans on tables that are read soon after they are written. This page follows PostgreSQL 18.

Setting index standards across many teams, such as review checklists for migrations or automated unused-index reports across a fleet, is staff-level work. This page stops at choosing and defending indexes for one service.

Start with B-tree; switch type only when the query asks a question B-tree can't answer, such as "contains", "overlaps", or "which block range" on a huge ordered table.

A meeting-room service must reject overlapping bookings for the same room, enforced by the database. Which index type backs that rule?

  1. A unique B-tree on (room, start_time)
  2. GIN on the booking's time range
  3. GiST, through an exclusion constraint with room WITH = and the time range WITH &&

Overlap is a GiST question. An exclusion constraint on (room WITH =, during WITH &&), with btree_gist for the room column, rejects any second booking that overlaps the first.

Interview drill: index design at the senior bar

Last part: a table for choosing the type. Still unsolved: defending a full design under questioning, with the trade-offs said out loud.

Three prompts that come up in product-company rounds. For each, commit to an answer before opening the reference.

For every prompt, say these four things: the query shapes you're serving, the index for each, what each costs on writes, and what you'd watch in production.

1. Payments. 200 million rows, 3,000 inserts and 6,000 status changes a second. Queries: (a) a merchant's payments in a date range, newest first, 50 per page; (b) workers fetch the oldest 100 pending payments; (c) ops counts failed payments in the last hour across all merchants. Design the indexes.

(a) (merchant_id, created_at): equality first, range and sort second, LIMIT stops early. (b) (created_at) WHERE status = 'pending': tiny, already in the right order. (c) (created_at) WHERE status = 'failed', small because failures are rare; skip it if ops runs the count rarely and a slow query is acceptable. No index on status alone: 4 values, mostly useless. The trade-off to say out loud: both partial indexes reference status in their predicate, so every status change is a non-HOT update that inserts into every index whose predicate the new row satisfies, including (a). That is accepted because the alternative is scanning, and it is the reason to keep the total count of indexes low. INCLUDE (status) on (a) would add no HOT cost here, since status already blocks HOT, but it makes (a) bigger; add it only if the dashboard must be index-only.

2. Searchable JSON. An orders table stores a details jsonb from many partners. Support searches by any of 30 fields; finance searches by details ->> 'invoice_no' thousands of times a minute. Writes are 2,000 a second.

Finance's hot key gets its own B-tree expression index on (details ->> 'invoice_no'): small, fast, cheap to maintain. Support's ad-hoc containment searches get one GIN index with jsonb_path_ops, which is smaller and more precise than jsonb_ops, accepting that key-exists queries with ? won't use it. The trade-off: GIN adds many entries per row, so at 2,000 writes a second watch for pending-list flushes in p99 latency and decide between fastupdate off and aggressive autovacuum on that table.

3. A 5-terabyte event log. Append-only, 2 billion rows a month, partitioned by month. Queries filter by a time window and sometimes by tenant_id. A B-tree on created_at per partition would be hundreds of gigabytes.

BRIN on created_at in each partition: rows arrive in time order, so ranges are narrow and the index is tiny; enable autosummarize so the newest ranges are summarized soon after filling. Partition pruning skips old months entirely. For the occasional tenant filter, a B-tree on (tenant_id, created_at) only in recent partitions, if those queries are frequent enough to pay for it. The trade-off: BRIN gives up precision and depends on physical order, so backfills or out-of-order loads must be sorted by time first. A new BRIN index is built concurrently on each partition, then created on the parent, which is then only a metadata change.

"Why not just index every column the API filters on?" A strong answer quantifies the write cost: every non-HOT update writes every index, and any index on a frequently updated column blocks HOT for those updates. It names the read gains it would give up by dropping indexes, and settles on the few composite or partial indexes that cover the real query shapes.

A senior index design names each query shape, the index that serves it, the write cost it adds, and the signal that would show it was wrong.

Pick one of the three prompts and give your full answer as you would in an interview, including what you'd give up.

For payments: a composite index on (merchant_id, created_at) for the dashboard, and partial indexes on created_at for pending and failed rows, written with literal predicates so the planner can match them. I'd skip an index on status alone. Status changes become non-HOT because the partial predicates reference status, so I keep the index count low and watch the HOT ratio, WAL rate and replica lag. If the failed-count query is rare, I'd drop its index and accept a slower scan.
