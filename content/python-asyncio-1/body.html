The system this series builds: a price-comparison gateway

A shopper types "kettle-1l" into a shopping app. The app calls your gateway: GET /compare?item=kettle-1l. Your gateway must ask 5 sellers for their price and answer within 250 ms with the cheapest offer. The slowest seller takes 900 ms.

Introduction

This page is Part 1 of a 10-page series on Python async programming. All 10 pages work on one system: the gateway in the problem above. Each page adds one layer to it, and each page ends by naming what is still broken, which the next page fixes.

Part 1 does not use the asyncio library at all. Instead, we build our own small scheduler from plain Python generators. When Part 2 opens up asyncio, you will recognise every piece, because you will have built a simpler copy of it yourself.

This first part fixes the numbers. Every solved example in the series uses exactly these numbers, so you can check each page's results against the earlier ones.

Comparison

Think of a travel agent finding you the cheapest bus ticket. The agent phones five bus companies. Each company takes a different time to answer. You have told the agent: "Call me back within a quarter of an hour, with the best price you have by then."

  • You, waiting for the call back = the shopping app.
  • The travel agent = the gateway.
  • The five bus companies = the five sellers.
  • "Call me back within a quarter of an hour" = the 250 ms budget.
  • "The best price you have by then" = the cheapest offer among the sellers that answered in time.

The comparison stops working at one point: a human agent can hold only one phone call at a time. Most of this page is about how one program can keep many calls waiting at once.

Definitions

  1. A gateway is a service that receives one request and, to answer it, calls several other services and combines their replies.

  2. A request budget is the longest time a request is allowed to take. Work still unfinished at that moment is given up, and the answer is built from what has arrived.

Working

The gateway's job, for every request, is:

  1. Receive GET /compare?item=<sku>. A sku is the item's product code, such as kettle-1l.
  2. Ask all 5 sellers for their price for that item.
  3. Collect the answers that arrive within the 250 ms budget.
  4. Reply with the cheapest offer among those answers.
  5. Also list the sellers that did not answer in time, or that failed.

Why each step is needed

  • Step 1: the item code is the only input; every seller is asked about the same item.
  • Step 2: without asking every seller, the gateway might miss the cheapest price.
  • Step 3: without the budget, one slow seller would make every shopper wait for it.
  • Step 4: the cheapest offer is the whole point of the service.
  • Step 5: without the list, the app could not tell "seller-e is more expensive" apart from "seller-e never answered".

Why asking five sellers one by one takes 1,450 ms

Last part: the gateway must answer within 250 ms with the cheapest offer that arrived. Still unsolved: what happens if we write it the obvious way?

A first version of the gateway calls seller-a, waits for the answer, then calls seller-b, and so on. Every request takes 1,450 ms, almost six times the 250 ms budget, and the CPU does almost nothing during that time.

Introduction

Most of the time in a network call is spent waiting: the request travels to the other machine, the other machine works, and the reply travels back. Your own program does nothing useful during that wait. This part measures how much of the gateway's time is waiting, using the simplest possible version, which we call gateway v0.

Comparison

Consider a person at a post office counter with five letters to send by registered post. They hand over the first letter and stand there until its receipt is printed, then hand over the second, and so on. The clerk's printer is slow; the person is idle almost the whole time.

  • The person = the one thread running gateway v0.
  • Standing at the counter until the receipt prints = a blocking call.
  • The five letters = the five seller calls.

The comparison stops working here: a real person could hand over all five letters at once. A blocking call does not allow that; the thread is held until the reply comes.

Definition

A blocking call is a call that does not return until its work is finished. The thread that made the call can do nothing else until then, even if the call is only waiting.

In this page's code, time.sleep() stands in for a network call to a seller. time.sleep() suspends execution of the calling thread for the given number of seconds. That is exactly what a blocking network call does to its thread: the thread is suspended until the reply arrives.

Working

  1. Start a timer.
  2. For each seller, in order: call it and wait for the reply (a blocking call).
  3. After each reply, print how many milliseconds have passed since the start.
  4. After all five replies, pick the cheapest offer and print the total time.

Why each step is needed

  • Step 1: without a start time we cannot see where the time goes.
  • Step 2: this is the design being tested: one call after another.
  • Step 3: the running total shows that each wait adds on top of the previous ones.
  • Step 4: the total is the latency the shopper would see.

Wrong belief: "The gateway is slow because Python is slow."

Why it is wrong: the Python code between calls takes far less than 1 ms. The 1,450 ms is all waiting for sellers. A faster language would wait exactly as long. What must change is the order of the waits, not the speed of the code.

  • A blocking call holds its thread until the reply arrives, even though the thread is only waiting.
  • Waits done one after another add up: 80 + 120 + 150 + 200 + 900 = 1,450 ms.
  • The time is idle waiting, not computation.

Calling five sellers one after another makes the request as slow as all five waits added together: 1,450 ms, nearly all of it idle.

A sixth seller, seller-f, is added. It takes 60 ms. Gateway v0 asks it last. What total time does v0 print now, and would asking it first change the total?

1,450 + 60 = 1,510 ms. Asking it first changes nothing about the total: one after another, the total is always the sum of all the waits, whatever the order. Only the moment each individual seller answers moves.

What it costs to give every waiting call its own thread

Last part: one after another, the five waits add up to 1,450 ms. Still unsolved: how do we make the waits happen at the same time, and what does that cost?

The obvious fix is one thread per seller call. The gateway then takes about 900 ms (the slowest seller) instead of 1,450 ms. But at 200 requests per second, how many threads are waiting at any moment, and how much memory do they hold?

Introduction

A thread is an independent line of execution inside a program. If each seller call runs in its own thread, all five threads can be waiting at the same time. This part runs that design, then measures what a waiting thread costs.

The question for the rest of the page is whether we can get the same overlap without paying for one thread per wait.

Comparison

Go back to the post office. Instead of one person queuing five times, you send five friends, each with one letter, to five counters at once. All five receipts arrive within the time of the slowest counter. But you needed five people, and each one spends nearly the whole time standing idle at a counter.

Definition

A thread-per-call design gives each waiting call its own thread. Each thread makes an ordinary blocking call. The waits overlap because the threads wait at the same time.

The Python docs support threads for this kind of work. The threading docs say threading is still an appropriate model for running multiple I/O-bound tasks simultaneously.

Working

  1. Create one thread per seller. Each thread calls ask_seller_blocking(), the same function as v0.
  2. Start all five threads. They begin their waits at almost the same moment.
  3. The main thread waits (join) for each of them to finish.
  4. Pick the cheapest offer from the list the threads filled.

Why each step is needed

  • Step 1: reusing the blocking function shows that threads overlap waits without changing the seller code.
  • Step 2: starting all of them before waiting on any is what makes the waits overlap.
  • Step 3: without join, the gateway would answer before the offers arrive.
  • Step 4: same as v0.

What one waiting thread costs

The program thread_cost.py below starts 500 threads that only wait, and measures memory and start time before and after.

Two memory numbers matter, and they are very different:

  • Virtual memory is address space the operating system has reserved for the process. In this run each waiting thread reserved about 10,182 KiB (about 10 MiB).
  • Resident memory is what is actually held in RAM. Each waiting thread used only about 21 KiB of it.

Most of the reserved part is the thread's stack. threading.stack_size() returns the stack size used for new threads; 0 means the platform or configured default is used. The measurement shows 0, so Python left the choice to the operating system. On Linux, if the RLIMIT_STACK soft limit is not "unlimited" when the program starts, it sets the default stack size of new threads. On the measuring machine that limit was 8,192 KiB, which is most of the 10,182 KiB reserved per thread.

Starting each thread took about 118 µs (microseconds) in this run. Your numbers will differ by machine; the test only checks that reserved memory is far larger than used memory.

Solved example

Given: 200 requests arrive per second. With threads, each request lasts about 900 ms and holds 5 threads while it waits. Use the measured costs above.

Step 1. Requests in progress at any moment = arrivals per second × seconds each lasts = 200 × 0.9 = 180 requests.

Step 2. Waiting threads = 180 requests × 5 threads = 900 threads.

Step 3. Reserved memory = 900 × 10,182 KiB ≈ 9,163,800 KiB ≈ 8.7 GiB of address space.

Step 4. Resident memory = 900 × 21 KiB = 18,900 KiB ≈ 18 MiB, before counting the per-thread objects of your own code.

Step 5. Thread starts per second = 200 requests × 5 threads = 1,000 starts; at about 118 µs each, that is about 118 ms of start-up work every second, spent only on creating threads.

Result: the waits overlap (900 ms instead of 1,450 ms), but 200 requests per second keeps about 900 threads alive. At 10 times the traffic it is about 9,000 threads. The real limits are then the per-process thread limit, start-up cost and the scheduling work of the operating system, not RAM alone. A thread pool reuses threads and removes the start-up cost, but it still needs one thread for every wait in progress.

Wrong belief: "Each thread costs 8 MiB of RAM, so 900 threads need 7 GiB."

Why it is wrong: the stack is reserved address space, not used RAM. In the measurement above a waiting thread reserved about 10 MiB but used about 21 KiB. Threads are expensive mainly in number (limits, start-up, scheduling), not in RAM per thread.

  • One thread per call overlaps the waits: about 900 ms instead of 1,450 ms.
  • Threads in use = requests in progress × waits per request; 200 requests per second here means about 900 threads.
  • A waiting thread reserves a large stack (8 MiB limit on the measuring machine) but uses little RAM; its cost is mostly count, start-up and scheduling.

Threads make the five waits overlap, but they spend one whole thread on every wait in progress, which at 200 requests per second is about 900 threads.

Concurrency is not parallelism

Last part: threads overlap the waits, but cost one thread per wait in progress. Still unsolved: do we actually need several things running at the same instant, or only several things waiting at the same time?

During the gateway's 900 ms, how much Python code actually runs? Less than 1 ms. The other 899 ms is five waits. We need the waits to overlap; we do not need five CPU cores.

Introduction

Two words get mixed up all the time: concurrency and parallelism. The difference decides which tool fits the gateway. This part defines both and shows that the gateway needs only the first.

Comparison

Consider one cook making tea, rice and boiled eggs. They put the kettle on, put the rice on, put the eggs on, and then check whichever is ready. All three dishes are in progress together, but there is only one cook. That is concurrency. Three cooks, each making one dish at the same moment, is parallelism.

  • The cook = one thread.
  • Waiting for the kettle = waiting for a seller's reply.
  • Checking whichever dish is ready = resuming whichever call has its reply.

The comparison stops working at one point: a cook can notice a pot boiling over in the middle of a task. A program on one thread only switches at points written into the code. The next parts of this page are about exactly those points.

Definitions

  1. Concurrency means several jobs are in progress over the same period of time, taking turns. They need not run at the same instant.

  2. Parallelism means several jobs are running at the same instant, on different CPU cores.

  3. An I/O-bound job spends most of its time waiting for input or output, such as a network reply. A CPU-bound job spends most of its time computing.

Working

  1. Measure where the request's time goes: computing or waiting.
  2. If it is mostly waiting (I/O-bound), concurrency is enough: let the waits overlap on as few threads as possible.
  3. If it is mostly computing (CPU-bound), only parallelism helps: the work must run on several cores at once.

Why each step is needed

  • Step 1: without measuring, you may pay for parallelism (more threads, more processes) that buys nothing.
  • Step 2: overlapping waits needs no extra cores, because waiting uses no CPU.
  • Step 3: overlapping cannot shorten computation; only more cores can.

In standard Python, threads give the gateway concurrency but not parallelism for Python code. In CPython, because of the Global Interpreter Lock, only one thread can execute Python code at once. The waiting does not need the lock, which is why the threaded gateway still finished in about 900 ms.

Python 3.14 makes the free-threaded build officially supported, but it is still optional. Free-threaded builds can disable the Global Interpreter Lock, but this is not available by default. It does not change this page's argument: the gateway is waiting, not computing, so parallel threads would make it no faster. Part 7 of the series returns to threads.

Solved example

Step 1. Fraction of time computing: under 1 ÷ 1,450, which is under 0.07%. The request is I/O-bound.

Step 2. With perfect concurrency the waits overlap fully. The total becomes the longest single wait: 900 ms.

Step 3. With 5 cores of parallelism and no overlap of waits, the computing part shrinks from under 1 ms to under 0.2 ms, saving under 1 ms of 1,450.

The rest of this page builds concurrency on one thread. The library that does this in real Python programs is asyncio. The Python docs describe asyncio as a library for writing concurrent code using the async/await syntax. They also say asyncio is often a perfect fit for IO-bound and high-level structured network code.

Wrong belief: "Async code runs things in parallel, so it makes Python faster."

Why it is wrong: async code on one thread runs one piece of Python at a time. It makes waits overlap, which helps I/O-bound work. A CPU-bound job, such as resizing 10,000 images, gets no faster on one thread however it is written.

  • Concurrency: many jobs in progress, taking turns. Parallelism: many jobs running at the same instant on several cores.
  • The gateway is I/O-bound, so it needs concurrency, not parallelism.
  • With the GIL, CPython threads run one piece of Python code at a time; waits still overlap.

The gateway needs its waits to overlap (concurrency), not its code to run on many cores (parallelism), so one thread is enough if it can switch between waits.

Which job gains the most from running on one thread with concurrency?

  1. A report job that calls 40 internal APIs, each taking about 100 ms
  2. Resizing 10,000 images on one server
  3. A single SQL query that takes 4 seconds

Forty 100 ms waits, overlapped, take about 100 ms instead of about 4,000 ms. The images are CPU-bound, and the single query has nothing to overlap with.

A function that can pause: yield

Last part: one thread is enough if it can switch between waits. Still unsolved: an ordinary Python function cannot stop halfway and continue later. What can?

To overlap five waits on one thread, the code for seller-a must be able to stop at "now wait 80 ms", let seller-b's code run, and later continue from exactly the same line, with all its variables intact. An ordinary function can only run to the end or raise.

Introduction

Python has had functions that can pause for a long time: generators. Every async feature in Python, including async def and await, is built on the same idea. So we start here.

Comparison

Think of a bookmark in a novel. You stop reading at page 112, close the book, do other things, and later open it at page 112 and carry on. The book does not forget the story so far.

  • Closing the book at the bookmark = yield.
  • Opening it again at the bookmark = next() on the generator.
  • The story so far = the function's local variables.

The comparison stops working here: a reader decides when to open the book again. A generator never resumes itself; some other code must call it.

Definitions

  1. A function whose body contains a yield expression is a generator function. Calling it returns a generator, an object that runs the function's body in pieces.

  2. The yield keyword pauses the generator and hands a value out to whoever resumed it.

Working

  1. Calling a generator function returns a generator; its body starts running only when one of the generator's methods is called, and then runs to the first yield.
  2. At a yield, the generator pauses and hands the yielded value to the caller of next(). When it pauses, it keeps all its local state, including variable bindings, the instruction pointer, the evaluation stack and exception-handling state.
  3. The next next() continues from the line after that yield.
  4. When the generator returns, StopIteration is raised, and the returned value becomes the StopIteration.value attribute.

Why each step is needed

  • Step 1: if calling the function ran its body, there would be no way to create one and start it later; a scheduler needs to hold work that has not started.
  • Step 2: keeping the local state is what makes pausing safe; without it, the function would forget where it was.
  • Step 3: resuming exactly after the pause is what lets the code read as one straight sequence.
  • Step 4: the caller needs a clear signal that the work is finished, and its result.

Wrong belief: "Calling countdown(3) runs the function and prints 'starting'."

Why people hold it: calling every other function runs it.

Why it is wrong: calling a generator function only builds the generator object. Nothing in the body runs until something resumes it. The same rule returns, with worse consequences, when we reach async def.

  • A function with yield in its body is a generator function; calling it runs nothing.
  • Each resume runs the body to the next yield, keeping all local variables.
  • A return ends it with StopIteration, carrying the returned value in .value.

A generator is a function that can pause at yield and later continue from the same line with its variables intact, which is exactly what a waiting seller call needs.

Sending a value back in: send()

Last part: a generator pauses at yield and hands a value out. Still unsolved: a waiting seller call must also receive something when it resumes, such as the reply. How does a value get in?

A shop counter adds up a bill one price at a time: 120, then 45. The code that adds them should pause after each item and be handed the next price when it resumes. next() can only resume; it cannot hand anything in.

Introduction

The yield keyword works in both directions. It sends a value out, and when the generator resumes, the yield expression itself has a value: whatever the resumer sent in. The method that sends a value in is send().

Definition

send(value) resumes a paused generator and makes value the result of the yield expression where it paused. The sent value becomes the result of the current yield expression, and send() returns the next value the generator yields.

Working

  1. Start the generator with send(None). It runs to the first yield and hands out the first value.
  2. Call send(v). The paused yield expression evaluates to v, and the body continues.
  3. The body runs to the next yield, and that yielded value is what send(v) returns.

When send() is used to start a generator, it must be called with None, because there is no yield expression yet that could receive a value. next(gen) and gen.send(None) do the same thing.

Why each step is needed

  • Step 1: a value can only be received by a yield that is paused; a new generator has not reached one yet.
  • Step 2: this is how information (a price, later a seller's reply) reaches the paused code.
  • Step 3: one call both delivers a value in and collects the next value out, so the two sides take turns cleanly.

Program

Explanation of the program

  1. counter.send(None) starts the generator. total = 0, and the body pauses at price = yield total, handing out 0.
  2. counter.send(120) resumes it: the paused yield evaluates to 120, so price = 120 and total = 120. The loop goes round and yields 120.
  3. counter.send(45): price = 45, total = 165, and 165 is yielded.
  4. bill().send(5) sends a value into a brand-new generator, which has no paused yield. Python raises TypeError.

Solved example

Given: counter = bill(), then send(None), send(120), send(45).

Step 1. send(None): total = 0; pauses at the yield; returns 0.

Step 2. send(120): price = 120; total = 0 + 120 = 120; pauses; returns 120.

Step 3. send(45): price = 45; total = 120 + 45 = 165; pauses; returns 165.

Result: outputs 0, 120, 165. Each call delivered one value in and got one value out.

Our scheduler will use send(None) to resume work, exactly as asyncio does. The values that matter will flow out, not in: each paused piece of work will yield a request such as "wake me in 80 ms".

Wrong belief: "send(120) delivers 120 to the yield that comes next in the code."

Why it is wrong: it delivers 120 to the yield where the generator is paused right now. That is why the first call must be send(None): before the first resume, the generator is not paused at any yield.

  • send(v) resumes the generator and makes the paused yield evaluate to v.
  • It returns the next value the generator yields.
  • The first resume must be send(None) (or next()).

send() resumes a paused generator and hands a value to the yield where it stopped, so information can flow both out of and into paused code.

A new counter = bill() is created. You call counter.send(None), then counter.send(30), then counter.send(30). What do the three calls return?

  1. 30, 60, 90
  2. 0, 30, 30
  3. 0, 30, 60
  4. TypeError on the first call

The first call starts it and returns total 0. Each later call adds the sent price and returns the new total: 30, then 60.

Interrupting or stopping a paused generator: throw() and close()

Last part: send() delivers a value to a paused generator. Still unsolved: what if the thing it is waiting for fails, or we stop waiting for it altogether, as with seller-e at the 250 ms budget?

At 250 ms, the gateway gives up on seller-e. seller-e's code is paused in the middle of its wait. Its cleanup code (closing a connection, writing a log line) must still run, and it must stop for good.

Introduction

A paused generator can be resumed in two more ways besides send(). throw() resumes it by raising an exception at the paused yield, as if the wait had failed. close() resumes it by raising a special exception that tells it to stop. Both run the generator's own except and finally blocks.

Definitions

  1. throw(exc) resumes a paused generator by raising exc at the yield where it paused. throw() raises the exception at the point where the generator was paused and returns the next value it yields; if the generator does not catch it, it propagates to the caller.

  2. close() stops a paused generator. close() raises GeneratorExit at the point where the generator was paused. GeneratorExit is the exception that means "stop now".

Working

  1. throw(exc): the paused yield raises exc inside the generator.
  2. If the generator catches it, it continues and runs to its next yield; throw() returns that value.
  3. If it does not catch it, the exception comes out of throw() to the caller.
  4. close(): the paused yield raises GeneratorExit. except and finally blocks run, and the generator ends.
  5. If the generator returns a value when it is closed, close() returns that value. If the generator yields a value instead of stopping, close() raises RuntimeError.

Why each step is needed

  • Steps 1 to 3: a failed wait must reach the code that was waiting, at the line where it waited, so its own try can handle it.
  • Step 4: work we stop waiting for must still release what it holds; running finally does that.
  • Step 5: the RuntimeError stops a generator from silently refusing to stop.

Handing control to another generator: yield from

Last part: throw() and close() reach a generator at the line where it paused. Still unsolved: real code calls functions that call functions. If the pause happens three calls deep, how does it reach the outside?

The gateway's handler calls ask_seller(), which calls a function that does the actual wait. The scheduler outside must see the innermost "wait 80 ms", and the reply must go back to the innermost function, not the handler.

Introduction

A generator can hand control to another generator for a while, with yield from. While it does, everything flows straight through: values yielded by the inner generator go out to the caller, and values sent in go to the inner generator. When the inner one returns, its return value becomes the value of the yield from expression.

Comparison

A customer phones a company's help line. The receptionist says "let me put you through" and connects the customer to an engineer. The customer and the engineer then talk directly. When the engineer hangs up, the receptionist comes back on the line knowing the outcome.

  • The receptionist = the outer generator.
  • "Let me put you through" = yield from.
  • The direct conversation = values passing straight between the caller and the inner generator.
  • The outcome the receptionist learns = the inner generator's return value.

Definition

yield from runs another generator to the end inside the current one. With yield from, the inner iterator's values are passed directly to the caller, send() and throw() are passed to the inner iterator if it has those methods, and its StopIteration.value becomes the value of the yield from expression.

Working

  1. The outer generator reaches yield from inner.
  2. The inner generator runs to its first yield. That value goes straight out of the outer generator to the caller.
  3. The caller's next send(v) goes straight to the inner generator's paused yield.
  4. When the inner generator returns, its return value becomes the value of yield from inner, and the outer generator continues.

Why each step is needed

  • Step 2: the scheduler only talks to the outermost generator, so a pause deep inside must travel out.
  • Step 3: the reply belongs to the code that asked for it, deep inside.
  • Step 4: the outer code needs the inner result, like an ordinary function's return value.

Program

Explanation of the program

  2. desk.send(3) goes straight to weigh's paused yield: weight = 3. weigh returns 3, so yield from evaluates to 3 and total = 3. The loop moves to box-2, and "weigh box-2" comes out.
  3. desk.send(5): weight = 5, total = 8, the loop ends, and parcel_desk returns 8, raising StopIteration with value 8.

Toy loop, step 1: a ready queue that takes turns

Last part: yield from lets a pause anywhere in a call chain reach the outside. Still unsolved: something on the outside must decide which paused generator to resume next.

We have two generators, A with 3 pieces of work and B with 2. One thread must run them so that each gets a turn in fair order, and neither waits for the other to finish completely.

Introduction

We now start building the toy event loop, in three steps. Step 1 is the simplest possible scheduler: a line of generators waiting for their turn, and a loop that resumes them one at a time. Each yield means "my turn is over; let someone else run".

Comparison

A doctor sees patients from a waiting-room queue. Each patient is seen for one short visit; if they need more, they rejoin the back of the queue. Patients who are fully treated leave.

  • The waiting room = the ready queue.
  • One short visit = running a generator to its next yield.
  • Rejoining the back = appending the generator again.
  • Fully treated = StopIteration.

Definitions

  1. A ready queue is a first-in, first-out line of pieces of work that can run right now.

  2. A scheduler is the loop that repeatedly takes the next piece of work from the ready queue and runs it until it pauses. An event loop is a scheduler that also knows what each paused piece is waiting for; we get there in step 2.

Python's collections.deque is the right container for the ready queue. A deque supports appends and pops from either end with approximately O(1) performance. Lists incur O(n) memory movement costs for pop(0) and insert(0, v) operations. That is every pop from the front of a long ready queue.

Working

  1. Put every generator in the ready queue.
  2. Take the generator at the front (popleft).
  3. Resume it with next(); it runs until its next yield.
  4. If it raised StopIteration, it is finished: drop it.
  5. Otherwise append it to the back of the queue.
  6. Repeat from step 2 until the queue is empty.

Why each step is needed

  • Step 2: taking from the front gives first-in, first-out fairness.
  • Step 3: the generator, not the scheduler, decides how long its turn lasts, by where it yields.
  • Step 4: finished work must leave, or the loop would never end.
  • Step 5: unfinished work goes to the back, so everyone else gets a turn first.

Diagram

Explanation of the diagram

  1. The scheduler takes the first generator from the ready queue.
  2. It resumes the generator. Only now does that generator's code run.
  3. The generator yields. This hands control back, like returning from a function, except the generator can be resumed later.
  4. The scheduler puts it at the back of the line. The same four steps repeat for the next generator. Later steps of the loop add boxes to this same picture.

Program

Explanation of the program

  1. counter("A", 3) and counter("B", 2) create two generators. Neither has run yet.
  2. run() puts both in a deque and loops while it is not empty.
  3. Each turn prints one line and yields, so the output alternates between A and B.
  4. B finishes after two lines; A finishes after three.

Wrong belief: "The scheduler interrupts a generator when its turn has lasted long enough."

Why it is wrong: the scheduler cannot interrupt anything. It gets control back only when the generator yields or finishes. This is called cooperative scheduling, and it is the root of the biggest async trap: code that never yields holds the thread for everyone. Rung 4 shows it.

  • The ready queue is a deque of work that can run now; the scheduler takes from the front and appends to the back.
  • Each yield ends a turn; StopIteration removes the work.
  • The scheduler only regains control when the running code yields.

A scheduler is a loop over a ready queue that resumes one generator at a time until it yields, then sends it to the back of the line.

Put one turn of the step-1 scheduler in order.

  1. Take the generator at the front of the ready queue
  2. Resume it with next()
  3. Its code runs until it reaches yield
  4. Control returns to the scheduler
  5. Append the generator to the back of the queue

The scheduler only gets control back at a yield, and only then can it put the generator back in line and pick the next one.

Toy loop, step 2: sleeping without blocking, with a timer heap

Last part: a ready queue gives each generator a turn. Still unsolved: a seller call does not want "another turn soon"; it wants "wake me in 80 ms". If it stays in the ready queue, the loop keeps resuming it for nothing.

Three jobs: A waits 30 ms then 50 ms, B waits 20 ms, C waits 40 ms. One after another that is 140 ms. On one thread, how do we make all the waits overlap, so everything is done after 80 ms (A's 30 + 50)?

Introduction

Step 2 changes what a yield means. Instead of yielding nothing, a generator now yields a number: how many milliseconds it wants to sleep. The loop does not keep a sleeping generator in the ready queue. It parks it in a separate structure ordered by wake-up time, and moves it back to the ready queue when its time comes.

Comparison

A hotel front desk takes wake-up call requests: room 12 at 6:30, room 7 at 6:20, room 30 at 6:40. The clerk keeps the list sorted by time and only ever looks at the top entry: the earliest call. Nobody is woken early, and nobody is phoned again and again to ask "is it time yet?".

  • The sorted list of wake-up calls = the timer heap.
  • The top entry = heap[0], the earliest wake-up.
  • Making the call = moving the generator back to the ready queue.

Definitions

  1. A timer heap is a list of (wake-up time, work) entries kept so that the earliest wake-up is always first. In Python's heapq module, heap[0] is always the smallest item.

  2. A virtual clock is a clock the loop keeps itself. When nothing is ready, it jumps straight to the next wake-up time instead of waiting for real time to pass. The toy loop uses one so that every run prints exactly the same times; the real asyncio loop of Part 2 waits on a real clock.

Working

  1. If the ready queue has work, take the first generator and resume it.
  2. If it yields a number ms, push (now + ms, order, generator) onto the timer heap. It is not put back in the ready queue.
  3. If it finishes, drop it.
  4. If the ready queue is empty, pop the earliest timer, set the clock to its wake-up time, and put its generator in the ready queue.
  5. Stop when both the ready queue and the timer heap are empty.

Why each step is needed

  • Step 2: a sleeping generator must not take turns; parking it costs nothing until its time.
  • Step 2, the order number: two timers with the same wake-up time would otherwise be compared by their generators, which Python cannot order. The counter breaks the tie in the order they were added.
  • Step 4: the heap gives the earliest wake-up at once, so the loop never scans every timer.
  • Step 5: the loop is done only when no work is ready and none is sleeping.

Diagram

Explanation of the diagram

  1. Steps 1 to 3 are the same turn as before, except the yield now carries a sleep time.
  2. Step 4 is new: the sleeping generator goes into the timer heap, not the ready queue.
  3. Step 5: when nothing is ready, the clock jumps to the earliest wake-up.
  4. Step 6: the generator whose time has come returns to the ready queue.

Program

Explanation of the program

  1. Loop holds the clock (now), the ready deque, the timer heap and the tie-breaking order counter.
  2. In run(), an empty ready queue means: pop the earliest timer, jump the clock, make that generator ready.
  3. Otherwise it resumes the first ready generator. The yielded number is a sleep request, so it is pushed onto the heap with its wake-up time.
  4. sleeper() prints the clock before each sleep and when done. It reads loop.now, so it sees the virtual time.

Wrong belief: "A sleeping generator is resumed over and over and checks whether its time is up."

Why it is wrong: a sleeping generator is not in the ready queue at all. It sits in the heap and costs nothing until the loop moves it back. Checking again and again (called busy waiting) would burn CPU for nothing.

  • A generator now yields a sleep request; the loop parks it in the timer heap with its wake-up time.
  • heap[0] is always the earliest wake-up; the loop jumps the clock there when nothing is ready.
  • Overlapped, the waits finish at the latest wake-up (80 ms), not the sum (140 ms).

The timer heap lets a generator say "wake me in 30 ms" and step aside completely, so many waits overlap on one thread.

Add a fourth job, D, that sleeps 10 ms then 60 ms. All start at 0. When does each job finish, and what is the clock when the loop ends?

B finishes at 20, C at 40, A at 80. D wakes at 10, sleeps again until 10 + 60 = 70, and finishes at 70. The heap always hands out the earliest wake-up, so the order is D at 10 (re-sleeps), B at 20, A at 30 (re-sleeps), C at 40, D at 70, A at 80. The clock ends at 80 ms.

From generators to async def and await

Last part: generators that yield sleep requests can overlap their waits on one thread. Still unsolved: code full of yield and yield from is hard to read, and nothing stops you mixing "yield a value for a for-loop" with "pause for the scheduler". Python has a dedicated syntax for the second meaning.

A teammate writes a function to save a receipt, but forgets one keyword. Tests pass, no error is raised, and no receipts are saved for two days.

Introduction

async def and await are Python's syntax for "a function that can pause for a scheduler". Underneath, they work like the generators of the earlier parts: a coroutine is resumed with send(), pauses, and finishes with StopIteration. The new syntax keeps this separate from ordinary generators, which are for producing values in a for loop.

Definitions

  1. A function defined with async def is a coroutine function; calling it returns a coroutine object. A coroutine object is that returned object: the function's body, ready to run in pieces.

  2. The await keyword pauses a coroutine until something else is done. An await expression suspends the execution of a coroutine on an awaitable object, and can only be used inside a coroutine function. The next part defines "awaitable" exactly.

Working

  1. Calling an async def function builds a coroutine object. The body does not run.
  2. coroutine.send(None) starts or resumes the coroutine. This is what an event loop does.
  3. The body runs until it pauses inside an await, or until it returns.
  4. When the coroutine returns, StopIteration is raised, and its value attribute holds the return value.

Why each step is needed

  • Step 1: a scheduler must be able to hold work that has not started.
  • Step 2: send(None) is the same resume operation our loop already uses on generators.
  • Steps 3 and 4: the loop needs to know whether the coroutine paused (and why) or finished (and with what result).

One thing is different from generators. Unlike generators, coroutines do not directly support iteration. You cannot for-loop over one or call next() on it. This keeps the two meanings of pausing apart.

Explanation of the program

  1. greet("asha") builds a coroutine object. "hello, asha" is not printed: the body has not run.
  2. coro.send(None) runs the body. It prints the greeting and returns len("asha"), which is 4. Returning raises StopIteration with value 4.
  3. next(other) fails with TypeError: a coroutine is not an iterator.
  4. other.close() marks the unused coroutine as finished, so Python does not warn about it.

What await actually does: the __await__ protocol

Last part: a coroutine is resumed with send(None) and pauses inside await. Still unsolved: a coroutine has no yield in it. So what actually pauses, and how does "wake me in 80 ms" reach the loop?

The gateway's handler awaits fetch_price(), which awaits a sleep of 80 ms. The loop must receive "sleep 80" from two calls deep, and 80 ms later resume the code exactly after the innermost await.

Introduction

await is yield from with stricter rules. Whatever is awaited must provide an iterator through a special method, __await__. The first value that iterator yields travels out through every await in the chain to whoever called send(): the loop. This part builds the smallest possible awaitable, Sleep, which the toy loop will use.

Definitions

  1. An awaitable is an object that can be used in an await expression: a coroutine, or an object with an __await__() method.

  2. __await__ is the special method that makes an object awaitable. __await__ must return an iterator.

The most important rule for building a loop is what may be yielded. The language places no restriction on what the iterator returned by __await__ yields; that is up to the framework managing the awaitable, such as asyncio. So every event loop invents its own messages. Ours is a tuple ("sleep", ms).

Working

  1. The loop calls send(None) on the outer coroutine.
  2. The outer coroutine runs until await fetch_price(), which starts the inner coroutine, the same as yield from.
  3. The inner coroutine runs until await Sleep(80). Python calls Sleep(80).__await__(), which is a generator.
  4. That generator yields ("sleep", 80). The value passes out through both awaits and is returned by the loop's send(None).
  5. Later, the loop calls send(None) again. The value goes in through both awaits to the paused generator inside Sleep, which finishes; the innermost await completes, and the code after it runs.

Why each step is needed

  • Steps 2 and 3: only the innermost awaitable knows what it is waiting for, so it must be the one that yields.
  • Step 4: the loop only talks to the outermost coroutine, so the request must travel out.
  • Step 5: the resume must arrive at exactly the code that asked, as with yield from. If the value sent is not None, coroutine.send() passes it to the send() method of the iterator that caused the coroutine to suspend.

Wrong belief: "await itself pauses the coroutine and hands control to the loop."

Why it is wrong: await on a coroutine runs it straight away, like a function call. Control reaches the loop only when something at the bottom of the chain actually yields. An await whose chain never yields never pauses at all. Part 2 shows the same rule in asyncio.

  • An awaitable has __await__, which must return an iterator.
  • The innermost yield travels out through every await to the loop; the resume travels back in.
  • What gets yielded is the loop's own private language; ours is ("sleep", ms).

await works like yield from: the innermost awaitable's __await__ yields a request that passes out through the whole chain to the loop, and the loop's next send() resumes exactly there.

You write a class Tick whose __await__ is def __await__(self): return 42. What happens on await Tick()?

  1. The await evaluates to 42
  2. The loop receives 42 as its request
  3. It fails with TypeError, because __await__ must return an iterator

__await__ must return an iterator. An int is not one, so Python raises TypeError when the await is evaluated. Returning an iterator that yields 42 would be allowed; the loop would then have to understand 42.

Toy loop, step 3: the scheduler drives coroutines

Last part: the innermost awaitable yields a request that reaches the loop. Still unsolved: putting it all together, a loop that runs async def code, parks it on sleep requests and records each result.

Two jobs written with async def: tea needs 30 ms, eggs need 20 ms. On one thread, both should finish by 30 ms, and the loop should keep each job's result.

Introduction

The final toy loop is step 2 with three changes. It resumes coroutines with send(None) instead of next(). It understands only one request, ("sleep", ms). And it wraps each coroutine in a small Task object that records whether it is done and what it returned. This is the loop the gateway uses from now on.

Definition

A task (in the toy loop) is a coroutine plus the loop's record of it: its name, whether it is done, and its result. asyncio's real Task, in Part 2, does much more.

Working

  1. spawn(coro, name) wraps the coroutine in a Task and puts it in the ready queue.
  2. run() loops: if a task is ready, resume it with send(None).
  3. If the coroutine finishes, StopIteration carries its result: mark the task done and store the result.
  4. If it yields ("sleep", ms), push it onto the timer heap at now + ms.
  5. If it yields anything else, raise TypeError: the toy loop does not understand it.
  6. If nothing is ready, jump the clock to the earliest timer and make that task ready.
  7. With run(until=T), stop as soon as the clock would pass T, leaving unfinished tasks as they are.

Why each step is needed

What breaks first at 10 times the load

Last part: one blocking call delays every task on the thread. Still unsolved: even with no blocking calls, every task's code runs on that one thread. What happens when there is much more of it?

The gateway handles 200 requests per second comfortably. A sale event brings 2,000 per second. Each request needs a little CPU for every seller reply. Which limit is hit first?

Introduction

An event loop removes the cost of waiting, but not the cost of running code. All the code of all requests shares one thread. That thread has exactly 1,000 ms of time per second. Once the code needs more than that, tasks queue up in the ready queue, and every request gets slower.

Definition

Loop lag is how much later a task is resumed than when it became ready, because the loop's one thread was busy running other code.

Working

  1. Each request's CPU time = the work per seller reply × 5 replies + its own small overhead.
  2. Thread time needed per second = requests per second × CPU time per request.
  3. While that stays well under 1,000 ms per second, loop lag stays near zero.
  4. As it approaches 1,000 ms per second, the ready queue grows and loop lag rises.
  5. Above it, the loop falls further behind every second: lag grows without limit, and every budget is blown.

Solved example

Given: parsing one seller reply and comparing prices costs 0.2 ms of CPU. Ignore the rest of the request's code.

Step 1. CPU per request = 5 replies × 0.2 ms = 1 ms.

Step 2. At 200 requests per second: 200 × 1 ms = 200 ms of CPU every second, 20% of the one thread.

Step 3. At 10 times the load, 2,000 requests per second: 2,000 × 1 ms = 2,000 ms of CPU every second.

Step 4. One thread can do only 1,000 ms per second. It falls behind by 1,000 ms every second; after 3 seconds, newly ready tasks wait about 3,000 ms in the ready queue.

Result: the first thing to break at 10 times the load is not memory or threads but the one thread's CPU time. The fix is more loops, typically one process per CPU core, each with its own event loop, behind a load balancer.

Decision rules

  1. If the time goes into computing, neither threads (in a standard build) nor a loop help; use more processes. In CPython, because of the Global Interpreter Lock, only one thread can execute Python code at once.
  2. If there are few waits at a time and the code is simple, threads are the least surprising choice.
  3. If there are many waits in progress at once and every library you call has an async version, use an event loop.
  4. If even one call on the path is only available as a blocking library, an event loop needs it run on a thread (Part 3 and Part 7), or it stalls everything.

Solved example

Given: the three services in the problem.

Step 1. Gateway: at 2,000 requests per second, about 2,000 × 0.25 s = 500 requests are in progress at once (each lasts at most the 250 ms budget), with 5 waits each: 2,500 waits in progress. Step 2. Image job: CPU-bound. Neither threads nor a loop help Python code; use a pool of processes.

Question: "When would you not use asyncio for an I/O-bound service?"

Strong answer: when only a few waits are in progress at once, so threads cost little; when a key dependency has only a blocking client, so the loop would need a thread for it anyway; or when the team cannot keep blocking calls out of async code. Says what is given up with threads: one thread per wait in progress, and harder sharing of state across threads.

Wrong belief: "asyncio is always faster than threads."

Why it is wrong: both overlap waits; neither speeds up a single wait. asyncio's advantage is the cost of each wait in progress, which only matters when there are many. With 3 waits at a time, threads are just as fast and simpler.

  • Threads: one thread per wait in progress; fine for few waits or blocking-only libraries.
  • Event loop: one paused coroutine per wait; for many waits, if every call is async.
  • CPU-bound work needs processes, not threads (standard build) or a loop.

Pick an event loop when many waits are in progress at once and every call can be async; pick threads for few waits or blocking-only libraries; pick processes for computation.

A report service makes 3 slow database calls per report, 2 reports per minute, and its database driver is only available as a blocking library. What is the best fit?

  1. asyncio, because the work is I/O-bound
  2. Threads (for example a small thread pool), because there are few waits and the library is blocking
  3. A process pool, because Python threads cannot run in parallel

Only a handful of waits are ever in progress, so threads cost little, and they can use the blocking driver directly. An event loop would gain nothing and would need threads for the driver anyway.

Introduction

Each prompt below draws on this page only. A strong answer explains the mechanism in plain steps and states what is traded away. Use the numbers from the gateway: they make an answer concrete and checkable.

Prompt 1: "Explain how await suspends a function without a thread."

Explain how await suspends a function without a thread, as you would in an interview.

A coroutine is an object that runs in pieces. The event loop resumes it by calling send(None). The coroutine runs until something at the bottom of its await chain, an awaitable whose __await__ is a generator, yields. That yield pauses every level of the chain at once, keeping their local variables, and the yielded value comes out of send() to the loop as a request, such as "wake me in 80 ms". The loop parks the task in a timer heap and runs other ready tasks on the same thread. When the time comes, it calls send(None) again and the coroutine continues on the line after its await. No thread waits; the paused task is just an object in a list. The trade-off: the loop can only switch at those yields, so any code that blocks without awaiting stalls every task.

Prompt 2: "Our gateway calls 5 sellers; p50 is 1,450 ms. Fix it."

The sellers take 80, 120, 150, 200 and 900 ms and are called one after another. The budget is 250 ms. Give the fix, the new latency, and what the shopper gives up.

The calls are waits done one after another, so they add up to 1,450 ms. Make them overlap: spawn one task per seller on an event loop, all before waiting, and the request takes the slowest wait, 900 ms, on one thread. That still misses the 250 ms budget, so cut the request at 250 ms: a, b, c and d answer by 200 ms and the cheapest of them is seller-b at 1,199. Close seller-e's task and list it as missed. The trade-off: when seller-e has the best price (1,149), the shopper gets 1,199 instead, in exchange for a fast answer on every request. Threads would also give 900 ms, but at about 900 threads at 200 requests per second.

Prompt 3: "Every endpoint of our async service got slow at once. CPU is 30%."

What is the most likely cause, how do you confirm it, and how do you fix it?

A blocking call on the event loop's thread: it delays every task, not only its own request, which is why all endpoints slowed together, and CPU stays low because a blocking network call waits rather than computes. Confirm with slow-callback logging (asyncio's debug mode logs callbacks over 100 ms) or by measuring loop lag. Fix by switching to an async client, or by running the blocking call in an executor. If instead CPU were near 100% of one core, the cause would be load: one loop's thread out of CPU time, fixed with one loop per core.

What separates a senior answer here: it names the mechanism (send, yield, timer heap) rather than saying "async is non-blocking"; it uses numbers (1,450 → 900 → 250 ms; about 900 threads at 200 requests per second); and it says what is given up (a worse price sometimes; every library must be async; one blocking call hurts everyone).

Wrong belief: "'Async is non-blocking' is a complete answer to how await works."

Why it is wrong: it names the result, not the mechanism. An interviewer asking this wants the pause (a yield at the bottom of the await chain), the parking (the loop's heap or, for sockets, the operating system), and the resume (send() again).

  • await suspends by a yield at the bottom of the chain; the loop resumes with send().
  • Overlap gives the slowest wait (900 ms); the budget gives a partial answer at 250 ms.
  • All endpoints slow at once with low CPU usually means a blocking call on the loop.

A strong answer about await names the yield that pauses, the loop that parks and resumes, the numbers, and what is given up.
