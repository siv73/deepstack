Why one thread can wait on 1,000 network calls

Your pricing service calls 3 downstream APIs per request, 100 ms each. Called one after another, each request takes 300 ms, and the CPU sits idle for nearly all of it. At 500 requests per second, a thread-per-request design needs about 150 threads just to wait.

Think of a waiter in a restaurant. A bad waiter takes one order, walks to the kitchen and stands there until the dish is ready. A good waiter hands the order in, serves other tables, and comes back when the kitchen rings the bell. One waiter, many tables, because most of the job is waiting.

  1. Your code starts a network call and says "I'll wait here" at a marked point.
  2. Instead of blocking the thread, it steps aside so other code can run.
  3. When the reply arrives, your code picks up exactly where it left off.

Running many waits at the same time on one thread, by switching between them at marked points, is concurrency. It is not parallelism: only one piece of Python code runs at any instant. The win comes from overlapping the waiting, not from doing more work per second.

Python's tool for this is asyncio. The Python docs describe asyncio as a library for writing concurrent code with the async/await syntax. The docs call asyncio often a perfect fit for IO-bound and high-level structured network code.

That last word matters. If your 300 ms is spent calculating, not waiting, a single waiter can't help: there is no idle time to overlap. This page follows the Python 3.14 documentation.

asyncio lets one thread overlap many waits; it speeds up waiting, not computing.

Which workload gains the most from asyncio?

  1. Resizing 10,000 images on one machine
  2. A single slow SQL query that takes 4 seconds
  3. A gateway that calls 5 internal services per request, each taking 80 ms

Five 80 ms waits per request, across many requests, are exactly the idle time one thread can overlap.

In your own words: what problem does asyncio solve, and what problem does it not solve?

Network-heavy code spends most of its time waiting for replies. asyncio lets one thread start many waits and switch between them at marked points, so the waits overlap instead of adding up. Only one piece of Python code runs at any moment, so this is concurrency, not parallelism. If the time goes into computing instead of waiting, there is nothing to overlap and asyncio does not help.

Why calling an async function runs nothing

Last part: asyncio overlaps waits at marked points. Still unsolved: what do those marked points look like in code?

A checkout handler "sends" a receipt email. Tests pass, no exception is raised, and zero receipts go out for 2 days.

A function written with async def is a coroutine function. Calling it is like writing an order ticket: nothing is cooked until the ticket reaches the kitchen.

  1. send_receipt(outbox, 42) builds a coroutine object and returns it. The body has not run.
  2. await send_receipt(outbox, 42) runs the body and gives you its return value.
  3. await is the marked point from Part 1: the only place your code may step aside while it waits.

Calling a coroutine function does not schedule it to run; it only returns a coroutine object. That is the receipt bug below: the coroutine is created and thrown away.

Python does leave a clue. If a coroutine is never awaited or scheduled as a task, asyncio emits a RuntimeWarning saying it was never awaited. It is a warning, not an error, so it scrolls past in logs. In CI, turn it into a failure with -W error::RuntimeWarning; a type checker such as mypy also flags an unused coroutine.

Old code marks coroutines with a decorator and yield from. The @asyncio.coroutine decorator for generator-based coroutines was removed in Python 3.11; use async def instead.

Calling an async function only builds a coroutine object; nothing runs until it is awaited or made into a task.

A handler calls audit_log.write(event), where write is async def, with no await. What ends up in the audit log, and what do you see?

Nothing is written. The call built a coroutine object and dropped it. The only sign is a RuntimeWarning that the coroutine was never awaited, printed once it is cleaned up.

The event loop: one thread taking turns

Last part: await is where code may step aside. Still unsolved: step aside to whom?

Two requests hit your service at once. Each needs one 50 ms database query. With one thread, how do both finish in about 50 ms instead of 100 ms?

The event loop is the waiter from Part 1. It holds a to-do list and runs one job at a time. A job it runs is a task: a coroutine the loop can pause and resume.

  1. The loop picks a ready task and runs it.
  2. The task starts a query and awaits the reply. It pauses and control returns to the loop.
  3. The loop runs the next ready task.
  4. When a reply arrives, the waiting task goes back on the ready list and resumes where it paused.

An event loop runs in one thread and executes all its callbacks and tasks in that thread. While a task is running in the event loop, no other task can run in the same thread. The waiter comparison stops working here: a real waiter can be interrupted, but the loop cannot take control back. A task gives it up only at an await that actually pauses.

One subtle rule decides whether an await really pauses. Awaiting a task hands control back to the event loop; awaiting a coroutine does not, by itself. await some_coroutine() runs it inline, like a normal function call. Control changes hands only when something inside it truly waits.

With wrap_in_task=False the log is a, a, a, b: B waits until A's loop is done. With True it is b, a, a, a, because each await on a task gives the loop a turn.

The loop runs one task at a time and only switches when a task pauses at an await that really waits.

Put one task's life in order.

  1. The loop picks the task from its ready list and runs it
  2. The task starts a network call and awaits the reply
  3. The task pauses and control returns to the loop
  4. The loop runs other ready tasks
  5. The reply arrives and the task resumes after its await

A task only gives up the thread at an await that waits; it only comes back when what it waited for is done.

Why two awaits in a row still take the sum

Last part: the loop switches tasks at real waits. Still unsolved: how do you get more than one task in the first place?

A new engineer converts a handler to async def and awaits its 1 s and 2 s calls one after the other. Latency stays at 3 s. "Async didn't help."

It didn't, because there was only one task. Each await finished before the next line started. To overlap, each wait must be its own task, created before you wait on any of them.

  1. asyncio.create_task() wraps a coroutine in a Task and schedules it to run soon.
  2. Create all the tasks first. Each starts running at the next await that pauses.
  3. Then wait for all of them. Total time is the slowest one, not the sum.

The modern way to do steps 1 and 3 together is a TaskGroup. asyncio.TaskGroup was added in Python 3.11. Its async with block waits for every task in the group to finish.

The tests time both: one_by_one([0.1, 0.2]) takes about 0.3 s, together([0.1, 0.2]) about 0.2 s.

Something has to start the loop. asyncio.run() creates the loop, runs the coroutine, finalizes async generators, closes the default executor and closes the loop. The docs say asyncio.run() should be the program's main entry point and ideally be called only once. asyncio.run() cannot be called while another event loop is running in the same thread. So calling it from inside any async def, such as an async FastAPI endpoint, raises RuntimeError; the tests check this. Await the coroutine instead.

Older code starts with loop = asyncio.get_event_loop() and loop.run_until_complete(main()). Since Python 3.14, asyncio.get_event_loop() raises RuntimeError when there is no current event loop. The Python 3.14 What's New says most get_event_loop() patterns can be replaced with asyncio.run(). Inside a coroutine, use asyncio.get_running_loop().

Concurrency comes from several tasks existing at once, all started by one asyncio.run() at the top; sequential awaits in one task add up.

A handler does user = await get_user() (100 ms) then orders = await get_orders() (150 ms). Neither needs the other's result. What is the smallest change that makes it about 150 ms?

  1. Swap the order so the slower call starts first
  2. Start both as tasks (a TaskGroup), then read both results after the block
  3. Wrap each call in asyncio.to_thread

Two tasks created before either is awaited both have a query in flight at once, so the total is the slower one, about 150 ms.

Explain to a teammate why converting a handler to async def did not make it faster, and what would.

async def only changes what calling the function returns: a coroutine object that runs when awaited. The event loop runs one task at a time and switches only when a task pauses at a real wait. Awaiting two coroutines one after another keeps them in one task, so the waits still add up. To overlap them, create each as its own task first, for example in a TaskGroup, and then wait for all of them; the total becomes the slowest call.

Calling 500 APIs at once without taking anything down

Last part: several tasks in a TaskGroup overlap their waits. Still unsolved: what if there are 500 of them, and one fails?

A nightly job enriches 500 merchant records from a partner API that allows 20 requests at a time. Fire all 500 at once and you get HTTP 429s, a pool of 500 open sockets, and one bad record that should stop the batch.

  1. A semaphore caps how many requests are in flight. An asyncio.Semaphore keeps a counter; acquire() waits while the counter is zero, until another task calls release().
  2. The preferred way to use a Semaphore is an async with statement. The slot is returned even if the request raises.
  3. A TaskGroup owns all 500 tasks. The first time a task in the group fails with an exception other than CancelledError, the group cancels the remaining tasks.
  4. After all tasks finish, the failures are combined into an ExceptionGroup (or BaseExceptionGroup) and raised.

What the tests prove: with limit=10, at most 10 requests are ever in flight; 50 calls of 50 ms take about 0.25 s (5 waves); results come back in input order; and when one call fails, the in-flight ones are cancelled and none completes.

Catch the group with except*. An except* clause matches by type against the exceptions inside the group; the unmatched ones propagate on in a new group. So except* ConnectionError as eg: handles every connection failure and lets a KeyError bug keep going up.

Production defaults: pick limit from the downstream's documented quota or connection pool size, not from your own CPU count. Share one HTTP client and its connection pool across all tasks; a new client per task defeats the cap.

"You need to call a partner API for 2 million rows. How do you do it with asyncio?" A strong answer does not create 2 million tasks at once. It caps in-flight work (a semaphore, or a fixed number of worker tasks reading from a queue, which Part 2 covers), sets a timeout per call, decides upfront whether one failure should stop the batch (TaskGroup) or be recorded and skipped, and makes each write idempotent so a retry is safe.

TaskGroup for fan-out, a semaphore for the cap, and one shared client: the batch runs at the downstream's pace and fails as a unit.

In fetch_all, request #7 raises ConnectionError while 9 others are in flight and 40 are waiting on the semaphore. What does the caller get?

  1. An ExceptionGroup containing the ConnectionError, after the other tasks are cancelled
  2. A list with 49 results and one exception in position 7
  3. A plain ConnectionError, while the other 49 keep running

The first non-cancellation failure makes the group cancel the rest; once everything has stopped, the failures are raised together as an ExceptionGroup.

Putting a deadline on anything you await

Last part: a TaskGroup with a cap. Still unsolved: a partner that accepts the connection and then never answers holds a slot forever.

Your recommendations call normally takes 40 ms. One day it hangs. With no deadline, every request waits on it, the semaphore fills, and your p99 goes from 120 ms to 30 s.

  1. Wrap the await in async with asyncio.timeout(seconds). asyncio.timeout() was added in Python 3.11, and timeout contexts can be safely nested.
  2. asyncio.timeout() cancels the current task when the delay runs out and turns the resulting CancelledError into a TimeoutError.
  3. That TimeoutError can only be caught outside the async with block.

Inside the block, a timeout arrives as a cancellation, the same mechanism a TaskGroup uses to stop siblings. The block's exit converts it. A try/except TimeoutError written inside the block catches nothing; the tests confirm it.

Use two layers. A per-call budget, as above, protects you from one slow dependency. A batch deadline, as in fan_out.py, bounds the whole job. Because the contexts nest, the inner budget and outer deadline both apply, and whichever is shorter wins.

You will also meet asyncio.wait_for(aw, timeout). asyncio.wait_for() cancels the awaitable on timeout and waits until it is actually cancelled, so the total wait can exceed the timeout. If the cancelled code runs slow cleanup, your "2 second" call can take longer. asyncio.timeout() behaves the same way: a test with a 50 ms timeout around code whose cleanup takes 200 ms returns after about 250 ms.

Older code catches asyncio.TimeoutError. Since Python 3.11, wait_for() raises the built-in TimeoutError instead of asyncio.TimeoutError. asyncio.TimeoutError is now a deprecated alias of the built-in TimeoutError. Old handlers still work; catch the built-in TimeoutError in new code.

Every await on something outside your process gets a deadline, and the TimeoutError is caught outside the timeout block.

You write async with asyncio.timeout(1): try: await call() except TimeoutError: return fallback. The call hangs. What happens?

The fallback never runs. Inside the block the timeout shows up as a CancelledError, which except TimeoutError does not match. The block's exit then turns it into a TimeoutError that escapes to your caller. Move the try outside the async with.

Using a library that has no async version

Last part: deadlines on every await. Still unsolved: some calls can't be awaited at all, like a sync-only SDK.

Your async service must call a vendor SDK that uses requests internally. Each call blocks for 200 ms. Five calls per request, and the whole service stalls for 1 s each time.

  1. Move the sync call off the loop's thread. asyncio.to_thread() runs a sync function in a separate thread and returns a coroutine you await for the result.
  2. to_thread() passes the call to the loop's default executor. Unless you set another, the default executor is a ThreadPoolExecutor created on first use.
  3. For CPU-heavy work, threads mostly don't help. Because of the GIL, to_thread() usually helps only IO-bound functions, unless the extension module releases the GIL or the Python implementation has none. For CPU-bound work, the docs say a process pool is in general preferable.

Five 200 ms calls take about 200 ms in total.

That default pool is small and shared. Since Python 3.13, a ThreadPoolExecutor with no max_workers uses at most min(32, (os.process_cpu_count() or 1) + 4) threads. Where os.process_cpu_count() returns 4, that is 8 threads for every to_thread call in the process. At 100 concurrent requests each making one 200 ms SDK call, 92 wait in the pool's queue, and latency climbs while CPU looks idle. Fix: give heavy sync dependencies their own sized ThreadPoolExecutor and call loop.run_in_executor(pool, fn), and put that queue wait under a timeout too.

A timeout around to_thread stops your wait, not the thread. A concurrent.futures call that is already running cannot be cancelled; cancel() returns False. The tests show a timed-out to_thread call still finishing its write 150 ms after the caller gave up, so sync work behind a timeout must be safe to complete late.

FastAPI builds this choice into its routing. FastAPI runs endpoints declared with plain def in an external thread pool that is then awaited. FastAPI's docs say to declare an endpoint with plain def when it uses a third-party library that does not support await. The trap is the mix: an async def endpoint that calls a sync library blocks the loop for every request.

"Your async service has to call a sync-only SDK. What are your options?" A strong answer lists them in order: an async client if one exists; to_thread or a dedicated, sized thread pool for IO-bound sync calls; a process pool for CPU-bound work; moving the work to a background worker if it is slow. It names each one's cost.

Sync IO goes to a thread pool you have sized, and CPU work goes to processes; a timeout stops your wait, not the thread.

You are writing a new async endpoint that fans out to 30 services, one of which only has a sync SDK. Walk through how you'd write it.

I create one task per service in a TaskGroup so the calls overlap, with a semaphore if the downstreams have a concurrency limit. Each call gets its own asyncio.timeout budget, and the TaskGroup sits under an overall deadline; I catch TimeoutError outside the timeout blocks. The sync SDK call goes through to_thread, or a dedicated sized thread pool if it is called heavily, because the default pool is small and shared by the whole process. Nothing CPU-heavy runs on the loop; that would go to a process pool.

The one slow line that freezes every request

Last part: sync calls go to threads. Still unsolved: how do you find the one you missed?

An async API serves 2,000 requests per second at 15 ms p50. After a release, p99 jumps to 900 ms on every endpoint, including /health, while CPU sits at 20%. The diff added one call to a sync PDF library in one endpoint.

This is the first thing that breaks at 10× load. The docs' own example: a CPU-heavy function that takes 1 second delays every other task and all IO by 1 second. A blocking IO call does the same. While one task runs without awaiting, the loop can't answer health checks, read sockets or fire timeouts. Even your asyncio.timeout can't fire until the blocking call returns.

The heartbeat should tick every 10 ms. Next to handler_blocking, its worst delay is over 250 ms. Next to handler_fixed, it stays under 100 ms.

Common hidden blockers: requests, sync database drivers, time.sleep, reading big files, json.loads on a 50 MB body, bcrypt, and logging handlers. The docs warn that network logging can block the event loop and suggest a separate thread for log handling.

How you detect it:

  1. Debug mode can be turned on with PYTHONASYNCIODEBUG=1, Python Development Mode, asyncio.run(..., debug=True) or loop.set_debug().

The fix: an async library, to_thread or a sized pool for sync IO, a process pool for CPU work. For a long pure-Python loop you must keep on the loop, asyncio.sleep() always suspends the current task, and sleep(0) is an optimized way to let other tasks run. Calling it every few thousand iterations lets other tasks in.

Background tasks that vanish or fail silently

Last part: a blocked loop stalls everything. Still unsolved: work that was started and then quietly lost.

After each payment, a handler fires asyncio.create_task(update_ledger(p)) and returns. About 1 in 10,000 ledger updates never happens. Nothing in the error logs.

Two separate problems cause this.

  1. The task can be collected. The event loop keeps only weak references to tasks, so a task nothing else references can be garbage collected before it is done.
  2. Its error goes nowhere. If nothing awaits a task or reads its result, its exception is never retrieved; asyncio logs "Task exception was never retrieved" when it is garbage collected. That line arrives late, under the asyncio logger, often filtered out.

The docs' fix for fire-and-forget: keep each task in a set and remove it with add_done_callback when it finishes. The version below also reads the exception in the callback, which counts as retrieving it, and logs it with the task's name right away.

Even with a strong reference, an in-process background task dies with the process. A deploy or an out-of-memory kill drops whatever is in the set. Anything that must happen, such as a ledger write, belongs in a durable queue or an outbox table, not in create_task. Use spawn for work you can afford to lose, like cache warming, and on shutdown, wait for or cancel what is in _running.

If the work belongs to a request or a job, prefer a TaskGroup: it holds the references, waits, and raises the errors for you.

A bare create_task can be collected and its failure goes unseen; keep a reference, log failures in a done callback, and use a durable queue for work that must happen.

Which change fixes both the vanishing task and the silent failure?

  1. Assign the task to a local variable: t = asyncio.create_task(...)
  2. Wrap the body of update_ledger in try/except and log
  3. Keep it in a module-level set and use a done callback that removes it and logs any exception

The set holds a strong reference until the task finishes; the callback drops it and reads the exception, so failures show up immediately with the task's name.

Why gather() keeps running after it fails

Last part: tasks with no owner get lost. Still unsolved: the older fan-out tool that half-owns its tasks.

A checkout calls asyncio.gather(charge_card(), reserve_stock()). The card charge fails and the handler returns an error. 100 ms later, the stock reservation completes anyway, for an order that doesn't exist.

You will see gather() in most existing code. gather() runs its awaitables concurrently and returns results in the order they were passed. If any argument to gather() is a coroutine, gather() schedules it as a Task automatically. Its failure rules are the problem:

  1. With the default return_exceptions=False, the first exception goes straight to the caller, and the other awaitables are not cancelled; they keep running.
  2. With return_exceptions=True, exceptions are returned in the result list like normal results. You must check each item.
  3. If gather() itself is cancelled, all its unfinished awaitables are cancelled too.

The docs say TaskGroup gives stronger safety guarantees than gather(): when a task fails, TaskGroup cancels the rest and gather() does not. Keep gather(..., return_exceptions=True) for one case: you want every result, successes and failures, and no failure should stop the others.

gather() stops waiting on the first error but leaves the other tasks running; TaskGroup cancels them.

You send a notification through 3 channels (email, SMS, push). A failure on one should not stop the others, and you need to know which failed. Which fits?

  1. A TaskGroup, catching the ExceptionGroup
  2. gather(..., return_exceptions=True), then check each result
  3. gather() with the default settings, in a try/except

Independent side effects where every outcome matters is the one job gather(return_exceptions=True) does well.

How one broad except breaks every timeout

Last part: TaskGroup stops siblings by cancelling them. Still unsolved: what if the sibling refuses?

A queue poller has except BaseException: log and retry so it "never crashes". Its 5 s timeout never fires, deploys hang for the full grace period, and a TaskGroup around it waits forever.

Timeouts and TaskGroup both stop work the same way: they cancel the task, which raises CancelledError at its current await. TaskGroup and asyncio.timeout() are built on cancellation and can misbehave if a coroutine swallows CancelledError.

  1. Since Python 3.8, asyncio.CancelledError inherits from BaseException, not Exception. So except Exception lets it pass. That is safe.
  2. except BaseException, a bare except:, or except asyncio.CancelledError without re-raising all swallow it.
  3. The docs recommend try/finally for cleanup, and if you catch CancelledError, re-raising it once cleanup is done.

Under a 50 ms timeout, swallowing_worker(6, errors) runs all 6 rounds, about 300 ms, and raises no TimeoutError at all: the block exits as if it succeeded. good_worker logs "closed connection" and the TimeoutError arrives on time.

Detecting it: grep for except BaseException, bare except: and except asyncio.CancelledError without a raise; Ruff's rule BLE001 (blind-except) flags except BaseException and except Exception clauses, unless they re-raise or log the exception with exc_info. At runtime, the symptom is shutdowns that hit the kill timeout and timeouts that never show in metrics.

"How does cancellation work in asyncio, and what can break it?" A strong answer: cancel() raises CancelledError at the task's next await; it is a BaseException so normal handlers skip it; timeouts and TaskGroup depend on it arriving; swallowing it silently breaks both; cleanup goes in finally; and a cancel can't interrupt sync code that never awaits. Shielding and uncancel() are Part 2.

Never swallow CancelledError: clean up in finally and let it propagate, or timeouts and TaskGroups stop working.

Which handler inside a worker loop is safe under asyncio.timeout?

  1. except Exception: log.exception("poll failed")
  2. A bare except: log.exception("poll failed")
  3. except asyncio.CancelledError: log.info("cancelled") then continue the loop

CancelledError is a BaseException, so except Exception lets it through and the timeout works.

Name the four production failures from this rung and one detection signal for each.

A fire-and-forget task can be collected or fail with no visible error; late "Task exception was never retrieved" logs are the sign, and a done callback that logs fixes it. gather() raises the first error but leaves siblings running, so side effects happen after the request failed; TaskGroup fixes it. A handler that swallows CancelledError makes timeouts never raise and shutdowns hang; a lint rule for blind excepts and shutdown timeouts in metrics reveal it.

Interview drill: three asyncio design prompts

Last part: when to pick asyncio. Still unsolved: defending it out loud, with the trade-offs.

You get 10 minutes per prompt. For each, commit to your answer before opening the reference.

A good answer to each prompt names the concurrency model, where the limits sit, what happens when one piece fails, and what you give up.

Prompt 1. A product page needs data from 6 services (price, stock, reviews, offers, delivery ETA, recommendations). p99 budget: 250 ms. Reviews and recommendations are optional. Design the handler.

Required calls (price, stock, offers, ETA) run as tasks in one TaskGroup under an overall timeout of about 200 ms: if one fails, the page can't render, so cancelling the rest is right. Optional calls each get their own short budget and a fallback (empty reviews), so they can never fail the page. Every downstream has a semaphore sized to its quota. Any sync SDK goes to a sized thread pool, not the small default one. Trade-off: the page sometimes renders without optional sections, in exchange for a hard latency ceiling.

Prompt 2. After an order is placed, the service must send a confirmation email and update a search index. Today it uses asyncio.create_task and returns 201. Emails sometimes go missing. What's wrong and what do you change?

Two issues. The bare tasks can be garbage collected and their exceptions are never retrieved, so failures are invisible. And even with a reference held and a done callback that logs, the work dies with the process on a deploy. Email is a must-happen side effect, so write an outbox row in the same transaction as the order and have a worker send it with retries. The index update can stay in-process with a logged fire-and-forget. Trade-off: an outbox and a worker to run, in exchange for at-least-once delivery.

Prompt 3. An async service's shutdowns take the full 30 s grace period and in-flight requests sometimes hang past their timeouts. p99 on all endpoints spikes every few minutes. How do you investigate?

Two suspects share one symptom: something is not giving control back. For the spikes, measure event-loop lag and run a staging instance in debug mode to log slow callbacks with task names; look for sync IO, large JSON parsing or logging handlers on the loop. For the hangs, search for handlers that swallow CancelledError (bare except, except BaseException, except CancelledError without raise); those make timeouts and shutdown cancellation silently fail. Also check the thread pools: sync calls already running in threads cannot be cancelled, so a stuck one holds up shutdown. Fix: move blocking work off the loop with its own timeouts, re-raise cancellations, clean up in finally.

Every async design answer names the cap, the deadline, what happens on failure, and what blocks the loop.

You are asked "Why did you use asyncio here and not threads?" Give a 4-sentence answer for the product-page handler in Prompt 1.

The handler spends almost all its time waiting on 6 network calls, which is the case asyncio is built for: one thread overlaps all the waits. A TaskGroup under a deadline gives me cancellation of required calls when one fails, and per-call budgets let optional calls degrade instead of failing the page. Threads would work at low load, but each in-flight call holds a thread, and a call already running in a thread can't be cancelled. The cost is that every library on the path must be async or pushed to a sized pool, and we monitor loop lag to catch blocking calls.
