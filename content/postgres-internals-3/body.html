Where a deleted row goes: nowhere, until something cleans it

A wallets table has 2 million rows, and each balance changes about 50 times a day. That is 100 million old row versions left behind every day. Nothing in your app deletes them.

Part 2 showed why they stay. An UPDATE or DELETE does not remove the old row version immediately, because other transactions may still see it; once no transaction needs it, VACUUM reclaims its space for new rows.

Think of a busy restaurant. Guests who leave are old row versions. The table stays taken until a waiter clears it. The waiter (VACUUM) may only clear tables whose whole party has left: if anyone in the party might come back for their coat (an open snapshot), the table waits. Cleared tables go on the host's list of free tables, and new guests are seated there. The restaurant never gets smaller.

The docs give VACUUM four jobs: recover or reuse space taken by updated or deleted rows, update planner statistics, update the visibility map, and protect against transaction ID and multixact ID wraparound. This page covers each of them except statistics, which belong to part 5 of the series.

  1. Clear dead row versions so their space can be reused (parts 2 to 4).
  2. Run often enough on its own: autovacuum (parts 6 and 7).
  3. Deal with space that is free but never given back (parts 8 and 9).
  4. Stop transaction IDs from running out (parts 10 and 11).

Standard VACUUM removes dead row versions from tables and indexes and marks the space reusable, but returns it to the operating system only when whole pages at the end of the table are free and an exclusive lock is easy to get. That single sentence explains most "why is my table still so big" questions.

Every UPDATE and DELETE leaves an old row version behind, and VACUUM is the only thing that turns that space back into room for new rows.

A nightly job deletes 30 percent of audit_log, then VACUUM runs. The next morning the table file is the same size. What happened?

  1. VACUUM failed and must be run again
  2. The space is now free for new rows inside the file, but it was not given back to the operating system
  3. Deleted rows are kept for 24 hours before VACUUM can touch them

Standard VACUUM makes the space reusable inside the table. Only empty pages at the very end can be cut off the file.

In your own words: why does PostgreSQL need VACUUM at all, and what does it give back?

Under MVCC an UPDATE writes a new version and a DELETE only marks the old one, so dead versions pile up in the table and its indexes. VACUUM removes the ones no open snapshot can still need and marks their space as free for new rows in the same table. It usually does not shrink the file. It also has other jobs, the most important being the protection against transaction ID wraparound.

What one VACUUM run does, pass by pass

Last part: VACUUM turns dead versions into reusable space. Still unsolved: why does it take so long on a big table, and why does it touch the indexes?

VACUUM on a 300-gigabyte orders table has been in the "vacuuming indexes" phase for forty minutes. The table has 9 indexes. What is it doing in there?

The trouble is that indexes point at row slots. Part 1 called a slot a line pointer: each index entry stores a page number and a line pointer number. If VACUUM freed a slot while an index entry still pointed at it, a new row could move into the slot and the old index entry would lead to the wrong row. So cleanup has to happen in a careful order.

  1. In phase one, VACUUM scans the table's pages, pruning and freezing rows and collecting the addresses of dead row versions. Pruning removes a dead version's data but leaves its slot marked dead: a dead line pointer.
  2. In phase two it deletes the index entries that point at those dead addresses. It can run several times in one VACUUM if maintenance_work_mem (or autovacuum_work_mem) is too small to hold all the dead addresses found.
  3. In phase three it revisits those pages and frees the dead slots for future rows.
  4. At the end it may truncate empty pages at the end of the table, then updates the free space map and the table's statistics in pg_class.

Back to the forty minutes: phase two has to visit all 9 indexes, so a table with many indexes can spend much of its VACUUM time there. By default VACUUM may skip index vacuuming when the table has very few dead rows, because scanning every index would cost far more than it saves.

VACUUM prunes the table, then cleans every index, then frees the dead slots; the index pass is why indexes dominate the cost.

Put one VACUUM run on a table with indexes in order.

  1. Scan pages: prune dead versions and collect their addresses
  2. Delete index entries that point at the dead addresses
  3. Mark the dead slots as unused
  4. Truncate empty pages at the end and update the free space map

Slots can only be freed after no index points at them, so the index pass sits between pruning and freeing.

Two small maps that make VACUUM and index-only scans cheap

Last part: VACUUM frees slots inside pages. Still unsolved: how does an INSERT find those free slots, and how does the next VACUUM avoid rereading a huge table?

A 300-gigabyte table where only the last day's 2 gigabytes of rows change. Reading the whole table on every VACUUM would take hours each time.

Two side files answer both questions. Think of them as the restaurant host's lists: one of tables with free seats, one of tables that need no attention.

  1. Every table and index, except hash indexes, has a free space map stored in a separate fork with an _fsm suffix; its bottom level keeps one byte per page for the space available on it. The free space map exists to find a page with enough room for a new row quickly, or to decide that the table must grow by a page.
  2. Every table has a visibility map holding two bits per page: all-visible, meaning nothing on the page needs vacuuming, and all-frozen, meaning every row on the page is frozen. Freezing is part 10's topic.
  3. Visibility map bits are set by vacuum and cleared by any change to the page. Before PostgreSQL 19, the only other way to mark pages all-visible was COPY ... FREEZE.
  4. VACUUM uses the all-visible bits to skip pages on its next run, and an index-only scan checks them to skip reading the table page for rows it already knows are visible.

So the big table is cheap to vacuum if its old pages stay all-visible: VACUUM reads mostly the part that changed. The map is the reason "VACUUM reads the whole table" is usually wrong.

The free space map tells writers where room is; the visibility map tells VACUUM and index-only scans which pages need no work.

An events table only receives INSERTs. Its index-only scans still read many table pages ("Heap Fetches" is high). Which is the most likely cause?

  1. No VACUUM has run since the latest inserts, so those pages are not marked all-visible yet
  2. Index-only scans don't work on tables that receive inserts
  3. The free space map is out of date

Only vacuum sets the all-visible bit. New pages stay unmarked until a VACUUM visits them, so index-only scans must check the table for those rows.

HOT: updates that leave the indexes alone

Last part: the maps that make VACUUM skip work. Still unsolved: can an UPDATE avoid creating index work in the first place?

The wallets table has 6 indexes. A balance update changes one integer, yet the database writes 7 new entries: one row version and one entry in each index.

When an UPDATE can't use the HOT optimisation, every index on the table needs a new entry pointing at the new version, including indexes whose columns did not change. That is the cost above. PostgreSQL has a way around it, called a HOT update.

  1. An update can be HOT only when it changes no column used by the table's indexes (summarizing indexes such as BRIN don't count) and the page holding the old row has enough free space for the new one.
  2. A HOT update needs no new index entries, although summarizing indexes may still need updating. The index keeps pointing at the old slot, and the old version points forward to the new one.
  3. After repeated HOT updates, versions between the oldest and newest can be removed during normal work, including SELECTs, without waiting for VACUUM; the original slot becomes a redirect to the oldest version still visible. This is pruning on access.
  4. If a page may hold removable versions, on-access pruning is attempted when an earlier UPDATE found no room on it, or when its free space falls below the table's fillfactor target, with a floor of 10 percent of the page.

If an UPDATE changes no indexed column and fits on the same page, it skips every index, and its old versions can be cleaned during normal reads.

A sessions table has a B-tree index on last_seen_at, and every request runs UPDATE sessions SET last_seen_at = now(). Predict the share of HOT updates, and what each update costs.

Zero HOT updates. Each update changes an indexed column, so it can never be HOT, and it adds a new entry to every index on the table, not only to last_seen_at's index. Dropping that index (or not updating the column on every request) brings HOT back.

Explain to a teammate why updating one non-indexed column can be cheap, while updating an indexed timestamp makes the table and all its indexes grow.

An update that changes no indexed column and fits on the same page is HOT: indexes keep pointing at the old slot and follow a chain on the page, and old versions can be pruned during normal reads. An update that changes an indexed column needs a new entry in every index. Those dead index entries can only be removed by VACUUM's index pass, after which the dead slots are freed. So the table and all its indexes collect garbage between VACUUM runs.

Measuring HOT updates and choosing a fillfactor

Last part: HOT updates skip the indexes. Still unsolved: how do you know whether your updates are HOT, and what do you change when they aren't?

Write latency on orders doubled after a release. Nothing in the query plans changed. You suspect updates stopped being HOT.

The statistics view counts three kinds of update for every table:

  1. In pg_stat_user_tables, n_tup_upd counts all updated rows, n_tup_hot_upd the HOT ones, and n_tup_newpage_upd the ones whose new version went to a different page, which are never HOT.
  2. Many updates going to a new page means pages are full. Few new-page updates but no HOT means an indexed column is changing.
  3. fillfactor is a percentage from 10 to 100, with 100 (full packing) as the default; a lower value leaves room on each page for updated rows and makes HOT updates more likely. fillfactor was introduced in part 1; here is what to do with it.
  4. ALTER TABLE ... SET (fillfactor = ...) does not rewrite existing pages; a rewrite such as VACUUM FULL or CLUSTER is needed for the full effect, and the command takes a SHARE UPDATE EXCLUSIVE lock.
SELECT relname, n_tup_upd, n_tup_hot_upd, n_tup_newpage_upd,
       round(100.0 * n_tup_hot_upd / nullif(n_tup_upd, 0), 1) AS hot_pct
FROM pg_stat_user_tables
ORDER BY n_tup_upd DESC
LIMIT 20;

The script below turns one row of that result into a diagnosis. Its tests use figures from a test run: small transactions on a table at fillfactor 100 were 99 percent HOT, because pruning kept making room, while adding an index on the updated column dropped HOT to zero.

The release that slowed orders added an index on updated_at for a dashboard. Every UPDATE sets that column, so every UPDATE stopped being HOT and started writing to every index. Check the HOT ratio before and after any migration that adds an index to a busy table.

"This table gets 5,000 updates a second. How do you keep it cheap?" A strong answer: keep the updated columns out of indexes, keep the row narrow, and lower fillfactor on the hot table, then measure n_tup_hot_upd against n_tup_upd. It names the cost: lower fillfactor means more pages for the same rows, so scans read more.

Compare n_tup_hot_upd with n_tup_upd: new-page updates mean lower the fillfactor; no HOT with room on the page means an indexed column is changing.

A table shows n_tup_upd 1,000,000, n_tup_hot_upd 120,000 and n_tup_newpage_upd 850,000. No indexed column changes. What do you try first?

  1. Drop indexes until updates become HOT
  2. Raise fillfactor to pack pages tighter
  3. Lower fillfactor, then rewrite the table so existing pages get the free room

85 percent of updates moved to a new page: the old page had no room. A lower fillfactor reserves room, and a rewrite applies it to existing pages.

When autovacuum decides a table needs cleaning

Last part: measuring HOT. Still unsolved: who runs VACUUM, and when?

A 50-million-row payments table collects dead rows all day, but autovacuum seems to visit it only every few days. Is autovacuum broken?

Autovacuum is a launcher plus worker processes. The launcher tries to start one worker in each database every autovacuum_naptime seconds, and at most autovacuum_max_workers workers run at once. autovacuum_naptime is one minute and autovacuum_max_workers is 3 out of the box.

  1. A table is vacuumed when the rows updated or deleted since its last VACUUM exceed min(max threshold, base threshold + scale factor × pg_class.reltuples).
  2. The base threshold (autovacuum_vacuum_threshold) is 50 rows, the scale factor (autovacuum_vacuum_scale_factor) is 0.2, and the cap (autovacuum_vacuum_max_threshold) is 100,000,000 rows. The cap is new in PostgreSQL 18.
  3. Inserts have their own trigger: 1000 rows plus 0.2 × reltuples × the fraction of pages not yet all-frozen. That lets append-only tables get their visibility map set and rows frozen.
  4. Separately, any table whose relfrozenxid is older than autovacuum_freeze_max_age is always vacuumed. Part 10 explains that one.

So the payments table waits for 20 percent of 50 million rows, about 10 million dead rows, before autovacuum touches it. Autovacuum isn't broken; the scale factor is too big for a large, busy table. The code below does the arithmetic, and its tests pin the numbers on this page.

Autovacuum waits for a fixed share of the table to change, so the bigger the table, the more dead rows it collects before cleanup starts.

A 2-billion-row events_archive table gets occasional deletes. With settings out of the box, how many dead rows trigger autovacuum: 400 million, or something else?

100 million. The formula gives 50 + 0.2 × 2 billion, about 400 million, but PostgreSQL 18 caps it at autovacuum_vacuum_max_threshold. Before version 18 there was no cap, so such a table would wait for about 400 million dead rows.

Tuning autovacuum for hot tables, and its speed limit

Last part: the trigger formula. Still unsolved: how do you make it react sooner for one table, and why is it slow once it starts?

After you lower the trigger for payments, autovacuum starts often but each run takes three hours, and dead rows keep growing. Adding workers doesn't help.

The thresholds, scale factors and cost settings can be overridden per table with storage parameters, and a per-table value wins over the global one. Tune the few big, busy tables; leave the rest alone.

ALTER TABLE payments SET (
  autovacuum_vacuum_scale_factor = 0.01,
  autovacuum_vacuum_threshold    = 1000
);

Now the speed limit. Autovacuum is throttled on purpose, so it doesn't swamp the disk:

  1. VACUUM keeps a running cost count of its I/O, and when it reaches vacuum_cost_limit it sleeps for vacuum_cost_delay, then resets and carries on.
  2. Each page costs 1 if found in shared buffers, 2 if read from disk and 20 more if vacuum dirties it, and vacuum_cost_limit is 200.
  3. autovacuum_vacuum_cost_delay is 2 milliseconds, and autovacuum_vacuum_cost_limit is -1, meaning it uses vacuum_cost_limit. For manual VACUUM, vacuum_cost_delay is 0, so throttling is off.
  4. The autovacuum cost limit is shared out among the running workers, so their total does not exceed it; workers on tables with their own cost settings are left out of this sharing.

The arithmetic in autovac.py's tests: a page read from disk and dirtied costs 22, so 200 per 2-millisecond sleep allows at most about 4,500 pages a second, for all workers together. A third worker gets a third of the same budget. That is why adding workers didn't help.

"Autovacuum can't keep up. Do you add workers?" A strong answer: not first. Workers share one cost budget, so more workers mean slower each. Raise autovacuum_vacuum_cost_limit (or lower the delay) globally or for the lagging table, check disk headroom, and confirm nothing holds back the xmin horizon (part 2). Add workers when many tables need vacuum at once, not when one table is slow.

maintenance_work_mem is 64 MB, and autovacuum can use up to autovacuum_max_workers times that much. Too little memory forces extra index passes (part 2). log_autovacuum_min_duration logs every autovacuum action that runs at least that long; it is 10 minutes out of the box. Lowering it shows you what each run did. Autovacuum holds a SHARE UPDATE EXCLUSIVE lock on the table, and a session asking for a conflicting lock normally interrupts it.

Tune triggers per table, and when vacuum is slow, raise its shared cost budget rather than adding workers.

You raise autovacuum_max_workers from 3 to 6 and keep the cost settings. Two big tables are being vacuumed. What happens to their speed?

  1. Each doubles, since there are twice as many workers
  2. Roughly nothing: the two workers still share the same cost budget
  3. Both slow down, because 6 workers now split the budget even when idle

The cost limit is divided among running workers. Two running workers split it the same way whether the maximum is 3 or 6.

Explain why a large, busy table can collect millions of dead rows even with autovacuum on, and the two settings you would change.

Autovacuum starts when dead rows exceed 50 plus 20 percent of the table, so a 50-million-row table waits for about 10 million. Lower the scale factor for that table so it starts sooner. Once running, vacuum is throttled by a cost budget shared by all workers, so on a big table each run can take hours. Raise the cost limit, globally or for that table, rather than adding workers.

Bloat: measuring space you pay for but don't use

Last part: tuning autovacuum. Still unsolved: when cleanup falls behind anyway, how much space is wasted, and where?

At ten times the write rate, dead rows arrive faster than the throttled worker removes them. The table grows from 40 to 120 gigabytes while holding the same 20 million live rows, and its indexes triple too.

Bloat comes in two kinds:

  1. Table bloat: dead versions not yet cleaned up, plus free space inside pages. Free space that new rows keep reusing is healthy; free space nothing will reuse is waste.
  2. Index bloat: completely empty B-tree pages are reused, but a page with only a few keys left stays allocated, so deleting most but not all keys in each range wastes space and calls for periodic reindexing.
  3. Why the file doesn't shrink: as the first part of this page said, only empty pages at the end can be cut off. That truncation is controlled by vacuum_truncate, on out of the box, and needs an ACCESS EXCLUSIVE lock on the table.

To measure it, use the pgstattuple extension. pgstattuple reads the whole table and reports its length, dead tuple percentage and free space; pgstattuple_approx is faster because it skips pages the visibility map marks all-visible. pgstatindex reports a B-tree's average leaf density and leaf fragmentation. By default only members of the pg_stat_scan_tables role (and superusers) may run these functions.

CREATE EXTENSION IF NOT EXISTS pgstattuple;
SELECT table_len, dead_tuple_percent, free_percent
FROM pgstattuple_approx('orders');
SELECT avg_leaf_density, leaf_fragmentation
FROM pgstatindex('orders_pkey');

How to see it coming without scanning: alert on n_dead_tup rising while last_autovacuum gets older (part 6's view), and on table size per live row. The health.py function from part 5 reads a pgstattuple row: many dead rows means find what blocks VACUUM; mostly empty pages that won't refill means a rewrite.

Running pgstattuple on a 500-gigabyte table during peak hours reads every page of it. Use pgstattuple_approx, or run the exact one on a replica.

Dead rows are VACUUM's job; empty space that will never be reused, in the table or its B-trees, needs a rewrite.

pgstattuple on sessions shows dead_tuple_percent 0.5 and free_percent 70. The app keeps inserting new sessions all day. What do you do?

  1. Run VACUUM again
  2. Probably nothing: steady inserts will reuse the free space
  3. Rewrite it now with VACUUM FULL

Free space is only waste if nothing will reuse it. A table that keeps receiving rows will fill it again; a rewrite would buy a few hours.

Getting disk space back without taking the table offline

Last part: measuring bloat. Still unsolved: when space really must come back, which tool, and what does it lock?

After archiving two years of data, orders is 400 gigabytes with 70 percent free space, and it won't refill. The disk is 85 percent full. The app can't stop for hours.

  1. VACUUM FULL, CLUSTER and table-rewriting forms of ALTER TABLE write a complete new copy of the table and its indexes, hold an ACCESS EXCLUSIVE lock, and temporarily need extra disk about the size of the table. ACCESS EXCLUSIVE conflicts with every lock mode, including the one a plain SELECT takes. So the table is unreadable for the whole run.
  2. pg_repack rebuilds the table online: it holds an ACCESS EXCLUSIVE lock only briefly at the start and end, and a SHARE UPDATE EXCLUSIVE lock during the copy, so reads and writes continue.
  3. pg_repack needs a primary key or a unique index on NOT NULL columns, free disk of about twice the size of the table and its indexes, and no DDL on the table while it runs.
  4. For bloated indexes alone, REINDEX CONCURRENTLY rebuilds them while holding only a SHARE UPDATE EXCLUSIVE lock.
  5. If a table's whole contents are deleted on a schedule, TRUNCATE frees the space at once with no VACUUM needed, at the cost of not following strict MVCC rules. Dropping old partitions works the same way for time-based data.

For the 400-gigabyte table: VACUUM FULL is out (hours of no access, and a full extra copy's worth of disk you may not have). pg_repack works if you can free about twice the size of the live data plus indexes, and pause migrations. If that disk isn't available, repack the largest indexes first with REINDEX CONCURRENTLY and plan partitioning so the next archive is a partition drop.

pg_repack still takes ACCESS EXCLUSIVE twice. If a long transaction holds a lock on the table, pg_repack has to wait for it. pg_repack's --wait-timeout (60 seconds by default) limits how long it waits for that lock before it cancels conflicting queries. Run it in a quiet hour, with long transactions ended first.

"The table is 80 percent empty. How do you shrink it in production?" A strong answer first asks whether it will refill (then do nothing). If not: pg_repack or partition and drop, never VACUUM FULL on a live table. It names the disk headroom needed, the brief exclusive locks at start and end, and the need for a primary key.

VACUUM FULL blocks even reads for the whole rewrite; pg_repack and REINDEX CONCURRENTLY rebuild online but need spare disk and a quiet moment for their short locks.

Why can't you run VACUUM FULL on orders at noon even if the API only reads from it?

  1. You can: VACUUM FULL only blocks writes
  2. VACUUM FULL can't run while autovacuum is enabled
  3. Its ACCESS EXCLUSIVE lock conflicts with the lock every SELECT takes, so reads wait until it finishes

ACCESS EXCLUSIVE conflicts with all lock modes. Every SELECT on the table waits for the whole rewrite.

Freezing: the deadline every table has

Last part: getting space back. Still unsolved: part 2 said transaction IDs wrap around. What stops that from corrupting old rows?

A payments platform uses 50 million transaction IDs a day. Rows written in January are still read in December. After a few billion IDs, how does PostgreSQL still know those January rows are in the past?

Transaction IDs are 32 bits and compared modulo 2^32, so every ID has about two billion older and two billion newer IDs; a row version left untouched for more than two billion transactions would suddenly look like it is in the future, and become invisible. To prevent that, every table in every database must be vacuumed at least once every two billion transactions.

  1. VACUUM freezes old rows: a frozen row counts as older than every normal transaction ID, so it stays visible however many transactions pass; since version 9.4 freezing sets a flag bit and keeps the original xmin. That is freezing.
  2. vacuum_freeze_min_age, 50 million transactions out of the box, is the cutoff age at which an XID makes VACUUM trigger freezing of the page holding it.
  3. Normal VACUUMs skip all-visible pages, so they can leave old rows unfrozen; when a table's relfrozenxid reaches vacuum_freeze_table_age (150 million) VACUUM runs aggressively, visiting every page that might hold unfrozen IDs.
  4. pg_class.relfrozenxid records the oldest unfrozen XID left in a table after the last VACUUM that advanced it, and pg_database.datfrozenxid is the minimum of those values in the database.
  5. Once relfrozenxid is older than autovacuum_freeze_max_age, 200 million out of the box, a VACUUM is forced on the table even if autovacuum is turned off. This anti-wraparound autovacuum shows "(to prevent wraparound)" in pg_stat_activity and, unlike a normal one, is not cancelled when another session asks for a conflicting lock.

Since PostgreSQL 18, normal vacuums may also freeze some all-visible pages early, spreading out the work of later aggressive vacuums; vacuum_max_eager_freeze_failure_rate (0.03) caps wasted attempts. Watch the number that matters with the query below; the source computes the limit as the oldest datfrozenxid plus 2^31 − 1 and counts the warning and refusal points back from there.

SELECT datname, age(datfrozenxid) AS xid_age,
       mxid_age(datminmxid)      AS mxid_age
FROM pg_database
ORDER BY xid_age DESC;

When several transactions lock one row, PostgreSQL stores a multixact ID in xmax; multixact IDs are also 32-bit, have their own forced-vacuum age, autovacuum_multixact_freeze_max_age (400 million), and running out blocks only writes that need a new multixact. Watch mxid_age(datminmxid) too.

VACUUM must freeze every old row before its table's oldest XID gets about two billion transactions old, and PostgreSQL forces that work long before the limit.

You run ALTER TABLE ledger ADD COLUMN note text and it hangs. pg_stat_activity shows autovacuum: VACUUM public.ledger (to prevent wraparound). What is going on?

  1. The anti-wraparound autovacuum holds a lock ALTER TABLE needs, and it won't step aside the way a normal autovacuum would
  2. The database has stopped accepting writes
  3. ALTER TABLE will cancel the autovacuum in a few seconds

A normal autovacuum gives way when someone needs a conflicting lock. An anti-wraparound one doesn't, so the DDL waits until it finishes.

When the counter runs out: two real outages

Last part: freezing and the forced autovacuum. Still unsolved: what if even that can't finish?

Write traffic grows ten times after a launch. The wraparound.py tests show the gap: from an age of 150 million, at 50 million IDs a day writes stop in about forty days; at 500 million a day, in four.

Near the limit, PostgreSQL escalates:

  1. Past vacuum_failsafe_age, 1.6 billion out of the box, VACUUM stops applying cost-based delays, skips non-essential work such as index vacuuming, and stops limiting how much of shared buffers it uses.
  2. Warnings start when the oldest XIDs are 40 million transactions from wraparound; with fewer than 3 million left, new XIDs are refused: running transactions continue, only read-only transactions can start, and VACUUM still runs.
  3. The documented recovery: resolve old prepared transactions, end long-running transactions, drop stale replication slots, then VACUUM the database; not VACUUM FULL, which needs an XID, and not VACUUM FREEZE, which does more work than needed. The docs say that in typical scenarios, stopping the server for single-user mode is no longer needed and should be avoided.

On 20 July 2015 Sentry was down for most of the US working day after its write-heavy PostgreSQL, with very large tables, hit wraparound protection and stopped accepting writes; it recovered once Sentry truncated the one huge table whose autovacuum hadn't finished. Afterwards Sentry doubled autovacuum workers from 3 to 6, set autovacuum_freeze_max_age to 500 million, autovacuum_naptime to 15 seconds and autovacuum_vacuum_cost_delay to 0.

From 05:35 UTC on 4 February to 22:09 UTC on 5 February 2019, Mailchimp's Mandrill sent only 80 percent of queued email because one hot shard of its PostgreSQL key-value store hit the XID limit; its autovacuum had likely fallen behind under the extra writes. Their highest estimate for the vacuum was 40 days, so they truncated two large tables, after which it finished in about an hour; XID wraparound alerting was added the same day.

The pattern in both: writes grew, autovacuum's throughput didn't, and no alert watched XID age. Alert when age(datfrozenxid) stays above autovacuum_freeze_max_age (forced vacuums aren't finishing), and on how fast it climbs.

"Your database says it is not accepting commands to avoid wraparound. What do you do?" A strong answer: don't restart and don't reach for single-user mode. Find what holds back cleanup (prepared transactions, long sessions, stale slots), end it, then run a plain VACUUM on the oldest tables first. Then name the cause: writes grew, vacuum budget and alerting didn't.

Wraparound outages come from vacuum throughput not growing with writes; alert on XID age and its rate, and recover with plain VACUUM after removing blockers.

Writes are failing with the wraparound error. A teammate proposes VACUUM FULL on the biggest table to "really fix it". What's wrong with that?

  1. Nothing can run until the server is restarted in single-user mode
  2. VACUUM FULL needs a transaction ID, which the database is refusing to hand out; a plain VACUUM is the documented fix
  3. VACUUM FULL doesn't freeze rows

With fewer than 3 million IDs left, new XIDs are refused. VACUUM FULL needs one; plain VACUUM doesn't, so it is the way out.

Explain to an on-call engineer what goes wrong first when write volume grows ten times, and how they would see each problem coming.

Dead rows arrive faster than a throttled autovacuum removes them, so tables and indexes bloat; you see n_dead_tup rising and last_autovacuum aging. Freed space is reused but not returned, so shrinking needs pg_repack or partitions, with spare disk. XIDs are used ten times faster, so tables hit the forced-freeze age sooner and the margin before writes are refused shrinks from weeks to days; you see age(datfrozenxid) and its daily rate climbing. Sentry and Mandrill both hit that wall because vacuum capacity and alerting didn't grow with writes.

This page follows PostgreSQL 18. The PostgreSQL 19 release notes, still for a beta: a new REPACK command replaces VACUUM FULL and CLUSTER, which remain for compatibility. With REPACK's CONCURRENTLY option, the ACCESS EXCLUSIVE lock is taken only to swap the table and index files, which is typically short. Wraparound warnings start at 100 million remaining XIDs instead of 40 million. Autovacuum can use parallel workers, a scoring system orders the tables it processes, and ordinary table scans can mark pages all-visible too. Check the final release before relying on any of it.

"Would you ever turn autovacuum off for a table?" A strong answer: almost never. With autovacuum_enabled set to false the table is still vacuumed to prevent wraparound, so you lose routine cleanup but not the forced kind, and that forced run arrives at the worst time. The legitimate case is a staging table you load and drop within minutes.

Interview drill: VACUUM questions at the senior bar

Last part: the decision table. Still unsolved: can you answer under pressure?

An interviewer at a payments company takes your ledger design and asks three questions about cleanup. Commit to an answer before opening each reference.

1. "Your wallet_balances table gets 20,000 updates a second. What will hurt first, and how do you design for it?"

Dead versions and index writes. Design for HOT: keep the balance and anything updated per request out of indexes, keep the row narrow, set fillfactor below 100 on that table. Give it its own autovacuum settings: a small scale factor and a higher cost limit. Watch n_tup_hot_upd against n_tup_upd and n_dead_tup. Trade-off: lower fillfactor means more pages, and a bigger vacuum budget means more I/O.

2. "Your write volume grows 10 times next quarter. What breaks in PostgreSQL maintenance, and what do you change before it does?"

XIDs are used 10 times faster, so tables reach the forced-autovacuum age 10 times sooner, and the headroom to the hard stop shrinks from weeks to days. Dead rows also arrive faster than a throttled autovacuum removes them, so bloat grows. Before the growth: raise the cost budget, tune the busiest tables, alert on XID age and its daily rate, and cut XID use by batching small write transactions. Trade-off: more background I/O and bigger transactions.

3. "A 1 TB table is 60 percent empty after a data purge. Shrink it with zero downtime."

First ask whether it will refill; if yes, leave it. If not: pg_repack with enough spare disk for the copy, a primary key, no DDL during the run, and a quiet hour for its two brief exclusive locks, with long transactions ended first. Or partition so future purges are partition drops. Never VACUUM FULL on a live table. Trade-off: spare disk and a rebuild's I/O, versus a maintenance window.
