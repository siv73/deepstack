Why agents need a way to hand work to other agents

Your payments company has a customer-support agent. Customers ask it 3 kinds of hard question: where is my refund, is my KYC done, why was my card charged twice. The answers live with 3 other agents: one run by the payments team, one by a KYC vendor, one by the risk team. Each is built on a different framework.

Think of a hammer and a contractor. You pick up a hammer and use it: one action, one result. You hire a contractor differently. You describe the job, they ask questions, they send updates, they hand over the finished work, and you never see their toolbox.

The spec describes A2A as an open standard for communication between independent, possibly opaque AI agents, built on different frameworks, in different languages or by different vendors. Its stated goal is that agents can work together without needing access to each other's internal state, memory or tools.

  1. Each agent publishes a description of what it can do and how to reach it.
  2. The support agent sends a job to the right agent in one shared format.
  3. The remote agent works its own way. It may ask a question or report progress.
  4. It hands back the result in the same shared format.

Why not expose each agent as a plain function call, the way an agent calls a tool? The A2A docs argue that wrapping an agent as a tool limits it, and that A2A lets agents be exposed as they are. A tool call is one request and one answer. A job for another agent can take days and need a conversation.

Google announced A2A on 9 April 2025, with more than 50 technology partners. The A2A docs describe MCP as the way an agent reaches its tools and resources, A2A as the way agents collaborate with each other, and the two as complementary.

MCP gives an agent tools; A2A lets an agent hand a whole job to another agent it doesn't control.

Which of these is an A2A job rather than an MCP tool call?

  1. The support agent reads a customer's last 5 orders from Postgres
  2. The support agent hands a disputed charge to the risk team's agent, which may ask questions and takes hours
  3. The support agent converts ₹ to $ through an exchange-rate API

The dispute goes to an independent agent that runs its own process, may need more input, and takes a long time. That is delegation to a peer, which is what A2A is for.

Who is who, and what stays hidden

Last part: A2A lets one agent hand a job to another. Still unsolved: what must the two sides agree on, and what may they keep private?

The refund agent runs on LangGraph with its own Postgres. The support agent runs on a different stack. If either side needs the other's prompts, memory or tool list, every internal change on one team breaks the other.

Think of a restaurant order ticket. The waiter writes the order in a fixed format. Any kitchen can read it. The waiter never needs the recipe, and the kitchen never needs the menu design.

The spec calls the side that starts a request the A2A client, and the agent that serves it the A2A server, or remote agent. In our example the support agent is the A2A client. The refund agent is the remote agent.

One guiding principle is opaque execution: agents collaborate through declared capabilities and exchanged information, without sharing internal thoughts, plans or tool code.

  1. The spec has three layers: a data model, abstract operations, and protocol bindings that map those operations onto JSON-RPC, gRPC and HTTP+JSON/REST.
  2. A binding is only the envelope. The meaning of each operation is the same in every binding.
  3. The file a2a.proto is the single authoritative definition of the protocol's data objects; schemas and SDK types must be generated from it.
  4. An agent that offers several bindings must provide the same operations and equivalent results on each of them.

So the two teams agree on the envelope: the data model, the operations and one binding. Everything behind the endpoint stays theirs to change.

Agents agree on the envelope (data model, operations, binding), never on each other's internals.

In your own words: why not expose the refund agent as one more MCP tool of the support agent?

A tool call is one structured request with one answer. A job for another agent can run for hours, ask for missing details and send progress, which a tool call can't express. A2A treats the refund agent as a peer that stays opaque: the support agent sees neither its prompts, memory nor tools. The teams agree only on A2A's data model, operations and a binding. Inside, the refund agent still reaches its database through its own tools, often over MCP.

How one agent learns what another can do

Last part: both sides agree on a shared envelope and keep their internals private. Still unsolved: how does the support agent find the refund agent's address, abilities and login rules?

The support agent must know 5 things before its first call: the URL, the binding, whether streaming works, which login scheme to use, and what jobs the agent is good at. Hard-coding them in 3 client teams means 3 broken clients on every change.

Think of a shop's signboard plus its opening-hours sticker: who they are, what they sell, which door to use, which cards they accept.

Every A2A server must make an Agent Card available. An Agent Card is that signboard. One way to find it is the well-known URI https://{server_domain}/.well-known/agent-card.json; registries and direct configuration are the others.

  1. Required fields include name, description, version, supportedInterfaces, capabilities, defaultInputModes, defaultOutputModes and skills.
  2. Each supportedInterfaces entry gives a URL, a protocolBinding (the core values are JSONRPC, GRPC and HTTP+JSON; custom bindings use a URI) and a protocolVersion; the list is in preference order and clients pick the first entry they support.
  3. The capabilities object flags optional features: streaming, pushNotifications, extendedAgentCard and extensions.
  4. A skill has an id, a name, a description and tags, and can list example prompts and its own input and output media types. A skill is a menu item, not a function signature.
  5. JSON uses camelCase field names, so the proto field protocol_version becomes protocolVersion.
{
  "name": "Refund Status Agent",
  "description": "Looks up the status of a customer refund by order ID.",
  "version": "1.0.0",
  "supportedInterfaces": [
    {"url": "https://refunds.example.com/a2a",
     "protocolBinding": "JSONRPC", "protocolVersion": "1.0"}
  ],
  "capabilities": {"streaming": true, "pushNotifications": false},
  "defaultInputModes": ["text/plain"],
  "defaultOutputModes": ["application/json"],
  "skills": [{
    "id": "refund-status", "name": "Refund status",
    "description": "Given an order ID like ORD-1234, returns where its refund is.",
    "tags": ["payments", "refunds"],
    "examples": ["Where is the refund for ORD-1234?"]
  }]
}

The JSON tab is the exact card the tested server returns for card.py.

The Agent Card is the contract: where to call, over which binding, which optional features work, and what the agent is good at.

The card above says pushNotifications is false. A client tries to register a webhook for a task anyway. What should happen?

If pushNotifications is false or missing, webhook setup calls must fail with PushNotificationNotSupportedError; if streaming is false or missing, streaming calls must fail with UnsupportedOperationError. The card is binding, not decoration: the client should read it before trying optional features.

A job with a status: the Task

Last part: the Agent Card says where and how to call. Still unsolved: what comes back when one job finishes in a blink and another runs for days?

A refund lookup is back in a couple of seconds. A chargeback investigation runs for days and waits on a human analyst for part of it. One request-and-response shape can't carry both.

Think of a courier tracking number. You get it the moment you hand over the parcel. It moves through states you can check, and the parcel itself arrives separately.

  1. When a client sends a message, the agent may reply with a direct Message for simple interactions, or create a Task that tracks the work.
  2. A Task has a server-generated id, a contextId, a status, and lists of artifacts and history. A Task is the tracking number.
  3. Its states are submitted, working, input-required, auth-required, completed, failed, canceled and rejected, written on the wire as TASK_STATE_SUBMITTED and so on.
  4. Completed, failed, canceled and rejected are terminal states; input-required and auth-required are interrupted states.
  5. The spec says results should come back as Artifacts, not Messages; messages are for talk such as questions and status updates. An artifact is the parcel.

An Artifact holds one or more Parts, and each Part carries exactly one of text, raw bytes, a url or structured data, plus an optional mediaType. A contextId groups related tasks, like one customer's case file.

Tasks carry state, artifacts carry results, and a terminal task is final.

A refund task is completed. The customer now says: send the refund to a different card. What should the support agent send?

  1. A new message with the same taskId, so the old task continues
  2. A new message with the same contextId, pointing at the old task in referenceTaskIds
  3. CancelTask on the old task, then the same message again

A task in a terminal state cannot restart; a follow-up must start a new task in the same contextId. Clients should use the Message field referenceTaskIds to point at related earlier tasks.

What actually goes over the wire

Last part: work is tracked as a Task that moves through states. Still unsolved: what do the requests and replies look like, and how does a paused task resume?

A customer types "Where is my refund?" with no order number. The refund agent can't answer yet. It needs to ask one question and then carry on the same job.

  1. In the JSON-RPC binding, methods use PascalCase names such as SendMessage and GetTask over HTTP(S), and streaming uses Server-Sent Events.
  2. A Message needs a messageId set by whoever creates it, a role (ROLE_USER from the client, ROLE_AGENT from the agent) and at least one Part.
  3. Task ids are always generated by the server; a client may only send a taskId that refers to an existing task.
  4. To answer an input-required task, the client sends a new message with the same taskId and contextId.
  5. Agents must reject a message whose contextId differs from its task's contextId, and must infer the contextId when only a taskId is sent.
{"jsonrpc": "2.0", "id": 1, "method": "SendMessage",
 "params": {"message": {
   "messageId": "9b1c…", "role": "ROLE_USER",
   "taskId": "a086…", "contextId": "4277…",
   "parts": [{"text": "It is ORD-1234"}]}}}
{"jsonrpc": "2.0", "id": 1, "result": {"task": {
  "id": "a086…", "contextId": "4277…",
  "status": {"state": "TASK_STATE_COMPLETED"},
  "artifacts": [{"artifactId": "1bca…", "name": "refund-status",
    "parts": [{"data": {"order": "ORD-1234", "refund": "processed"}}]}]}}}

Enum values travel as their proto names in SCREAMING_SNAKE_CASE, for example "TASK_STATE_INPUT_REQUIRED" and "ROLE_USER". The page's tests send these exact shapes to the official SDK server.

A paused task resumes when the client replies with the same taskId and contextId; the result arrives as an artifact on that task.

Put the exchange in order.

  1. Client fetches the Agent Card
  2. Client sends SendMessage without a taskId
  3. Agent replies with a Task in TASK_STATE_INPUT_REQUIRED
  4. Client sends SendMessage with that taskId and contextId
  5. Agent replies with the same Task, completed, with an artifact

Discovery comes first. The first message creates the task; only the server mints its id, so the client can reference it only after the reply.

Waiting for slow work: block, poll, stream or webhook

Last part: a message creates or resumes a task, and the reply carries its state. Still unsolved: what if the job runs for days?

The chargeback investigation runs for days. Your API gateway kills any request after 60 s. Holding one HTTP call open until the job ends is not an option.

Think of a tailor. You can wait in the shop, phone every hour, stay on a live call, or leave your number so they ring you when it's ready.

  1. SendMessage is blocking unless told otherwise: the server waits until the task is terminal or interrupted before it replies. That is waiting in the shop.
  2. With returnImmediately set to true, the server replies as soon as the task exists, and the caller then polls, subscribes or relies on push notifications.
  3. A task stream starts with the Task object, then status and artifact update events, and closes when the task reaches a terminal state. That is the live call.
  4. SubscribeToTask reconnects to a running task and must send the current Task as its first event, so nothing is lost between a GetTask and the subscription.
  5. Push notifications are HTTP POSTs to a webhook the client registered, carrying the same StreamResponse payload a stream would. That is leaving your number.
Way to get updatesPick it when (the spec's own guidance)Cost
Poll with GetTaskSimple integrations, infrequent updates, clients behind restrictive firewallsDelay between polls, many wasted calls
Stream (SSE)Interactive apps and live progress; needs capabilities.streaming set to trueOne open connection per watcher
Push (webhook)Server-to-server work, long-running tasks, event-driven systems; the client must be reachable over HTTPYou run and secure a public endpoint

Events must arrive in the order they were generated, and several clients may stream the same task at once. For push, the agent must attempt delivery at least once, and clients should process notifications idempotently because duplicates may occur.

Block for quick jobs; for long ones, return at once and choose poll, stream or webhook by who can hold a connection and who can receive a call.

The support agent is streaming a task. A network blip drops the connection for 20 s. How does it catch up, and what might it have missed?

It calls SubscribeToTask, which needs the streaming capability. The first event is the task's current state, so its status and artifacts are up to date. If the task reached a terminal state during the gap, SubscribeToTask fails with UnsupportedOperationError, so the client falls back to GetTask. A client that disconnects and reconnects may miss status messages, so messages must not be treated as reliable delivery for critical information. Anything that matters must live in the task's state or artifacts.

Walk through, end to end, how the support agent gets a refund status from the refund agent, including what changes if the job takes 3 days.

The support agent fetches the Agent Card and picks the first interface it supports. It sends SendMessage with the customer's text. The refund agent creates a Task and, missing the order ID, moves it to input-required with a question. The support agent replies with the same taskId and contextId; the task completes with a data artifact. For a 3-day job the client sets returnImmediately, gets the task at once, and then polls GetTask, streams, or registers a webhook.

Build the refund agent with the official SDK

Last part: clients can block, poll, stream or take webhooks. Still unsolved: what does a correct agent look like in code?

The payments team wants 3 other teams' agents to look up refund status. They need a server that publishes a card, runs the task lifecycle and speaks JSON-RPC, without writing protocol plumbing by hand.

The A2A project hosts official SDKs in six languages: Python, Go, JavaScript, Java, .NET and Rust. The Python SDK, a2a-sdk, implements spec version 1.0 over JSON-RPC, HTTP+JSON/REST and gRPC, with a compatibility mode for 0.3.

  1. Your logic lives in an AgentExecutor. It publishes events to a queue; the SDK turns them into replies, streams and stored task state.
  2. Since SDK version 1.0, an executor must pick one pattern per stream: exactly one Message, or a Task first followed by update events; mixing them fails with InvalidAgentResponseError.
  3. The SDK's executor contract: to ask for input, publish an input-required status and return; the request resumes when the user's input arrives.
  4. Since SDK version 1.0, the server is assembled from Starlette route factories such as create_agent_card_routes and create_jsonrpc_routes.

The tests call this server in process and check each behaviour on this page: the pause, the resume, the artifact, the stream order and the error codes.

Production changes from this sketch:

  • Swap InMemoryTaskStore for a database store. The SDK has optional extras for PostgreSQL, MySQL and SQLite. Part 10 shows what breaks without it.
  • Put the real HTTPS URL in supportedInterfaces and add securitySchemes (part 9).
  • Return a Task, not a Message, for anything that may pause, fail or be audited later.
  • If you turn on push notifications, turn on the push-URL validator too (part 11).

"Why return a Task for a 2-second lookup instead of a plain Message?" A strong answer: a Task gives a server-owned id you can log, audit and re-read with GetTask; it can pause for input and it records a terminal state. A Message is fine for chit-chat or negotiating scope. The cost is stored state per request, so you need a durable store and a retention policy.

Write an executor that publishes a Task first, then status and artifact events; the SDK handles the wire, the card and the stored state.

In refund_agent.py, when the order ID is missing, why does execute() publish input-required and return, instead of waiting for the answer?

  1. Because waiting would publish events in the wrong order
  2. Because returning deletes the task, and the next message starts clean
  3. Because the client's answer comes as a new SendMessage, and the SDK calls execute() again with the paused task as current_task
  4. Because blocking calls never return until the task completes

The reply is a separate request. The executor returns, the task sits in input-required, and the next message with that taskId resumes it: that's why the code checks context.current_task.

Call it with plain HTTP, and read its errors

Last part: the SDK runs the agent. Still unsolved: what must a client send, and what do failures look like?

A partner team calls your agent from Go with no A2A SDK. Their first request fails with a version error, though they never picked a version.

You will meet A2A v0.3 in tutorials, older SDKs and some platforms. It used slash-style method names such as message/send, tasks/get and tasks/resubscribe; v1.0 renamed them SendMessage, GetTask and SubscribeToTask. It used lowercase values such as "completed", "input-required" and "user", now TASK_STATE_COMPLETED, TASK_STATE_INPUT_REQUIRED and ROLE_USER. Its parts had a kind field (text, file, data), replaced by one Part type holding text, raw, url or data, and its card named the primary endpoint in a top-level url field, now supportedInterfaces[0].url. Version 1.0.0 shipped these breaking changes on 12 March 2026; 1.0.1 followed on 26 May 2026.

Always send the A2A-Version header; a missing header silently means v0.3.

A client built from a 2025 tutorial sends method message/send with role "user" and no version header. What does a 1.0 agent built on a2a-sdk do, and how can the agent's team keep that client working during migration?

In this page's tests, a2a-sdk 1.1.5 answered message/send with -32601, with or without a version header: it doesn't know that method name. In the JSON-RPC binding, -32601 is the standard Method not found error. A 1.0 method name sent without the header gets VersionNotSupportedError (-32009) instead, because an empty version counts as 0.3. The Python SDK can serve 0.3 clients alongside 1.0 if you add a 0.3 interface to the card and turn on the route factory's 0.3 compatibility flag.

Who is calling: identity lives outside the message

Last part: clients send a version header and read standard error codes. Still unsolved: how does the refund agent know who is calling, and what may they see?

The KYC vendor's agent must accept calls only from your company, and only for your customers. The refund agent must never show customer A's refunds to a call made for customer B.

  1. The client learns the required schemes from the card's securitySchemes, gets credentials outside A2A, and sends them in headers or metadata on every request.
  2. The server must authenticate every incoming request. The A2A docs say protocol payloads don't carry user or client identity; identity is set at the transport or HTTP layer.
  3. Scheme types are API key, HTTP auth such as Bearer, OAuth 2.0, OpenID Connect and mutual TLS, modelled on OpenAPI security schemes.
  4. Production deployments must use HTTPS for HTTP bindings and TLS for gRPC.

In v1.0 the OAuth implicit and password flows are deprecated in the card; it offers authorization code (with a pkceRequired flag), client credentials and device code.

Sometimes the agent needs a credential in the middle of a job, such as a token for a downstream bank API. The agent can move the task to auth-required and explain in its status message what authorization it needs. The agent may carry on as soon as it receives the credential out of band, so a client without an open stream should subscribe, register a webhook or poll to avoid missing updates.

If credentials are passed in-band through a chain of agents, every agent in the chain can see them, so the spec recommends binding them to the agent that requested them. An agent can also serve a richer, extended Agent Card to authenticated callers when capabilities.extendedAgentCard is true; that call must be authenticated.

"Your orchestrator calls the refund agent on behalf of a customer. How does the refund agent decide which refunds to return?" A strong answer: from a validated token, never from text or metadata in the message. Use an OAuth token that carries the end user (or a delegated scope), check it on every request, and scope every task read and list to that caller. The trade-off: user-delegated tokens need a token exchange hop per call; service-only tokens are simpler but make the refund agent trust the orchestrator for the user's identity.

Identity comes from credentials checked on every request, never from the message body.

Where should the refund agent get the identity of the customer it is serving?

  1. A customerId field the client puts in message metadata
  2. The credential in the request's Authorization header, validated on every call
  3. The contextId, since each customer has their own context

A2A leaves identity to the HTTP layer, and the server must authenticate every request. Payload fields are caller-controlled.

Explain how authentication works in A2A, including what happens when an agent needs a new credential in the middle of a task.

The Agent Card lists security schemes such as OAuth 2.0 or mTLS. The client gets credentials outside A2A and sends them on every request; the server authenticates each one, because the payload carries no identity. If a job needs another credential halfway, the agent moves the task to auth-required and says what it needs. The credential usually arrives out of band and the agent resumes on its own, so the client should keep a stream, webhook or poll going. Credentials passed through chains of agents should be bound to the agent that asked.

What breaks first at 10× load

Last part: identity comes from credentials checked on every request. Still unsolved: what fails when traffic grows, and how do you see it coming?

A sale week pushes refund questions from 200 to 2,000 a minute. Chargeback tasks can run for most of an hour. The refund agent runs on 3 replicas behind a round-robin load balancer, using the in-memory store from part 7.

  1. Blocked connections. Blocking is what you get unless you ask otherwise (part 6). If calls last 30 s on average, 2,000 a minute means about 1,000 requests held open at once. Workers and gateway slots run out first. Fix: returnImmediately for anything slow, then webhook or stream.
  2. Lost and "missing" tasks. An in-memory store forgets every task on restart. With 3 replicas, a GetTask lands on a replica that never saw the task about 2 times in 3. Fix: a shared database store; keep streams on the replica that runs the task or fan events out through a shared bus.
  3. Slow stream readers. One watcher that reads slowly can back up events for everyone on that task. In a2a-sdk version 1.1.4 (7 September 2026), a full subscriber queue now evicts that subscriber instead of wedging dispatch.
  4. Webhook storms. Agents should time out webhook calls (10 to 30 seconds recommended) and may stop after a set number of consecutive failures; on retrying with exponential backoff the spec says MAY in one section and SHOULD in another. A slow receiver turns into retries, then duplicates.
  5. Listing everything. ListTasks uses cursor pagination; with pageSize unset it returns at most 50 tasks, pageSize may not exceed 100, and nextPageToken is an empty string on the last page.

The SDK's own code notes that after a cancel, a client that was streaming may not receive the terminal state and may have to re-read the task. Treat GetTask as the source of truth after any cancel or reconnect, not the last event you saw.

"How do you run an A2A agent on 3 replicas?" A strong answer: task state in a shared store; replies to blocking calls from any replica; streams either pinned to the replica running the task or fed from a shared event bus; long tasks via returnImmediately and webhooks; idempotent webhook receivers. What you give up: a database round trip per event and more moving parts than one process.

At scale, move long work off blocking calls, keep task state in a shared store, and treat GetTask as the truth.

3 replicas, in-memory store, round-robin load balancer. A client sends a message with returnImmediately and then polls GetTask 6 times. What does it see?

Only the replica that created the task knows it. About 4 of the 6 polls land elsewhere and get TaskNotFoundError (-32001). The client may give up on a task that is running fine. A shared task store fixes it; sticky sessions only hide it until that replica restarts.

What an attacker or a careless peer does

Last part: what breaks under load and how to see it. Still unsolved: what goes wrong when a caller is hostile, or a peer isn't who it claims to be?

Your agent accepts webhook URLs from any authenticated partner. One partner registers a webhook URL inside your private 10.x network: your cache admin endpoint. Every task update now makes your server call your own internal admin endpoint.

  1. Webhook SSRF. The spec says agents should validate webhook URLs against SSRF: reject private ranges such as 10.0.0.0/8 and 192.168.0.0/16, reject localhost and link-local addresses, and use allowlists where appropriate. a2a-sdk 1.1.4 added push-URL checks both when a config is created and again before dispatch, as SSRF hardening; they run only if you pass a push_url_validator to the request handler, which is unset by default.
  2. Reading other callers' tasks. Every operation must be authorization-checked and scoped to the caller, including ListTasks with no filter, and the check must run before any query that could reveal whether a resource exists. The same SDK release made cancel and subscribe check the task's owner.
  3. A fake agent. Agent Cards may be signed with JWS (RFC 7515) over a JCS-canonicalized form (RFC 8785), and clients should verify at least one signature before trusting a card. Clients should also verify the server's TLS certificate against trusted certificate authorities.
  4. Forged notifications. Webhook receivers must validate the credentials on each notification; on checking that the task ID is one they created, the spec says MUST in one section and SHOULD in another.
  5. Hostile content. A remote agent's text and artifacts come from another party. Treat them like user input before they reach your own model or tools.

The official Python SDK's 1.1.4 release fixed bugs in each of these areas: SSRF checks on push URLs, owner scoping on cancel and subscribe, and a subscriber queue that could wedge dispatch. If you pinned an older version, you had these gaps. Changelog.

"A partner agent can register webhooks on your agent. What do you check?" A strong answer: HTTPS only; resolve the host and reject private, loopback and link-local addresses at dispatch time, not only at registration (DNS can change); an allowlist per partner where possible; a unique token per config; timeouts and retry caps. The trade-off: strict allowlists slow partner onboarding.

Treat every URL, card and message from another agent as untrusted: validate webhooks, scope every task read, verify who the peer is.

A partner registers https://hooks.partner.example as its webhook. It passed your checks, but a week later its DNS points to 10.0.4.12. Which defence still stops the attack?

  1. Rejecting private addresses when the webhook is registered
  2. Sending a unique Bearer token with each notification
  3. Resolving the host and rejecting private addresses right before each delivery

A check at registration saw a public address. Only a check at dispatch sees where the name points now, which is why the SDK checks at both points. Connect to the address you checked, or a second DNS lookup can still switch it.

  • Microsoft Foundry's a2a tool is generally available on protocol 1.0; when the remote agent is itself a Foundry agent, version 1.0 uses JSON-RPC, only text is supported and streaming responses aren't.
  • AWS AgentCore Runtime expects an A2A server to speak JSON-RPC 2.0 on port 9000 at the root path, serve its card at /.well-known/agent-card.json, and its contract page's sample card shows protocolVersion 0.3.0.

So a defensive client does 4 things. It sends A2A-Version on every call. It checks the card's capabilities before optional features. It branches on the task's state from GetTask, not on exact error codes. It checks that returned taskId and contextId match what it sent.

The A2A project offers a Technology Compatibility Kit (a2a-tck) and the A2A Inspector to help validate agents. Run them in CI against every peer you depend on.

"You depend on a vendor's A2A agent. How do you stop their upgrade from breaking you?" A strong answer: pin A2A-Version; run contract tests (the TCK, plus your own golden flows) against their staging agent in CI; alert on -32009 and on unexpected states; branch on task state rather than error codes. The trade-off: a contract suite you must maintain for every external peer.

Interoperability is tested, not assumed: code against task state, check capabilities, and run conformance tests on every peer.

Your client treats error -32004 on SendMessage as "that task already finished, start a new task in the same context". What happens against an agent on a2a-sdk 1.1.5?

  1. The message is accepted and the finished task changes
  2. The client gets -32602, misses its branch, and shows the user a generic error
  3. The call hangs until the task times out

The spec names -32004 for this case, but the SDK answers -32602. Calling GetTask and branching on a terminal state works against both.

Interview drill: designs where A2A is the crux

Last part: A2A belongs only at the boundary between independent agents. Still unsolved: can you defend a design with it under questioning?

3 prompts of the kind asked in senior system-design rounds. Answer each out loud, in about three minutes, before opening the reference.

Prompt 1: Design a support orchestrator that delegates to a refund agent (payments team), a KYC agent (vendor) and a dispute agent (risk team). Walk through discovery, a long dispute, and security.

The orchestrator is an A2A client to three remote agents. It caches each Agent Card (ETag) and picks the first supported interface. Refund lookups use blocking SendMessage; disputes use returnImmediately plus a webhook, with an idempotent receiver that re-reads GetTask. Each peer gets an OAuth token scoped to the customer; peers scope every task to the caller. Trade-off: A2A adds a task store and a contract per peer, but lets three teams change their internals without breaking the orchestrator.

Prompt 2: A partner's agent takes 6 hours per task. Your gateway cuts requests at 60 s, and your webhook endpoint sometimes returns 503 during deploys. What goes wrong with a naive integration, and what is your design?

Naive: a blocking SendMessage is held until the task ends, so the gateway cuts it and the client never learns the task id. Design: set returnImmediately to get the task id at once; register a webhook; make the receiver idempotent, since delivery is attempted at least once and may repeat; run a reconciler that polls GetTask for tasks with no update in N minutes, to cover notifications that never arrive, since retries are optional. Trade-off: you now run a public webhook plus a reconciler job instead of one call.

Prompt 3: Partners want to use your refund service from their agents. Do you expose it as an MCP server or an A2A agent? Defend the choice.

If partners want a fixed lookup (order ID in, status out), MCP is simpler: one tool, no task state. If they want to hand over a job, such as resolving why a refund failed, which may need questions and hours, A2A fits: tasks, input-required and webhooks are built in. You can offer both over one backend. The trade-off: A2A costs you a task store, per-peer auth and conformance tests; MCP costs your partners the orchestration of any multi-step work.

In interviews, place A2A at team or company boundaries, move long work off blocking calls, take identity from tokens, and say what the extra protocol costs.
