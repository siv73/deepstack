Why reserving room for the longest answer caps the batch

Last part: continuous batching lets requests join and leave at every step, so the batch is as big as the KV cache memory allows. Still unsolved: how that memory is handed to each request.

Part 2's Llama 3.1 8B on one H100 leaves about 54.6 GB for the KV cache, at 131,072 bytes per token. A request arrives. It may answer in 20 tokens or in 2,000. How much memory do you give it?

Picture a restaurant that does not know how many friends will join each party. To be safe, it seats every party at a 12-seat table. Most tables end up with three people and nine empty chairs, and the queue outside grows.

Before vLLM, serving systems stored each request's KV cache in one contiguous chunk of memory, reserved up front for the request's maximum possible length. They had to guess high, because the output length depends on the input and the model, and generation stops at an end-of-sequence token or at the maximum length.

The vLLM paper's own example: one token of OPT-13B's KV cache takes about 800 KB, so a request of up to 2,048 tokens can need 1.6 GB.

Now our model. Llama 3.1 8B has 32 layers, a model dimension of 4,096, 32 attention heads and 8 key/value heads. That gives Part 2's 131,072 bytes per token.

  1. Set the maximum length to 2,048 tokens. Each request reserves 2,048 × 131,072 = 268 MB.
  2. A request answers in 300 tokens. It uses 39.3 MB of its 268 MB: 85% of the chunk sits idle.
  3. 54.6 GB ÷ 268 MB = 203 requests at once, however short the real answers are.

Reserving for the longest possible answer caps the batch by the worst case, not by what requests actually use.

With contiguous reservation, you lower the maximum length from 4,096 to 2,048 tokens. Real answers stay the same. What happens to the number of requests that fit?

  1. It doubles, because each reservation halves
  2. It stays the same, because real answers did not change
  3. It halves

Capacity is the budget divided by the reservation. Halving the reservation doubles capacity, and requests longer than 2,048 tokens are now rejected. The real lengths never enter the sum.

Three ways a reserved chunk wastes memory

Last part: contiguous reservation sizes every request for the worst case. Still unsolved: where exactly the memory goes, and how bad it gets in practice.

Take one request with 2,048 reserved slots. It has produced 300 tokens and will stop at 900. Which of its 1,748 empty slots are wasted, and are they all wasted the same way?

Back at the restaurant: some chairs are empty because friends are still on their way. Some will stay empty all night. And between tables there is floor space too narrow for another table.

The vLLM paper names three kinds of waste in this scheme. Reserved slots hold space for tokens the request will produce later, so no other request can use it in the meantime. Internal fragmentation is space reserved for the maximum length that is never filled, because the answer ends sooner. External fragmentation is memory the allocator cannot hand out, because each request's chunk is a different size.

The paper uses two terms for this. Internal fragmentation is waste inside a chunk. External fragmentation is waste between chunks.

Measured in existing systems, only 20.4% to 38.2% of KV cache memory held actual token states. The rest was one of the three kinds of waste.

A sample of eight requests, final lengths from 60 to 2,048 tokens, lands in that range. Reserved at 2,048 each, they hold 16,384 slots and use 6,178: 37.7% used, 62.3% wasted.

Reserved slots, internal fragmentation and external fragmentation together left 62% to 80% of KV memory without real tokens in the paper's measurements.

The request above has 2,048 slots, has written 300 tokens and will stop at 900. Split its 1,748 empty slots into reserved slots and internal fragmentation.

600 slots are reserved: tokens 301 to 900 will fill them later, but nobody else can use them until then. 1,148 slots are internal fragmentation: they will never be filled. External fragmentation is not inside this chunk at all; it is in the gaps around it.

Blocks and block tables: allocate as you grow

Last part: 62% to 80% of a contiguous KV cache can sit empty. Still unsolved: how to stop reserving memory for tokens that may never come.

Keep the same 54.6 GB, but stop guessing lengths. Hand each request memory in small pieces as it grows. The pieces will land all over GPU memory. How does the request find its own?

The restaurant switches to 4-seat tables. A party gets one table, then another as friends arrive. The host keeps a card per party listing its tables. They need not be next to each other.

  1. At startup, cut the KV memory into equal pieces, each with room for a fixed number of tokens.
  2. A request fills its own numbered pieces left to right: piece 0, piece 1, and so on.
  3. A per-request list maps each of those numbers to whichever physical piece was free.
  4. Take a new piece only when the last one is full. Return all of them when the request ends.

Each piece is a KV block. The per-request list is its block table.

In the paper, a request's logical blocks fill left to right, and a block engine maps them to physical blocks carved out of a contiguous chunk of GPU memory. Each block table entry records the physical block and how many of its positions are filled. Because blocks are taken only when needed, the paper bounds a request's waste to one block. Because every block is the same size, external fragmentation goes away.

Step through a 12-block pool with 4-token blocks. Watch the block tables point at blocks that are not next to each other. Steps 7 to 9 preview sharing, covered in its own part below.

Back to the 300-token request, with 16-token blocks: it holds 19 blocks, 304 slots, and wastes 4 slots instead of 1,748.

Fixed-size blocks taken on demand, found through a per-request block table, cap each request's waste at one partly filled block.

Block size is 16 tokens. A request holds 33 tokens. How many blocks does it hold, and how many slots are empty?

  1. 2 blocks, 0 empty
  2. 3 blocks, 15 empty
  3. 128 blocks, as many as a 2,048-token maximum needs

Two full blocks hold 32 tokens; the 33rd starts a third block with 15 free slots. That last partly filled block is the only waste.

The same trick your operating system plays

Last part: requests take fixed-size blocks on demand and find them through a block table. Still unsolved: where this idea comes from, and how far the comparison holds.

Two processes on your laptop each believe they own a long, unbroken stretch of memory starting at the same address. Neither is true, and neither process can tell. The KV cache needs the same illusion.

An operating system splits memory into fixed-size pages and maps each program's logical pages to physical pages. The program sees one unbroken range; the physical pages can be anywhere. The vLLM paper draws the mapping itself: blocks are pages, tokens are bytes, and requests are processes. That is where the name PagedAttention comes from.

Where the comparison stops working:

  1. No hardware does the lookup. Address translation in an OS happens in the CPU's memory hardware. Here the attention code reads the block table itself (next part).
  2. No page faults. In vLLM v0.31.0 the scheduler asks the KV cache manager for every scheduled request's blocks before the model runs; a request that cannot get them is not run in that step.
  3. No disk. An OS can write a page out and read it back. In vLLM V1 the default preemption mode is RECOMPUTE rather than SWAP. The v0.31.0 scheduler has no swap path at all; copying KV blocks to CPU memory is a separate feature, off unless kv_offloading_size is set. Thrown-away blocks are rebuilt by running the model again, as a later part shows.
  4. A block is not a few kilobytes of one array. In v0.31.0, when all of a model's layers share one KV cache group, as Llama 3.1 8B's do, one block ID covers its token slots in every layer: the bytes per block are the sum of every layer's page size. Hybrid models split layers into groups, and a block then covers one group.

PagedAttention borrows virtual memory's core move, fixed-size units behind a per-owner mapping table, but the lookup is software, nothing faults, and evicted blocks are recomputed rather than read back.

Which operating-system behaviour has no direct counterpart in vLLM v0.31.0's default setup?

  1. Mapping logical units to physical units through a per-owner table
  2. Handing out memory in fixed-size units
  3. Writing evicted units to slower storage and reading them back later

V1 has no swap preemption path: a preempted request's blocks are freed and rebuilt by running the model again, not saved and restored. CPU offloading exists, but as a separate opt-in feature.

How attention reads keys scattered across blocks

Last part: the block table is the page table, but software reads it. Still unsolved: how attention works when a request's keys and values are spread across blocks 2, 6 and 9.

Request B's next token must attend to all its earlier tokens. Their keys and values sit in physical blocks 2 and 6, with request A's data in between. A normal attention routine expects one unbroken array.

Think of a paginated API. You cannot fetch a 10,000-row table in one call, so you walk the page tokens and fold each page into a running result. The answer is the same as one big read.

  1. Take the new token's query vector.
  2. Walk the request's block table in order: block 2, then block 6.
  3. For each block, load its keys and score the query against them.
  4. Load that block's values, weight them by the scores, and add them to a running total.
  5. Normalise the scores across all blocks, so the result equals reading one long array.

PagedAttention computes attention block by block: it fetches each key block, scores the query against it, then weights the matching value blocks and sums them. That is what lets keys and values that belong together sit in non-contiguous memory.

Writing new tokens needs an address too. In v0.31.0 the model runner keeps block tables for the running requests and, each step, computes a slot mapping that tells the kernel which cache slot each scheduled token's key and value go to.

vLLM's PagedAttention kernel design doc is now marked historical: it follows the original paper and no longer describes the code vLLM uses today. You will meet it in blog posts. The idea above still holds; the kernel it describes does not.

Attention walks the block table and folds in one block at a time, so the request's keys and values can live anywhere in the pool.

In your own words: what does PagedAttention change about KV cache memory, and why does attention still work?

Without paging, each request gets one contiguous chunk sized for its maximum length, and most of it never holds a token. PagedAttention cuts memory into equal blocks and gives a request a new block only when its last one is full, so the most it wastes is one partly filled block. Each request keeps a block table, like a page table, that maps its logical blocks to physical blocks anywhere in GPU memory. Attention walks that table, scoring the query against one key block at a time and summing the weighted values, so the result is the same as if the cache were one array.

Sharing blocks between samples, and what changed since 2023

Last part: attention reads blocks wherever they are. Still unsolved: can two requests point at the same block?

A user asks for 4 different answers to one 1,000-token prompt. Stored separately, the prompt's keys and values exist 4 times: 524 MB where 131 MB would do.

Like a shared Google Doc: everyone reads one copy, and an editor makes their own copy first.

  1. Each sample's block table points at the same prompt blocks.
  2. Each block counts the tables pointing at it.
  3. Writing into a shared block copies that one block first.
  4. A finished sample lowers its blocks' counts; a block at zero is free.

The count is a reference count; copying only on the first write is copy-on-write. For parallel sampling, the paper maps every sample's prompt blocks to the same physical blocks and gives each physical block a reference count. When a sample writes to a shared block, it gets a fresh copy first, so copy-on-write happens one block at a time. In beam search most blocks stay shared; a dropped beam lowers its blocks' reference counts, and blocks that reach zero are freed. The paper reports that the prompt's cache was 12% of KV memory in its parallel-sampling experiment, and that sharing saves up to 55% of memory in beam search.

In vLLM v0.31.0, a request with n greater than 1 is split into n child requests, each with n = 1. Its offline beam search runs above the engine: every step submits each beam as a new request for one token, asking for 2 × beam_width log-probabilities. Those requests share blocks through prefix caching, the next part, and only full blocks are cached. v0.31.0's block pool treats a block as writable only when one request holds it and it has no hash. So a shared full block is never written. Copy-on-write survives for one case: when a prefix-cache hit ends inside a block, the request gets a private copy of that block; vLLM allows such hits only for hybrid models whose Mamba layers use mamba_cache_mode align with a match unit finer than their block size.

Asked: "How does vLLM avoid storing the same prompt 4 times for n = 4?" Strong answer: the 2023 design shares blocks with reference counts and copy-on-write; current vLLM splits n = 4 into four requests that share full prompt blocks through prefix caching. Each sample computes the partly filled last prompt block itself. Cost: up to one block of repeated work per sample, for simpler, append-only block tables.

Reference counts let many requests point at one block; the paper copies a shared block only on its first write, while vLLM v0.31.0 mostly shares full, never-written blocks through prefix caching instead.

Under the paper's design, two samples share a prompt that ends halfway through a block. Each then generates 100 tokens with block size 16. How many blocks get copied?

  1. Every prompt block, once per sample
  2. One: the half-full last prompt block, on the first write while it is still shared
  3. One per generated block, for both samples

Full prompt blocks are only read. The half-full block is written by both samples; the first writer copies it, and the second becomes its only owner and writes in place. New blocks after that are fresh, never shared.

Automatic prefix caching: finding blocks someone already computed

Last part: current vLLM shares full blocks across requests. Still unsolved: how a new request finds them.

Your RAG endpoint sends the same 3,000-token system prompt and document with every question. Each request redoes 3,000 tokens of prefill. That is the same work, thousands of times a day.

It works like git's content-addressed storage: a chunk named by the hash of its contents and history is found by name.

  1. When a block fills, hash it with its parent block's hash and its own tokens.
  2. A new prompt is hashed block by block and each hash looked up, stopping at the first miss.
  3. On a hit, the block's reference count goes up and the prompt's prefill skips those tokens.
  4. Freed blocks keep their hashes until the pool reuses them, least recently used first.

The hash is the block hash. vLLM hashes each full block from three things: the parent block's hash, the block's own tokens, and extra keys such as LoRA IDs, image hashes or a cache salt. Prefix caching is on by default in v0.31.0, and the default hash algorithm is sha256.

On a hit, the cached block's reference count goes up, and it leaves the free queue if no running request was using it. If every prompt token hits, the last token is still recomputed to get its logits, which can recompute a whole block.

The free list is the free queue. A finished request's blocks are freed in reverse order, so its tail blocks, the least likely to be reused, are evicted first. Allocation takes blocks from the queue's head, and a taken block that is still cached is evicted from the cache at that moment. In the v0.31.0 source, freed blocks with no hash go to the front of the queue to be reused first, and cached blocks go to the back, so the least recently used one is evicted first.

The design doc's worked example still appends every freed block to the back of the queue. Replayed on the toy, which follows the source, its last request gets blocks 6, 4, 7, 8, 9, not the doc's 7, 8, 9, 4, 3.

Block tables are append-only in v1, so a request that computes a block already in the cache keeps its own duplicate until it is freed. Prefix caching only cuts prefill time; it does not shorten decoding, so it helps little when answers are long or prompts share nothing.

Prefix caching names each full block by a hash of its whole prefix, keeps freed blocks findable until they are reused, and evicts the least recently used one first.

Block size 4. Request 0's prompt has 15 tokens and is cached. Request 1 has 14 prompt tokens; its first 10 match request 0. How many prompt tokens hit the cache?

  1. 10, every shared token
  2. 8: two full blocks match; the third matches only 2 of its 4 tokens
  3. 0, because the prompts differ

Matching is per full block. Blocks 0 and 1 hash the same; block 2 differs in its last two tokens, so the lookup stops there. This is the design doc's own example.

How gpu_memory_utilization becomes a pool of blocks

Last part: blocks are shared and reused through hashes. Still unsolved: how many blocks there are, and which knobs set that number.

Your service runs Llama 3.1 8B on one H100 SXM. You leave the defaults. How many requests can hold KV cache at once, and what would raise it?

In v0.31.0 the default block size is 16 tokens and the default gpu_memory_utilization is 0.92. If you do not set a block size, the attention backend can replace 16 with a size it prefers, and hybrid models get sizes aligned to their other layers. That fraction is a per-instance limit: two vLLM instances sharing one GPU can each be set to 0.5.

  1. At startup the worker requests total GPU memory × gpu_memory_utilization, and fails if that much is not free.
  2. A profiling run measures non-KV memory, such as weights and peak activations, and the KV cache gets the requested memory minus that.
  3. The number of blocks is that KV memory divided by the bytes one block needs across all layers, rounded down.

For a standard attention layer, one block takes KV heads × block size × (key size + value size) × bytes per value. Setting kv_cache_memory_bytes replaces this calculation, so gpu_memory_utilization no longer sizes the KV cache, though the startup free-memory check still uses it.

Llama 3.1 8B in BF16: 32 layers × 8 heads × 16 tokens × (128 + 128) × 2 bytes = 2,097,152 bytes per block. The H100 SXM has 80 GB of memory. At 0.92, minus 16 GB of weights and a 3 GB guess for everything else, 54.6 GB is left: 26,035 blocks, or 416,560 token slots.

Block size trades two costs. Hugging Face Transformers v5.19.0, which also pages its cache, defaults to 256-token blocks to match its decode kernel, and notes that larger blocks cut bookkeeping but waste space when a sequence does not fill its last block. Larger blocks also coarsen prefix matching, since only full blocks are cached.

With the default mix: contiguous holds 16,384 slots for 6,178 tokens and fits 203 requests; paged holds 6,224 slots and fits 535, about 2.6 times as many. Try block size 256, or one 2,048-token request among short ones.

Asked: "Your vLLM pods show KV cache usage near 100% and preemptions. Do you raise gpu_memory_utilization to 0.98?" Strong answer: it adds blocks, but the profile run already reserved peak activation memory; going higher risks out-of-memory errors from anything the profile missed. First check whether max_model_len, prompt sizes or max_num_seqs explain the pressure, then add GPUs or tensor parallelism. State the trade: more blocks per GPU against crash risk.

vLLM sizes the block pool once at startup: requested memory minus measured non-KV memory, divided by the bytes per block across all layers.

You change block_size from 16 to 32 and change nothing else. What happens to the number of blocks and to the number of token slots?

  1. Blocks stay the same; token slots double
  2. Both double
  3. Blocks roughly halve; token slots stay about the same

Bytes per block scale with block size, and the KV memory is fixed, so the block count halves. Total slots stay about the same; what changes is waste per request and prefix-match granularity.

A toy block allocator you can run

Four short files implement everything so far: block tables, allocate, append, free, a copy-on-write fork, and prefix reuse with reference counts. Run them with uv run pytest examples/llm-serving-4.

What the tests pin down:

  2. A fork copies no data; the first write to a shared, partly filled block copies exactly one block.
  3. A second prompt sharing 10 tokens hits 8; a fully cached 8-token prompt hits only 4.
  4. Different cache salts never share; freed cached blocks still hit until evicted.
  5. The diagram on this page and the calculator's numbers come from this code.

What the toy leaves out: vLLM's pool sets aside block 0 as a placeholder null block. Its free queue is a doubly linked list threaded through the block objects, so moving a block out of the middle takes constant time. It also tracks several cache groups for hybrid models, and never stores keys or values in Python.

A paged KV cache is a small allocator: a free queue, reference counts, per-request block tables, and a hash map from prefix to block.

Put the toy's allocate() in order for a request whose prompt partly hits the cache.

  1. Hash the prompt's full blocks and look them up, stopping at the first miss
  2. Check that enough free blocks remain for the rest of the prompt
  3. Raise the reference count of every hit block, taking it off the free queue if needed
  4. Write the remaining tokens, taking a new block at each block boundary
  5. Hash each new block as it fills, so later requests can find it

Lookup comes first so the capacity check counts only blocks that must be new. The check comes before any change, so a refused request leaves the pool untouched.

When blocks run out: preemption by recompute

Last part: the allocator in code. Still unsolved: what happens when a running request needs a block and none is free?

At 10 times your usual traffic, 500 running requests keep growing. Request #500 needs block 26,036; there are 26,035.

The paper offered two ways out: swap a preempted request's blocks to CPU memory, or drop them and recompute the cache later from the prompt plus the tokens generated so far. It evicted all of a sequence group's blocks or none, and preempted the latest-arrived requests first.

  1. In v0.31.0, when a running request cannot get its new blocks, the scheduler preempts the last request in the running list under the default policy, or the lowest-priority, latest-arriving one under the priority policy.
  2. The victim's blocks are freed, its count of computed tokens is set to zero, and it goes back to the waiting queue. There is no swap step.
  3. Because its count is zero, it does a fresh prefix-cache lookup when readmitted, so its full blocks that were not evicted meanwhile are reused instead of recomputed.

vLLM's tuning guide says V1 defaults to RECOMPUTE rather than SWAP, because recomputing costs less in the V1 architecture. Moving blocks to CPU memory lives on as KV offloading, a later part. Hugging Face's continuous batching offers the other road as an option: with cpu_offload_space set (default 0.0, off), it copies evicted blocks to a pinned CPU buffer and back without recomputing; otherwise it frees them and requeues the request.

What breaks first at 10 times load: KV usage hits 100%, preemptions start, and each victim redoes its prefill inside decode steps, so TPOT rises for everyone. Victims' streams stall, then resume.

vLLM exports vllm:kv_cache_usage_perc, where 1 means 100%, vllm:num_preemptions, a running total, and vllm:prefix_cache_queries and vllm:prefix_cache_hits, both counted in tokens. Alert on the rate of num_preemptions; a full cache is fine if nobody is preempted.

The tuning guide's fixes for frequent preemption: raise gpu_memory_utilization, lower max_num_seqs or max_num_batched_tokens, or add GPUs through tensor or pipeline parallelism.

Recompute storms. Under sustained overload, victims re-enter and push out others, recomputing tokens already computed once. Their cached blocks are reused fast under load, so prefix caching helps little. Cap max_num_seqs or shed load at your API.

Asked: "Paging admits more requests than fit at full length. Isn't that overbooking?" Strong answer: yes, deliberately, like an airline, because most answers end early. The cost is preemption when many run long at once: recomputed prefill and latency spikes for victims. Bound it with max_num_seqs and watch num_preemptions. Contiguous reservation never preempts but fits about 2.6 times fewer requests in the sample mix.

vLLM v0.31.0 handles a full pool by preempting the newest running request and recomputing it later, with prefix caching as the only shortcut back.

Request R is preempted with 1,200 tokens computed, 16-token blocks. Before it is readmitted, other requests take 30 of its 75 freed blocks. What does readmission cost?

R's computed count is zero, so it looks up the prefix cache again. Its blocks were freed tail first and joined the back of the queue in that order, so the 30 taken first are its last 30. The first 45 blocks, 720 tokens, still hit. It recomputes the other 480 tokens in one prefill, then resumes decoding.

Prefix caching in a multi-tenant service: the security traps

Last part: a full pool means preemption and recompute. Still unsolved: what can go wrong when blocks are shared between users who should not see each other's data.

Your API serves two customers from one vLLM fleet. Customer B sends a guessed prompt, such as a rival's confidential system prompt, and times the first token. A fast reply means the guess was already cached.

That is a timing side channel: a cache hit makes prefill shorter, and the attacker can measure it. vLLM's answer is an optional per-request cache_salt, mixed into the first block's hash, so only requests with the same salt can reuse each other's blocks; the docs name timing attacks as the threat. Because each block's hash includes its parent's, the salt changes every block after the first too.

Choosing a fast hash. The xxhash options are faster but not cryptographic; the docs warn that a collision can cause undefined behaviour or leak private information in multi-tenant setups. A collision maps one user's prompt to another user's cached keys and values. The docs say the default became sha256 as of v0.11, because earlier hash keys were not guaranteed collision-free.

Detecting misuse: a per-tenant salt makes cross-tenant hits impossible by construction, so there is nothing to detect. Without salts, watch prefix_cache_hits per tenant; a tenant with a high hit rate on prompts it never sent before is probing.

Asked: "We serve many tenants from one vLLM pool. Turn prefix caching off?" Strong answer: no; salt it per tenant, and use a shared salt only for prompts that are public, such as a common product system prompt. You give up cross-tenant reuse of the same document, and keep sha256. Turning caching off throws away within-tenant reuse, which is most of the win.

Shared prefix blocks leak through timing and through hash collisions; per-tenant cache salts and the sha256 default close both.

Two tenants send the identical 4,000-token prompt with different cache_salt values. How many blocks do they share?

  1. None: the salt changes the first block's hash, and every later hash includes its parent's
  2. All but the first block
  3. All of them, but the salt hides the hit from the attacker

Hashes chain: block 1's hash includes block 0's, and so on. A different salt in block 0 changes every hash in the chain, so nothing matches.

Interview drill: designs where KV memory is the crux

Three prompts an interviewer could give a senior backend candidate. Commit to an answer before opening each one.

1. "A support bot sends a 2,500-token system prompt with every chat. 400 chats run at once on one GPU. Size the win from prefix caching."

3. "Design KV memory management for an API serving 4 samples per prompt to many tenants." Explain your design and its main trade-off.

Use a paged KV cache with fixed blocks, so memory follows real lengths and each request wastes at most one block. The 4 samples share the prompt's full blocks through reference counts; only the last partly filled prompt block and each sample's new tokens are separate. Turn on prefix caching with a per-tenant salt and the sha256 default, so repeated prompts reuse blocks without leaking across tenants. When memory runs out, the newest request is preempted and recomputed, so cap max_num_seqs and alert on preemptions. The trade-off is overbooking: far more concurrent requests than contiguous reservation, paid for with occasional preemption and recompute.

Named previews of later parts: chunked prefill, which splits long prompts across steps; disaggregated prefill and decode on separate GPUs; KV offloading and connectors, which move blocks off the GPU; and KV cache quantization, which shrinks bytes per token.

In KV memory design, state the number of blocks, who shares them, and what happens when they run out; every senior answer turns on those three.
