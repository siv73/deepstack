Why the server keeps every token's keys and values

Your 8B chat model gets a 2,000-token prompt and writes a 300-token answer. To pick the 300th token, the model needs something from all 2,299 tokens before it. Recomputing that from scratch for every new token would make the answer about seven times slower on an H100, even counting only the weights.

Part 1 said a decode step takes in only the newest token. That only works because the server keeps a per-request store of attention state. This page is about that store: what goes in it, how big it gets, and why it, not the model, decides how many users one GPU can serve.

You already know the pattern. A web app keeps session state in Redis so each request does not rebuild the user's context from the database. The KV cache is the model's session state: the server keeps it for each request so the next token does not rebuild everything.

Hugging Face's guide to caching describes the KV cache as stored key-value pairs from the attention layers of tokens already processed, reused for later tokens so they need not be recomputed. The same guide contrasts the two: without a cache every step recomputes all previous keys and values, while with a cache each step computes only the current token's.

The work without a cache grows with the square of the answer length: 280 times more tokens processed for 300 output tokens. It is "only" seven times slower because Part 1's decode steps wait on memory anyway, so the extra arithmetic partly hides in idle time. Longer answers make the gap ten times and worse.

The KV cache trades GPU memory for not reprocessing the whole sequence on every output token.

A teammate turns off the KV cache "to save GPU memory" on a summarisation endpoint with 2,000-token prompts and 2,000-token answers. What happens?

  1. Answers come back at the same speed with less memory used
  2. Each step reprocesses every earlier token, so total work grows with the square of the answer length and answers get roughly ten times slower
  3. The model produces different, lower-quality answers

Without a cache, step k recomputes keys and values for all earlier tokens. The work adds up quadratically: about 97 s instead of 9.6 s for a 2,000-token answer by the weights-only estimate.

What attention needs from earlier tokens

Last part: the cache saves the model from reprocessing the whole sequence. Still unsolved: what exactly does attention need from earlier tokens, and why can it be saved?

For the word "it" in "The server dropped the request because it timed out", the model must work out what "it" refers to. To do that it looks back at every earlier token in the context, in every layer.

Attention is that look-back. Each token is turned into three vectors. The query is the question the current token asks. The keys and values belong to every token: keys are matched against the query, values are what gets mixed in.

Hugging Face's caching guide writes attention as softmax(QKᵀ/√d_head) × V, where the query, key and value matrices are projections of the input with shape (batch, heads, tokens, d_head).

  1. Old tokens never change: because of the causal mask a token cannot look at later tokens, so once processed its keys and values never change and can be cached and reused.
  2. Only the new query matters: at inference only the newest token's query is needed; at each step its new key and value are appended to the cached ones.
  3. Every layer has its own: attention is computed separately in each layer, so the cache is kept per layer.

In backend terms, keys are an index and values are the rows. Each new token runs one query against the index and reads the matching rows. Old rows are never updated, only appended to, like an append-only log.

Attention needs every earlier token's key and value in every layer, and those never change, so they can be stored once and reused.

Before the next part: for a model with 32 layers, after a 4-token prompt and 2 decode steps, how many key-and-value pairs are in one request's cache?

6 tokens × 32 layers = 192 pairs (each pair is one key and one value, per key/value head). Every processed token adds one pair to every layer, and no stored pair is rewritten while the request runs.

One request's cache, layer by layer

Last part: attention needs each earlier token's key and value in every layer, and they never change. Still unsolved: how does the cache fill up during prefill and decode?

A 4-token prompt asks for an answer. Watch what each phase from Part 1 writes into the cache and what each decode step reads back.

Transformers stores the cache as a list of layers, each holding key and value tensors of shape [batch_size, num_heads, seq_len, head_dim]; in the simplest layer type the seq_len dimension grows with each new token. The vLLM paper notes that the KV cache grows and shrinks as the model generates tokens, and that its lifetime and length are not known in advance.

That last point is where the Redis comparison first strains. A session object has a size you can predict. A request's cache grows by one column per token until the request ends, and the server cannot know in advance how long that will be.

Prefill writes one column per prompt token in every layer; each decode step appends one more column and reads all of them.

Put one request's cache activity in order.

  1. Prefill writes keys and values for all prompt tokens in layer 1
  2. Later layers write their own keys and values for the same prompt tokens
  3. The last layer finishes and the first output token is produced
  4. Decode step 1 appends that token's keys and values in every layer and reads all columns
  5. The request ends and its cache can be freed

Prefill fills the prompt columns layer by layer, which yields output token 1. Each decode step then appends one column across all layers. The cache lives exactly as long as the request.

Sharing key/value heads: MHA, MQA and GQA

Last part: every token adds keys and values to every layer. Still unsolved: how many keys and values does each layer store per token, and can that number shrink?

Attention in each layer is split into many heads, each looking for a different kind of relationship. If every head keeps its own key and value per token, the cache is as large as it can be.

That original design is MHA. Two later designs let query heads share keys and values.

  1. MQA: Shazeer's paper on multi-query attention (MQA) has all query heads share a single set of keys and values. It argues that incremental decoding is slowed by repeatedly loading the large key and value tensors from memory.
  2. GQA: Ainslie et al.'s grouped-query attention (GQA) divides the query heads into groups, and each group shares one key head and one value head. With one group GQA equals MQA; with one group per query head it equals ordinary multi-head attention (MHA).
  3. The trade: The GQA paper reports that MQA can lower quality, and that an existing multi-head model can be converted and further trained with about 5% of its original pre-training compute.

In Hugging Face model configs this is the num_key_value_heads field: equal to num_attention_heads means MHA, 1 means MQA, anything in between is GQA. The cache shrinks in proportion to the key/value heads; the query heads still do all their own work.

The cache stores keys and values per key/value head, so letting query heads share them (GQA, MQA) shrinks it by the sharing factor.

A config has num_attention_heads 64 and num_key_value_heads 8. What does each layer cache per token, compared with MHA?

  1. 64 heads of keys and values, the same as MHA
  2. 1 head of keys and values, a 64th of MHA
  3. 8 heads of keys and values: GQA with groups of 8 query heads, an eighth of MHA

8 key/value heads shared by 64 query heads is GQA with groups of 8. The cache stores 8 heads per token per layer instead of 64.

In your own words: what goes into one request's KV cache, when, and what decides how much is stored per token?

Attention in each layer compares the newest token's query with every earlier token's key and mixes in their values. Those keys and values never change once computed, so the server stores them per request. Prefill stores them for all prompt tokens in every layer; each decode step appends the new token's and reads everything. Per token, each layer stores one key and one value per key/value head, so designs where query heads share key/value heads (GQA, MQA) store less. The cache keeps growing until the request ends.

How many bytes one token costs

Last part: the cache stores one key and one value per key/value head, per layer, per token. Still unsolved: how many bytes is that for a real model?

Your capacity plan needs a number, not a shape. Before you can say how many users fit on a GPU, you need the bytes one token adds to one request's cache.

Multiply out what the last two parts showed. For one token, each layer stores a key and a value for each key/value head. Each of those is a vector of head_dim numbers. In bfloat16 each number takes 2 bytes, which is why Hugging Face's rule of thumb puts X billion parameters at about 2 × X GB.

  1. Per token: 2 (key and value) × layers × key/value heads × head_dim × bytes per number.
  2. Per request: that × the tokens in the request so far, prompt plus output.

Meta's own code matches it. Meta's reference Llama 3 code allocates, in every attention layer, a key cache and a value cache of shape (max_batch_size, max_seq_len, key/value heads on that GPU, head_dim), with head_dim equal to dim divided by n_heads.

From GPU memory to how many requests fit

Last part: Llama 3.1 8B costs 131,072 bytes of cache per token. Still unsolved: how many requests does that let one GPU hold?

Product asks how many simultaneous 8,000-token conversations one H100 can hold with the 8B model. Part 1 says the weights take 16 GB of 80. That leaves room for hundreds of conversations, unless you size the cache.

This page follows vLLM v0.31.0, the same release as Part 1. In vLLM v0.31.0, gpu_memory_utilization is the fraction of GPU memory the model executor may use, 0.92 by default, and it is a per-instance limit. vLLM v0.12.0 defaulted to 0.9. Older guides still quote that number.

  1. Request a share: at startup vLLM requests total GPU memory × gpu_memory_utilization, and refuses to start if less than that is free.
  2. Measure what is not cache: it then runs a profiling forward pass with dummy inputs and gives the KV cache whatever is left of that request after non-KV memory: the weights, the peak activation memory, memory used outside PyTorch and, by default, an estimate of CUDA graph memory.
  3. Report capacity: it then logs the cache size in tokens and the maximum concurrency for requests of max_model_len tokens.

vLLM's tuning guide says it pre-allocates the cache using this percentage of memory, so raising it gives more KV cache space. The pool is claimed up front, like a connection pool sized at boot, not grown on demand.

Decode reads the cache too: Part 1's roofline, corrected

Last part: capacity and decode speed are now one command away. Still unsolved: Part 1 promised that 64 requests share one weight read. Does that hold once each request has a cache?

Part 1 predicted that batching 64 chats on the H100 keeps the step at about 4.8 ms and reaches about 13,400 tokens per second. You load-test with 64 users holding 2,000 tokens each. Steps take about 9.8 ms and you get about 6,500 tokens per second: half the promise.

Part 1 counted one cost per step: reading the weights, shared by every request in the batch. There is a second read. To attend, each request's newest token must read that request's whole cache, in every layer. Nobody else can share that read.

The GQA paper notes that decoder inference is limited by memory bandwidth spent loading the weights and all attention keys and values at every decoding step.

Why batching does not save you here: count the arithmetic per cached byte. For each cached token, each query head does a dot product with a key and a weighted add of a value: 4 × head_dim FLOPs. For Llama 3.1 8B that is 524,288 FLOPs per 131,072 cached bytes, or 4 FLOPs per byte. That 4 is the GQA group size, and it does not change with batch size, because no two requests share a cache.

"We batched 64 requests and got half the throughput our roofline predicted. What did the model miss?" A strong answer: the weights-only roofline treats decode as one shared weight read. Each request also reads its own KV cache every step, at about 4 FLOPs per byte for a GQA model with groups of 4. At 64 × 2,000 tokens that is 16.8 GB, as much as the weights, so the step doubles. The fix is not more FLOPs: fewer cache bytes (shorter contexts, fewer KV heads, a smaller cache data type) or more bandwidth.

Every decode step reads each active request's whole cache, and that read is not shared, so it grows with batch × context and can outweigh the weights.

Same H100 and 8B model. You double the batch from 32 to 64 requests, all with 6,000-token contexts. What happens to the decode step time, by this page's model?

  1. It rises from about 12.3 ms to about 19.8 ms, because cache reads double while the weight read stays the same
  2. It stays at about 4.8 ms, because the weights are read once for the whole batch
  3. It doubles exactly, because every byte read doubles

Weights: 16 GB either way. Cache: 32 × 6,000 × 131,072 bytes ≈ 25.2 GB becomes 50.3 GB. Total reads go from about 41 GB to about 66 GB, so the step grows about 1.61 times while throughput grows only about 1.24 times.

Why long contexts keep decode memory-bound

Last part: each request's cache read is not shared and runs at about 4 FLOPs per byte. Still unsolved: at what batch size does decode finally become compute-bound, as Part 1 said it would at about 296?

An agent team asks for "a bigger batch until the GPU is compute-bound". Their requests carry 8,000 tokens of context. You need to tell them whether any batch size gets there.

Each request in a step brings two things: about 2 FLOPs per parameter of new work, and its whole cache as new bytes to read. Add requests and both grow. The ratio heads toward a ceiling set by context length, not batch size.

  1. Zero context: only weights, so intensity equals batch. It crosses the H100's ridge near 295 at a batch of 296, Part 1's answer.
  2. Short context: each request adds a few bytes, so you need a bigger batch. At 200 tokens, 566.
  3. The cliff: at 418 tokens it takes 130,477 requests. From 419 tokens on, no batch size crosses the ridge.
  4. Typical chat: at 2,000 tokens the ceiling is about 65 FLOPs per byte; at 8,192 tokens, about 19. Both are far below 295.

Fewer key/value heads move the ceiling. The 8B model with MQA would cache 16,384 bytes per token, and its attention does 32 FLOPs per cached byte. At 2,000 tokens it turns compute-bound at a batch of 642, and that many requests fit in its cache. With MHA, attention does 1 FLOP per cached byte, the worst case.

So for long contexts, a bigger batch buys throughput only until the cache is full, and each step gets slower as it grows. The levers are bytes per token and bandwidth, not FLOPs.

With context of more than a few hundred tokens, cache reads keep an 8B model's decode memory-bound at every batch size on an H100.

The agent team switches to a 70B model with GQA groups of 8 (64 query heads, 8 key/value heads). Does its attention do more or fewer FLOPs per cached byte than the 8B model's 4, and why?

More: 8 FLOPs per cached byte. Attention's work scales with query heads, and the cache scales with key/value heads, so the ratio is the group size: 64 ÷ 8 = 8. Its weights are also much larger, so its ceiling at a given context is higher. That still does not make long-context decode compute-bound on one GPU, which it does not fit on anyway.

When the cache fills: what breaks at 10 times the load

Last part: long contexts keep decode memory-bound at any batch. Still unsolved: what happens when more requests arrive than the cache can hold?

Your 8B service holds 50 requests of 8,192 tokens on one H100. Launch brings 10 times the traffic, and a customer starts sending full 128K-token documents. Compute is nowhere near busy. The cache is full.

vLLM's tuning guide says that when KV cache space runs out, vLLM can preempt requests to free space and recompute them once space is available again, which hurts end-to-end latency. In vLLM V1 the default preemption mode is RECOMPUTE rather than SWAP. A preempted request redoes prefill over everything it had, then continues.

  1. What breaks first: cache memory, long before compute. Requests queue for cache space, and some running ones get preempted.
  2. What users see: TTFT climbs as requests wait for space. Preempted streams pause mid-answer while their prefill reruns, which shows up as ITL spikes.
  3. Misuse: each 128K-token request holds about 17.2 GB of cache. Three of them fill the H100's 54.6 GB budget, and everyone else waits.
  4. Detection: vLLM exports vllm:kv_cache_usage_perc, a gauge of how full the KV cache is (0 to 1), next to vllm:num_requests_running. Alert on usage near 1 with waiting requests rising, and on preemption warnings in the logs.
  5. The fix: the tuning guide's suggestions include raising gpu_memory_utilization, lowering max_num_seqs or max_num_batched_tokens, and spreading the model over more GPUs with tensor or pipeline parallelism. Also cap prompt and output tokens per tenant.

"Raise gpu_memory_utilization to 0.99 and the preemptions stop." From 0.92 to 0.95 on an 80 GB H100 adds 2.4 GB of cache: 53 requests of 8,192 tokens instead of 50. That is 6% more room for 10 times the load. Because vLLM checks at startup that its requested share is free, a value near 1 also breaks startup whenever anything else holds GPU memory. Capacity problems at 10 times the load need more GPUs or fewer bytes per request.

"GPU utilization is low, but latency spiked after a big customer onboarded. What do you check?" A strong answer checks the cache, not compute: vllm:kv_cache_usage_perc near 1, waiting requests climbing, preemption warnings, and the prompt-length histogram for very long requests. The fix trades something: a per-tenant context cap protects other users but rejects some documents; more GPUs cost money; a model with fewer key/value heads may cost quality.

At high load the cache fills before compute does; vLLM then queues and preempts, so watch cache usage and cap long requests.

Dashboards show vllm:kv_cache_usage_perc pinned near 1, waiting requests rising, and occasional ITL spikes of several seconds. Which explanation fits best?

  1. Prefill is compute-bound and the GPU needs more FLOPs
  2. The cache is full, so new requests wait and some running ones are preempted, pausing while their prefill is recomputed
  3. The tokenizer is slow on long prompts

A full cache blocks new admissions (waiting rises) and forces preemption. In V1 a preempted request is recomputed, so its stream stalls for a prefill: the ITL spikes.

In your own words: why did Part 1's batching promise fall short, and what fails first when load grows ten times?

Part 1 counted only the weight read, which a batch shares. Each request also reads its own cache every step, at only about group-size FLOPs per byte, so batch × context bytes pile on top of the weights. With more than a few hundred tokens of context, no batch size makes an 8B model compute-bound on an H100. Under ten times the load the cache fills first: requests wait, some are preempted and recomputed, and TTFT and ITL spike. You see it as cache usage near 1 and waiting requests rising, and you fix it with fewer bytes per request or more GPUs.

Interview drill and final check

Last part: cut bytes per request first, then add memory. Still unsolved: can you size and defend a deployment under interview pressure?

Three prompts an interviewer could open with. Commit to an answer before revealing each one; each reference answer names the trade-off.

Prompt 1: "Serve Llama 3.1 8B to 200 concurrent chats of up to 4,096 tokens of context. How many H100s?"

Size the cache, not the FLOPs. Per token 131,072 bytes; per 4,096-token chat about 0.54 GB. Budget per H100: 0.92 × 80 GB − 16 GB weights − about 3 GB reserve ≈ 54.6 GB, so about 101 chats. 200 chats need 2 GPUs, each a separate copy of the model, with almost no slack: plan a third for headroom and failover. Decode at 101 chats is memory-bound, about 21 ms per step, about 4,800 tokens per second per GPU. The trade-off: capping context lower fits more chats per GPU but refuses longer conversations.

Prompt 2: "We doubled the max batch for our agents (6,000-token contexts) and ITL got 60% worse for only 24% more throughput. Why?"

Each step reads the weights once plus every request's cache. At 6,000 tokens per request, going from 32 to 64 requests raises cache reads from about 25 GB to 50 GB, so steps go from about 12.3 ms to 19.8 ms. Attention runs at about 4 FLOPs per cached byte, so decode never turns compute-bound. The trade-off is explicit: throughput per GPU against ITL per user. Set the batch limit from the ITL SLO, not from "fill the GPU".

Prompt 3: "Why can't long-context decode be made compute-bound by batching more?"

Each request adds its own cache read to every step, and attention does only group-size FLOPs per cached byte. As the batch grows, intensity approaches a ceiling set by context: about 65 FLOPs per byte at 2,000 tokens for the 8B model, far below the H100's ridge near 295. Levers that help are fewer bytes per token (fewer key/value heads, a smaller cache data type) and more bandwidth. Each costs quality, accuracy or money.

Every serving capacity question starts by sizing the cache: bytes per token, times tokens, against memory left after the weights.

Attention needs every earlier token's key and value in every layer, and they never change, so the server stores them per request instead of reprocessing the sequence each step. Per token that costs 2 × layers × key/value heads × head_dim × bytes: 131,072 bytes for Llama 3.1 8B, which uses GQA to share key/value heads. vLLM requests 0.92 of GPU memory by default and gives the cache what is left after the weights and runtime, so one H100 holds about 50 requests of 8,192 tokens.
