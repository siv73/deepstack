Why the app shouldn't get your password

PrintNest, a photo-printing site, wants 40 photos from your photo cloud. The old way: you type your photo-cloud password into PrintNest.

That one step goes wrong in three ways:

  • PrintNest can now do anything you can: read your email, delete every photo, change your password.
  • To cut PrintNest off, you must change your password, which also breaks every other app that stored it.
  • PrintNest now stores a password it can leak.

Think of a valet key. It starts the car but won't open the boot, and you can cancel it without changing the locks. PrintNest needs a valet key, not your house keys.

  1. PrintNest sends you to your photo cloud's own login page.
  2. You log in there. PrintNest never sees the password.
  3. You approve one thing: "PrintNest may read photos".
  4. The photo cloud hands PrintNest a limited key.
  5. PrintNest uses the key. You can cancel it any time.

This hand-over is OAuth 2.0. The spec names four roles: the resource owner (you), the client (the app), the authorization server (issues the keys) and the resource server (hosts the data). This page uses plain names: you, PrintNest, the login server and the Photos API.

OAuth lets an app act for you with a limited, cancellable key, and the app never sees your password.

You want to stop PrintNest but keep your other apps working. With OAuth, what do you do?

  1. Change your photo-cloud password
  2. Cancel PrintNest's key at your photo cloud
  3. Delete your PrintNest account

Each app gets its own key, so you can cancel one without touching the others.

In your own words: why is handing your password to a third-party app a bad design, and what does OAuth do instead?

A password gives the app everything you can do, forever, and the only way to take it back is to change the password for every app. OAuth sends you to the login server you already trust. You log in there and approve a narrow permission. The app gets a limited key that you can cancel on its own.

The key is a token, and whoever holds it can use it

Last part: the app gets a limited key instead of your password. Still unsolved: what is that key, and how does the API check it?

PrintNest now sends 40 requests for 40 photos. The Photos API must decide, 40 times, whether each request is allowed.

Think of a hotel key card. The front desk checks your ID once and programs a card for room 412 until Friday. The door never asks your name. It only checks the card.

The card is an access token. An access token is a string that represents an authorization issued to the client. What it allows is its scope, for example "read photos" but not "delete photos".

The door-card comparison has a sharp edge. Whoever holds a bearer token can use it; they don't have to prove they own any key. A copied card opens the door just as well.

Clients send the token in the Authorization header using the Bearer scheme: Authorization: Bearer followed by the token.

GET /v1/photos?album=holiday HTTP/1.1
Host: photos.example.com
Authorization: Bearer eyJ0eXAiOiJhdCtqd3Qi...

The spec says bearer tokens should not be passed in page URLs, because URLs end up in places like browser history and logs.

An access token is a key card with a scope: the API checks the card, not you, and anyone holding the card can use it.

A teammate proposes GET /photos?access_token=eyJ... because it's easier to test. What's the real problem?

  1. URLs are too short for tokens
  2. The API can't read tokens from the query string
  3. The token gets copied into history and logs, where anyone who reads them can use it

A bearer token works for whoever holds it, so every place it gets written down is a place it can be stolen from.

The login dance, step by step

Last part: the key is a bearer token the API checks on every request. Still unsolved: how does the token get from the login server to PrintNest safely?

You log in on the login server's site, in your browser. PrintNest runs on its own servers. How would you get the token from the login server to PrintNest without exposing it?

Split it into two hops. Your browser carries only a short-lived, one-time code back to PrintNest. PrintNest's server then trades that code for the token by calling the login server directly, server to server. The token never passes through the browser.

This two-hop design is the authorization code flow. Step through it below; every later part adds to this picture.

The parameters have exact names you'll see in every library. The authorization request carries response_type=code and client_id, and usually redirect_uri, scope and state. PKCE adds two parameters to that request: code_challenge and code_challenge_method.

The browser carries only a one-time code; the token itself travels server to server.

Put the core of the flow in order.

  1. PrintNest redirects your browser to the login server
  2. You log in and approve
  3. The login server redirects back with a code
  4. PrintNest trades the code (plus secret) for a token, server to server
  5. PrintNest calls the Photos API with the token

Redirect out, approve, redirect back with a code, trade the code on the back channel, then use the token.

Why a code first, and not the token straight away

Last part: the browser carries a code, and the token moves server to server. Still unsolved: why not skip the code?

Every redirect is a URL your browser visits, so everything in it passes through your machine and whatever is watching it. Treat anything in a redirect URL as half-leaked.

So OAuth uses two channels. The front channel is the browser redirect: useful, but leaky. The back channel is a direct server-to-server call. Valuable things go on the back channel.

The code on the front channel is built to be worth little:

  • The spec says the code must expire shortly after it is issued and recommends a maximum lifetime of 10 minutes.
  • The client must not use an authorization code more than once. If a code is used more than once, the login server must deny the request.

The implicit grant skipped the code and put the access token straight into the redirect. RFC 9700 says clients should not use the implicit grant (response type token), because access tokens returned in the redirect can leak and be replayed. RFC 9700 was published in January 2025 as a Best Current Practice.

The front channel carries only a short-lived, single-use code; anything valuable moves on the back channel.

An attacker finds a code in your browser history 30 minutes after you logged in. Why is it useless to them?

  1. It should have expired (10 minutes is the recommended maximum), and PrintNest already spent it, so a second use is denied
  2. Codes are encrypted
  3. The attacker doesn't know your password

Codes are meant to die within minutes and be spent once. The next part covers the window before that.

PKCE: making a stolen code worthless

Last part: codes are short-lived and single-use. Still unsolved: what if an attacker grabs the code in the first few seconds and redeems it first?

PKCE was designed against an attack where a malicious app on the same device intercepts the code meant for the real app. The thief can redeem the code well inside the 10-minute window.

Think of a cloakroom ticket torn in half. You keep one half. The coat comes back only to someone holding the matching half.

That is PKCE:

  1. The app makes a code_verifier: a random string of 43 to 128 characters drawn from letters, digits and the symbols - . _ ~.
  2. With the S256 method, the code_challenge is BASE64URL(SHA256(code_verifier)). Only this hash goes in the redirect.
  3. The login server stores the hash alongside the code.
  4. At the token endpoint the server transforms the code_verifier and compares it with the stored challenge; if they differ, it returns an invalid_grant error.

An attacker steals the code and races PrintNest to the token endpoint. They send the code but make up a verifier. What happens?

The login server hashes the made-up verifier. The result doesn't match the stored challenge, so the request fails with invalid_grant. The attacker can't reverse the hash to find the real verifier, and the real one never left PrintNest.

RFC 9700 notes that PKCE was designed to protect native apps, but its advice now applies to all kinds of clients, including web applications.

  • RFC 9700 says public clients must use PKCE and recommends it for confidential clients too.
  • Clients should use S256, currently the only PKCE method that doesn't expose the verifier in the authorization request.
  • Authorization servers must support PKCE and must reject a token request with a code_verifier when the authorization request carried no code_challenge.

If code_challenge_method is left out, it defaults to plain, where the challenge is the verifier itself. Old code sometimes relies on that. Always send S256.

PKCE binds the code to a secret only the real app holds, so a stolen code can't be redeemed.

Explain PKCE to a teammate who thinks "the code is short-lived, so we don't need it".

Short-lived isn't enough, because an attacker who intercepts the redirect can redeem the code within seconds. With PKCE the app creates a random verifier, keeps it, and sends only its SHA-256 hash in the redirect. To trade the code for a token, the app must present the original verifier. The server hashes it and compares. A thief who has the code but not the verifier fails, and the verifier never travelled through the browser.

Short-lived tokens, and how to renew them

Last part: PKCE makes a stolen code worthless. Still unsolved: a stolen access token still works until it expires. How long should that be?

Make the access token last a year and a stolen one works for a year. Make it last 10 minutes and you must log in again every 10 minutes. Neither is acceptable.

The fix is a second, longer-lived key that is used in only one place. That is a refresh token.

  • Refresh tokens are used only with the authorization server and are never sent to resource servers.
  • The client exchanges a refresh token at the token endpoint with grant_type=refresh_token, and the server may issue a new refresh token at the same time.

How much to trust the app depends on where it runs. The spec splits clients into confidential clients, which can keep a secret (typically server-side apps), and public clients, which can't (native apps and apps running in the browser).

A refresh token sitting on a phone is a juicy target, so public clients get an extra rule:

  • For public clients, RFC 9700 requires refresh tokens to be sender-constrained or rotated.
  • Rotation means every refresh returns a new refresh token and invalidates the previous one. If an old refresh token is used again, which happens when both a thief and the real app hold it, the login server can detect the reuse and revoke the active refresh token.

Access tokens stay short-lived; a refresh token, shown only to the login server, renews them without a new login.

The PrintNest phone app stores a refresh token on the device. What does RFC 9700 require for it?

  1. Encrypt it with PrintNest's client secret
  2. Bind it to a key the app holds (sender-constrained), or rotate it on every use
  3. Never give phone apps refresh tokens

A public client can't keep a secret, so the refresh token itself must be either unusable elsewhere or single-use.

Build it: the client side in Python

Last part: short access tokens plus refresh tokens. Still unsolved: what does correct client code look like?

The client is about 30 lines. Most real bugs come from three shortcuts: skipping the state check, sending PKCE as plain, and keeping the verifier somewhere the browser can see.

The token request sends grant_type=authorization_code and the code, plus the redirect_uri if the first request had one, and with PKCE the code_verifier; a client that doesn't authenticate also sends its client_id. A server-side PrintNest would authenticate itself here, because it is a confidential client.

This code was run against a small stand-in login server that checks S256. Four results:

  • Normal login: token issued.
  • Same code sent twice: rejected with invalid_grant.
  • Stolen code with a made-up verifier: rejected with invalid_grant.
  • Callback with a state PrintNest never issued: rejected before any network call.

Login servers must compare the redirect URI you send with the registered one character for character, apart from the port of a localhost redirect for native apps. https://photos.example.com/callback and https://photos.example.com/callback/ are different strings. A trailing slash is enough to break login.

"Where do you keep the state and the verifier between the redirect and the callback?" A strong answer: in a server-side session tied to the user's browser (a secure, HTTP-only cookie pointing at it), never in the redirect URL, and deleted after one use. Then say why: the state proves the callback belongs to this browser's login, and the verifier must never travel through the browser.

A correct client makes a fresh state and S256 verifier per login, keeps both server-side, checks state first, then redeems the code once.

PrintNest's callback receives a code, but the state doesn't match the one in the session. What should it do?

  1. Ignore the state and redeem the code
  2. Retry the token request with the old state
  3. Reject it without calling the token endpoint, and restart the login

A state mismatch means this browser didn't start this login. Fail closed: stop before trading the code, even if you also use PKCE.

Build it: the API checks every token

Last part: the client gets a token correctly. Still unsolved: what exactly must the Photos API check before trusting it?

The Photos API takes 2,000 requests a second, each with a token. Skip one check and a token meant for another service, or an expired one, gets in.

When the login server issues access tokens as signed JWTs, the API can check them locally. RFC 9068 says a JWT access token must declare itself in its typ header, normally as at+jwt, which lets APIs tell it apart from other JWTs such as ID tokens.

  • The resource server must check that typ is at+jwt, that iss exactly matches the expected issuer, that aud contains its own identifier, that the signature is valid, and that exp is in the future, and must reject tokens with alg none.
  • Required claims in a JWT access token are iss, exp, aud, sub, client_id, iat and jti.
  • If scopes were requested, the token should carry them in a scope claim.

Run against test tokens, it accepted the valid one and rejected each of these: wrong audience, wrong issuer, expired, an ID token, alg: none, a token signed by another key, and a token missing the needed scope.

When a token is rejected, the error invalid_token goes with HTTP 401 and insufficient_scope with HTTP 403.

PyJWT's documentation warns never to build the algorithms list from the token's own alg header. If you trust the token to say how it was signed, an attacker picks the algorithm.

An API trusts a token only after checking type, signature with a fixed algorithm, issuer, audience, expiry and scope.

A token arrives with a valid signature from your login server, but its aud is the billing API. What should the Photos API do?

  1. Accept it: the signature is valid
  2. Reject it with 401 invalid_token
  3. Reject it with 403 insufficient_scope

The audience check stops a token issued for one service from being replayed at another.

Explain what "doing OAuth correctly" means on the client side, on the API side, and when choosing a flow.

The client creates a fresh random state and an S256 PKCE pair for every login, keeps both in a server-side session, rejects callbacks with the wrong state, and redeems each code once. The API checks the token type, verifies the signature with a fixed algorithm list, and checks issuer, audience, expiry and scope before serving anything. The flow depends on who is present: code plus PKCE for people, client credentials for machines, device flow for TVs and CLIs.

Attacks on the redirect

Last part: pick the flow by who is present. Still unsolved: the redirect runs through a browser an attacker can steer. Where does it break?

An attacker can't touch PrintNest's servers, but they can send you a link. Every attack below starts with your browser visiting a URL the attacker built.

  1. Loose redirect matching. If the login server accepts "anything starting with" the registered URL, the attacker picks a redirect that lands on their site, and the code goes to them. Authorization servers must compare redirect URIs by exact string match; the only exception is the port of a localhost redirect for native apps.
  2. Open redirectors. Clients and authorization servers must not expose open redirectors, pages that forward the browser to any URL given in a query parameter. An exact-match redirect that then bounces anywhere is no better than a loose one.
  3. Forged callbacks (CSRF). The attacker makes your browser deliver their code to PrintNest, so you end up using the attacker's account. Clients must prevent CSRF, either with a one-time state value bound to the user's browser or by relying on PKCE when the authorization server is known to support it.
  4. Mix-up. An app that trusts several login servers can be tricked into sending a code to the wrong one. Such a client should use the iss response parameter to tell the servers apart, or failing that, a distinct redirect URI per server.

A login server accepts any redirect URI that starts with https://printnest.com. What URL would an attacker register or use?

Something like https://printnest.com.attacker.io/cb. It starts with the allowed prefix but is a different domain the attacker owns. The code lands on their server. Exact string matching closes this attack.

A tempting shortcut: allow any subdomain so preview deployments like https://pr-123.printnest.dev/callback work. Then any subdomain an attacker can take over becomes a place to receive codes. Register each redirect URI explicitly instead.

"PKCE is on. Do we still need the state parameter?" A strong answer: PKCE also stops injected codes, and RFC 9700 allows a client to rely on PKCE for CSRF protection once it has ensured the login server supports PKCE. Keep state anyway if you can't guarantee that support, or if you need it to carry where to send the user after login. Show you know both jobs.

The redirect is only as safe as its matching: exact URIs, no open redirectors, and state or PKCE on every login.

A login server accepts any redirect URI under https://photos.example.com/. PrintNest also has a page /go?next= that forwards the browser anywhere. What can an attacker do?

  1. Nothing: the code never leaves PrintNest's domain
  2. Redeem the code without PKCE
  3. Set the redirect URI to /go?next= their site, so the code is forwarded to them

Loose matching plus an open redirector hands the code to the attacker. That's why both rules exist: exact matching, and no open redirectors anywhere.

When a token is stolen

Last part: attacks on the redirect. Still unsolved: attackers who skip the flow and steal tokens that were already issued.

In April 2022, attackers used OAuth user tokens stolen from two GitHub integrators, Heroku and Travis CI, to list and clone private repositories of dozens of organisations. GitHub spotted it when a compromised AWS key was used to access npm's production infrastructure; it revoked the tokens tied to its own use of the affected apps and asked Heroku and Travis CI to revoke all the others.

No flow was broken there. The tokens were valid, just held by the wrong people. Bearer tokens can't tell the difference, so defence is about limiting what a stolen token can do and for how long.

  1. Keep them narrow. RFC 9700 says access tokens should be audience-restricted to a specific resource server and limited to the privileges needed.
  2. Keep them short. A stolen token that expires in minutes is a small problem. Pair short tokens with refresh tokens.
  3. Bind them to the sender. RFC 9700 says authorization and resource servers should use sender-constrained access tokens, through mutual TLS (RFC 8705) or DPoP (RFC 9449).
  4. Be able to kill them. The revocation endpoint takes a token by POST, and revoking a refresh token should also invalidate the access tokens issued from the same grant, if the server supports that.

DPoP turns a bearer token into one that only works with its owner's private key. With DPoP the client signs a small proof JWT for each request with its private key; the proof names the HTTP method and URL, includes a hash of the access token when calling an API, and travels in a DPoP header.

"A partner tells you your OAuth tokens leaked from their logs. Walk me through the next hour." A strong answer: revoke the partner's refresh tokens and grants, so access tokens die at expiry; for high-risk APIs, block the partner's client ID or switch those APIs to introspection so revocation bites immediately; pull API logs by client ID for unusual reads; tell affected users. Then the fix: shorter lifetimes, audience-restricted tokens, and sender-constrained tokens for that partner.

A stolen bearer token works until it expires, so make tokens narrow, short-lived, revocable, and ideally bound to a key.

An attacker copies a DPoP-bound access token from a log file. Why can't they use it?

  1. The token is encrypted
  2. Every request needs a fresh proof signed with the client's private key, which the attacker doesn't have
  3. The API only accepts it from the client's IP address

The token is bound to a key pair. Without the private key, the attacker can't produce the per-request proof.

What breaks first at 10× traffic

Last part: limit what a stolen token can do. Still unsolved: checking tokens costs something on every request. What happens when traffic grows?

The Photos API goes from 200 to 2,000 requests a second. Every one of them carries a token that must be checked. There are two ways to check.

  • With token introspection the API POSTs the token to the authorization server, which answers with JSON whose required active field says whether the token is currently valid.
  • RFC 7662 describes the caching trade-off: a longer cache cuts load on the introspection endpoint, but a revoked token can stay usable until the cache entry expires.
  • For local checks, the authorization server can publish its signing keys at a jwks_uri listed in its metadata, and RFC 9068 says it should do so for resource servers. By default that metadata lives at /.well-known/oauth-authorization-server on the issuer's host, placed before any path the issuer URL has.

PyJWT's decode function takes a leeway argument that allows a small margin when checking expiry, for clocks that are slightly out of sync.

"Your API validates JWTs locally. How do you make revocation fast enough?" A strong answer names the trade-off: local checks can't see revocation, so keep access tokens short (minutes) and revoke refresh tokens; for the few endpoints where seconds matter (payouts, admin), use introspection with a short cache. You pay latency only where the risk justifies it.

Introspection buys instant revocation with a network call per request; local JWT checks buy speed and give up revocation until expiry, so most systems mix the two.

Your API is growing 10×. Explain which token-checking approach you'd use and what breaks first with each.

Introspection asks the login server about every token, so at 10× the introspection endpoint takes 10× the calls and its latency is added to every request; caching helps but delays revocation. Local JWT checks scale with the API because they only need cached public keys, but a revoked token keeps working until it expires, and key rotation or clock skew can cause sudden 401s. I'd use short-lived JWTs checked locally for most endpoints and introspection with a short cache for the few high-risk ones.

OAuth is not login: where OpenID Connect fits

Last part: scale and revocation trade-offs. Still unsolved: PrintNest wants to show "Hi, Asha". Can it use the access token for that?

An access token says what PrintNest may do. It doesn't reliably say who is sitting at the keyboard, or that they logged in just now.

OpenID Connect is an identity layer on top of OAuth 2.0; OAuth by itself does not tell the app who the user is or how they authenticated.

  • An OpenID Connect request must include openid in its scope.
  • OpenID Connect adds the ID token, a JWT whose required claims include iss, sub, aud, exp and iat, with aud including the client's ID. The ID token is for the app; the access token is for the API.

For single-page apps the question is where tokens live. RFC 10017 (August 2026), on browser-based apps, strongly recommends the Backend for Frontend pattern for business applications, sensitive applications and apps that handle personal data. In a BFF a server-side component acts as the confidential OAuth client and keeps the tokens, so there are no tokens in the browser to steal. RFC 10017 notes one attack remains: someone who hijacks the app inside the user's browser can still act through it, a problem inherent to web applications.

RFC 6749 is still the core OAuth 2.0 spec; RFC 8252, RFC 8996 and RFC 9700 update it. OAuth 2.1, which folds these best practices into one document meant to replace RFC 6749 and RFC 6750, is still an IETF working-group draft as of September 2026. This page follows RFC 9700's rules.

OAuth answers "what may this app do"; OpenID Connect answers "who is this user". Use each for its own question.

PrintNest's new single-page app must show "Hi, Asha" and call the Photos API. Which design fits current guidance?

  1. OpenID Connect through a BFF: the ID token identifies Asha, the backend keeps the access token and calls the API
  2. Decode the access token in the browser to get her name
  3. Use the implicit grant to get a token faster

Identity comes from the ID token; API access comes from the access token; and the BFF keeps tokens out of the browser.

Interview drill: three designs

Last part: OAuth for access, OpenID Connect for identity. Now use all of it the way an interviewer will ask.

Expect OAuth to come up inside a design, not as a definition. For each prompt, write your answer before revealing.

Design 1. You're building a mobile app for a lending startup. It calls your own APIs for balances and repayments. How do users sign in and how does the app call the APIs?

Authorization code + PKCE (S256) in the system browser, with OpenID Connect for sign-in. Access tokens short-lived and audience-restricted to the lending API. Refresh tokens rotated on every use, because a phone app is a public client. The API validates JWTs locally; repayment endpoints use introspection with a short cache so a revoked session stops within seconds.

Trade-off to say out loud: introspection on repayments adds a network call; you accept that latency for money-moving endpoints only.

Design 2. Forty internal microservices call each other. Security wants each call authenticated and limited. What do you do?

Client credentials, one client per service. RFC 9700 recommends asymmetric client authentication, such as mutual TLS or signed JWTs with a private key, over shared secrets. Tokens audience-restricted per target service with narrow scopes, validated locally with a cached key set.

Trade-off to say out loud: a login server on the hot path of service start-up is a dependency; cache tokens until shortly before expiry and alert on token-endpoint errors.

Design 3. When an employee leaves, their access to every internal tool must stop within one minute. Tools use OAuth. How?

Revoke the employee's refresh tokens and grants at the login server, which may also kill the access tokens from those grants if the server supports it. Access tokens validated locally must then expire within the minute, so keep them very short, or have the sensitive tools introspect with a cache under a minute.

Trade-off to say out loud: one-minute revocation costs either very frequent refreshes or introspection traffic. Say which tools deserve it.

In a design, OAuth decisions are trade-offs between revocation speed, latency and blast radius; say which one you're paying for and why.

Final teach-back: explain OAuth end to end, as you would at the start of a design interview. The problem, how it works, how you'd build it, what breaks, and when you'd pick something else.

Apps need to act on a user's data without holding the user's password, with access that's limited and revocable. In the code flow the user logs in at the login server; the browser carries back only a short, single-use code; the app trades it for a token on a direct server call, with PKCE proving it's the same app that started. The client keeps state and the verifier server-side; the API checks the token's type, signature with a fixed algorithm, issuer, audience, expiry and scope. It breaks at the redirect (loose matching, open redirectors, CSRF), through stolen bearer tokens, and at scale through introspection load or slow revocation. Use code with PKCE for users, client credentials for services, the device flow for TVs and CLIs, OpenID Connect when you need identity, and a BFF to keep tokens out of single-page apps.
