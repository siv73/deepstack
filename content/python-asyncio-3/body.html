The system so far, and what this page adds to it

Part 2 ended with gateway v3: five seller Tasks on asyncio's real loop, talking to five real seller servers. It answers seller-b at 1,199 in 250 ms. But three of its pieces are hand-made: the budget is a call_later timer that cancels Tasks by hand, "wait for all five" is a Future with a counter and five done callbacks, and nothing limits how many seller calls are open at once.

Introduction

This is Part 3 of a ten-part series. Every part works on the same system: a price-comparison gateway that asks five sellers for a price and must answer within a budget of 250 ms. Parts 1 and 2 are the prerequisites for this page. This part recaps them in one screen; if any line below is unfamiliar, read that part first.

What Parts 1 and 2 built

  1. The five sellers: seller-a (80 ms, 1,249), seller-b (120 ms, 1,199), seller-c (150 ms, 1,229), seller-d (200 ms, 1,215) and seller-e (900 ms, 1,149). The right answer within 250 ms is seller-b at 1,199, with seller-e missing.
  2. Part 1: asked one after another, the waits add up to 1,450 ms. Overlapped on one thread with a toy event loop, the request takes 900 ms, the slowest seller.
  3. Part 2: the sellers became real TCP servers on this machine. asyncio's loop waits on their sockets with a selector (epoll on Linux, kqueue on macOS), runs callbacks with call_soon and timers with call_later, and hands results over in Futures.
  4. A Task is a Future that drives a coroutine step by step. When a seller's coroutine raises, its Task stores the exception, so one failing seller no longer ends the request.
  5. At high load, every open connection is a file descriptor, and a process may hold only so many: about 1,600 seller connections at 10 times the load, against a limit that may be 1,024.

What was still broken

  • No structured way to run many Tasks: waiting for all five is hand-made, and a Task nobody reads can lose its result or its error.
  • No limits: nothing caps how many seller calls are in flight.
  • No deadlines: the budget is a hand-made timer, and nothing gives a single call a deadline inside the request's.

This page fixes all three with three standard tools: a TaskGroup to start and wait for the seller calls, a Semaphore to cap calls in flight, and asyncio.timeout_at to turn the 250 ms budget into a real deadline. Then it asks what happens to those tools at 10 times the load.

Why two awaits in a row still take the sum

Last part: Part 3 replaces gateway v3's hand-made pieces. Still unsolved: why does the gateway need Tasks at all? Is await not enough to make the calls overlap?

A teammate writes the gateway in the most natural way: await seller-a, then await seller-b. Both calls are async def; the code runs on asyncio's real loop. Yet the request takes 200 ms for two sellers, not 120 ms, and 1,460 ms for all five.

Introduction

Many engineers believe that writing async def and await is what makes code run at the same time. It is not. await pauses the coroutine that wrote it until the awaited thing is finished. If the code awaits one call, then the next, the second call does not even start until the first is finished. This part shows the difference with real seller calls and the numbers from Part 1.

Comparison

Consider two errands: posting a parcel (80 minutes in the queue) and collecting a suit from the tailor (120 minutes). If you stand in the post office queue and only then walk to the tailor and wait there, the afternoon takes 80 + 120 = 200 minutes. If you hand the parcel to one friend and the suit ticket to another before either queue starts, you get both back after 120 minutes, the longer of the two.

  • Standing in one queue, then the next = await one call, then await the next.
  • Handing each errand to a friend first = creating a Task for each call before awaiting any of them.

The comparison stops working here: friends are extra people. Tasks are not extra threads; all of them still take turns on the loop's one thread, which is free to switch whenever a Task is waiting.

Definition

Two calls run sequentially when the second starts only after the first has finished, so their times add up. They overlap when both are in progress during the same period, so the total is about the longer of the two. An await on a coroutine runs that coroutine to the end before the next line runs, so a list of awaits is sequential.

Working

  1. await ask_seller(seller-a): seller-a's coroutine runs inside the gateway's coroutine. It opens a connection, sends the item code and waits for the answer.
  2. While it waits, the gateway's coroutine is paused at that await. The loop is free, but nobody has asked it to start seller-b.
  3. At 80 ms seller-a answers; the await returns; only now does the next line run.
  4. await ask_seller(seller-b) starts seller-b at 80 ms; it answers at 80 + 120 = 200 ms.
  5. With Tasks: create_task() for both first. Each Task's first step runs as soon as the gateway gives the loop a turn, so both connections are open at about 0 ms, and the gateway then awaits the Tasks.

Why each step matters

  • Step 2 is the whole point: a paused coroutine does not start the work written after it. Something must have been started before the pause.
  • Step 5: a Task is the "something started before the pause". Part 2 showed that create_task() schedules the Task's first step with call_soon; the loop runs it at its next iteration.

In the docs' own example, awaiting say_after(1, ...) and then say_after(2, ...) takes about 3 seconds, and creating both as Tasks first takes about 2.

Wrong belief: "Making a function async def makes its calls run concurrently."

Why people hold it: the word "async" suggests "in the background".

Why it is wrong: async def only makes a function that can pause. Whether calls overlap depends on whether more than one of them has been started before the code pauses. Part 1 showed the same mistake on the toy loop: for s in SELLERS: await ask_seller(...) took 1,450 ms.

  • await pauses the coroutine that wrote it until the awaited thing finishes.
  • Awaits in a row are sequential: 80 + 120 = 200 ms for seller-a then seller-b.
  • Calls overlap only if they were started (as Tasks) before the code pauses: max(80, 120) = 120 ms.

Two awaits in a row take the sum of their times, because the second call does not start until the first await returns; overlap needs both calls started first.

The gateway awaits seller-d (200 ms), then creates Tasks for seller-a and seller-b and awaits both. How long does the request take?

About 320 ms. seller-d is awaited alone first, so nothing else starts until 200 ms. Then seller-a and seller-b start together at 200 ms and the longer of them, seller-b, answers at 200 + 120 = 320 ms. Only the calls started together overlap; the first await still adds its full 200 ms.

In your own words: why do two awaits in a row take 200 ms for seller-a and seller-b, and what change brings it to 120 ms?

An await pauses the coroutine until the awaited call has finished. The line after it, which starts seller-b, only runs at 80 ms, when seller-a has answered, so seller-b answers at 80 + 120 = 200 ms. If both calls are wrapped in Tasks before the code awaits anything, both start at once, the loop overlaps their waits, and the request takes the longer of the two: 120 ms.

A coroutine waits to be awaited; a Task is already on the loop

Last part: overlap needs calls started as Tasks before the code pauses. Still unsolved: what exactly is the difference between awaiting a coroutine and creating a Task, and when does each one's code run?

A handler calls ask_seller(...) and gets back a coroutine object. Another handler calls asyncio.create_task(ask_seller(...)) and gets back a Task. One of them has already been put on the loop's ready queue; the other will never run unless someone awaits it. Which is which, and in what order does their code run?

Introduction

Part 1 built coroutines from generators, and Part 2 showed a Task driving a coroutine with send(). This part puts the two side by side in the order an application meets them, because every tool on this page (gather, TaskGroup, as_completed) either takes coroutines and wraps them in Tasks, or takes Tasks directly.

Comparison

A recipe card and a cook. The card says what to do, but nothing happens until someone picks it up. Handing the card to a cook in the kitchen means the dish will be made when the cook gets a free moment, whether or not you stand there watching.

  • The recipe card = a coroutine object.
  • Following the recipe yourself, right now, until it is done = await coro.
  • Handing it to the kitchen = asyncio.create_task(coro); the kitchen is the loop.

The comparison stops working here: the kitchen has one cook who switches dishes only when a dish is waiting (for the oven, say). A Task's code runs only when the loop gets a turn.

Definitions

  1. A coroutine object is what calling an async def function returns. The docs say that calling a coroutine function does not schedule it to run; it only creates a coroutine object.

  2. asyncio.create_task() wraps a coroutine into a Task and schedules its execution; it raises RuntimeError if there is no running loop in the current thread. The docs say to save a reference to the Task that create_task() returns, because the event loop keeps only weak references to tasks.

Working

  1. task = create_task(note("task")): the Task's first step goes into the ready queue. Nothing of note has run.
  2. await note("coroutine"): the coroutine runs right here, inside the caller, to its end. It never yields, so the loop gets no turn and the Task still has not run.
  3. await asyncio.sleep(0): the caller's first real pause. The loop runs one iteration, and the Task's first step runs then.
  4. await task: the Task is already done, so the await returns at once.

Why each step matters

  • Step 2: awaiting a coroutine gives the loop a turn only if that coroutine actually waits on something. A coroutine that finishes without waiting runs like an ordinary function call.
  • Step 3: a Task's code starts at the caller's first pause, not at create_task(). This is Part 2's call_soon at work.

Program

Explanation of the program

  2. Lines 2 and 3: the awaited coroutine ran in place, before the Task, even though the Task was created first.
  3. Line 4: the Task ran at the first real pause, sleep(0), before the line after it (line 5).
  4. The last line: a Task wraps a coroutine. The Task is what the loop schedules; the coroutine is what the Task drives.

gather(): many calls, one list of results in argument order

Last part: only Tasks put calls on the loop. Still unsolved: creating five Tasks and awaiting each one is repetitive. Is there one call that starts them all and collects their results?

The gateway needs all five offers in one list so it can pick the cheapest. Writing five create_task lines and five await lines is tedious, and gateway v3's done-callback counter is worse. asyncio.gather() has been the usual one-line answer for years.

Introduction

gather() is the oldest of this page's tools. It is still everywhere in real code and interviews, so it is taught first. Its behaviour when one call fails is the reason TaskGroup was added; this part states that behaviour, and the "When it breaks" rung measures it.

Comparison

A teacher hands out five exam papers at once and collects them in roll-number order, however early each student finishes. If one student is caught cheating, the teacher walks out to report it at once, and the other students keep writing; nobody tells them to stop.

  • Handing out the papers = gather scheduling every awaitable.
  • Collecting in roll-number order = results in argument order.
  • Walking out while the others keep writing = the first exception propagating while the other calls continue.

Definition

gather() runs its awaitables concurrently, and any coroutine passed to it is automatically scheduled as a Task. If all succeed, gather() returns a list of results in the order of the awaitables passed, not necessarily the order in which the results arrived.

Working

  1. gather wraps each coroutine in a Task, so all five seller calls are in flight together.
  2. It waits until every Task is done, then returns their results as a list in argument order.
  3. A failure, by default. With return_exceptions=False, the default, the first exception is immediately propagated to the task awaiting gather(), and the other awaitables are not cancelled and continue to run.
  4. A failure, collected. With return_exceptions=True, exceptions are treated the same as successful results and placed in the result list.
  5. gather itself cancelled. If gather() itself is cancelled, every submitted awaitable that has not completed yet is also cancelled.

Why each step matters

  • Step 2: argument order lets the caller match each result to its call without names.
  • Step 3 is the dangerous default: the caller has moved on, but the other calls still hold connections and may still fail, and nobody is waiting to read those failures.
  • Step 4 is safe but slow: gather waits for every call, including seller-e's 900 ms.

Program

The sellers are passed slowest first, so finishing order and argument order differ.

  2. The answers print in finishing order (a at 80 ms, … e at 900 ms), but the returned list is in argument order: seller-e first.
  3. With return_exceptions=True and seller-c failing, gather still waits 900 ms, and seller-c's place in the list holds its SellerError.

  • gather wraps coroutines in Tasks and returns results in argument order.
  • Default: the first exception is raised at once; the other calls keep running.
  • return_exceptions=True: exceptions come back in the list, after every call finishes.

TaskGroup: start a group of Tasks, wait for all, fail together

Last part: gather raises the first failure and leaves the other calls running. Still unsolved: how do we start the five seller calls so that the gateway always waits for all of them, keeps a reference to each, and stops the rest when one fails unexpectedly?

Gateway v3 needed about a dozen lines of hand-made code (a list of Tasks, a counter, a Future and a done callback on each Task) to wait for five calls, and it still had no answer for "one call failed in a way we did not expect: stop the others". A TaskGroup does all of it in one async with block.

Introduction

Python 3.11's release notes recommend TaskGroup for new code over using create_task() and gather() directly. This part first states what a TaskGroup promises, then opens CPython's source to show that it is gateway v3's hand-made waiting, done properly.

Comparison

A school trip. The teacher writes every child's name on a list before leaving, and the bus does not leave the museum until every name is ticked off. If one child is badly hurt, the teacher calls everyone back at once, waits until all of them are on the bus, and then reports what happened.

  • The list of names = the group's set of Tasks (strong references).
  • The bus waiting = the end of the async with block waiting for every Task.
  • Calling everyone back = cancelling the remaining Tasks on the first failure.
  • The report = the ExceptionGroup raised at the end.

The comparison stops working here: a child who is late is still waited for. A TaskGroup has no deadline of its own; the deadline comes later on this page.

Definition

A TaskGroup starts Tasks and owns them until they finish. asyncio.TaskGroup, added in Python 3.11, is an asynchronous context manager holding a group of tasks: tasks are added with its create_task() method, and all of them are awaited when the context manager exits. Running Tasks this way, so that no Task outlives the block that started it, is called structured concurrency.

Working

  1. async with asyncio.TaskGroup() as tg: enters the group.
  2. tg.create_task(coro) creates a Task exactly like asyncio.create_task, and the group keeps it.
  3. At the end of the block, the group waits until every Task is done.
  4. A failure. The first time a task in the group fails with an exception other than CancelledError, the remaining tasks are cancelled, no further tasks can be added, and the task running the async with body is also cancelled if the body is still active.
  5. The report. Once all tasks have finished, the failures other than CancelledError are combined into an ExceptionGroup or BaseExceptionGroup, which is raised.
  6. The body itself fails. If the body of the async with block raises, this is treated as if a task failed: the remaining tasks are cancelled and waited for, and the body's exception, unless it is CancelledError, is included in the group.

If a task fails with KeyboardInterrupt or SystemExit, the group still cancels and waits for the remaining tasks, then re-raises that exception instead of an exception group.

A group has no "stop now" button. Terminating a task group early is not natively supported; the docs show adding a task that raises a custom exception and catching it with except*.

Why each step matters

  • Step 2: the group holds a strong reference, which fixes Part 2's weak-reference warning. The create_task() docs recommend TaskGroup because it keeps a strong reference to each task, awaits them and propagates their exceptions.
  • Step 3: no Task can outlive the block, so nothing is left running when the request answers.
  • Step 4: a failure nobody expected stops the work that no longer matters, instead of leaving it running as gather does.
  • Step 5: every failure is reported, not only the first.

Inside: the hand-made waiting from Part 2, packaged

In CPython 3.14's taskgroups.py, a TaskGroup keeps its tasks in a set, adds a done callback to each task, and its __aexit__ awaits a Future that the done callback completes once the set is empty. When a task in the group fails, that done callback cancels every task that is not done yet and then cancels the parent task, which interrupts the await in the async with body. Compare gateway v3: a list of Tasks, a done callback that counts down, and a Future all_done filled by the last callback. The group adds the cancelling, the error collecting and years of tested corner cases.

Wrong belief: "TaskGroup is gather with a nicer syntax."

Why it is wrong: the difference is what happens on failure and who owns the Tasks. The group cancels the rest and always waits for every Task before raising; gather raises at once and leaves the others running. And a Task created in a group cannot outlive the block, while a Task created with gather can.

  • Create Tasks with tg.create_task(); the block's end waits for all of them.
  • First failure: cancel the rest, wait for them, raise an ExceptionGroup of every failure.
  • Inside: a set of Tasks, a done callback each, and one Future, gateway v3's waiting done properly.

A TaskGroup owns its Tasks: it waits for all of them, and on the first unexpected failure it cancels the rest and raises every failure as one ExceptionGroup.

Handling several failures at once: ExceptionGroup and except*

Last part: a TaskGroup raises every failure as one ExceptionGroup. Still unsolved: an ordinary except SellerError does not match a group. How does code handle the SellerErrors in it one way and the connection errors another?

In one request, seller-c and seller-b both answer ERROR and seller-d refuses the connection. The TaskGroup raises one ExceptionGroup holding two SellerErrors and one ConnectionRefusedError. The gateway wants to log seller errors as "seller problem" and connection errors as "network problem".

Introduction

ExceptionGroup, BaseExceptionGroup and the except* syntax were added in Python 3.11 (PEP 654). TaskGroup was added in the same release and is their main user in asyncio.

Comparison

A sorting office receives one sack holding letters and parcels. The letters counter takes out the letters; the parcels counter takes out the parcels. Anything nobody takes out is sent back up the line in a new sack.

  • The sack = the ExceptionGroup.
  • Each counter = an except* clause.
  • The new sack sent back up = the unmatched exceptions propagating on.

Definitions

  1. An ExceptionGroup is an exception that holds several exceptions, in its exceptions attribute. (A BaseExceptionGroup is the same for exceptions that do not derive from Exception.)

  2. except* T handles the part of a group that matches T. An except* clause matches by type against the exceptions inside the group: each clause splits the group into a matching subgroup, which its body handles, and a non-matching subgroup, which goes on to the next except* clause. After all except* clauses have run, the exceptions no clause matched propagate on as a new exception group.

Working

  1. The group (SellerError c, ConnectionRefusedError d, SellerError b) reaches except* SellerError. Its body runs once, with a subgroup of the two SellerErrors.
  2. The rest (ConnectionRefusedError d) goes to except* OSError. ConnectionRefusedError is a subclass of OSError, so it matches, and that body runs once.
  3. Nothing is left, so nothing propagates and the code after the try runs.
  4. If something were left over (say a ValueError from a bad price), it would be raised on, in a new ExceptionGroup, after both clauses had run.

A try statement can have except clauses or except* clauses but not both, and break, continue and return cannot appear in an except* clause.

Program

Explanation of the program

  1. Three of the four Tasks raise in the same loop iteration, so all three failures are collected before the group's done callbacks cancel anything.
  2. Each except* body runs once with a group, not once per exception: group.exceptions holds both SellerErrors.
  3. In the second block only SellerError is handled; the ValueError is raised on in a new ExceptionGroup and caught by the outer plain except ExceptionGroup.

Solved example

Given: a group of [SellerError c, ValueError e] and one clause, except* SellerError.

as_completed(): act on each answer the moment it arrives

Last part: except* handles the failures a group collects. Still unsolved: gather and TaskGroup both hand results back only when everything is done. What if the gateway wants to act on each offer as soon as it arrives?

A product manager asks for a "fast path": if any seller offers the kettle at 1,200 or less, answer at once. seller-b offers 1,199 at 120 ms. With gather or a TaskGroup, the gateway would only see it at 900 ms, when seller-e finishes.

Introduction

as_completed() hands back each call as it finishes, in finishing order. It is the tool for "first good result wins", progress reporting, and streaming partial results. Its one trap is what happens to the calls you stop waiting for.

Comparison

A takeaway counter calls out order numbers as each meal is ready, not in the order people ordered. You walk up when your number is called. If you get bored and leave, the kitchen keeps cooking the meals that nobody will collect, unless someone tells it to stop.

Definition

as_completed() runs the awaitables concurrently and returns an object that can be iterated to get their results as they finish. With async for, as_completed() yields the original Task or Future objects as they finish, which makes it easy to tell which call finished.

Working

  1. Create the five seller Tasks and pass them to as_completed().
  2. async for done in as_completed(tasks) yields seller-a's Task at 80 ms, seller-b's at 120 ms, and so on.
  3. The loop body checks the price and breaks at the first offer of 1,200 or less.
  4. The gateway must now cancel the Tasks it no longer needs. as_completed() does not cancel the remaining tasks: if a timeout occurs or the iteration is cancelled, they continue to run.

With a timeout, as_completed() raises TimeoutError if the timeout occurs before all awaitables are done.

Why each step matters

  • Step 2: yielding the original Tasks means done.get_name() says which seller it was.
  • Step 4 is the trap: leaving the loop does not stop the calls. Without the cancel, seller-c, seller-d and seller-e keep their connections open, and seller-e holds its connection for 900 ms with nobody waiting.

Program

Explanation of the program

  2. seller-b's 1,199 is good enough at 120 ms, so the loop breaks.

Eager tasks: when a Task starts running inside create_task()

Last part: as_completed hands back calls in finishing order. Still unsolved: everything so far assumed Part 2's rule that a Task's first step waits for the loop's next iteration. Python 3.12 added a way to change that rule. What changes, and when is it worth it?

The gateway caches recent prices. For a cached item, cached_price() returns at once without awaiting anything. Yet each lookup still creates a Task, puts its first step in the ready queue and waits for the next loop iteration, only to return a value that was available immediately.

Introduction

Scheduling a Task's first step through the ready queue costs a little time and a trip round the loop. For coroutines that often finish without waiting, that cost is pure overhead. An eager task runs its first step immediately, inside create_task().

Definition

With eager_task_factory, added in Python 3.12, coroutines begin running synchronously during Task construction, and a task is scheduled on the event loop only if it blocks. The docs name coroutines that use caching or memoization to avoid real I/O as a common case where eager execution helps. The Task constructor's eager_start parameter was added in Python 3.12, and asyncio.create_task() accepts eager_start since 3.14; when it is not passed, the mode set by the loop's task factory is used.

Working

  1. create_task(coro, eager_start=True) (or a loop whose task factory is asyncio.eager_task_factory) runs the coroutine at once, inside the call.
  2. If the coroutine returns or raises without awaiting anything that waits, the Task is done before create_task() returns.
  3. If the coroutine waits (a cache miss that asks a seller), the Task is scheduled on the loop as usual from that point.

The docs call eager execution a semantic change: a coroutine that returns or raises without blocking is never scheduled to the event loop, and the application's task execution order is likely to change.

Program

Explanation of the program

  1. Default (eager_start=False): "after create_task" is logged first, and the Task is not done yet; the lookup runs at the await task.
  2. Eager: "lookup started" is logged inside create_task(), and the Task is already done when create_task() returns.
  3. With the eager factory and a cache miss, the lookup starts inside create_task(), reaches await asyncio.sleep(0.12), and from there is scheduled normally: not done after create_task().

  • Eager: the coroutine runs inside create_task() until it first waits.
  • Helps coroutines that often finish without waiting, such as cache hits.

Capping calls in flight: the Semaphore

Last part: eager tasks change when a Task's first step runs. Still unsolved: none of the tools so far limits how many calls run at once. Part 2 showed 10 times the load needing about 1,600 open connections. What keeps the count bounded?

During a sale, 2,000 requests per second each start five seller calls the moment they arrive. Nothing in gather, TaskGroup or as_completed says "no more than N at a time", so the gateway opens as many connections as it has calls, until the file descriptor limit or a seller gives out.

Introduction

The standard tool for "at most N at a time" is a semaphore. Every seller call takes a slot before it starts and gives it back when it ends; when no slot is free, the call waits in line. This part uses a deliberately small cap of 3 so the waiting is easy to see.

Comparison

A car park with 3 spaces and a barrier. A car enters only if a space is free; otherwise it queues at the barrier. When a car leaves, the first car in the queue goes in.

  • The number of free spaces = the semaphore's counter.
  • Entering = acquire(); leaving = release().
  • The queue at the barrier = tasks waiting in acquire().

The comparison stops working here: a car park counts cars, but a semaphore counts nothing it can check. If code releases without having acquired, the counter simply grows.

Definition

A Semaphore manages a counter that each acquire() decrements and each release() increments; the counter can never go below zero, and acquire() waits while it is zero until some task calls release(). Semaphore(value) starts the counter at value, 1 by default, and raises ValueError if value is less than 0. The preferred way to use a Semaphore is async with, which the docs show is equivalent to await acquire(), then the block in a try, with release() in the finally.

Working

  1. limit = asyncio.Semaphore(3): three free slots.
  2. seller-a, seller-b and seller-c enter async with limit at 0 ms and take the three slots.
  3. seller-d and seller-e find the counter at 0 and wait inside acquire().
  4. At 80 ms seller-a finishes and its async with releases the slot; seller-d, first in line, takes it.
  5. At 120 ms seller-b releases; seller-e takes the slot.

asyncio's synchronization primitives are not thread-safe, and their methods take no timeout argument; the docs point to asyncio.wait_for() for timeouts. Gateway v4 does the same job with timeout_at around the async with, as the timeouts part explains.

In CPython 3.14's locks.py, an acquire() that has to wait puts a Future on the Semaphore's deque of waiters, and release() wakes the first waiter that is not done, so waiters get slots in first-in, first-out order. That is Part 2's pattern once more: a waiting coroutine is parked on a Future, and someone else fills it.

Why each step matters

  • Step 2: the cap does not slow anything while there are free slots.
  • Step 3: the cap turns "too many calls" into "calls waiting in line", which costs time but not connections.
  • Steps 4 and 5: async with releases in a finally, so a slot comes back even when the call fails or is cancelled.

Program

Explanation of the program

  1. Only three calls start at 0 ms. seller-d starts at 80 ms, in seller-a's freed slot; seller-e starts at 120 ms, in seller-b's.
  2. seller-d answers at 80 + 200 = 280 ms, and seller-e at 120 + 900 = 1,020 ms.
  3. The most calls in flight at once is 3, never more.

Why it is wrong: it changes neither the speed of a call nor the work done; it only decides when each call may start. With five calls of different lengths, what it does to the total depends on the order in which slots free up, which is why the table above works it out call by call.

Real deadlines: asyncio.timeout, timeout_at and wait_for

Last part: a Semaphore caps calls in flight. Still unsolved: the 250 ms budget is still gateway v3's hand-made call_later. What is the standard way to say "stop waiting at this time"?

seller-e answers at 900 ms. The request must answer at 250 ms. And a request that first waits 80 ms for seller-a and then asks seller-e must still stop at 250 ms from the start, not 250 ms after seller-e was asked.

Introduction

asyncio has three tools for this. Two of them are context managers that put a deadline on a block of code: asyncio.timeout(delay) counts from now; asyncio.timeout_at(when) takes an absolute time on the loop's clock. The third, wait_for(), puts a timeout on one awaitable. All three are, underneath, Part 2's budget: a timer on the loop that cancels a Task.

Comparison

An exam has a fixed end time, written on the board: 12:00. A student who arrives late still stops at 12:00. That is timeout_at. "You have three hours from when you start" is timeout: each student's end time depends on when they began.

Definitions

  1. A deadline is the absolute time at which waiting must stop. asyncio.timeout(delay) returns an asynchronous context manager; if the work inside takes longer than delay seconds, it cancels the current task and turns the resulting CancelledError into a TimeoutError. That TimeoutError can only be caught outside the async with block.

  2. asyncio.timeout_at(when) is like asyncio.timeout(), except that when is the absolute time to stop waiting, measured on the event loop's clock. delay can be None for no limit; the deadline can be changed later with reschedule(), and expired() says whether the context manager exceeded its deadline. Timeout context managers can be safely nested; asyncio.timeout() and timeout_at() were added in Python 3.11.

  3. wait_for(aw, timeout) cancels aw and raises TimeoutError when the timeout occurs, and it waits until aw is actually cancelled, so the total wait can exceed the timeout. Since Python 3.12, wait_for() is implemented using asyncio.timeout(), and a coroutine passed to it is no longer wrapped in a Task when the timeout is positive.

Working: how a timeout cuts a call

In CPython 3.14's timeouts.py, timeout(delay) creates Timeout(loop.time() + delay); entering it schedules a callback with loop.call_at() for that time, the callback calls the task's cancel(), and leaving the block cancels that timer.

  1. Entering async with asyncio.timeout(0.25) at 1,000.00 on the loop clock puts a timer on Part 2's timer heap, due at 1,000.25.
  2. The body awaits seller-e. The loop's select() timeout is bounded by that timer, exactly as in Part 2.
  3. At 1,000.25 the timer runs and calls cancel() on the current Task: CancelledError is thrown in at seller-e's readline(), and its finally closes the connection.
  4. The CancelledError travels out of the block. The context manager's exit sees that it caused it and raises TimeoutError instead.
  5. If the body finishes first, the exit cancels the timer handle: nothing fires.

Why each step matters

  • Step 1: the deadline is a single timer, so it costs nothing while waiting.
  • Step 4: turning the cancellation into TimeoutError means the caller can tell "this block ran out of time" from "someone cancelled the whole request".
  • Step 5: this is what gateway v3's hand-made budget lacked: a timer that is always cleaned up when the work ends early.

Program

Explanation of the program

  2. timeout_at(start + 0.25) around two calls: seller-a answers at 80 ms, and seller-e is cut at 250 ms from the start, not 80 + 250 = 330 ms. One deadline covers the whole block.
  3. wait_for(…, 0.25) gives the same 250 ms for a single call.
  4. Nested: the inner 0.1 s timeout fires first and its TimeoutError is caught inside the outer block, which then asks seller-b: 100 + 120 = 220 ms, inside the outer 250 ms.

Wrong belief: "try: … except TimeoutError inside the async with asyncio.timeout() block will catch the timeout."

Why it is wrong: inside the block the timeout arrives as a CancelledError; only the context manager's exit turns it into TimeoutError. The docs say the TimeoutError can only be caught outside the block. A handler inside sees CancelledError, and if it swallows that, the timeout breaks.

  • timeout(d): d seconds from now; timeout_at(t): absolute loop time t. Both cancel, then raise TimeoutError outside the block.
  • wait_for(aw, t): one awaitable; built on timeout() since 3.12.
  • Underneath: one call_at timer and Task.cancel(), Part 2's budget done properly. Nested deadlines: the earliest wins.

Gateway v4: a TaskGroup, a shared cap and one deadline per request

Last part: timeout_at gives one absolute deadline. Still unsolved: putting TaskGroup, Semaphore and deadline together in the gateway, so that it answers within 250 ms with partial results, reports each seller's fate, and never leaves a call running.

Gateway v4 must answer "cheapest: seller-b at 1,199 after 250 ms; timed out: seller-e", with seller-a to seller-d answering. A failing seller must be reported, not end the request. And all requests in the process must share one cap on calls in flight.

Introduction

Three decisions shape gateway v4. First, which failures belong in the TaskGroup: a seller answering ERROR or timing out is normal data for a price-comparison gateway, so each call catches those and returns them as values; only real bugs reach the group. Second, where the cap lives: one Semaphore per gateway object, created once per process and shared by every request. Third, what the deadline covers: the wait for a slot as well as the call.

Working

  1. compare() computes deadline = start + 0.25 on the loop's clock.
  2. Inside async with asyncio.TaskGroup() it creates one Task per seller, running _ask().
  3. _ask() enters timeout_at(deadline) first, then async with self.limit, then calls the seller. Waiting for a slot therefore counts against the deadline.
  4. A TimeoutError, a SellerError or an OSError is caught inside _ask() and returned as a value. Any other exception (a bug) escapes and makes the group cancel the rest.
  5. When the group's block ends, every Task is done. Results are sorted into offers, timed-out sellers and failed sellers.

Why each step matters

  • Step 1: one absolute deadline for all five calls, so no call can push the request past 250 ms.
  • Step 3: if the deadline started only after the slot was taken, a call stuck in the line could still run for a full 250 ms afterwards. The "When it breaks" rung measures this.
  • Step 4: a seller failure stays out of the group, so it cannot cancel the other four calls. A bug still does, which is what the group is for.
  • Step 5: the group guarantees that nothing is left running when the gateway answers.

Program

Explanation of the program

  2. In _ask(), timeout_at(deadline) is the outer block, so both the wait in async with self.limit and the seller call are inside the deadline.
  3. Run 1 (cap of 100): seller-a to seller-d answer by 200 ms; seller-e is cut at 250 ms and reported as timed out.
  4. Run 2 (cap of 3): seller-d gets a slot only at 80 ms and would answer at 280 ms, so it is cut at 250 ms too, the semaphore part's table with a deadline added.
  5. Run 3: seller-c's ERROR is reported as failed; the other calls go on. Compare the TaskGroup part, where the same failure cancelled seller-d and seller-e.

Production defaults vs tutorial defaults

Last part: gateway v4 runs the five calls in a group, under a shared cap and one deadline. Still unsolved: the values on this page (a cap of 3, a 250 ms budget, raw TCP sellers) are chosen to teach. What changes in a real service, and what do the usual client libraries do by default?

A team moves gateway v4 to production with an HTTP client library in place of raw streams. They keep the library's defaults. Under load, a slow seller holds requests for minutes, not 250 ms, and the library's own connection limit quietly queues calls the gateway thought were in flight.

Introduction

Real services rarely talk raw TCP; they use an HTTP client with its own connection pool and its own timeouts. Those defaults are tuned to "do not fail for no reason", not to a 250 ms budget. This part lists what each default is, from the libraries' own docs, and what a gateway like ours sets instead.

Definition

A connection pool is the set of connections a client library keeps open and reuses, with a maximum size. When every connection is busy, a new call waits for one. It is a semaphore built into the client.

What two common clients do by default

  • HTTPX's connection pool defaults to max_connections=100 and max_keepalive_connections=20, with idle keep-alive connections expiring after 5 seconds. HTTPX raises a TimeoutException after 5 seconds of network inactivity by default, and has separate connect, read, write and pool timeouts; the pool timeout limits the wait for a connection from the pool and raises PoolTimeout.
  • aiohttp's TCPConnector allows 100 simultaneous connections by default (limit=100) and has no per-host limit by default (limit_per_host=0). aiohttp's default timeout is a total of 300 seconds (5 minutes) for the whole operation. aiohttp's connect timeout covers getting a connection from the pool, including waiting for a free connection when the pool limits are exceeded; it is not set (None) by default.

  2. Need each result as it arrives: as_completed() over Tasks created with tg.create_task inside a TaskGroup. Cancel the rest once you have your answer; the block's end then waits until they have all finished cleaning up.

  4. Only one awaitable: timeout() or wait_for(), no grouping tool at all.

Probing question: "Why did Python add TaskGroup when gather already existed?"

What a strong senior answer contains: gather has no ownership: when one call fails, the error returns while the other calls keep running, and nothing guarantees that they finish or that their errors are read. TaskGroup is structured concurrency: every Task belongs to a block, the block does not end until every Task is done, and a failure cancels the rest and reports all errors as an ExceptionGroup. The trade-off: a TaskGroup fails as a unit, so partial-result fan-outs must catch their expected errors per call, as gateway v4 does.

Wrong belief: "asyncio.wait(tasks, timeout=0.25) is the same as putting a 250 ms timeout on the tasks."

Why it is wrong: it only stops waiting. It raises nothing, cancels nothing, and its timeout counts from when wait() was called. The batch job in the problem left calls running for hours because nothing cancelled the pending set.

  • TaskGroup: owns its Tasks; the default for new code.
  • gather: argument order; leaves calls running on failure.
  • as_completed: finishing order; cancel the rest yourself.
  • wait: done and pending sets; no exception and no cancelling on timeout.

Use a TaskGroup with a deadline and a cap by default; reach for as_completed for results in finishing order, and treat gather and wait as tools that never clean up after themselves.

Expected failures and timeouts are returned as values, so one bad call does not cancel the other 499; bugs still fail the group. At 40 ms per call, 10 rounds of 50 take about half a second. If the API slows to 180 ms, only 5 rounds fit in the second, so about 250 calls answer and 250 are reported as timed out: a partial report on time, with the API never overloaded.

Prompt 2: "Our fan-out uses gather and sometimes hangs for minutes"

The code is results = await asyncio.gather(*calls) with an HTTP client on default settings. Name the two most likely causes and the fix.

First, there is no request deadline: gather has no timeout of its own, and the client's default (for aiohttp, 300 seconds in total) is far longer than the request's budget, so one stuck downstream holds the request for minutes. Second, when a call fails, gather returns the error but leaves the other calls running, so stuck calls accumulate. Fix: run the calls in a TaskGroup inside one asyncio.timeout or timeout_at for the request, return expected errors as values, and cap calls in flight. The trade-off is a partial answer at the deadline instead of a complete one late.

Prompt 3: "Where does the deadline go?"

A colleague writes async with limit: and then async with asyncio.timeout(1): around each call. The report has a 1 s promise. What goes wrong at peak, and what is the one-line fix?

The timer starts only after a call gets a slot, so time spent waiting in line is not counted: at peak, calls wait for slots and then still get a full second each, and the report runs well past 1 s (the pool-wait part measured requests at about 1,770 ms against a 250 ms budget). The fix is to swap the two lines and use one absolute deadline: async with asyncio.timeout_at(deadline): outside async with limit:.

Wrong belief: "A higher cap always makes the fan-out faster."

Why it is wrong: past the downstream's capacity, a higher cap only moves the queue from the gateway to the downstream, where abandoned calls still cost work (the overload part: 90 wasted jobs without a cap, 20 with one). The cap should match what the downstream can take, not what the gateway can send.

  • Cap from the downstream's capacity; deadline around the wait and the call; failures as values; one TaskGroup.
  • Rounds = calls ÷ cap; time ≈ rounds × call time; compare with the deadline.
  • Say what is given up: partial results on time instead of complete results late.

A senior fan-out answer is four decisions and one sum: a cap from the downstream's capacity, a deadline around the wait, failures as values, one TaskGroup, and calls ÷ cap × call time against the deadline.
