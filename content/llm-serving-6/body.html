Why a token costs what it costs, and the two ways to cut it

Your 8B chat service on one H100 decodes one request at about 200 tokens per second. The GPU's math units sit mostly idle. Buying a faster GPU of the same memory speed would barely help.

Part 1 showed why. Every decode step reads all the model's weights from GPU memory to produce one token per request. At 2 bytes per parameter, that is 16 GB of reading per step for an 8B model. Memory speed, not arithmetic, sets the pace. Hugging Face's docs say the main options for faster generation are quantizing the model or using hardware with more memory bandwidth.

If each step is "read everything, then emit one token", there are only two ways to make each token cheaper:

  1. Read fewer bytes per step. Store each weight in fewer bits. That is quantization.
  2. Get more tokens out of each read. Let a cheap model guess several next tokens, and have the big model check all the guesses in one pass. That is speculative decoding.

A delivery van makes the same comparison. The trip time is fixed by the road, not the engine. You either pack lighter boxes so one van does the job (quantization), or you deliver several parcels per trip instead of one (speculation).

Both levers attack the same bottleneck from different sides. That is also why they combine: smaller weights make each check cheaper, and speculation makes each check yield more.

Decode is limited by bytes read per token, so either shrink the bytes (quantization) or raise the tokens per read (speculative decoding).

A team's 8B model decodes at batch 1 on an H100. Which change would speed up each token the most?

  1. A GPU with twice the FLOPs and the same memory bandwidth
  2. Storing the weights in 8 bits instead of 16
  3. Moving the API server to a bigger CPU

Halving the bytes per weight halves the bytes each step reads, which is what limits decode at batch 1.

What "8-bit" and "4-bit" mean in bytes

Last part: fewer bytes per weight means faster decode. Still unsolved: what exactly gets smaller, and what stays at 16 bits?

A vendor says "INT4 Llama, runs on a 24 GB card". Is that the weights, the cache, or the math? Each answer changes your memory plan.

A quantized weight is a small integer or small float plus a shared scale. To use it, the GPU multiplies back by the scale. The bytes per parameter:

FormatBytes per weight8B model's weights
BF16 (no quantization)216 GB
FP8 or INT818 GB
INT40.54 GB, plus scales

vLLM's docs describe two FP8 layouts: E4M3, with 4 exponent and 3 mantissa bits, reaching ±448, and E5M2, with 5 exponent and 2 mantissa bits, reaching ±57,344 at lower precision. In GPTQ, storing one scale per group of 128 weights adds about 0.15 bits per weight.

There are two kinds of scheme, and the name tells you which:

  1. Weight-only (W4A16, W8A16): smaller weights, but the multiply still runs in 16 bits. Hugging Face's guide explains that such weights are dequantized to BF16 for each matrix multiply.
  2. Weight and activation (W8A8): the multiply itself runs in 8 bits, on Tensor Cores built for it.

The KV cache is a third, separate choice. A "4-bit model" can still keep a 16-bit cache.

Snowflake makes the same trade with storage. Snowflake stores each micro-partition by column, compresses each column on its own, and chooses the compression algorithm itself. Fewer bytes on disk means less to scan, the same reason quantized weights decode faster. The comparison breaks on one point: Snowflake's compression gives back exactly what you stored. Quantization rounds, so the model you serve is not exactly the model you trained.

Quantization names three separate choices: weight bytes, the precision of the multiply, and the KV cache's bytes.

The 70B Llama 3.1 model in INT4 weight-only. Roughly how many GB of weights, and does it fit on one 80 GB H100?

70 billion × 0.5 bytes is about 35 GB, plus small scales. It fits, with roughly 35 GB left for the KV cache after vLLM's usual reserves. In BF16 the same model needs 140 GB and does not fit.

How to round weights without breaking the model

Last part: what the formats cost in bytes. Still unsolved: rounding 8 billion numbers to 16 levels each sounds like it should ruin the model. Why doesn't it?

Plain rounding to the nearest 4-bit level is called RTN. In the GPTQ paper's table, 4-bit RTN takes OPT-125M's WikiText2 perplexity from 27.65 to 37.28. Two published methods do much better.

Perplexity is the usual first quality measure. Lower is better.

GPTQ: fix the error as you go.

  1. GPTQ quantizes one linear layer at a time, choosing quantized weights that keep the layer's output on a small calibration set close to the original.
  2. Within a layer it quantizes columns in a fixed order and, after each, adjusts the not-yet-quantized weights to cancel the error, using second-order (inverse Hessian) information.
  3. Its calibration set is 128 random 2,048-token segments from the C4 dataset, and it quantizes weights only.

AWQ: protect the weights that matter.

  1. AWQ observes that protecting about 1% of salient weights sharply cuts quantization error, and that salient channels are found from activation sizes, not weight sizes.
  2. Instead of keeping those channels in higher precision, it multiplies them by a scale above 1 and divides their inputs by the same scale, which shrinks their relative rounding error.
  3. AWQ uses no backpropagation or weight reconstruction, and it quantizes weights only, in groups of 128 by default, keeping activations in 16 bits.

Both are post-training: no retraining, minutes to hours of GPU time. GPTQ reports quantizing a 175B-parameter model in about four GPU hours.

GPTQ corrects rounding error column by column; AWQ shields the few channels that large activations make important.

AWQ finds that 1% of channels matter most. Why doesn't it simply keep those channels in FP16?

  1. Mixed precision inside one matrix is hard to run fast; scaling keeps every weight in the same format
  2. FP16 channels would double the model size
  3. FP16 channels cannot be trained with backpropagation

A matrix with a few FP16 columns among INT4 ones needs awkward kernels. Scaling the important channels up before rounding protects them while every weight stays INT4.

One speculative round: guess, check, keep a prefix

Last part: shrinking each read. Still unsolved: getting more than one token out of each read of the big model.

At batch 1 the 8B model reads 16 GB to emit one token. Reading 16 GB to score five positions costs about the same, because the math was idle anyway. Can we use those spare four slots?

Chen et al. note that scoring a short draft continuation with the large model in parallel takes about as long as sampling one token from it. So a small draft guesses k tokens, and the big target model checks them all in one pass.

Leviathan et al. keep a draft token when the draft's probability for it is at most the target's, and otherwise reject it with probability 1 − p/q. On rejection they sample a replacement from the normalized positive part of the target's minus the draft's distribution. Both papers show that tokens produced this way follow the target model's own distribution, so output quality does not change.

A backend comparison: optimistic concurrency control. In DynamoDB's optimistic locking, a save succeeds only if the item's stored version still matches the one you read; otherwise it fails and you reload and retry. Speculation also works ahead without a lock and validates afterwards. Where it breaks: a failed write is all-or-nothing, while speculation keeps the valid prefix and repairs the first bad token on the spot. The repair is not a retry; it is the special resample that keeps the distribution exact.

The draft proposes, the target verifies all guesses in one pass, keeps the agreed prefix and adds one token of its own, so output matches the target exactly.

Put one round in order.

  1. The draft guesses k tokens one by one
  2. The target scores all k positions plus one more in a single pass
  3. Guesses are accepted left to right until the first rejection
  4. The target samples a correction at the rejected position, or a bonus token if none was rejected
  5. The accepted tokens and the target's token stream to the user together

Guess, verify in one pass, keep the agreed prefix, add the target's own token, emit together.

How many tokens a round buys you

Last part: one round yields between 1 and k + 1 tokens. Still unsolved: how many on average, and what the draft's time costs you.

With k = 4 guesses and a 70% chance each guess is accepted, does a round yield 4 tokens? 2.8? Less than 1? The answer decides whether speculation pays.

Call the chance a guess is accepted the acceptance rate α. If every position has the same acceptance chance α, the expected tokens per target pass are (1 − α^(k+1)) / (1 − α).

For k = 4 and α = 0.7: (1 − 0.7⁵) / 0.3 ≈ 2.77 tokens per pass. Each extra guess adds less, because a later guess counts only if every earlier one passed.

The draft is not free. The paper's cost coefficient c is the time of one draft run divided by one target run, and it was always under 0.05 in their experiments. Their expected wall-time improvement is (1 − α^(k+1)) / ((1 − α)(kc + 1)), assuming long generations and enough spare compute that verifying k + 1 tokens takes no longer than one target step. With c = 0.05: 2.77 / 1.2 ≈ 2.3 times faster.

Watch out for two different "acceptance rates". vLLM reports a draft acceptance rate (accepted draft tokens ÷ proposed draft tokens) and a mean acceptance length (1 + accepted draft tokens per verification step). The mean acceptance length is the formula's tokens per pass. vLLM's rate is (2.77 − 1) / 4 ≈ 44%, not the 70% per-guess α, because every guess after the first rejection counts as proposed but can never be accepted.

Where the van comparison stops working: extra parcels per trip are free only while the van has room. Part 1's roofline is that room, and rung 4 shows when it fills up.

Tokens per pass = (1 − α^(k+1)) / (1 − α); the speed-up divides that by the draft's cost, and vLLM's acceptance rate is a different, lower number.

vLLM reports a mean acceptance length of 1.2 with k = 5. What is happening?

  1. Speculation is giving about 5 tokens per pass
  2. 1.2 draft tokens are accepted per step, a healthy rate
  3. About 0.2 draft tokens are accepted per step; the draft rarely matches and most guesses are wasted

Mean acceptance length is 1 plus accepted draft tokens per step. At 1.2, each round pays for 5 guesses and keeps 0.2 of them.

Explain to a teammate why speculative decoding is faster without changing the answers.

At small batches a decode step is spent reading weights, so scoring several positions in one pass costs about the same as scoring one. A cheap draft guesses k tokens; the target scores them all at once. Each guess is kept with probability min(1, p/q), left to right, and at the first rejection the target samples from the leftover part of its distribution. That rule makes the output follow the target's distribution exactly. The gain is the expected tokens per pass, (1 − α^(k+1)) / (1 − α), divided by the draft's cost, k·c + 1.

What quantization costs in quality, and how to measure it

Last part: the speed and capacity gains. Speculation keeps outputs exact; quantization does not. Still unsolved: how much quality you lose, and how you would know.

A team ships an INT4 build because a blog said "4-bit is lossless". Two weeks later, support tickets about wrong arithmetic in answers double.

Quality loss is measured, never assumed. Three levels, cheapest first:

  1. Perplexity on held-out text. GPTQ reports perplexity on WikiText2, PTB and C4, with zero-shot tasks such as LAMBADA, ARC and PIQA alongside.
  2. Standard task scores. vLLM's FP8 guide evaluates the quantized model with lm_eval on gsm8k and warns that quantized models can be sensitive to a missing bos token.
  3. Your own product's tasks, compared side by side with the unquantized model.

What the primary sources report, with their conditions:

  • In GPTQ's table, OPT-175B's WikiText2 perplexity is 8.34 in FP16, 8.37 with 4-bit GPTQ and 10.54 with 4-bit RTN; OPT-125M goes from 27.65 to 31.12 with GPTQ.
  • The GPTQ authors observe that larger models generally appear easier to quantize, with OPT-66B an exception.
  • Hugging Face's guide cautions that 4-bit quantization can often give different results from 8-bit or full BF16 inference.

So the same "4-bit" is near-free on a 175B model and costly on a small one. Your model, method and task decide.

vLLM's support table is marked as subject to change, and points to the quantization source directory for current details. Check support against your exact version, not a blog post.

"How would you decide whether to ship an INT4 model?" A strong answer: run perplexity and a standard suite as a smoke test, then the product's own eval set against the BF16 model, with the same prompts and sampling. Define a regression budget before looking. Canary to a slice of traffic and compare task-level metrics. Name the trade: memory and latency against a measured, accepted quality loss.

Quantization's quality cost depends on model size, method and task, so measure it on your own tasks before shipping.

GPTQ 4-bit keeps OPT-175B's perplexity at 8.37 against 8.34. What can you conclude about a 1B model in 4-bit?

  1. It will lose about as little
  2. Nothing safe: smaller models lose more in the same table, so measure it
  3. It is guaranteed fine for any task if perplexity barely moves

The same paper shows small models losing much more. Results transfer across neither sizes nor tasks.

At high batch, weight-only quantization's edge fades

Last part: the quality bill. Still unsolved: do the speed gains hold when traffic grows tenfold?

Moving the 8B model from FP8 W8A8 to INT4 weights nearly doubles batch-1 decode on an H100: 415 to 824 tokens per second at 1,000 tokens of context. At 400 concurrent requests this page's estimator gives 13%, before the cost of expanding weights. Why does the edge melt?

Part 1's roofline: decode turns compute-bound once each weight read is shared by enough requests. With weights alone, that crossover batch is:

W8A8 halves the bytes and doubles the math, so the crossover stays put and the gain holds at every batch. Weight-only shrinks the bytes but not the math, so on weights alone it hits the compute ceiling four times sooner. Past that point only the KV reads it shares with FP8 are left to save, and INT4 pays to expand every weight. Hugging Face's guide notes that because weights are dequantized for every multiply, inference time is often not reduced and can increase. vLLM's INT4 guide pitches it for keeping latency low at low queries per second.

Long contexts delay this, because KV reads keep the step memory-bound (Part 2). The table is the short-context worst case.

Detect it: compare tokens per second per GPU against the BF16 or FP8 build at your real batch, not batch 1. Fix it: use W8A8 on Hopper for busy pools; keep INT4 for memory-limited or low-traffic pools.

"INT4 is smaller than FP8, so why not always INT4?" A strong answer separates bytes from math: INT4 W4A16 still multiplies in BF16, so its edge over FP8 shrinks as batches grow past about 74 on an H100, while its quality risk stays. FP8 W8A8 on Hopper keeps its 2× all the way up. Pick by memory pressure, traffic level and the measured quality loss.

Weight-only formats help most at small batches; W8A8 keeps its gain at high batch because it speeds the math too.

At high batch, speculation turns into extra work

Last part: weight-only formats lose their edge at high batch. Speculation has a sharper version of the same problem.

In this page's estimator, with α = 0.5 and k = 4, short 500-token chats run 1.6 times faster at batch 1. At 256 concurrent requests this page's estimator says 0.82 times: slower than no speculation.

The verify pass scores k + 1 positions per request. At batch 1 that is free: the step was waiting on memory. At batch 256 it is 1,280 positions, past Part 1's crossover, so the pass costs real compute. Rejected guesses become pure waste. Leviathan et al. show that speculation can raise the total arithmetic performed, because work on rejected guesses is wasted. vLLM's dynamic speculation docs say verification multiplies the effective batch by k, and past a critical batch speculation hurts TPOT.

vLLM's docs present speculative decoding for reducing inter-token latency in memory-bound workloads at medium to low request rates. At 10 times the load, the first thing to break is the verify pass's compute, then everyone's TPOT.

The metric trap. Part 1 warned that ITL and TPOT diverge when one streamed output carries several tokens. vLLM's metrics docs say vllm:inter_token_latency_seconds records one sample per streamed output while TPOT is per request, so they differ under speculative decoding. With speculation, TPOT drops while each gap between outputs grows: in this page's model (8B, BF16, 1,000-token context, k = 4, α = 0.7), 2.1 ms TPOT but 5.8 ms between bursts at batch 1. A dashboard on ITL alone can show a regression that is really a win.

Detect it: track TPOT and the acceptance rate together, by load level. Fix it: vLLM's num_speculative_tokens_per_batch_size takes ranges of batch sizes and a k for each, including 0 to switch speculation off at high concurrency.

"Speculative decoding helped in the benchmark and hurt in production. Why?" A strong answer names batch size: benchmarks at low concurrency see a memory-bound verify, production at high concurrency pays k + 1 positions of compute per request. Low acceptance on real traffic makes it worse. The fix is k scaled down with batch, or a proposer that adds no model work.

Speculation spends idle compute; once the batch fills the GPU, the verify pass and rejected guesses cost real time, so shrink k as load rises.

Your EAGLE setup uses k = 3. Traffic swings between 10 and 300 concurrent requests. What do you configure, and what do you watch?

A batch-size schedule with num_speculative_tokens_per_batch_size: k = 3 at low concurrency, smaller in the middle, 0 at the top. Watch TPOT by load band and accepted ÷ draft tokens; judge stream smoothness with ITL, knowing it counts bursts, not tokens.

Explain why the same speculative setup can speed up a quiet server and slow down a busy one, and what you would monitor.

Each round verifies k + 1 positions per request. On a quiet server the step is memory-bound, so those positions cost almost nothing and accepted guesses are free tokens. On a busy server the batch times k + 1 positions crosses the compute ceiling, so verification takes real time and every rejected guess is waste. I would watch TPOT and the acceptance rate by load band, and read ITL knowing it measures gaps between bursts. The fix is a k that shrinks with batch size, down to zero.

Three prompts. Commit to an answer before you open each reference.

1. Serve a 70B model for an internal assistant on 80 GB H100s, one GPU per replica, 4,096-token conversations, under 30 concurrent users per replica. Design it.

BF16 is 140 GB and does not fit; FP8 is 70 GB and leaves almost no cache. INT4 weight-only (AWQ or GPTQ) is 35 GB, and an FP8 cache fits about 53 conversations of 4,096 tokens: enough. At under 30 users the batch stays below INT4's crossover, so its speed gain holds. Trade-off: the largest quality risk of the options, so gate on an eval against the BF16 model. The alternative is H200s with FP8 weights, at higher cost per GPU.

2. A product team wants speculative decoding to cut TPOT on a pool that peaks at 250 concurrent requests and idles at 20. What do you agree to, and what do you insist on?

Agree to EAGLE with a batch-size schedule: a few draft tokens at low concurrency, zero at the peak. Insist on load tests at several concurrency levels and on dashboards for TPOT, the acceptance rate and ITL, read knowing ITL measures bursts. Give up the drafter's memory and some throughput at peak if the schedule is wrong.

3. Finance wants to halve GPU count for an 8B chat service by switching to INT4. You have H100s at high utilization. Respond.

At high batch, INT4 weight-only still multiplies in BF16, so its throughput edge over FP8 shrinks to about 13% at 400 requests of 1,000 tokens in this page's model, before dequantization costs, while quality risk rises. Offer FP8 weights and an FP8 cache instead: W8A8 keeps its 2× ceiling at high batch and the cache change roughly doubles concurrency. State what is given up: a measured accuracy loss, checked on the product's own tasks.

Every answer sizes memory first, checks the batch against the roofline, and names the quality cost.

Final check. Which statement is true of speculative decoding with vLLM's default (standard) rejection sampling?

  1. It leaves the output distribution unchanged and helps most at low to medium load
  2. It trades a small quality loss for speed, like quantization
  3. It speeds up decode at every batch size

Rejection sampling keeps the target's distribution; the speed-up depends on spare compute, which shrinks as batches grow.

Explain to a new teammate how you would make each token cheaper for an LLM service, and when each technique stops paying.

Decode reads the weights and cache every step, so I would either read fewer bytes or get more tokens per read. Quantization reads fewer bytes: an FP8 cache roughly doubles concurrency, FP8 W8A8 weights halve weight reads and double the math ceiling on Hopper, and INT4 weight-only shrinks memory most but loses its edge past small batches. Quantization changes the model, so I measure quality on our own tasks. Speculative decoding gets more tokens per read with identical outputs, but at high batch the verify pass and rejected guesses cost real compute, so k must shrink with load.
