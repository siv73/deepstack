Why sharing a step is the main lever

Your FastAPI service fronts one H100 running Llama 3.1 8B. One chat decodes at about 4.8 ms per token, roughly 207 tokens per second. Sixteen chats decoded one after another would need 16 GPUs to keep that pace. Run them in the same step and one GPU does it.

Think of a bus. The trip costs the same fuel whether one passenger rides or forty. Each passenger only adds their own luggage. The fuel is the model's weights; the luggage is each request's KV cache.

  1. Every decode step reads all 16 GB of weights from GPU memory, whatever the number of requests in it (Part 1).
  2. Each request in the step also reads its own KV cache, and nobody else can share that read (Part 2).
  3. So a step for 16 requests costs one weight read plus 16 small cache reads, not 16 weight reads.

The vLLM paper explains why batching helps: requests in a batch share the same weights, so the cost of moving them is spread across the batch. Running several requests in one forward pass is called batching.

With Part 2's step model: one request with 1,000 cached tokens takes 4.82 ms per step. Sixteen such requests take 5.40 ms. That is 16 times the tokens for 12% more time, or about 14 times the throughput.

The rest of this page is about one question: which requests go into each step, and when. Two terms from Part 1 come back. TTFT is how long a user waits for the first word. TPOT is how fast the words then stream.

One step reads the weights once for every request in it, so putting more requests in each step is the biggest throughput lever a server has.

A decode step for 1 request takes 4.82 ms; for 16 requests it takes 5.40 ms. Why so little extra time?

  1. The GPU runs the arithmetic for 16 requests faster than for 1
  2. The weight read, the biggest cost, happens once per step and is shared; each request adds only its own small cache read
  3. The 16 requests share one KV cache

Decode is memory-bound: reading 16 GB of weights dominates the step, and that read is shared by everyone in it. Each request adds only its own cache read, about 0.04 ms here.

Static batching: fill a batch, pad it, wait for the slowest

Last part: sharing a step is the lever. Still unsolved: the simplest way to share, and what it costs.

Four requests arrive together: prompts of 300, 800, 1,200 and 2,000 tokens, answers of 50, 120, 300 and 600 tokens. You batch them the obvious way. The 50-token answer is ready after 0.38 s but reaches the user after 3.21 s.

The obvious way works like a tour bus that leaves only when every seat is full, and returns only when the last sightseer is back.

  1. Wait until the batch has its fixed number of requests.
  2. Pad every prompt to the longest one, so the batch is a neat rectangle, and prefill it in one step.
  3. Decode all rows together, one token each per step.
  4. Keep every row running until the longest answer is done; finished rows produce padding.
  5. Return the whole batch, then start the next one.

This is static batching. The vLLM paper names the two problems with batching naively: requests arrive at different times, so some wait for others, and requests of different lengths need padding, which wastes compute and memory. Hugging Face's architecture guide describes traditional batching as running a fixed group together and waiting for the slowest request before the next group starts, which leaves the GPU idle between batches.

Static batching wastes work twice, on padded prompts and on finished rows, and makes every request wait for the slowest one.

A static batch holds 8 requests. Seven want 20 tokens; one wants 2,000. Ignoring prompts, roughly what share of decode row-steps is wasted?

Continuous batching: re-pick the batch every step

Last part: static batches wait to fill, pad, and hold every request until the slowest ends. Still unsolved: how to stop finished rows from blocking new ones.

Six requests, A to F, arrive over 5 steps; the server has room for 3 at a time. Under static batching the last one finishes in step 11. Can the same GPU finish by step 8?

Swap the tour bus for a city bus. It never waits to fill. At every stop some passengers get off and whoever is waiting gets on, up to the number of seats.

The Orca paper (OSDI 2022) calls static batching request-level scheduling: a request that finishes early cannot go back to its client until the whole batch is done, and a new request waits until the running batch completes. Orca's fix is iteration-level scheduling: the scheduler runs one iteration of the model at a time over the requests it picks, and returns any finished request to its client right away.

  1. Before each step, look at the waiting queue and the free slots.
  2. Admit waiting requests into free slots; their prefill runs in this step.
  3. Run one forward pass: one new token for every running request.
  4. Retire every request that just finished and return it immediately.

Scheduling per step like this is continuous batching. Hugging Face's guide describes the same loop: at every generation step the scheduler removes finished requests and replaces them with waiting ones.

Step through both policies on the same six requests. The top row shows which requests arrive at each step.

Both lanes do the same 14 decode tokens. Static also burns 10 slot-steps on padding and 3 waiting, and returns A four steps after it was ready. Continuous never pads; its empty cells are slots with nobody waiting, not wasted work.

Continuous batching rebuilds the batch at every step, so finished requests leave at once and new ones join at the next step instead of the next batch.

Put one continuous-batching step in order.

  1. Check the waiting queue and free slots
  2. Admit waiting requests into free slots
  3. Run one forward pass for all running requests
  4. Return requests that just finished

Admission happens before the pass so newcomers' prefills share it; retirement happens after, so their slots are free for the next step.

How requests of different lengths share one forward pass

Last part: continuous batching mixes requests at every step. Still unsolved: in one step, request A is at token 3 and request B at token 900. How does one forward pass run both without padding?

Your step holds 16 decoding requests with caches from 200 to 2,000 tokens, plus one new 1,500-token prompt. Padding them to one shape would bring back the waste continuous batching was meant to remove.

Look at what each layer does. Most of the work, the big matrix multiplies, treats each token on its own. It does not care which request a token came from. Attention is different: a token must look at its own request's earlier tokens, and only those.

Orca's answer is selective batching: operations such as Linear, LayerNorm, Add and GeLU are batched by flattening every request's tokens into one tensor, while attention is split and run per request, because attention must look only at each request's own tokens, and each request has a different number of them.

  1. Line up every token in the step: 16 decode tokens plus 1,500 prompt tokens, 1,516 rows.
  2. Run the weight-heavy layers once over all 1,516 rows. This is where the shared weight read pays off.
  3. Split the rows back by request for attention; each reads only its own cache.
  4. Join the rows again for the next layer.

The bus comparison stops here. Passengers on a bus do not slow each other down. Requests in a step do: the step ends only when its slowest piece of work ends, so one long prompt delays every decode in it. Rung 4 puts a number on that.

On GPT-3 175B, the Orca paper reports 36.9 times the throughput of NVIDIA FasterTransformer at the same latency level.

Per-token layers run once over every request's tokens flattened together; only attention is split per request, so no padding is needed.

Which part of a layer cannot be run as one flattened batch across requests at different positions?

  1. Attention, because each request must attend only to its own tokens, and every request has a different number of them
  2. The Linear (matrix multiply) layers
  3. LayerNorm

Linear, LayerNorm, Add and GeLU work token by token, so tokens from all requests can be stacked. Attention mixes a token with its own request's history, and each history has a different length.

Explain to a teammate why continuous batching beats static batching, and how one forward pass can serve requests of different lengths.

Static batching waits for a fixed group, pads it to one shape, and holds every request until the slowest one ends, so short requests wait and many rows do padding. Continuous batching decides the batch at every step: finished requests leave and waiting ones join right away. One pass works across lengths because most layers treat each token alone, so all tokens are stacked into one tensor; only attention is run per request over its own cache.

Inside vLLM: one scheduler loop, two queues

Last part: one pass can serve requests of any length. Still unsolved: how a real server decides, every few milliseconds, who is in the next pass.

Your vLLM pod shows 40 running requests and 12 waiting on its dashboard. Before you tune anything, you need to know what the scheduler does between two forward passes and why those 12 are not running.

This page follows vLLM v0.31.0, as Parts 1 and 2 do. The scheduler keeps two lists. The running queue holds requests already in the batch. The waiting queue holds the rest.

In vLLM v0.31.0, each engine step does three things: the scheduler picks requests and tokens, the model runs once over them, and the scheduler updates every request from the output. The scheduler has no separate prefill and decode phases: each request has a count of tokens computed so far and a count it needs, and each step hands out tokens so the first catches up with the second.

It schedules the running requests first, then admits waiting requests in queue order while token budget is left and, by default, fewer than max_num_seqs requests are running. The scheduling policy is first come, first served by default; a priority policy is also available.

So your 12 waiting requests are blocked by one of three things: no free slot under max_num_seqs, no token budget left this step, or, as the next parts show, no room in the KV cache.

"Walk me through what happens between two decode steps in vLLM." A strong answer: the engine asks the scheduler for a plan; running requests are served first, then waiting ones join in order under the token budget and the request cap; one forward pass runs; the output updates each request and finished ones are freed. There is no separate prefill phase: a new request is a request whose computed-token count is far behind.

vLLM runs one loop: plan the step (running first, then waiting), run one forward pass, update and free finished requests.

A request reaches the front of the waiting queue. Running requests are below max_num_seqs, but they used the whole token budget this step. What happens to it?

  1. It joins this step, because there is a free slot
  2. It waits for a later step, because running requests are served first and no budget is left
  3. A running request is evicted to make room

Running requests are scheduled first. Waiting ones are admitted only while budget remains and the running count is under max_num_seqs.

When the cache runs out mid-answer: preemption

Last part: a cap on the batch trades TPOT against TTFT. Still unsolved: what happens when the batch is under its cap but the KV cache fills while answers are still growing.

Your server admitted 300 requests while their caches were small. Every step each one adds a token to its cache. Halfway through their answers, the cache has no room for the next token of all 300.

Orca's scheduler caps each batch at a maximum size and admits a request only if enough key/value slots remain for its maximum total length: its prompt plus the most tokens it may generate. vLLM's scheduler allocates cache space for each request's new tokens at every step, rather than for its whole answer at admission. That fits more requests, but the cache can run out mid-answer. How it hands out that space is Part 4.

  1. Before the step, the scheduler finds no cache room for a running request's next token.
  2. It picks a victim and frees all of that request's cache.
  3. The victim goes back to the waiting queue, and no new request is admitted this step.
  4. Later, when there is room, the victim is admitted again and its prompt plus the tokens it already made are prefilled again.

This is preemption. vLLM's tuning guide says that when KV cache space runs out, vLLM can preempt requests to free space and recompute them once space is available again, which can hurt end-to-end latency. Under the default policy the victim is the most recently admitted running request: its cache blocks are freed, its count of computed tokens goes back to zero, and it goes to the front of the waiting queue. In a step where a running request had to be preempted, no waiting request is admitted. In vLLM V1 the default preemption mode is RECOMPUTE rather than SWAP.

In the simulator at 40 requests per second with max_num_seqs 512: the full H100 budget of about 416,565 tokens never preempts. Shrink the cache to 100,000 tokens and there are 51 preemptions; throughput falls from 7,411 to 5,930 tokens per second and mean TTFT rises from 0.07 s to 1.89 s.

Preemption shows up as a user's stream pausing, then resuming after a recompute, and as a rising vllm:num_preemptions. The guide's fixes: raise gpu_memory_utilization, lower max_num_seqs or max_num_batched_tokens, or spread the model over more GPUs with tensor or pipeline parallelism.

When the cache cannot hold the next token for everyone, vLLM evicts the newest running request, frees its cache, and recomputes it later; a rising preemption count means the batch is bigger than the cache.

The cache is full. Request X was admitted 2 s ago; request Y was admitted 10 ms ago and is mid-prefill. Under the default policy, which is preempted, and can a third request Z join in that step?

Y, the most recently admitted running request, is preempted: its cache is freed and it returns to the front of the waiting queue. Z cannot join that step, because no waiting request is admitted in a step that preempted. The default keeps the requests admitted earliest.

Batch job vs worker pool, and where the analogy breaks

Last part: one prefill stalls every decode it shares a step with. Still unsolved: how to explain all of this in terms a backend team already knows, and when to pick which policy.

Your platform team asks: "Isn't continuous batching just a Celery worker pool?" Half right. The half that is wrong is where the incidents come from.

Static batching is a fixed-size batch job. A cron-style job waits for N records, processes them together, and writes all results at the end. Records that finish early still wait for the job.

Continuous batching is a worker pool pulling from a queue, like a Celery pool or a Kafka consumer group. A free worker takes the next message; a finished task acks at once. max_num_seqs is the pool's concurrency and the waiting queue is the broker.

Where it breaks:

  1. Celery workers run independently. Here every running request is a row in one shared forward pass, so a heavy task slows every other task in the same step.
  2. A worker pool's limit is a worker count. Here the binding limit is often memory: the KV cache each request grows while it runs. The vLLM paper notes that how many requests can be batched is limited by GPU memory, especially KV cache space.
  3. Workers do not get evicted mid-task for using too much broker memory. Requests do: preemption throws away their cache and redoes the work.
  4. Adding a worker adds capacity. Adding a request to a step adds throughput but slows every request already in it.

vLLM's tuning guide says chunked prefill helps because it puts compute-bound prefill work and memory-bound decode work in the same batch.

Continuous batching is a worker pool whose workers share one forward pass and one memory budget, so every admission slows the others and memory, not worker count, is the usual limit.

Interview drill and final check

Last part: the worker-pool picture and where it breaks. Still unsolved: putting it together under interview pressure.

Three design prompts where batching is the crux. Commit to an answer before you open each one.

1. "Design the serving layer for a chat product: 30 requests per second at peak, 1,000-token prompts, 250-token answers, 8B model, TPOT target 15 ms." How many H100s, and how do you set the batch?

Use continuous batching. By the estimator, one H100 at 30 requests per second runs about 90 requests at about 12 ms TPOT, inside the target, using about 13 GB of the 54.6 GB cache. The bound is TPOT, not memory. Keep vLLM's default max_num_seqs of 1,024 but alert on TPOT, and add a second GPU before about 35 requests per second, where the estimator puts TPOT at 14.5 ms with about 127 running. The trade-off: a lower cap protects TPOT and pushes overload into TTFT; more GPUs cost money.

2. "Users paste 20-page documents into a chat that also serves short questions. Streaming stutters for everyone." What do you change?

The long prefills share steps with everyone's decodes. vLLM V1 already chunks prompts by default, so lower max_num_batched_tokens (towards 2,048) to cap the prefill per step and smooth inter-token latency, accepting slower TTFT for the document users. If both targets must hold at scale, run prefill and decode on separate GPUs. The trade-off: smoother streams cost long-prompt TTFT, or the operational weight of two pools.

3. "After a model update with longer answers, p99 end-to-end latency doubled but the average barely moved." What do you check first?

Check vllm:num_preemptions. Longer answers grow each cache further, so the cache fills mid-answer and vLLM evicts the most recently admitted requests and recomputes them: the tail pays, the average barely does. Fixes from vLLM's guide: more gpu_memory_utilization, a lower max_num_seqs or max_num_batched_tokens, or more GPUs. The trade-off: a lower cap reduces the cache the batch needs, and so the preemptions, but raises queueing (TTFT) at peak.

"Why not always max out the batch?" A strong answer: throughput keeps rising until the cache is full, but every request added lengthens every step, so TPOT rises with it, and a full cache risks preemption that hurts the tail. Size the batch to the latency target, not to the memory.

Batching decisions are latency decisions: choose the batch size from your TTFT and TPOT targets, then check the cache can hold it.

Final check. A team says: "Static batching at batch 32 gives us the same tokens per second as vLLM at our current traffic, so it is just as good." What is the strongest reply?

  1. Static batching always has lower throughput
  2. Below capacity throughput equals arrival rate for both; static still waits to fill each batch and returns each request with its slowest batch-mate, so TTFT and end-to-end latency are far worse, and it saturates sooner
  3. Static batching reads the weights once per request

In the simulator at 4 requests per second, throughput was 1,040 vs 1,072 tokens per second, while TTFT was 2.55 s vs 20 ms. At 8 requests per second static fell behind.

Explain batching for LLM serving end to end, as you would in a senior interview, in five sentences.

Batching works because a decode step reads the weights once for every request in it, while each request adds only its own cache read. Static batching waits for a full batch, pads it, and holds everyone until the slowest finishes, wasting about half its work in realistic traffic. Continuous batching, from Orca's iteration-level scheduling, re-picks the batch every step, and vLLM bounds each step by max_num_seqs, max_num_batched_tokens and the free KV cache, preempting the newest request when the cache fills. Bigger batches raise throughput but slow every token, and capping the batch moves that cost into the queue as TTFT. A long prefill stalls every decode in its step, which is why vLLM chunks prompts by default and why some systems split prefill and decode onto separate GPUs.
