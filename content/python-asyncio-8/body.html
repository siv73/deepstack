The system so far, and what this page adds to it

Gateway v8 from Part 7 answers seller-b at 1,199 within 250 ms, makes one call per seller and item however many shoppers ask, serves seller-e's 1,149 from its cache once the slow fill lands, and tags every log line with the right request id. It has never been stopped on purpose. Every deploy stops it, several times a day, and nothing in its code says what should happen then.

Introduction

This is Part 8 of a ten-part series. Every part works on the same system: a price-comparison gateway that asks five sellers for a price and must answer within a budget of 250 ms. Parts 1 to 7 are the prerequisites for this page. This part recaps them in one screen; if any line below is unfamiliar, read that part first.

Every deploy cuts some requests in half

Last part: Part 8 adds a shutdown sequence. Still unsolved: what exactly goes wrong today, and how much of it.

The gateway is deployed four times a day. Each time, the support team gets a handful of tickets: "the app spun and said connection closed", always within seconds of the deploy. The audit store has no row for those shoppers, and the metrics show nothing unusual, because the process that would have counted them is gone.

Introduction

To replace a running gateway with a new version, the platform starts the new one and stops the old one. "Stops" means it sends the old process a signal. This part runs gateway v8 exactly as it was deployed before this page, sends it that signal while 20 shoppers are waiting for their answers, and counts what they get.

Definitions

  1. A signal is a notification the operating system delivers to a process, identified by a number. SIGTERM (15) asks a process to terminate; SIGKILL (9) ends it with no chance to react.
  2. A request is in flight when the server has accepted it but not yet answered it.
  3. A graceful shutdown stops a service so that the work it has accepted is finished or handed over, within a time limit, instead of dropped.

Working: what SIGTERM does to gateway v8

  1. 0 ms: 20 shoppers connect and send their request lines. Gateway v8 starts asking the sellers for each.
  2. 100 ms: the stand-in orchestrator sends SIGTERM. Gateway v8 has no handler for it, so the operating system's default action applies: the process ends at once.
  3. Same instant: the kernel closes every socket the process held. Each shopper's readline() returns an empty line: the connection closed with no answer.
  4. 150 ms: one more shopper arrives. Nothing listens on the port any more, so the connection is refused.

Program

deploy.py is a small stand-in for the orchestrator: it starts a gateway process, sends shoppers, sends SIGTERM at 100 ms, tries one more shopper at 150 ms, and sends SIGKILL if the process is still running 3 s after SIGTERM. server_v8.py is gateway v8 started as a long-running server, the way it ran before this page.

Explanation of the program

  1. All 20 shoppers got "no answer (connection closed)", the last at 100 ms: the moment SIGTERM arrived. Not one of them got the 1,199 that was 150 ms away.
  2. The return code is -15. For a child process on POSIX, a negative return code -N means the child was terminated by signal N. Signal 15 is SIGTERM: the process did not exit, it was ended.
  3. stderr lines: 0. No traceback, no log line, no metric: the process had no chance to say anything. That is why the tickets in the problem are the only evidence.
  4. The shopper at 150 ms was refused, which is correct: the old process should stop taking new work. The cost is that it also dropped the work it had already taken.

Solved example: what four deploys a day cost

Given: 2,000 requests a second reach each gateway process; each takes about 250 ms; there are 8 processes and 4 deploys a day, each replacing every process once.

Step 1. Requests in flight in one process at any instant, by Little's law (Part 6): 2,000 × 0.25 = 500.

Step 2. One deploy ends 8 processes, so 8 × 500 = 4,000 requests are cut off.

Step 3. Four deploys: 16,000 cut-off requests a day, with no audit row and no metric for any of them.

Result: about 16,000 shoppers a day see "connection closed", and the gateway's own records say nothing happened. A smaller service sees fewer, which is how the problem survives testing: a deploy in a quiet test environment cuts off nobody.

Wrong belief: "Shoppers whose connection drops just retry, so nothing is lost."

Why it is wrong: some clients retry and some do not, and a retry is not free: it arrives at a fleet that is in the middle of replacing itself, and the original request may already have changed something (Part 5's audit row, a charge in a payments service). Retries make cut-off requests cheaper for reads; they do not make them safe.

  • A deploy stops the old process with a signal; gateway v8 has no handler, so SIGTERM ends it at once (return code -15).
  • Every request in flight is cut off with "connection closed"; nothing is logged or counted.
  • At 2,000 requests a second and 250 ms each, that is 500 cut-off requests per process per deploy.

With no handler for SIGTERM, a deploy ends gateway v8 instantly and silently, cutting off every request in flight.

The stand-in orchestrator sends SIGTERM at 400 ms instead of 100 ms, when the 20 shoppers have already had their answers (the last at about 300 ms). What does the output change to?

All 20 shoppers now get seller-b 1,199: they were answered before the signal. The late shopper is still refused, the return code is still -15 and stderr is still empty. Nothing about the shutdown improved; the deploy just landed between requests. Whether a deploy hurts depends on what is in flight at that instant, which under real load is never nothing.

How a container is stopped: SIGTERM, a grace period, then SIGKILL

Last part: SIGTERM ends gateway v8 at once. Still unsolved: who sends it, what they wait for, and what happens to a process that does not exit.

The platform team says "we give you 30 seconds". The gateway team asks: 30 seconds from what? Before or after the load balancer stops sending traffic? Does the pre-stop hook count? And what arrives at second 31?

Introduction

Gateway v9 will run as a container under Kubernetes in production and under Docker on developer machines. Both stop a container the same way in outline: a polite signal, a wait, then a forced kill. The details decide how long the gateway has, and they are documented, so this part takes them from the documentation and not from habit.

Comparison

A shop closing for the night: at closing time the manager locks the front door and announces "we close in 30 minutes". Shoppers already inside finish at the tills. At the end of the 30 minutes the lights go off, whoever is still inside or not.

  • The announcement = SIGTERM.
  • The 30 minutes = the grace period.
  • Lights off = SIGKILL.

The comparison stops working at the door: in a cluster, the sign that sends shoppers to other shops (the load balancer) is updated by someone else, a little later. Rung 3 measures that.

Definitions

  1. The grace period is the time the orchestrator waits after the stop signal before killing what is still running.
  2. A preStop hook is a Kubernetes hook that runs before the stop signal is sent.
  3. An EndpointSlice lists the Pod addresses behind a Kubernetes Service; load balancers route by it.

Working: a Kubernetes Pod being deleted

  1. The Pod is marked terminating with its grace period. The default terminationGracePeriodSeconds is 30 seconds.
  2. The preStop hook runs, if there is one. The grace period countdown starts before the preStop hook runs, the hook must finish before the stop signal is sent, and the grace period covers the hook and the container's own stop together. A hook handler can run a command in the container, make an HTTP request to it, or simply sleep for a given time.
  3. SIGTERM. The kubelet has the container runtime send TERM (SIGTERM) to the main process in each container; many runtimes send the image's STOPSIGNAL instead when the image defines a different one.
  4. At the same time, traffic is moved away. When the kubelet starts the graceful shutdown, the control plane also evaluates removing the Pod from the Service's EndpointSlices; a terminating endpoint is reported with ready set to false, so load balancers stop using it for regular traffic, while a separate serving condition shows whether it can still answer.
  5. SIGKILL. When the grace period expires, the container runtime sends SIGKILL to any process still running in the Pod's containers. If the preStop hook itself is still running at that point, the kubelet grants a one-off extension of 2 seconds.

Why each step matters

  • Step 2: a preStop sleep is not free time. Every second it sleeps is a second the gateway no longer has after SIGTERM.
  • Steps 3 and 4 happen together. For a short while after SIGTERM, new requests can still arrive. Rung 3 deals with that.
  • Step 5 is not negotiable. Whatever the gateway has not finished by then is lost exactly as in the last part.

Docker

docker stop sends the container's main process SIGTERM by default and SIGKILL after a grace period; the first signal can be changed with STOPSIGNAL in the Dockerfile or --stop-signal when the container is created. The default grace period is 10 seconds for Linux containers and 30 seconds for Windows containers; docker stop --timeout (-t) sets it for one stop, and -1 waits with no limit.

In Kubernetes, kubectl delete --grace-period=<seconds> overrides the Pod's value, and --grace-period=0 with --force removes the Pod from the API at once without waiting for the kubelet to confirm that it stopped. A forced delete is for stuck Pods, not deploys: it skips everything this page builds.

Solved example: how long does the gateway really have?

Given: Kubernetes, the default grace period, and a preStop hook that sleeps 10 s (rung 3 explains why).

Step 1. The countdown starts when the Pod is marked terminating: 30 s.

Step 2. The hook sleeps 10 s inside those 30 s. SIGTERM reaches the gateway at second 10.

Step 3. SIGKILL arrives at second 30, so the gateway has 30 − 10 = 20 s from SIGTERM.

Result: the gateway's shutdown budget is 20 s, not 30. Under Docker on a laptop it is 10 s with no hook. Rung 3 divides that budget between the steps.

Wrong belief: "The preStop hook runs before the grace period starts, so it adds to the 30 seconds."

Why it is wrong: the Kubernetes documentation says the countdown begins before the hook runs, and gives the example of a 60 s grace period, a 55 s hook and a container that needs 10 s to stop: the container is killed before it finishes. The hook and the shutdown share one budget.

  • Kubernetes: preStop hook, then SIGTERM, then SIGKILL when the grace period ends; the hook counts against it. The default terminationGracePeriodSeconds is 30 seconds.
  • Endpoint removal starts at the same time as shutdown, so traffic can arrive after SIGTERM.
  • Docker: SIGTERM, then SIGKILL after a grace period of 10 seconds for Linux containers by default.

An orchestrator stops a container with SIGTERM and kills it with SIGKILL when the grace period ends, and in Kubernetes the preStop hook spends part of that same grace period.

A Pod has terminationGracePeriodSeconds 30 and a preStop hook that sleeps 25 s. The gateway needs 8 s after SIGTERM to finish its requests. What happens?

  1. The gateway gets SIGTERM at 25 s and has until 55 s, so it finishes
  2. The gateway gets SIGTERM at 25 s and SIGKILL at 30 s, 3 s short of finishing
  3. The hook kills the container at 25 s

The grace countdown starts before the hook runs, and covers the hook and the stop together. 30 − 25 leaves 5 s after SIGTERM; the gateway needs 8 s, so it is killed 3 s early. Either shorten the hook or raise the grace period.

In your own words: what happens to the 500 requests in flight in one gateway v8 process during a Kubernetes deploy, and what time does a gateway really have to stop?

The kubelet runs the preStop hook, then has SIGTERM sent to the gateway's main process. Gateway v8 has no handler for SIGTERM, so the process ends at once and the kernel closes every socket: all 500 shoppers get "connection closed", and no audit row or metric records it. The grace period, 30 s by default, starts before the hook, so the gateway's real budget is the grace period minus the hook; at the end, SIGKILL ends anything still running. Meanwhile the Pod's endpoint is being removed at the same time as shutdown starts, so a few new requests can still arrive after SIGTERM.

Catching SIGTERM in an asyncio program

Last part: the orchestrator sends SIGTERM and waits for the grace period. Still unsolved: how a program built on an event loop hears that signal at all.

A developer adds signal.signal(SIGTERM, lambda *_: stop.set()) to a small asyncio service. In testing, stopping it works. In production, idle replicas ignore SIGTERM and are killed after 30 s on every deploy, while busy replicas stop fine.

Introduction

Python has two ways to run code when a signal arrives. The signal module's handler is the general one. asyncio's loop.add_signal_handler is the one made for event loops. The problem above is the difference between them, and this part measures it.

Definitions

  1. A signal handler is code registered to run when the process receives a given signal, instead of the default action.
  2. The default action is what the operating system does when no handler is set; for SIGTERM it ends the process. Python itself installs only a few handlers: SIGPIPE is ignored, and SIGINT becomes a KeyboardInterrupt exception. SIGTERM is not one of them, which is why gateway v8 simply ended.

Working: two ways a signal reaches the code

signal.signal(SIGTERM, handler)

  1. A Python signal handler does not run inside the operating system's low-level handler: the low-level handler only sets a flag, and the Python handler runs later, for example at the next bytecode instruction.
  2. An idle event loop executes no bytecode: it is blocked in the selector, waiting for a socket or a timer. Since Python 3.5, select() and epoll's poll() are retried with a recomputed timeout when a signal interrupts them, unless the signal handler raises an exception.
  3. So the handler runs during that retry and sets the Event, but the selector goes straight back to waiting. The Tasks waiting on the Event are woken only when something else wakes the loop: a timer, a socket, another request.

loop.add_signal_handler(SIGTERM, callback)

  1. loop.add_signal_handler sets a callback that the loop itself invokes along with its other queued callbacks; unlike a handler set with signal.signal, this callback may interact with the event loop, and it must be set from the main thread.
  2. To make that work, the loop arranges to be woken when the signal arrives (rung 4's program shows the call it makes), so the callback runs in the next loop iteration whatever the loop was waiting for.

Program

Each case runs as its own process. The child may start one 300 ms job, a stand-in for a request in flight, and then waits on an Event. The parent sends SIGTERM at 100 ms and SIGKILL if the child is still running at 2 s.

Explanation of the program

  1. No handler: return code -15 and no output. The job's finally never ran: that is gateway v8.
  2. add_signal_handler, a job in flight: the stop is seen at 100 ms, the job still finishes at 300 ms, its finally runs, and the process exits with 0. Seeing the stop and stopping the work are separate decisions; this program chose to let the job finish.
  3. add_signal_handler, idle: stop seen at 100 ms, exit at 100 ms.
  4. signal.signal, a job in flight: the handler ran at 100 ms, but "stop seen" says 300 ms. The loop slept until the job's timer woke it, and only then ran the Task waiting on the Event.
  5. signal.signal, idle: nothing wakes the loop, ever. The parent's SIGKILL at 2 s ends it: return code -9. This is the problem's idle replica, killed at the end of every grace period.

Wrong belief: "A signal handler runs the moment the signal arrives."

Why it is wrong: the operating system interrupts the process at once, but Python only notes the signal and runs the handler at its next chance. For an asyncio program, "ran" is still not "acted on": the loop must also wake up and run the Tasks the handler released. add_signal_handler arranges both; signal.signal arranges neither.

  • Python sets no SIGTERM handler of its own: the process just ends.
  • Use loop.add_signal_handler: the callback runs on the loop and the loop is woken for it.
  • signal.signal + an Event never wakes an idle loop; the measured idle process was SIGKILLed.

In an asyncio program, catch SIGTERM with loop.add_signal_handler, which runs the callback on the loop and wakes it, not with signal.signal, which can leave an idle loop asleep until it is killed.

The idle replica from the problem uses signal.signal and also runs a health-check Task that wakes every 5 s. The grace period is 30 s. When does it stop after SIGTERM?

  1. Within about 5 s, at the health check's next wake-up
  2. Never: it is still killed at 30 s
  3. At once, because the handler sets the Event immediately

The handler runs during the retried selector wait and sets the Event, but the selector waits on. The health check's timer wakes the loop within 5 s, and in that iteration the waiting Task runs. The busy replicas in the problem stopped fine for the same reason: their traffic kept waking the loop.

What asyncio.Runner and asyncio.run do at exit

Last part: add_signal_handler lets SIGTERM release a Task on the loop. Still unsolved: once main() returns, what does asyncio.run do with everything still running, and in what order?

A developer presses Ctrl-C on the gateway in a terminal and it stops cleanly, with its finally blocks run. In a container, SIGTERM ends the same program instantly. "Ctrl-C works, so shutdown works" turns out to be false.

Introduction

Part 2 listed what asyncio.run does when main() returns. This part revisits it in the code it actually calls, asyncio.Runner, because every step there is a step gateway v9's shutdown must finish before, or must do itself with a time limit.

Definition

asyncio.Runner, added in Python 3.11, is a context manager that owns one event loop and one context; asyncio.run(main()) is the same as creating a Runner and calling its run() once, and CPython's asyncio.run is written exactly that way.

Working: Runner.close(), step by step

Runner.close() cancels every Task still running on the loop and waits for all of them with no time limit, then closes the open async generators with shutdown_asyncgens(), then shuts down the default executor, and finally closes the loop.

  1. Cancel every Task left. Each gets CancelledError at its next await (Part 5). The runner then waits for all of them, however long that takes.
  2. Close async generators still open (the next part).
  3. Shut down the default executor. asyncio.run gives the default executor 5 minutes to shut down; after that a warning is emitted and the executor is closed.
  4. Close the loop. Closing the loop discards any pending callbacks, and no other loop method should be called after it.

Why each step matters

  • Step 1 has no time limit. One Task that does not finish after its cancel holds the whole exit (rung 4).
  • Step 1 is also where single-flight fills die, as Part 7 showed: they are Tasks like any other.
  • Step 3 waits for threads, which cannot be cancelled at all.

Working: Ctrl-C

Runner.run() installs its own SIGINT handler, but only in the main thread and only if SIGINT still has Python's default handler; on Ctrl-C it cancels the main Task, so CancelledError is raised inside it and its finally blocks run, and after the main Task is cancelled run() raises KeyboardInterrupt; a second Ctrl-C raises KeyboardInterrupt at once. There is no such handler for SIGTERM.

Program

Explanation of the program

  1. SIGINT: the main Task got CancelledError at its await, its finally ran, and runner.run raised KeyboardInterrupt, which the child caught. Return code 0.
  2. SIGTERM: return code -15 and no output at all. The same program, the same moment, a different signal.
  3. That is the problem's "Ctrl-C works": the developer tested the one signal asyncio handles for them, and production sends the other.

Code written before Python 3.11. Without Runner, programs ran the loop by hand and had to do the exit steps themselves: loop.shutdown_asyncgens() closes every open async generator with aclose(), after which the loop warns if a new async generator is iterated; the documentation's pattern runs it in a finally after run_forever() and before loop.close(), and says there is no need to call it when asyncio.run() is used. You will meet try: loop.run_forever() finally: ... in older services. On 3.11 and later, use asyncio.run or a Runner, and put your own clean-up before main() returns.

Wrong belief: "asyncio.run cleans up after me, so shutdown is handled."

Why it is wrong: it cleans up in its own order, with no time limits, by cancelling. It cancels requests instead of letting them finish, cancels fills instead of waiting for them, and waits forever for a Task that ignores the cancel. It is the last safety net, not the shutdown.

  • asyncio.run = a Runner; at exit: cancel all Tasks and wait (no limit), close async generators, shut down the default executor (5 min), close the loop.
  • Ctrl-C cancels the main Task and raises KeyboardInterrupt; SIGTERM gets no handling at all.
  • Your shutdown must run before main() returns.

asyncio.run ends by cancelling whatever is left and waiting for it without a limit, so a service's real shutdown has to happen before main() returns.

Put what happens after main() returns inside asyncio.run in order.

  1. Every Task still running is cancelled, and the runner waits for all of them
  2. Open async generators are closed with aclose()
  3. The default executor is shut down, waiting for its threads
  4. The loop is closed and pending callbacks are discarded

That is Runner.close() in CPython 3.14's runners.py: cancel and gather the Tasks, shutdown_asyncgens, shutdown_default_executor, then loop.close().

Async generators, and why their clean-up runs late

Last part: asyncio.run closes leftover async generators near the end. Still unsolved: what an async generator is holding when the code that used it walks away, and when it lets go.

The quick quote reads offers as they arrive and stops at the first one at or below 1,200. Each answered quote leaves three seller asks still running behind it, holding seller connections and cap slots (Part 6) on behalf of requests that have already answered.

Introduction

Part 1 built generators by hand. An async generator is the same idea inside async def: it yields values and can await between them, and it is read with async for. That makes it a natural shape for "offers as they arrive". It also gives it a problem plain generators rarely show: its clean-up code can itself need to await, so it can only run on a loop, in some Task.

Definitions

  1. offers() below is an async generator. Its finally is its clean-up: cancel the seller asks still waiting, and wait for them.
  2. A consumer leaves early when it stops reading before the generator is exhausted, by break, return, an exception or a cancel. The generator stays paused at its yield, and its finally has not run.

Working: three ways to leave the stream

When an async generator is left early by break, by its caller being cancelled or by an exception, its async clean-up code may run in an unexpected context, possibly after the tasks it depends on have finished, or during loop shutdown when the garbage-collection hook calls it; to prevent this the caller must close it explicitly with aclose(). When an async generator that was not closed is finalized while the loop is still open, asyncio's hook schedules its aclose() in a new Task with call_soon_threadsafe.

  1. Left open, nothing else refers to it. The request returns; the last reference to the generator goes; CPython finalizes it at once, and the hook schedules its aclose() in a new Task. The clean-up runs after the request has answered, in another Task.
  2. Left open, something keeps a reference (a list for debugging, a cache, a closure). Nothing finalizes it, so its finally waits for shutdown_asyncgens() at the very end of asyncio.run.
  3. Closed by the consumer (next part). The clean-up runs in the request's own Task, before the request answers.

Program

Three quick quotes for kettle-1l, each stopping at seller-b's 1,199. The asks are stand-in timers with the sellers' latencies. Every log line shows the time, the request id and the Task that wrote it.

Explanation of the program

  1. Left open: the request answered with 3 asks still waiting (seller-c, seller-d, seller-e). The stream's finally ran in Task-2, not in the request's Task. Here it ran within the same millisecond, because CPython frees the generator as soon as its last reference goes. The request id is still right because the hook ran while the request's context was current, and the new Task copied it.
  2. aclosing: "offer stream closed" comes before "answered", in the request's own Task, and 0 asks are left waiting.
  3. Kept: the request answered with 3 asks waiting, and nothing more happened until main() returned. Then asyncio.run's shutdown_asyncgens() closed it in Task-4, with no request id ("-"), and found 0 asks to cancel: they had finished on their own long before. For a real stream holding a seller connection, that connection stayed open for the whole life of the process.

Part 7's last part said an abandoned stream keeps its seller connection until asyncio.run ends. The measurement above is more precise: that happens only when something still refers to the generator. An unreferenced one is cleaned up almost at once, but in a different Task, after the request answered. Either way the clean-up is not where the code left the stream, which is the problem this rung fixes.

Wrong belief: "break out of an async for closes the generator, like closing a file."

Why it is wrong: break only stops reading. The generator stays paused at its yield with its finally not run, and its clean-up happens whenever the garbage collector or the loop's shutdown gets to it, in whatever Task that is. The program shows both versions of "whenever".

  • Leaving an async for early leaves the generator paused, its finally not run.
  • Unreferenced: cleaned up soon, in another Task, after the request answered. Referenced: only at shutdown_asyncgens().
  • Explicit closing puts the clean-up back in the request's Task.

An async generator left early runs its clean-up later and elsewhere, in a Task the garbage-collection hook or the loop's shutdown creates, unless the consumer closes it.

Introduction

The shutdown plan: what stops, in what order, in how long

Introduction

Rung 2 gave the parts: a SIGTERM callback on the loop, the knowledge that asyncio.run cancels and waits with no limit, and closing in reverse order. This part turns them into a plan. Rung 3's remaining parts build each step and then gateway v9.

Definitions

  1. To drain is to stop taking new work and let the work already accepted finish.
  2. A step deadline is the longest one shutdown step may take before the next step starts anyway.
  3. Owned work is work the process started that no single request waits for: fills, queued audit rows, flushes.

Working: the order, and why

  1. Stop accepting. Close the listeners and mark the gateway draining. Nothing else can stop while new work keeps arriving.
  2. Drain requests, up to the drain deadline. Requests are the reason everything else exists, so they get the first and largest share of the time.
  3. Cancel the requests still running, and give their finally blocks a short deadline. They may still write an audit row, so the audit queue must still be open.
  4. Wait for fills, up to a deadline; cancel the rest. Fills use seller-e's SDK pool, so the pool must still be open.
  5. Stop the feed thread and wait for it. Its callbacks run on the loop and write audit rows, so it must stop while the loop and the audit queue are still up.
  6. Flush the audit queue and the metrics. Everything that writes rows has stopped, so the queue can be closed and emptied.
  7. Return from main(). asyncio.run now finds almost nothing to cancel; then the pools' with blocks shut the pools down.

Solved example: dividing 20 seconds

The waits, and their limits

  • Server.close_clients() and Server.abort_clients(), added in Python 3.13, close all existing client connections, by calling close() or abort() on their transports; close() should be called first so new clients cannot connect in between.

Python 3.11 and 3.12. The fix for a loop in another thread

Catch the signal in the main thread and hand it to the loop's thread with the one call made for that. The documentation says call_soon_threadsafe is safe to call from a signal handler.

def forward(signum, frame):
    loop.call_soon_threadsafe(stop.set)  # queues stop.set on the loop and wakes it

signal.signal(signal.SIGTERM, forward)  # the main thread may set handlers

Windows (from the documentation, not measured here)

  • No event loop on Windows supports loop.add_signal_handler() or loop.remove_signal_handler(). Gateway v9's run() fails there at its first line.
  • On Windows, signal.signal() can only be called with SIGABRT, SIGFPE, SIGILL, SIGINT, SIGSEGV, SIGTERM or SIGBREAK; anything else raises ValueError.
  • So on Windows, use signal.signal for SIGINT (and SIGBREAK) with the forwarding handler above, and accept rung 2's caveat: the handler runs between bytecodes, so the forward must be call_soon_threadsafe, which also wakes the loop.

Drain, hard stop or durable handoff: choosing how work survives a stop

Last part: at fleet scale, a correct shutdown still has costs. Still unsolved: when draining is the wrong tool altogether, because the work cannot finish inside any grace period, or must not be lost even when the process is killed.

A payments worker beside the gateway charges orders from a queue: charge (100 ms), then record the charge (100 ms). Each job takes 200 ms; the worker runs two at a time. Deploys and crashes must not leave an order uncharged, charged twice, or charged with no record.

Introduction

Gateway v9 drains because its work is short and can be redone: a price comparison lost at a deploy costs one shopper a retry. Some work is long, or has effects outside the process, such as a charge. For that work, how it survives a stop is a design decision, made before the shutdown code. This part compares three answers on the same eight jobs.

Definitions

  1. Hard stop: the work in progress stops where it is. A crash, an out-of-memory kill and SIGKILL are all hard stops, whatever the shutdown code says.
  2. Drain: no new work; the work in progress finishes within a deadline.
  3. Durable handoff: the work lives outside the process, in a broker or an outbox table, and is acknowledged only after it is done, so whatever a stopped process had not finished is delivered again to another one.
  4. At-least-once delivery: a job is delivered until it is acknowledged, so it can run more than once. An idempotency key makes running it twice have the effect of running it once.

Program

8 jobs, a stop at 350 ms, then a replacement worker that processes whatever the first one left. A job taken from the in-process queue is gone from it as soon as it is taken; a job taken from the broker is acknowledged only after it is recorded.

Explanation of the program

  1. Hard stop, in-process queue: jobs 5 to 8 were never charged: they were in a queue that died with the process. Jobs 3 and 4 were charged and not recorded: they were cut between the two steps. The worst row.
  2. Drain, in-process queue: the two jobs in progress finished, but jobs 5 to 8 are still lost. A drain finishes work in progress; it does not save work waiting in memory.
  3. Hard stop, broker, no key: nothing is lost, because the broker redelivered 3 and 4 and kept 5 to 8. But 3 and 4 were charged twice: the first worker charged them and died before acknowledging.
  4. Drain, broker: clean, because nothing was in progress when the worker stopped.
  5. Hard stop, broker, with an idempotency key: clean. The redelivered 3 and 4 found their charges already made and did not repeat them. This is the only row that is clean whether the stop was graceful or a crash.

Decision rules

  • Can the work be lost and redone by the client? Drain, and accept that a crash loses it. The gateway.
  • Does it change something outside the process? Durable handoff with an idempotency key; then also drain, so normal deploys cause no redeliveries.
  • Is it longer than the grace period? Durable handoff, checkpointing progress, or a longer grace period for that workload alone; a drain cannot finish it.
  • Is the queue in memory? Then a drain does not save it, as row 2 shows; Part 6's audit queue is safe only because it is flushed in its own step, and still not across a crash.

Probing question: "We drain gracefully on SIGTERM. Is our job processing safe across deploys?"

What a strong senior answer contains: safe across deploys that go as planned, not across crashes, out-of-memory kills or a drain that hits its deadline, which are all hard stops. What survives a hard stop is only what is stored outside the process, so jobs belong in a broker or an outbox and are acknowledged after they are done; that makes delivery at-least-once, so each job needs an idempotency key checked where the effect happens. Then drain on top, to keep redeliveries rare. Numbers: job length against the grace period, and the redelivery rate after deploys as the metric that shows it working.

Wrong belief: "A good graceful shutdown means no work is ever lost."

Why it is wrong: graceful shutdown only runs when the process is asked to stop. Crashes and kills skip it entirely, and even a drain loses work queued in memory. Only work stored outside the process survives every kind of stop, and then it must be safe to run twice.

  • Hard stop: what crashes do. Drain: finishes work in progress, not work queued in memory.
  • Durable handoff: ack after done; survives crashes; delivers at least once.
  • At-least-once needs idempotency keys; with them, even a hard stop is clean.

Drain for short work clients can redo; for work with outside effects or longer than the grace period, keep it in a durable store, acknowledge it after it is done, and make it idempotent, because only that survives a crash.

In stop_ways.py, the broker worker acknowledges each job when it takes it, before charging. A hard stop at 350 ms, no idempotency key. What does the line show?

Ack after done is what makes the handoff durable.

Interview drill: stopping an async service

Last part: choose drain, hard stop or durable handoff by the kind of work. Still unsolved: explaining it out loud, with the mechanism, the numbers and the trade-offs, the way an interviewer asks.

"How does your service shut down?" A weak answer says "it handles SIGTERM". A strong one says what happens to each kind of work in flight, in what order, in how long, and what is lost when a step runs out of time.

Introduction

Three prompts follow. Each draws on this page and at least one earlier part. Try each before opening the reference answer.

Prompt 1: "Every deploy causes 502s, and sometimes takes 30 seconds per Pod"

An asyncio API in Kubernetes: grace period 30 s, no preStop hook, Dockerfile CMD python app.py, SIGTERM handled with add_signal_handler. During every rollout, the load balancer reports a burst of 502s, and each old Pod takes exactly 30 s to go away. Diagnose both and fix them.

The 30 s: the CMD is in shell form, so SIGTERM goes to /bin/sh, which does not forward it; the handler never runs and the kubelet sends SIGKILL at 30 s, losing whatever the shutdown would have flushed. Fix: exec form, so Python is PID 1. The 502s: endpoint removal starts at the same time as SIGTERM, so the load balancer keeps sending for a while; today those requests hit a process that is about to be killed, and after the first fix they will hit a closed listener. Fix: a preStop sleep longer than the propagation, and a grace period that covers the sleep plus the shutdown's step deadlines, since the hook spends grace time. Then verify with a deploy under load: zero refusals, every Pod exiting with 0 well before the grace period, and a shutdown report per Pod.

Prompt 2: "Design shutdown for a streaming service"

An asyncio service streams price updates to 50,000 open WebSocket clients per instance, from async generators that each hold a seller subscription. Design what happens on SIGTERM.

After a preStop pause, close the listener and fail readiness. Streams never end on their own, so draining by waiting is pointless: send every client a "going away" close with a reconnect hint, then give the closes a short deadline; aiohttp, for example, has an on_shutdown hook for closing websockets before it waits for handlers. Each stream's data comes from an async generator holding a subscription, so each handler reads it inside aclosing, and closing the stream runs the generator's clean-up in the handler's own Task, releasing the subscription there and not at loop shutdown. Clients reconnect to another instance, so they need to resume from the last update they saw, which the server supports with a sequence number. Spread the closes over a second or two, or 50,000 clients reconnect at once to the remaining instances. Then the usual owned-work steps and flushes, each with a deadline.

Prompt 3: "Our jobs take 10 minutes and the grace period is 30 seconds"

An asyncio worker processes video jobs from an in-memory queue fed by an HTTP endpoint. Jobs take up to 10 minutes and write results to object storage. Each deploy loses jobs. What do you change, and what does each option cost?

A drain cannot fix it: 10 minutes do not fit in 30 s, and the in-memory queue dies with the process anyway. Move jobs into a durable queue or outbox and acknowledge each only after its result is written, so a stopped worker's jobs are redelivered. That makes delivery at least once, so the result write must be idempotent, for example keyed by job id. To avoid redoing 10 minutes of work, checkpoint progress to storage and resume from the checkpoint. On SIGTERM: stop taking jobs, checkpoint the jobs in progress within the grace period, and exit without acknowledging them. Alternatives: a very long grace period for this workload alone, which makes deploys and node drains take as long as the longest job; or running jobs outside the deployed service entirely. Cost of the durable design: a queue to operate, idempotent writes and checkpoint code.

What separates a senior answer here: it starts from the kinds of work in flight and what each costs to lose, not from the signal; it gets the platform facts right (the hook spends the grace period, endpoints update in parallel, shell-form CMD swallows SIGTERM); it orders the steps by dependency and gives each a deadline that adds up; it treats crashes as the case graceful shutdown cannot cover and answers it with durable handoff and idempotency; and it says how a deploy is observed, with counts per step, so a step that hits its deadline is visible.

Wrong belief: "In an interview, 'handle SIGTERM and drain' is the complete answer."

Why it is wrong: it skips the questions interviewers actually probe: does the signal reach the process, does traffic stop before the listener closes, what is the order, what are the deadlines, what happens to work that cannot finish, and what about crashes. Each of the three prompts above fails on one of those, not on the signal.

  • Platform: exec-form CMD, preStop pause, grace period ≥ pause + step deadlines.
  • Process: ordered steps, each with a deadline; close async generators where they are used.
  • Work that must survive anything: durable store, ack after done, idempotent.

A senior answer about shutdown follows each kind of work in flight to its end, inside a time budget, and names what survives a crash.
