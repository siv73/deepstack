The system so far, and what this page adds to it

Gateway v6 from Part 5 answers seller-b at 1,199 in 250 ms, stops every seller call when its shopper hangs up, and writes one audit row per request. It decides well when to stop work. It never decides how much work to accept: every connection that arrives gets a Task, whether or not the gateway can finish it.

Introduction

This is Part 6 of a ten-part series. Every part works on the same system: a price-comparison gateway that asks five sellers for a price and must answer within a budget of 250 ms. Parts 1 to 5 are the prerequisites for this page. This part recaps them in one screen; if any line below is unfamiliar, read that part first.

What Parts 1 to 5 built

  1. The five sellers: seller-a (80 ms, 1,249), seller-b (120 ms, 1,199), seller-c (150 ms, 1,229), seller-d (200 ms, 1,215) and seller-e (900 ms, 1,149). The right answer within 250 ms is seller-b at 1,199, with seller-e missing.
  2. Part 1: one after another the waits add up to 1,450 ms; overlapped on one thread, 900 ms.
  3. Part 2: asyncio's loop, Futures and Tasks. A coroutine that waits is parked on a Future; whoever fills the Future wakes it with a callback scheduled by call_soon.
  4. Part 3: a TaskGroup owns the five seller calls, a Semaphore shared by every request caps calls in flight, and one timeout_at deadline per request covers both the wait for a slot and the call. Calls in flight ≈ arrival rate × time each is held: about 1,600 at 2,000 requests a second.
  5. Part 4: seller-e's sync SDK runs in a thread pool of 4, ranking runs in a process pool of 2 at about 1 ms of CPU per request, and background Tasks are owned with spawn().
  6. Part 5: a watcher cancels the request when the shopper hangs up, the deadline is passed down to seller-e's SDK, and the audit row is written by an owned Task behind shield().

What was still broken

  • When requests arrive faster than the gateway can finish them, nothing refuses any of them. They wait, and the gateway has no rule for how long or how many.
  • One shared cap serves all five sellers, so one slow seller can hold slots the others need.
  • Audit writes pile up as Tasks if the audit store slows down; nothing slows the requests that produce them.

What this page adds

Rungs 1 and 2 explain why work must be bounded and how asyncio's queues bound it. Rung 3 builds gateway v7 on that. Three things change in the running system from this page on, and later pages keep them:

  1. A front door that can say no. When the gateway already has as many requests in progress as it can finish, a new request gets the one-line reply busy at once, before any work is done. On HTTP that reply would be a 503.
  2. A cap and a short line per seller, and a rate limit for seller-d. A seller whose line is full is skipped for that request instead of waited for.
  3. Audit rows go through a bounded queue to a fixed pool of writer Tasks. If the store slows down, the requests waiting for their rows slow down with it, and the front door starts saying no.

Work in, work out: why memory climbs during a seller outage

Sale day, 2,000 requests a second. At 11:00 seller-c stops answering: it accepts connections and never replies. Shoppers see answers without seller-c's price and press refresh, so arrivals rise to 3,000 a second. The gateway's memory, normally a few MB of request state, passes 400 MB in the first minute and 4 GB by 11:10, when the process is killed. Every seller call was still cut at 250 ms the whole time.

Introduction

The gateway is a chain of stages: read the request, call the sellers, rank the offers, write the audit row, answer. Each stage holds some requests at any moment. This part gives one rule for how many, applies it stage by stage to the outage above, and finds the stage that grew. The rule is ordinary arithmetic; the surprise is which stage it points at.

Comparison

Consider a ticket counter at a railway station. Two clerks each serve one passenger a minute. If two passengers arrive a minute, the line stays short. If three arrive a minute, the line grows by one passenger every minute, for as long as the rush lasts. It does not matter how polite the clerks are or how fast the passengers walk: in minus out, per minute, is the growth.

  • The clerks = the ranking processes, which finish 2,000 requests a second.
  • Passengers arriving = shoppers' requests, 3,000 a second.
  • The line = requests waiting for a ranking process, each holding its connection and its Task.

The comparison stops working here: a passenger in a long line can see it and leave. A request in the gateway's ranking line is invisible to the shopper, who sees only a spinner.

Definitions

  1. The arrival rate of a stage is how many requests reach it per second.
  2. Its capacity is the most requests it can finish per second.
  3. Its in progress count is how many requests it holds at one moment, waiting or being worked on.

Little's law: in a stage that keeps up, requests in progress = arrival rate × average time each request spends in the stage. Parts 3 and 4 used it to size the cap and the thread pool. When arrivals exceed capacity the stage does not keep up, and in progress grows by (arrival rate − capacity) every second instead.

Working

  1. List the stages a request passes through, and for each one ask: what limits the time a request can spend here?
  2. A stage with a deadline holds each request for at most the deadline, so in progress ≤ arrival rate × deadline, however slow its downstream is.
  3. A stage that keeps up holds arrival rate × its normal time.
  4. A stage without a deadline that does not keep up grows by (arrivals − capacity) every second, and each request in it waits longer than the one before.
  5. Multiply by the memory one waiting request holds to turn requests into bytes.

Why each step is needed

  • Step 1: the outage is at a seller, but the growth can be anywhere downstream of the extra arrivals; only a stage-by-stage list finds it.
  • Steps 2 and 3: they clear the stages that cannot grow, so attention goes to the one that can.
  • Steps 4 and 5: they give the two numbers an incident needs, how fast memory grows and how long the newest request will wait.

Wrong belief: "An awaiting coroutine costs almost nothing, so an async service can let requests wait."

Why people hold it: Part 1 measured that a parked coroutine is far cheaper than a thread, which is true.

Why it is wrong: cheap per request is not free per minute. At 7 KB each, a line that grows by 1,000 requests a second costs 410 MB a minute, and the waiting time grows just as fast. Cheap waiting only delays the moment the arithmetic wins.

  • In a stage that keeps up: in progress = arrival rate × time in the stage (Little's law).
  • A deadline caps a stage's time, so it caps the stage's memory, whatever the outage.
  • A stage without a deadline that cannot keep up grows by (in − out) per second: here 1,000 requests, about 7 MB, every second.

When work arrives faster than a stage finishes it, the difference piles up every second at the first stage that has no limit, and memory and waiting time grow until something is killed.

Arrivals during the outage are 2,400 a second instead of 3,000. Everything else is the same. How many requests wait for ranking after 5 minutes, about how much memory do they hold, and how long does a new request wait?

Growth = 2,400 − 2,000 = 400 a second. After 300 s: 120,000 requests. Memory ≈ 120,000 × 7 KB = 840,000 KB, about 820 MB. A new request waits 120,000 ÷ 2,000 = 60 s. A smaller excess only slows the growth; it does not stop it.

Three answers to too much work: wait, slow down, or say no

Last part: extra work piles up at the first stage without a limit. Still unsolved: once a limit is reached, what should happen to the next piece of work?

The ranking line is given a limit of 600 requests. Request 601 arrives. It can wait anyway, somewhere else; the code that produced it can be made to pause; or it can be refused at once. Each choice moves the extra work to a different place, and each is right for a different kind of producer.

Introduction

Every bounded system makes the same decision at its limit. This part names the three possible answers, so that the rest of the page can apply each one where it fits. The test for each is the same: where does the extra work go, and who pays for it?

Comparison

A small restaurant kitchen can cook 40 meals an hour. On a busy night:

  • It can take every order and cook them in turn. Orders placed at 8 pm arrive at 10 pm, cold, to tables that have left. That is waiting without limit.
  • The waiter can stop taking orders while the kitchen has 10 tickets on the rail, and take the next one when a ticket clears. Guests already seated simply wait for the waiter. That is backpressure.
  • The host can tell new guests at the door "we are full tonight", before they sit down. That is load shedding.

The comparison stops working here: a restaurant's guests decide for themselves to try elsewhere. A program's caller does only what its code says, so the reply must tell it clearly what happened and when to try again.

Definitions

  1. Waiting without limit keeps every piece of extra work in an unbounded line. Nothing is refused; memory and waiting time grow for as long as the overload lasts.
  2. Backpressure makes the producer wait when the next stage is full, so the producer runs at the speed of the slowest stage after it. The extra work stays with the producer, which has not made it yet.
  3. Load shedding refuses work at the edge, quickly and cheaply, when accepting it would exceed capacity. The extra work goes back to the caller, with a reply that says so.
  4. Goodput is the useful work finished per second: answers that arrive in time to be used. Throughput counts every answer, late or not.

Working: how to pick for a given producer

  1. Ask whether the producer can wait. A batch job, a stream reader or a background writer can pause without anyone noticing. A shopper waiting for a price cannot pause usefully: after 250 ms the answer is worthless.
  2. If it can wait, use backpressure. Bound the line and make the producer wait for room. The extra work is never made, or stays in a durable place upstream (a stream's log, a file).
  3. If it cannot, shed at the edge. Refuse before any expensive work is done, with a reply the caller understands, such as HTTP 503.
  4. Never wait without limit for work that has a deadline: every request in the line is paid for at full cost and answered too late.

Why each step is needed

  • Step 1: the same limit means a pause to one producer and a failure to another; the producer decides.
  • Step 3: shedding early is what keeps goodput up. A request refused at the door costs almost nothing; a request refused after the fan-out has cost five seller calls.
  • Step 4: the last part's ranking line is the cost of skipping this step.

Wrong belief: "Refusing requests is a failure; a good system accepts everything and catches up."

Why it is wrong: during an overload, a system that accepts everything does not catch up: the line grows by the excess every second, and every request in it is answered late, so goodput falls toward zero while throughput looks normal. Refusing the excess is what lets the rest be answered in time.

  • Three answers at a limit: wait without limit, backpressure (the producer waits), load shedding (refuse at the edge).

asyncio.Queue: a line with or without a limit

Last part: bound the line, then wait, slow down or refuse at the limit. Still unsolved: what does asyncio give us to build a bounded line, and what do its operations do at the limit?

A developer writes rows = asyncio.Queue() for the gateway's audit rows and moves on. During the outage the audit store slows down, and the queue holds 100,000 rows. rows.full() returns False the whole time, so the dashboard that alerts on "queue full" never fires.

Introduction

asyncio's queue is the standard way for coroutines to hand work to each other: one side puts items in, the other takes them out, and either side can wait. Its one setting, maxsize, decides which of the last part's answers it gives. This part covers the operations and what each does when it cannot go ahead.

Definition

An asyncio.Queue is a line of items shared by coroutines. asyncio.Queue is a first in, first out queue; if maxsize is less than or equal to zero its size is infinite, and if maxsize is greater than 0, await put() blocks when the queue reaches maxsize until an item is removed by get(). With maxsize=0, the default, full() never returns True.

Working: the operations

  1. await put(item) adds the item, or waits for room if the queue is full.
  2. put_nowait(item) adds the item or fails at once. put_nowait() raises QueueFull if no free slot is immediately available, and get_nowait() raises QueueEmpty if no item is immediately available.
  3. await get() takes the oldest item, or waits for one if the queue is empty. get_nowait() takes one or fails at once.
  4. qsize(), empty(), full() report the state. On one event loop no other coroutine runs between a check and the next line, so a check followed by an operation, with no await between them, sees the same state.

Why both forms exist

  • The waiting forms, put() and get(), give backpressure and idle workers: the waiting side is parked and costs nothing until the other side acts.
  • The _nowait forms give the caller the decision at the limit. put_nowait() raising QueueFull is exactly the moment to shed.

asyncio queues are not thread-safe, and their methods have no timeout parameter; the docs point to asyncio.wait_for() for queue operations with a timeout. Gateway code from Part 3 on uses asyncio.timeout() around the await for the same job.

How a full queue slows its producer: put() parked on a Future

Last part: await put() waits when the queue is full. Still unsolved: what exactly waits, what wakes it, and what that does to a producer that is faster than its consumer?

The gateway produces an audit row every 10 ms. The audit writer needs 30 ms per row. In 300 ms the producer makes 30 rows and the writer finishes 9. With no limit, 20 rows wait and the count rises by 2 every 30 ms for as long as the rate gap lasts.

Introduction

Part 2 showed the one way anything waits in asyncio: a coroutine is parked on a Future, and someone else fills it. A full queue uses the same mechanism. This part follows one put() through it and then measures the effect on a producer that is three times faster than its consumer.

Working: one put() on a full queue, in CPython 3.14's queues.py

  1. The queue is full. In CPython 3.14's queues.py, a put() that finds the queue full appends a new Future to the queue's deque of waiting putters and awaits it; get_nowait() wakes the first waiting putter that is not done, and the woken put() checks for room again before adding its item. put_nowait() wakes waiting getters the same way.
  2. The producer is parked. Its Task waits on that Future exactly as Part 2's Tasks waited on a socket's Future. It uses no CPU and runs no code.
  3. A consumer takes an item. get() removes the oldest item and sets the first putter's Future's result.
  4. The producer wakes in a later turn of the loop, finds room, adds its item, and goes on to make the next one.

Why each step matters

  • Step 2: a parked producer makes nothing new. That is the whole effect of backpressure: the work that would have been made is never made yet.
  • Step 3: putters are woken in the order they parked, so several producers share the room fairly.
  • Step 4: the check is repeated after waking because another coroutine might have filled the room first.

Wrong belief: "A bounded queue drops the items that do not fit."

Why it is wrong: await put() drops nothing; it waits until there is room. Dropping happens only if the producer calls put_nowait() and decides to drop on QueueFull. The program's bounded run loses no rows; it makes fewer, later.

  • A full queue parks each put() on its own Future in a deque of putters; get() wakes the first one.
  • A parked producer makes nothing, so it runs at the consumer's speed: 13 rows instead of 30 in 300 ms.
  • Backpressure moves the waiting into the producer; it drops nothing.

A bounded queue slows a fast producer by parking its put() on a Future that only a consumer's get() can fill.

Put one put() on a full queue in order.

  1. put() finds the queue full
  2. put() appends a new Future to the deque of waiting putters and awaits it
  3. A consumer's get() removes the oldest item
  4. get_nowait() sets the result of the first waiting putter's Future
  5. The producer's Task runs again, finds room and adds its item

The producer can only add its item after a consumer has removed one, which is what ties the producer's speed to the consumer's.

A fixed number of workers: the queue's other half

Last part: a bounded queue parks a fast producer. Still unsolved: on the other side of the queue, how many consumers should there be, and how does anyone know when all the work is finished?

Nine audit rows wait to be written, 20 ms each. One writer takes 180 ms. Starting a Task per row would take 20 ms but would also start 900 Tasks for 900 rows, 900 connections to the audit store, and no limit at all. The answer in between is a fixed number of writer Tasks.

Introduction

A queue on its own only holds work. A worker pool is a fixed number of long-lived Tasks that each repeat the same loop: take an item, do the work, mark it done. The number of workers is a concurrency limit, like Part 3's Semaphore, and the queue in front of them is the line. This part builds the loop and the bookkeeping that tells the producer when everything is finished.

Comparison

Three bank tellers serve one line of customers. Each teller calls "next" when free. The manager wants to lock the door only when every customer has been served, not just called.

  • The tellers = the worker Tasks; three tellers = a limit of three at once.
  • Calling "next" = await queue.get().
  • Saying "done" when a customer leaves = queue.task_done().
  • The manager waiting to lock up = await queue.join().

The comparison stops working here: the bank can see its tellers. A worker that crashes silently looks, from the queue's side, exactly like a worker that is still busy.

Definitions

The unfinished count is the queue's count of items put but not yet marked done. join() blocks until all items have been received and processed: the count of unfinished tasks goes up whenever an item is added to the queue and goes down whenever a consumer calls task_done(); when it drops to zero, join() unblocks. task_done() raises ValueError if it is called more times than there were items placed in the queue.

So get() alone does not lower the count. An item is finished only when its worker says so.

Working: the worker loop

  1. item = await queue.get(): park until there is work.
  2. Do the work inside try.
  3. queue.task_done() in finally: the item is finished whether the work succeeded, failed or was cancelled.
  4. Loop. The worker never ends by itself; something must stop it (the next part).
  5. The producer puts the items and then await queue.join() to learn that all of them are finished.

Why each step is needed

  • Step 3: if task_done() is skipped once, the count never returns to zero and join() never returns. Rung 4 measures that hang.
  • Step 5: join() waits for the work to be done, not for the queue to be empty. An empty queue only means every item has been taken.

Solved example: sizing the gateway's audit writers

Given: 2,000 requests a second, one audit row each, 20 ms a write.

Step 1. Writers needed. Writes in progress = 2,000 × 0.020 = 40, by Little's law. Fewer than 40 writers and the queue grows; 40 is the minimum.

Step 2. Headroom. Sizing at exactly 40 leaves no room for a slow minute; 50 writers runs them at 80% busy.

Step 3. The line. A row may wait for a writer only as long as its request can afford. If 20 ms of waiting is acceptable: 2,000 × 0.020 = 40 rows in the queue.

Result: about 50 writers and a queue of about 40. If the store slows to 40 ms a write, 50 writers can finish only 1,250 rows a second, the queue fills, and the request handlers wait in put(): the backpressure rung 3 turns into "busy" at the front door.

Wrong belief: "join() returns when the queue is empty."

Why it is wrong: it returns when the unfinished count is zero, which needs one task_done() per item put. In the program the queue was empty 20 ms before join() returned, while the last three rows were still being written.

  • A worker pool is N Tasks looping get → work → task_done; N is the concurrency limit.
  • join() waits for task_done() on every item put; put task_done() in finally.
  • Workers needed ≈ items per second × seconds per item (40 for 2,000 rows at 20 ms), plus headroom.

A fixed pool of worker Tasks behind a queue caps how much work runs at once, and task_done() with join() tells the producer when every item is finished.

Ending a worker pool: Queue.shutdown()

Last part: workers loop forever on get(). Still unsolved: when the producer has nothing more to send, how do the workers find out and end by themselves, after finishing what is queued?

The gateway is stopping. Its audit queue still holds 3 rows, and 2 writers are each writing one. Cancelling the writers loses all 5 rows. Waiting forever is not an option either. The stop code needs a way to say "no more rows are coming; finish the queued ones and stop".

Introduction

Up to Python 3.12 there was no built-in way to say that, and every codebase invented one. Python 3.13 added it to the queue itself. This part shows the built-in way and the older one you will still read in existing code.

Definition

To shut down a queue is to tell both sides that no new items will come. Queue.shutdown() puts the queue into shutdown mode: later put() calls raise QueueShutDown and blocked put() callers are woken to raise it; with immediate=False, the default, items already in the queue can still be taken with get(), and once the queue is empty, get() raises QueueShutDown. Queue.shutdown() and the QueueShutDown exception were added in Python 3.13.

With immediate=True the queue is drained at once, the unfinished count is reduced by the number of items drained, join() callers are unblocked if that count reaches zero, and blocked get() callers raise QueueShutDown; the docs warn that this unblocks join() even when no work was done on the drained items.

Working: a pool that ends itself

  1. Each worker catches QueueShutDown around get() and returns. That is its only way out of the loop.
  2. The producer calls queue.shutdown() when it has nothing more to add.
  3. Workers keep taking the items still queued; each task_done() lowers the count as usual.
  4. When the queue is empty, each worker's next get() raises QueueShutDown and the worker returns.
  5. The producer awaits join() and then the worker Tasks, all of which have ended normally.

Why each step is needed

  • Step 1: without it, QueueShutDown would end the worker with an exception instead of a clean return.
  • Step 3: the default mode loses nothing that was accepted; only new items are refused.
  • Step 5: the workers end by returning, not by being cancelled, so a worker that was in the middle of a write finishes it.

Program

Explanation of the program

  1. Both runs refuse row-5 after the shutdown with QueueShutDown.
  2. Default mode: row-4, still waiting at 15 ms, is written; all 5 rows are written and both writers return by themselves.
  3. immediate=True: row-4 is drained unwritten. Row-2 and row-3 were already being written, so they finish; join() waits for those two task_done() calls only.

Wrong belief: "shutdown() stops the workers immediately."

Why it is wrong: in the default mode it only stops new items. The workers finish every queued item first and end when get() finds the queue empty. Even immediate=True does not interrupt an item a worker already took; it drops only those still waiting.

  • shutdown() (3.13+): puts fail at once; gets go on until the queue is empty, then raise QueueShutDown.
  • immediate=True drops waiting items and lowers the count by them; items already taken still finish.
  • On 3.11 and 3.12: one stop marker per worker, put behind the real items.

Changing who goes first: PriorityQueue and LifoQueue

Last part: a worker pool can end itself with shutdown(). Still unsolved: every queue so far serves items in arrival order. What if some work matters more, or the oldest work is the least useful?

During a sale, a shopper at checkout asks for a final price while 500 browsing shoppers are already waiting. In arrival order the checkout request waits behind all of them. And under heavy overload, the oldest requests in a line are the ones whose shoppers have most likely given up.

Introduction

asyncio has two variants of the queue that change only the order items come out. Everything else from the last four parts, maxsize, put and get, task_done, join and shutdown, works the same. This part shows the orders and the one trap in priority order.

Definitions

  1. PriorityQueue retrieves entries in priority order, lowest first, and its entries are typically tuples of the form (priority_number, data); LifoQueue retrieves the most recently added entries first.
  2. In CPython 3.14's queues.py, PriorityQueue keeps its items in a list managed with heapq.heappush() and heapq.heappop(). A heap orders items by comparing them with <, so it compares whole entries: the priority first, and the data whenever two priorities are equal.

Working

  1. Queue: the oldest item first. Fair, and right when every item is worth the same.
  2. LifoQueue: the newest item first. Under overload, the newest request is the one whose shopper is most likely still waiting.
  3. PriorityQueue: the lowest priority number first. Put (priority, data); equal priorities fall back to comparing the data.
  4. The tie-breaker. Put (priority, n, data) with n from a counter. Equal priorities then compare by n, which is always comparable and keeps arrival order within a priority.

Program

Explanation of the program

  1. The same three arrivals come out in arrival order, in reverse, and checkout first (priority 0), then the other two in arrival order.
  2. Two entries with the same priority and a Request object each make the heap compare two Requests, which have no order: TypeError.
  3. The failed put is not undone: qsize() is 2, so the heap stored the entry before the comparison failed. In CPython 3.14's queues.py, put_nowait() raises the unfinished count only after the item has been stored, so an exception while storing leaves the count unchanged. The queue now holds an item that join() does not wait for. Treat a TypeError from a PriorityQueue as a broken queue, not a refused item.
  4. With a counter as the second element, the same requests go in without error and come out checkout first.

Solved example

Given: a line of 500 browsing requests (priority 1) and one checkout request (priority 0) arriving last; one worker, 10 ms each.

Step 1. Queue. The checkout request is 501st: it waits 500 × 10 ms = 5 s.

Step 2. PriorityQueue. It is next: it waits at most for the item being worked on, 10 ms.

Step 3. The cost. Every browsing request now waits 10 ms longer, and if checkout requests keep coming faster than the worker finishes them, browsing requests are never served at all.

Result: priority moves waiting from important work to other work; it does not remove waiting. It needs a bounded queue and shedding behind it, or the low-priority line grows without limit.

Wrong belief: "A PriorityQueue compares only the priority number."

Why it is wrong: it compares whole entries, as a heap does. With equal priorities the next element is compared, and if that is an object without an order, the put raises TypeError, as the program shows, and leaves the queue inconsistent. The counter as the second element prevents it.

  • Queue: oldest first. LifoQueue: newest first. PriorityQueue: lowest number first.
  • Use (priority, counter, item) so equal priorities never compare the items.
  • Priority reorders the wait; without a bound, low-priority work can wait forever.

LifoQueue and PriorityQueue change only who leaves the line first; a priority queue needs a tie-breaking counter and still needs a bound.

A PriorityQueue receives (1, {"shopper": "a"}) and then (1, {"shopper": "b"}). What happens on the second put?

  1. It is stored behind the first, in arrival order
  2. It raises TypeError, because the heap compares the two dicts, which have no order
  3. It replaces the first, because the priorities are equal

The heap compares whole tuples; with equal first elements it compares the dicts, and < is not defined between dicts. A counter between the priority and the data avoids it. And the failed put is not clean: the second entry stays in the heap, uncounted by join(), as the program showed.

The front door: refusing a request before any work is done

Last part: priority and LIFO change who goes first. Still unsolved: for shoppers, who cannot usefully wait, how does gateway v7 refuse the extra requests, and what does the refusal say?

3,000 requests a second arrive; the gateway can finish 2,000. Gateway v6 accepts all of them and the ranking line grows by 1,000 a second. Gateway v7 must instead answer the extra 1,000 at once, in about 0 ms, without asking a single seller, and in a form the shopping app knows how to handle.

Introduction

Load shedding at the front door needs three decisions: what to count, where the limit sits, and what to reply. The count must be cheap and checked before any expensive step. The limit comes from Little's law. The reply comes from HTTP, which already has a status for "too busy, try later".

Definitions

  1. max_requests is the most requests gateway v7 lets be in progress at once. A request that arrives when the limit is reached is refused before its request line is acted on.
  2. HTTP's 503 (Service Unavailable) status means the server is currently unable to handle the request because of a temporary overload or scheduled maintenance, which will likely be alleviated after some delay, and the server MAY send a Retry-After header field suggesting how long the client should wait before retrying.
  3. Retry-After's value is either an HTTP date or a number of seconds to wait; sent with a 503, it says how long the service is expected to be unavailable to the client.
  4. The 429 (Too Many Requests) status means the user has sent too many requests in a given amount of time, and its response MAY include a Retry-After header saying how long to wait before a new request. So 503 says "I am overloaded"; 429 says "you, this caller, are over your limit".

The gateway's line protocol has no status codes, so gateway v7 replies with the line busy. Behind an HTTP front end, the same decision would be a 503 with Retry-After:

HTTP/1.1 503 Service Unavailable
Retry-After: 1

Working: gateway v7's serve()

  1. Check the count first. When a connection arrives, compare in_progress with max_requests, before anything else.
  2. If full, refuse. Count the refusal, read the request line (so that closing does not reset a connection with unread data), write busy, close. No seller, no ranking, no audit row.
  3. If not full, admit. Add one to in_progress, run gateway v6's serve() unchanged, and subtract one in finally.

Why each step is needed

  • Step 1: a refusal is cheap only if it comes before the expensive steps. Refusing after the fan-out would save the ranking but not the five seller calls.
  • Step 2: the reply must be distinct from a failure, so the app can back off instead of reporting an error.
  • Step 3: finally keeps the count right when a request ends by hang-up, cancellation or error. The check and the increment have no await between them, so on one event loop no other request can slip in between; Part 7 returns to what changes when such a check spans an await.

Solved example: choosing max_requests

Given: ranking finishes 2,000 requests a second per process; an admitted request is in the gateway about 0.28 s (250 ms of sellers, then ranking, counts and the audit row).

Step 1. At capacity, requests in progress = 2,000 × 0.28 = 560, by Little's law.

Step 2. A limit well above 560 admits more than ranking can finish, and the ranking line grows again; a limit well below 560 refuses work the gateway could have done. Round to 600 and watch two signals: ranking wait time (should stay near zero) and the refusal rate.

Step 3. At 3,000 arrivals a second, about 1,000 a second are refused, each in about the time it takes to read one line.

Result: max_requests = 600. Memory stays near 600 × 7 KB ≈ 4 MB for admitted requests, whatever the arrival rate.

Google's SRE book describes load shedding as dropping some proportion of load as a server approaches overload, and gives as an example a server returning HTTP 503 to incoming requests when more than a given number of client requests are in flight. Gateway v7's front door is that rule, with busy in place of 503.

Probing question: "Your service is at 150% of capacity. Do you queue the extra requests or reject them?"

What a strong senior answer contains: reject the excess at the edge, early and cheaply, because a queue cannot drain while arrivals exceed capacity: it only grows, and everything in it is answered late. The candidate sizes the in-flight limit with Little's law, replies 503 with Retry-After so clients back off, keeps refusals out of the error rate but alerts on them, and states the trade-off: some users get "try again" so that the rest get a timely answer. A short queue is fine only for bursts shorter than the budget.

Wrong belief: "Load shedding means the server is broken."

Why it is wrong: a 503 under overload is the server working as designed: it protects the requests it has accepted. The broken behaviour is the one from the work-in, work-out part, where every request is accepted and goodput falls toward zero.

  • Count requests in progress; check before any expensive step; refuse when the count is at the limit.
  • Limit ≈ capacity × time in the gateway: 2,000 × 0.28 ≈ 560, rounded to 600.
  • Reply 503 with Retry-After when the server is overloaded; 429 when one caller is over its own limit.

Gateway v7 counts the requests it has in progress and refuses the next one at the door with "busy", the line protocol's 503, before any seller is asked.

One shopping app has a bug and sends 50 requests a second; everyone else is normal, and the gateway is well below capacity. The gateway limits each app to 10 requests a second. Which reply fits the extra 40?

  1. 503 Service Unavailable with Retry-After
  2. No reply: close the connection
  3. 429 Too Many Requests, with Retry-After

429 means this caller has sent too many requests in a given time. 503 means the server itself cannot handle requests right now, which is not the case.

A cap and a short line for each seller

Last part: the front door refuses requests the gateway cannot finish. Still unsolved: inside an admitted request, the five seller calls still share one cap. What stops one slow seller from taking the slots the others need?

During seller-c's outage each seller-c call holds its slot for the full 250 ms instead of 150 ms, so seller-c alone needs 500 slots instead of 300. The extra 200 come out of the same 1,600 that seller-a, seller-b and seller-d need, and their calls start waiting in line behind seller-c's.

Introduction

Part 3's table of fixes already named the remedy: a cap per seller as well as the shared one, so one seller cannot take every slot. Gateway v7 builds it, and adds the bound this page is about: each cap gets a short line, and a call that finds the line full is skipped for this request instead of waiting.

Comparison

A food court has five counters. With one shared line for all five, a counter that is slow today holds up people who want the other four. With one line per counter, the slow counter's line grows and the others keep moving; and a sign that says "line full, try later" keeps the slow counter's line from filling the hall.

  • A counter = a seller; its staff = its cap.
  • Its own line = the waiters on its Semaphore.
  • "Line full" = skipping that seller for this request.

The comparison stops working here: a person in a food court wants one counter. A gateway request wants all five sellers and is happy with four, so skipping one seller costs one price, not the whole request.

Definitions

  1. A bulkhead is a separate limit for each downstream, so that one slow downstream cannot use up capacity the others need. Each seller's Semaphore is a bulkhead.
  2. Semaphore.locked() returns True if the semaphore cannot be acquired immediately. In CPython 3.14's locks.py, locked() is also True while any waiter that is not cancelled is in line, even if the counter is above zero, so a newcomer cannot go ahead of the line.

Working: SellerLimits.call()

  1. Line full? If the seller's cap cannot be taken at once and its line already holds max_waiting calls, raise Skipped at once.
  2. Rate? If the seller has a rate limit and no token is free, raise Skipped at once (next part).
  3. Join the line: count the call as waiting and await cap.acquire(). The request's timeout_at deadline, which the caller entered first, still covers this wait.
  4. Call the seller and release the slot in finally.
  5. Gateway v7's _ask() returns a Skipped as a value, like a timeout: the seller is missing from this answer, and the answer is marked partial.

Why each step is needed

  • Step 1: the line's length bounds how many calls can wait; the deadline already bounds how long, but a long line means most of its calls are cut anyway, after holding a Task for 250 ms each.
  • Step 3: the deadline around the wait is Part 3's rule; without it the line would bound the count but not the time.
  • Step 5: a skipped seller is an expected outcome of a limit, not an error, so it must not fail the TaskGroup.

Calls per second, not calls at once: a rate limit for seller-d

Last part: each seller has its own cap and line. Still unsolved: seller-d's contract does not say "200 calls at once"; it says "at most 20 calls a second". A cap cannot express that. What can?

Introduction

A cap limits calls at once; a rate limit limits calls per unit of time. Little's law links them: calls at once = rate × time per call. When the time per call changes, a cap keeps calls at once fixed and lets the rate move, while a rate limit keeps the rate fixed and lets calls at once move. A contract stated as a rate needs a rate limit.

Comparison

A ticket machine at a museum hands out one entry ticket every 3 seconds and can hold up to 5 tickets ready. A school group that arrives after a quiet hour takes the 5 ready tickets at once; after that, people get a ticket only as fast as the machine prints them.

The comparison stops working here: a person without a ticket waits by the machine. Gateway v7 never waits for a token, because a token that arrives after the request's deadline is useless; it skips seller-d instead.

Definition

A token bucket holds up to burst tokens and refills at rate tokens per second; a call is allowed only if it can take a token. Over any period, it allows at most burst + rate × the period's length calls.

Working: TokenBucket.try_take()

  1. Refill: add rate × the time since the last call, up to burst.
  2. Take: if at least one token is there, remove one and allow the call.
  3. Otherwise refuse at once. SellerLimits.call() turns that into Skipped.

Why each step is needed

  • Step 1: refilling on demand, from the elapsed time, needs no timer and no background Task.
  • Step 3: waiting for a token would build one more line in front of seller-d, which the deadline would cut anyway. The check has no await in it, so on one event loop two requests cannot both take the last token.

Backpressure inside the gateway: the audit queue

Last part: seller-d gets a rate limit as well as a cap. Still unsolved: Part 5's audit writes. Each request starts one as an owned Task behind shield(), and nothing limits how many run at once. What happens when the audit store slows down?

The audit store slows from 20 ms to 200 ms a write. Gateway v6 still starts one write Task per request, 2,000 a second; by Little's law 2,000 × 0.2 = 400 writes are in flight at once against a store that was sized for 40. The store slows further, and the write Tasks of shoppers who hung up keep running, uncounted by anything.

Introduction

The audit write is the one producer in the gateway that can wait: every answer already waits for its row (Part 5's rule "no answer without its row"). So it is the place for backpressure. Rows go into a bounded queue served by a fixed pool of writers; when the store slows, the queue fills, the requests waiting for their rows slow down, they stay in progress longer, and the front door starts refusing new requests. The overload travels back to the edge, where it is cheap to refuse.

Working: AuditQueue

  1. write(row), which gateway v6's _audit() already calls through its owned, shielded Task, makes a Future for "committed", puts (row, future) into the queue with await put(), and awaits the Future.
  2. A full queue parks that put(): the request's Task waits for room, as in the put-waits part.
  3. Each of the fixed writers loops: get(), write to the store, set the Future's result (or its exception, so the request hears about a failure), and task_done() in finally.
  4. close() calls shutdown(), waits for join(), then for the writers, which return on QueueShutDown. Gateway v7's stop() calls it.

Why each step is needed

  • Step 1: the put and the wait happen inside the shielded Task from Part 5, so a shopper hanging up while the row waits for room does not lose the row.
  • Step 3: setting the exception on the Future replaces the per-write failure report that each owned Task gave in Part 5; the owned Task awaiting the Future still reads it, so spawn() still counts it.
  • Step 4: the default shutdown writes every queued row before the writers end.

Diagram

Explanation of the diagram

  1. Step 1 is the cause: the store's capacity falls tenfold.
  2. Steps 2 and 3 are backpressure: the queue does not grow past its limit; the waiting moves into the requests.
  3. Steps 4 and 5 are shedding: the requests stuck behind the store fill the front door's count, and new requests are refused instead of starting fan-outs whose rows could not be written in time anyway.

Solved example

Given: 2,000 requests a second, 50 writers, a queue of 40, max_requests 600; the store slows from 20 ms to 200 ms a write.

Step 1. Writers' capacity. 50 ÷ 0.2 = 250 rows a second, down from 2,500.

Step 2. What fills. The queue's 40 places fill within a fraction of a second; then each finished request waits in put(). In-progress requests climb to 600.

Step 3. What the door does. With 600 in progress, admitted requests leave only as fast as their rows are written, 250 a second, so the door admits about 250 a second and refuses the other 1,750.

Step 4. Memory. At most 600 requests, 40 queued rows and 50 writers, whatever the store does.

Result: the slow store costs throughput, which no design can avoid, but not memory or unbounded Tasks: gateway v6 would have had 400 writes in flight, growing, while gateway v7 has 50 writes and refuses the rest at the door in about 0 ms.

Backpressure needs a bound on every line it passes through. Introduction

The worker loop is four lines long, and the order of those lines decides whether one bad item stops the whole pool forever. This part reproduces the hang with the gateway's audit writers, shows why it is silent, and lists the fixes, each of which closes a different gap.

Working: how one bad row hangs join()

  1. The writer takes row-2 with get(). The unfinished count does not change; it went up when row-2 was put.
  2. The store raises for row-2. The writer's loop has task_done() after the write, not in finally, so the exception skips it.
  3. The writer's Task ends with the exception. Nobody awaits it, so nothing reports the failure while the process runs.
  4. The other writer finishes every remaining row, and the queue is empty. The unfinished count is still 1, for row-2.
  5. join() waits for that count to reach zero. It never will.

Why it is silent

  • The queue is empty and every other row was written, so queue depth and write rate look healthy.
  • The failure lives in a Task nobody reads: Part 4's trap 3, inside a worker pool.

A queue that hides overload until latency explodes

Last part: a skipped task_done() hangs join(). Still unsolved: a queue can be bounded, correct and still wrong. What does a bound that is too large do to a service with deadlines?

A team adds a bounded queue of 10,000 requests in front of 5 workers to "absorb bursts". Workers finish 100 requests a second; for two seconds 150 a second arrive. Nothing is refused, no error is logged, CPU is normal, and 4 of every 5 answers arrive after their 250 ms budget.

Introduction

A queue's limit should match how long its items can afford to wait, not how much memory there is. A limit far above that turns the queue into a standing queue: during an overload it stays long, every item waits the full length of the line, and the service answers every request, late. This part measures one, then fixes it two ways.

Working: why the big queue answers late

  1. Arrivals exceed capacity by 50 a second, so the queue grows by 50 a second (the work-in, work-out part).
  2. Each new arrival waits queue length ÷ capacity: after one second, 50 ÷ 100 = 0.5 s, already twice the budget.
  3. Workers keep busy on requests whose budget has passed. Every finished request is late, and every late one cost the same work as a timely one.
  4. Nothing looks wrong to the usual checks: no refusals, no exceptions, CPU at its normal level. Only latency and time in queue show it.

Two more fixes for when the queue is already long

  • Serve newest first. Under a long overload, the newest request is the one whose shopper is most likely still waiting; a LifoQueue (the priority-and-LIFO part) serves it first, and dropping by time in queue removes the ones already given up on.
  • Measure time in queue, not only depth: depth 100 means 1 s at 100 a second but 0.1 s at 1,000 a second. Time in queue is the number to compare with the budget.

The SRE book suggests changing the queue from first-in, first-out to last-in, first-out, or using the controlled delay (CoDel) algorithm, to drop requests that are unlikely to be worth processing because the user has probably given up.

Introduction

Working: the order things break

  1.   3. One client takes the front door. The misbehaving build's 5,000 requests a second fill the in-flight limits of the processes it reaches, and real shoppers are refused in its place.
  4. Only then the gateway's own capacity: ranking at 2,000 a second per process, which the front door already protects.

Solved example: the fixes, with numbers

Step 1. Divide shared limits by the number of processes. seller-d: 1,500 ÷ 10 = 150 a second per process, burst 10. seller-c: 200 ÷ 10 = 20 at once per process. With processes added or removed during the day, a fixed split drifts; one limiter shared by every process (a separate service or store all processes ask) keeps the total exact, at the cost of a network call per token.

Step 2. Tell clients when to come back. Reply 503 with Retry-After (the front-door part), and have the app wait that long plus a random extra before retrying. 1,000 refusals a second that come back spread over 1 to 2 s add about 1,000 a second, not a doubling every few milliseconds.

Google's SRE book says to always use randomized exponential backoff when scheduling retries, and to consider a server-wide retry budget, giving 60 retries per minute in a process as an example.

Step 3. Limit each client before the global limit. A token bucket per app build or API key, 429 with Retry-After when it runs out (the front-door part's 429). The misbehaving build gets its share, say 500 a second, and the other 4,500 are refused before they take any of the in-flight limit.

Probing question: "Why not put everything behind Kafka or a queue service and let consumers pull at their own speed?"

What a strong senior answer contains: a broker bounds memory and survives crashes, but it does not bound time: a shopper waiting 250 ms gains nothing from a message that will be processed in 30 s. For interactive requests, the queue in front of the work must be no longer than the wait the caller can afford, and the excess must be refused. A broker also adds an operated system, at-least-once delivery (so idempotent handling), and a hop of latency. Use it where work must survive or outlast the request; use shedding and in-process limits where a person is waiting.

Wrong belief: "A Semaphore and a bounded queue with workers are two spellings of the same limit."

Why it is wrong: both cap work in flight, but a Semaphore keeps the work in the caller's Task, so the caller's deadline, cancellation and context come along, and its line has no size limit of its own. A worker pool moves the work into other Tasks, gives the line a size, and cuts the link to the caller: cancellation must be passed by hand, and the request's context does not follow, which is Part 7's subject.

  • Caller waits within a deadline: Semaphore + counted line + edge shedding.
  • Producer can wait, work stays in process: bounded queue + workers.
  • Work must survive or outlast the request: a broker, with idempotent consumers.

Pick the bound by who is waiting and what must survive: a Semaphore for calls inside a request, a bounded queue for producers that can wait, shedding for callers who cannot, and a broker for work that must outlive the process.

The timed-out calls cannot be the growth: a stage with a 300 ms deadline holds at most 1,500 × 0.3 = 450 requests, whatever the outage does. Growth of a steady 300 MB a minute means a stage without a deadline whose capacity is below 1,500 a second: at about 7 KB a request, 300 MB a minute is about 700 requests a second of excess, so that stage now finishes only about 800 a second: it must itself have slowed in the outage, such as a database or pool shared with the failing downstream, since it kept up with 1,000 a second before. Look for an await with no timeout after the calls, such as a CPU pool, a database write or a lock, and compare its capacity with the arrival rate. Fixes: put a limit at the edge sized by Little's law (capacity × time in the service) and shed with 503 and Retry-After; give the slow stage a deadline or a bounded queue; and find out why arrivals rose, usually clients retrying partial answers, and make them back off. Trade-off: some callers are refused so the rest stay within their budget.

Prompt 2: "Design the overload behaviour of a fan-out gateway"

A travel search API asks 6 airline APIs per search, each with different speeds and quotas, and must answer within 2 s. Peak traffic is 3 times normal. Design how it behaves when demand exceeds what it or the airlines can handle, and say what each choice gives up.

At the edge, an in-flight limit per process equal to capacity × time per search, refusing the excess with 503 and Retry-After so clients back off, and a per-client limit with 429 ahead of it so one client cannot take the capacity. Each airline gets its own cap sized to rate × its latency or its stated concurrency, whichever is lower, and a line no longer than what can still finish within the 2 s, so a slow airline is skipped and costs only its own results; airlines with per-second quotas also get a token bucket, divided by the number of processes or shared. One deadline per search covers waiting for slots and the calls, as in Part 3. Any internal writer, such as search logging, gets a bounded queue with backpressure, behind the edge limit. The cost: under peak, some searches are refused and some answers miss an airline, so that admitted searches finish in 2 s and no airline is pushed past its quota.

Prompt 3: "Everything looks healthy, and p99 is 4 seconds"

A worker-pool service has a 1 s budget. Dashboards show no errors, no refusals, CPU at 45%, 40 workers all busy, a queue depth of 2,000, and p99 latency of 4 s. Each item takes about 80 ms. What is happening and what do you change first?

A standing queue. 40 workers at 80 ms finish 500 items a second, so 2,000 queued items are 4 s of waiting, which matches p99. The workers are busy doing work that is already late; CPU is moderate because the work is mostly waiting on I/O. First change: cut the queue to what the budget allows, about 500 × 0.5 s = 250 if half the budget may be spent waiting, and refuse the rest with 503 and Retry-After; check the deadline when taking an item and drop items that can no longer finish. Then decide whether capacity must grow (more workers, if the downstream can take it, or more processes). Watch time in queue and goodput, not only depth.

What separates a senior answer here: it treats every place work can wait as a line with a size and a time; it uses Little's law to size each line and to explain growth (in − out per second); it puts the refusal at the edge, early and cheap, with Retry-After; it matches each limit to the scope of what it protects (process, seller, client); and it names what the limits cost: refused requests and partial answers, in exchange for answers that arrive in time.

Wrong belief: "In an interview, 'add a queue' is the answer to overload."

Why it is wrong: a queue absorbs bursts shorter than the budget and nothing else. Under sustained overload an unbounded queue grows until memory runs out, and a large bounded one answers everything late. Interviewers look for the bound, the refusal and the arithmetic, not the queue.

  • Growth = arrivals − capacity per second, at the first line with no deadline or bound.
  • Edge: in-flight limit and 503; per client: 429; per downstream: cap, short line, rate.
  • Queue size = capacity × affordable wait; watch time in queue and goodput.

A senior answer about overload finds the first unbounded line with Little's law, bounds it, refuses early with a clear reply, and states who gets refused so the rest are answered in time.

This needs Parts 3 and 5. Gateway v7's seller calls are moved into a worker pool behind a bounded queue: each request puts five jobs and awaits five Futures under its 250 ms deadline, and the workers call the sellers with no timeout of their own. A shopper hangs up at 100 ms. What happens to that request's seller calls that the workers have already started?

  1. They are cancelled through the request's TaskGroup, as in Part 5
  2. The 250 ms deadline cancels them inside the workers
  3. They run to completion in the workers' Tasks, because nothing links the workers to the request's cancellation unless the code passes it on by hand

Part 5's hang-up reached the seller calls because they were Tasks in the request's TaskGroup. In a worker pool the calls run in Tasks owned by the pool, so cancelling the request cancels only its waits on the Futures. That lost link is why gateway v7 keeps seller calls in the request's Task, under a Semaphore.

What is still broken

Every limit on this page is a small piece of shared state: a count, a bucket, a queue. Each is safe today for one reason only: no await sits between reading it and changing it, so on one event loop no other Task can run in between. That stops being true as soon as the gateway does something more useful:

  • State shared by Tasks across an await. A price cache that checks "is seller-e's price fresh?", awaits a fetch, and stores the result lets 500 requests all see "stale" before the first fetch returns, and all fetch. A counter updated as read, await, write loses updates.
  • Request data that does not follow the work. The audit writers run in Tasks started when the gateway started. They see the row's text and nothing else: a request id set by the handler, for logs and traces, is not visible in the writer that handles that request's row.
  • Threads that touch the loop's state. seller-e's SDK thread finishes in another thread; anything it hands back to the loop, or any state both sides touch, needs the right crossing, which Part 2 only introduced.
