Why one long prompt freezes twenty other users

Twenty users are streaming chat answers from one H100 running Llama 3.1 8B, each getting a token every 5.6 ms. A customer pastes a 50,000-token contract. In this page's model every one of the twenty streams stops for 1.47 seconds.

Part 1 named this prefill-decode interference. Part 3 put many requests into each step with continuous batching. Inside that loop, the problem gets sharper: every running request gets its next token only when the current step ends.

A step lasts as long as its heaviest work. Twenty decodes read the weights once and are done in 5.6 ms. A 50,000-token prefill does 50,000 tokens of arithmetic. If both share one step, the step takes 1,471 ms, and all twenty users wait that long for one token.

Think of a supermarket with one till. Twenty people are buying one item each. Someone arrives with three full trolleys. If the cashier scans all three trolleys before serving anyone else, twenty people stand still.

With chunked prefill off, vLLM refuses to start if max_num_batched_tokens is smaller than max_model_len, so even the longest allowed prompt fits in one step's budget. That is exactly the trolley case: the scheduler has to swallow the full prompt at once.

The user sees it as a stutter, not a slowdown. Average time per token barely moves, because one frozen step hides among hundreds of fast ones. The tail of the gap between tokens, the ITL p99 or maximum from Part 1, is where it shows.

In a continuous-batching server one step carries everyone, so one huge prefill in a step freezes every stream for the whole step.

Keep the twenty streams, but make the pasted prompt 100,000 tokens instead of 50,000. Does the freeze roughly double, or grow by more than double? Why?

More than double. The weight arithmetic doubles, but attention grows faster: each prompt token attends to every earlier one, so that part grows with the square of the length. Doubling the prompt roughly quadruples the attention work, and the step stretches by more than two times.

Chunked prefill: cut the trolley into baskets

Last part: one step carries everyone, so a whole-prompt prefill freezes every stream. Still unsolved: how to keep the streams moving while the long prompt is processed.

You cannot make the 50,000 prompt tokens cheaper. You can decide how many of them go into each step.

Give every step a fixed token budget. Each step, every decoding stream takes one token from it first. Whatever budget is left goes to the waiting prompt. A prompt that does not fit gets split, and the rest continues next step. That is chunked prefill.

  1. Step starts with a budget of 8,192 tokens.
  2. The 20 decoding streams take 20 tokens: one each.
  3. The long prompt takes the other 8,172 tokens as one chunk.
  4. The step ends; all 20 streams get a token, and the prompt is 8,172 tokens further.
  5. Repeat until the prompt is done; its last step produces its first token.

In vLLM v0.31.0, unless you set it yourself, chunked prefill is on for generative models other than encoder-decoder ones. vLLM's tuning guide says that with it on, the scheduler batches all pending decodes first, fills what is left of the max_num_batched_tokens budget with pending prefills, and chunks any prefill that does not fit. The v0.31.0 code serves running requests in the order they were admitted, and a prompt still being chunked is one of them, so decodes go first when they were admitted before it. Streams already running when the long prompt arrives, as here, are ahead of it. Hugging Face's continuous batching guide describes the same fix: a long prompt in one step blocks other requests from generating, so prompts larger than the token budget are split across steps.

The idea comes from research. Sarathi-Serve splits a prefill into near-equal-sized chunks and builds batches that add new requests without pausing the decodes already running, which it calls stall-free batching.

The analogy breaks in one place. A cashier's baskets cost the same each. Here a later chunk costs more than an earlier one, because its tokens must attend to all the prompt before them.

Chunked prefill gives each step a token budget, serves decodes first and feeds the long prompt in chunks, so no stream waits for the whole prefill.

Put one chunked-prefill step in order.

  1. The step starts with the full token budget
  2. Each decoding stream takes one token from the budget
  3. The waiting prompt takes what is left as a chunk
  4. The step runs and every stream gets its next token
  5. The prompt continues from where it stopped, next step

Decodes are served first so they are never starved; the prompt only gets what is left, which is what caps the step's length.

It names the trade: smaller means smoother streams and more steps per prompt; too small wastes each weight read.

Chunking protects the streams, not the queue

Last part: the budget caps the worst gap for running streams. Still unsolved: what happens to a request that arrives while the long prompt is being chunked?

Ten milliseconds after the contract arrives, someone sends "hi" with a 500-token chat history. Their first token takes 1.47 seconds, at every budget you try.

Each step, the long prompt takes every token the decodes leave. Nothing is left for the newcomer, so it waits for the whole prefill. That is head-of-line blocking. A smaller budget does not help: the chat still waits 1.477 s at a budget of 2,048.

vLLM's long_prefill_token_threshold (default 0, off) caps how many tokens one prefilling request may take in a step; the cap is skipped when that request is the only one waiting or running. The v0.31.0 source says the cap exists to stop a long prefill from starving other requests of the token budget.

With a budget of 8,192 and a threshold of 2,048, the contract takes 2,048 tokens per step and the chat fits beside it. The chat's TTFT drops from 1.471 s to 69 ms. The contract's TTFT rises only from 1.481 s to 1.488 s, and the worst gap for the streams falls to 86 ms.

Waiting requests are admitted in queue order; when the request at the head cannot get KV blocks for its whole prompt (the default check), admission stops for that step, and requests behind it do not jump ahead. So a huge prompt at the head of the queue can also block admission on memory, not only on budget.

The budget bounds how long running streams wait; a per-request prefill cap bounds how long new requests wait behind a long prompt.

Streams are smooth, but new chat requests sometimes wait over a second for their first token, always while someone's long document is being prefilled. Which setting targets that?

  1. Set long_prefill_token_threshold below the budget, so the long prompt leaves room in each step
  2. Halve max_num_batched_tokens
  3. Raise max_num_seqs

The newcomer waits because the long prompt takes every leftover token. Capping that request's share leaves budget for others to be admitted each step.

In your own words: how does chunked prefill work, what does the budget trade, and what problem does it not solve on its own?

Every engine step carries all running requests, so a step that includes a whole long prefill freezes every stream until it ends. Chunked prefill gives each step a token budget, serves one token per decoding stream first and gives the prompt only what is left, so the prompt is split across steps. A bigger budget means longer worst gaps for the streams but fewer steps per prompt; a budget too small turns each step memory-bound and slows long prompts. On its own it does not help new requests: the long prompt takes all the leftover budget, so newcomers wait for the whole prefill unless a per-request cap such as long_prefill_token_threshold leaves room.

Count the requests users were happy with, not the tokens

Last part: one knob trades one user's wait against another's. Still unsolved: what number tells you the server as a whole is doing well?

At ten times normal traffic your dashboard shows 35 requests per second served, more than ever. Support tickets say chat takes eight seconds to start.

An SLO is a per-request promise: first token within 1 s, and an average gap between tokens under 50 ms. Goodput counts only requests that kept the promise.

The DistServe paper defines per-GPU goodput as the highest request rate that can be served while meeting an SLO attainment goal, such as 90% of requests meeting their TTFT and TPOT targets, for each GPU provisioned. It argues that systems tuned for overall throughput, tokens per second across all users, must over-provision GPUs to meet latency targets.

vLLM's benchmark, vllm bench serve --goodput, takes SLOs for ttft, tpot and e2el in milliseconds, counts a request as good only if it meets every one given, and reports good requests per second of benchmark time. Its per-request TPOT is (latency minus TTFT) divided by (output tokens minus 1), and its help text points to the DistServe paper for the definition. The simulator uses the vLLM form, with 1 s TTFT and 50 ms TPOT targets chosen for a chat product:

First come, first served, or priority

Last part: goodput tells you how many users were served well. Still unsolved: when not everyone can be served well, who gets served first?

Your paid tier and your free tier share one vLLM server. A free-tier batch job floods the queue at 2 a.m., and paid users' first tokens slow down with it.

vLLM v0.31.0 accepts two scheduling policies: "fcfs", first come, first served, which is the default, and "priority". Under "priority" a lower value is handled earlier, and arrival time breaks ties; the waiting queue is a heap ordered by those two. A request's priority field defaults to 0, and any other value raises an error unless the server runs the priority policy. You turn it on with --scheduling-policy priority.

Know what priority does not do. In v0.31.0 a priority changes two things: the order of the waiting queue, and which running request is preempted when KV blocks run out. A high-priority arrival does not preempt running requests just to get in. So it shortens the paid user's queue wait, but a long free-tier prefill that is already running still stalls their stream.

vllm serve meta-llama/Llama-3.1-8B-Instruct --scheduling-policy priority

# paid tier: 0 (handled first); free tier: 10
curl localhost:8000/v1/chat/completions -H 'Content-Type: application/json' \
  -d '{"model": "meta-llama/Llama-3.1-8B-Instruct", "priority": 0,
       "messages": [{"role": "user", "content": "hi"}]}'

"How do you guarantee paid users a better experience on shared GPUs?" A strong answer separates queue order from step sharing. Priority scheduling fixes queue order. Stalls inside running steps need a smaller budget or a per-request prefill cap. Real isolation needs separate capacity, and starvation of the low tier needs a limit, or it may never run.

Priority reorders the waiting queue and picks preemption victims; it does not stop a running long prefill from stalling anyone's stream.

You switch to the priority policy and give paid users priority 0. Paid users' TTFT improves, but their streams still stutter. Why?

  1. Priority is ignored unless max_num_seqs is lowered
  2. Priority orders the waiting queue, but free-tier prefills already running still share each step with paid decodes
  3. Paid requests are being preempted by free ones

Stutter comes from prefill work inside the steps that paid streams are part of. Priority does not remove that work; a smaller budget or a per-request prefill cap does.

Saying no early: queue caps and load shedding

Last part: priority chooses who goes first. Still unsolved: at ten times the load, everyone waits; what if some requests are never accepted at all?

At 40 requests per second, a request accepted now waits 7.5 seconds in the queue. The user gives up at 3 seconds. The GPU later does the work anyway.

Load shedding refuses work you cannot serve in time, early and cheaply, so the work you accept stays good. By default vLLM's request queue has no limit. v0.31.0 has two valves:

  1. max_num_queued_reqs caps waiting plus running requests; past it, new requests get HTTP 503 so a client can retry on another instance.
  2. max_num_queued_tokens caps the total prompt tokens of requests still in prefill, also with a 503; its docstring suggests setting it to the TTFT target times prefill throughput.
  3. Both are checked in the API server process, and the token count is conservative: a partly prefilled prompt still counts in full.

The simulator caps waiting plus running at 300 and replays the 10× load:

Turning away 7.6% of requests more than tripled goodput. Without the cap, the scheduler kept admitting until the KV cache was full, then preempted 148 times and recomputed that work.

A 503 only helps if clients behave. Retrying immediately against the same instance turns shedding into a retry storm. Clients need backoff with jitter, and the load balancer must send retries elsewhere.

"Why reject requests when the GPU still has queue room?" A strong answer: a request served after its deadline costs full GPU time and earns nothing. Rejecting it early is cheap, lets the client retry another replica, and protects the requests already accepted. Size the cap from the latency target: queue depth that drains within the TTFT budget.

An unbounded queue turns overload into late answers for everyone; a cap turns it into fast 503s for a few and on-time answers for the rest.

You set max_num_queued_tokens from your TTFT target, and find it rejects slightly earlier than your math predicts during long-document traffic. Why?

  1. It counts each prefilling prompt in full until prefill ends, even when chunks are already done
  2. It also counts the output tokens each request may generate
  3. It is checked inside the GPU worker, which lags behind

The API server does not see chunk progress, so a half-prefilled prompt still counts at its full length. The error is on the safe side: it rejects a little early.

In scheduler.py, a running request is preempted to make room. Why does the code put it at the front of the waiting queue rather than the back?

It was already admitted once, so it is older than anything behind it. Under FCFS, putting it at the back would let newer requests overtake it, and a request could be preempted again and again. At the front it gets the next free room.

What preemption costs the request that loses

Last part: the budget sets worst gaps, and percentiles can hide them. Still unsolved: at high load, KV memory runs out; who pays, and how much?

At 10× load the simulator preempted 148 times. One of the victims was 400 tokens into an answer on a 2,000-token prompt.

When a running request cannot get new KV blocks, v0.31.0 preempts the last request in the running list under FCFS, or the one with the largest priority value, latest arrival first, under the priority policy. The victim's blocks are freed, its count of computed tokens goes back to zero, and it returns to the waiting queue. No waiting request is admitted in a step that preempted anything.

The victim pays three times. Its stream stops while it waits. When it runs again it must recompute 2,400 tokens: about 40 ms of GPU time against 4.9 ms for one decode step. And that recompute is a prefill, so it slows every stream it shares a step with: beside 100 decodes, that step takes 42 ms instead of 8.7 ms.

The watermark setting (default 0.0, off) keeps a fraction of KV blocks free when admitting waiting or preempted requests, to avoid repeated preemption. A cap on queued requests helps more: in the simulator, 300 requests in flight caused no preemptions at all.

Under FCFS the victim is the newest running request, so a user who just got their first token is the one frozen. Their TTFT looked fine; their answer stalls a second later. Watch the preemption counter, not only TTFT.

Preemption frees memory by throwing away a request's cache; the victim waits, then recomputes everything, slowing its step-mates too.

Under the priority policy with paid users at 0 and free at 10, KV memory runs out while a free user's 5,000-token prefill and a paid user's decode are running. Which one is preempted, and what does it lose?

  1. The paid request; it loses its last token only
  2. The free request; its cache is copied to CPU memory
  3. The free request; its blocks are freed and its computed tokens are redone later

Under the priority policy the victim has the largest priority value, here the free request. Its blocks are freed and its computed-token count reset, so the prefill is redone; with prefix caching on, blocks still in the cache can shorten that.

CPU time slices, API gateways, and where both analogies break

Last part: tenant fairness lives outside the scheduler. Still unsolved: which tool to reach for, and how this maps to systems you already run.

An interviewer asks: "This is just CPU scheduling and API rate limiting, right?" Half right.

OS time slicing. An operating system gives each runnable thread a short slice of CPU, so one long job cannot freeze interactive ones. Chunked prefill is the same move: the budget is the slice, and the long prompt is the batch job. Where it breaks: a CPU runs one thread per core per slice, while one GPU step runs everyone at once, so a heavy chunk slows everyone in it. And a context switch saves registers and resumes; a preempted request loses its cache and redoes its work.

API gateway timeouts and shedding. A gateway caps concurrency, times out slow requests, and returns 503 when full. max_num_queued_reqs is the same valve. Where it breaks: an HTTP request costs roughly the same each time, so request counts work as limits. LLM requests differ in cost by a factor of 100 or more by prompt length, so limits must count tokens.

The DistServe paper argues that chunked prefill trades TTFT for TPOT and cannot remove the interference between the two phases. Its answer, separate GPUs for prefill and decode, is Part 7.

Chunked prefill is time slicing and queue caps are load shedding, but steps are shared, preemption discards work, and cost scales with tokens, not requests.

Why does "100 requests per minute per key" fail to protect other tenants of an LLM API, when it works for an ordinary REST API?

  1. LLM request cost scales with prompt and output tokens, so 100 maximum-length requests can cost as much as thousands of short ones
  2. LLM servers cannot count requests
  3. The limit must be combined with priority scheduling to work at all

The limit's unit is wrong. Cost depends on tokens: a 32,000-token prompt costs at least as much prefill as 64 500-token ones. Limits must count tokens.

Interview drill: designs where scheduling is the crux

Last part: the options and their costs. Still unsolved: defending a choice under pressure.

Three prompts. Commit to an answer before you open each reference.

1. A legal-tech product: users upload 80,000-token contracts and also chat. Contracts can take 10 s to first token; chat needs TTFT under 1 s and no gap above 150 ms. One H100 pool. Design the scheduler settings.

Keep chunked prefill on and pick the budget from the 150 ms gap target: about 2,048 tokens per step meets it with margin in this page's model. Add a per-request prefill cap below the budget so chats are admitted beside a contract instead of behind it. Give chat priority 0 and contracts a higher value, so chats go first in the queue. Trade-off: contracts take more steps and wait longer; they have a 10 s budget to spend. If the contract volume grows until chat SLOs slip anyway, split contracts onto their own pool or separate prefill from decode.

2. Your vLLM fleet shows 95% GPU busy, record throughput, and rising complaints. How do you convince the team that the dashboard is lying?

Replace throughput with goodput at the product SLOs, measured with vllm bench serve --goodput or from request logs. Show queue time p99 and waiting requests: at overload they climb while throughput plateaus. Show that the GPU is busy on requests that will miss their target anyway. Propose a queue cap with 503s and client backoff; give up a few percent of requests to get most of goodput back, as the simulator's 7.6% rejected for 3.5 times goodput showed.

3. Paid and free users share GPUs. Free traffic sometimes spikes tenfold. Paid users must keep TTFT p99 under 1 s. What do you build, and what does free tier lose?

Priority scheduling inside vLLM for queue order, plus a gateway with per-tenant token-per-minute limits and a separate queue cap per tier, because vLLM's metrics and policies do not know tenants. Preemption under the priority policy falls on free users first. Free users lose: longer waits, preemption and recompute, and 503s during spikes. If paid ITL also matters, cap prefill per request or move free bulk work to its own pool, at the cost of capacity that sits idle when free traffic is low.

Every answer names the target (goodput at an SLO), the knob, and who pays for it.

Final check. A default vllm serve on an H100 serving Llama 3.1 8B receives a 50,000-token prompt while 20 streams decode. What does the scheduler do?

  1. Runs the whole prompt in one step and freezes the streams for about 1.5 s
  2. Rejects it because it exceeds max_num_batched_tokens
  3. Serves the 20 decodes first each step and feeds the prompt in chunks of the remaining 8,192-token budget

Chunked prefill is on by default, and vllm serve on an H100 defaults to an 8,192-token budget. Each step the decodes go first and the prompt takes the rest.

Explain to a new teammate how you would run a shared vLLM service so that it degrades gracefully under load.

Pick goodput at product SLOs as the target, not throughput. Keep chunked prefill on and set the token budget from the inter-token target, with a per-request prefill cap so new requests are not stuck behind long prompts. Use the priority policy if tiers exist, knowing it orders the queue and chooses preemption victims but does not stop stalls inside a step. Cap queued requests so overload produces fast 503s instead of late answers, and limit tokens per tenant in the gateway, because vLLM does not know tenants. Alert on queue time, waiting requests, KV usage and preemptions.
