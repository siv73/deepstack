Definitions

  1. A stuck request is one the server accepted that is neither answered nor failed, and is not making progress.
  2. A signal is anything a running service emits about its own state: a metric, a log line, a dump of what it is doing.
  3. A metric is a number a service keeps and exports over time, such as a count of seller answers. A log line is a record of one event.

Comparison

A shop whose card machine has frozen mid-payment. The till's sales log shows every sale up to the freeze and nothing after. The camera shows customers standing at the till, not moving. The shop's "busy?" sign shows normal, because the shop is not busy: nobody is doing anything.

Solved example: what this costs

Given: one process takes 2,000 requests a second (Part 8's figure); the audit store stalls for 30 s; the gateway's front door admits at most 200 requests in progress (Part 6).

Step 1. Each stuck request holds one of the 200 places. At 2,000 a second, all 200 are taken after 200 ÷ 2,000 = 0.1 s.

Step 2. From then on the front door answers busy to every new request: 2,000 × 29.9 ≈ 59,800 refusals in the 30 s.

Step 3. The 200 stuck shoppers wait the whole 30 s, or until they give up.

Result: a 30-second stall of a dependency that no request needs for its answer turns into a 30-second outage, with no error logged and every seller counter green. The busy count is the only alarm, and it says "too much traffic", which is the wrong diagnosis.

Wrong belief: "If something were wrong, it would be in the logs."

Why people hold it: most failures raise an exception, and exceptions get logged.

Why it is wrong: a wait with no time limit raises nothing. A log line is written when code runs, and a parked Task runs no code. The failures that hurt most in async services are often waits, and a wait leaves no trace until something with a deadline gives up.

  • A stalled audit store left 5 requests stuck, with 0 log lines, a green dashboard and 0 ms of loop lag.
  • Counters written before the stuck step make stuck requests look like successes.
  • The only moving numbers were requests in progress and the audit queue's size, and neither was exported.

A request that waits forever raises nothing, logs nothing and uses no CPU, so every signal built around errors or work reports a healthy gateway.

Introduction

Part 4 taught debug mode as the detector for three of its traps. This part does not re-teach it; it asks one question about it. What exactly does debug mode measure, and is a stuck request one of those things?

Definition (recap from Part 4)

Debug mode is asyncio's development setting. The docs list four ways to enable it: the PYTHONASYNCIODEBUG environment variable set to 1, the Python Development Mode, debug=True passed to asyncio.run(), or loop.set_debug().

Working: what the slow-step report measures

  1. In debug mode, callbacks taking longer than 100 milliseconds are logged, and loop.slow_callback_duration sets the minimum duration, in seconds, that counts as slow.
  2. In CPython 3.14's base_events.py, debug mode reads the loop's own time() before and after each callback and logs the callback when the difference is at least slow_callback_duration.
  3. A Task step is one callback (Part 2). A Task parked at an await has no step to run, so there is nothing to time.

Why it matters

  • Step 1: debug mode is a stopwatch on code that runs. It answers "what held the loop?".
  • Step 3: a stuck request holds nothing. The question "what is everyone waiting for?" is a different question, and needs a different tool.

Wrong belief: "Debug mode shows everything wrong with an asyncio program."

Why it is wrong: it reports slow callbacks, slow selector calls, calls from the wrong thread, and adds creation tracebacks to never-awaited and never-retrieved warnings (Part 4). Every one of those is about code that ran. A coroutine waiting on a Future that nobody will complete runs no code, and debug mode has nothing to say about it.

  • Debug mode times callbacks: it finds what held the loop.
  • Measured: 0 records for 5 stuck requests; 1 record for a 200 ms blocking callback.
  • Stuck requests need a view of Tasks, not of steps.

Debug mode is a stopwatch on the loop's callbacks, so it catches code that holds the loop and stays silent about Tasks that wait forever.

With debug mode on and the default threshold, which of these does asyncio log?

  1. A request awaiting a lock that is never released
  2. seller-e's 900 ms SDK call running in its own thread pool
  3. A request that parses a 3 MB JSON body for 140 ms between two awaits

Only the JSON parse is a callback that runs for at least 100 ms. The lock wait and the thread-pool wait are waits: the loop is free the whole time, and debug mode has nothing to time.

Introduction

Part 2 showed that a Task holds its coroutine and that a suspended coroutine is paused at one await. If the program can list its Tasks and ask each where its coroutine is paused, it has the camera from the shop comparison. Two APIs do that, on every version this series covers.

Definitions

  1. asyncio.all_tasks() returns the set of not yet finished Task objects run by the loop.
  2. Task.get_stack() returns the stack frames where the Task's coroutine is suspended, and only one stack frame is returned for a suspended coroutine. Task.print_stack() prints output similar to the traceback module's for the frames that get_stack() returns.
  3. A frame is one function call in progress: its code, its current line, its local variables.
  4. If no name has been given to a Task, the default Task implementation generates one when the Task is created. On CPython these look like Task-53.

Introduction

Python 3.14 added call-graph introspection to asyncio. It follows the chain of coroutines inside a Task, and it records which Task awaits which, across Tasks. This part runs it on the same incident.

Definitions

  1. An await chain is the chain of coroutines inside one Task, from its own coroutine down to the await where it is paused.
  2. A Task is awaited by another Task when the other one is waiting for its result.
  3. asyncio's call graph functions, print_call_graph(), format_call_graph() and capture_call_graph(), were added in Python 3.14.
  4. capture_call_graph() returns a FutureCallGraph whose call_stack is a tuple of FrameCallGraphEntry objects and whose awaited_by is a tuple of FutureCallGraph objects; with no argument it uses the current task, and it returns None if there is no current task.
  5. print_call_graph() prints the graph starting from the top frame and going down towards the invocation point, and format_call_graph() returns the same text as a string.
  6. The limit argument keeps at most abs(limit) entries of each call stack: a positive limit keeps the entries closest to the invocation point, a negative one keeps the topmost, and 0 prints only the awaited-by information.

Introduction

The call graph from the last part has a second user: Python 3.14 ships two commands that read the same information out of another running process. They need no code in the target and no restart.

Definitions

  1. python -m asyncio ps PID and python -m asyncio pstree PID inspect the task graph of another running Python process without modifying or restarting it, and they read its state without executing any code in it. Both commands were added in Python 3.14.
  2. ps prints a flat table of all pending tasks; each row shows the event-loop thread id, the task's id and name, its coroutine stack, and the awaiting task's stack, name and id, if any.
  3. pstree prints the tasks as a tree, each task with its coroutine stack nested under the task awaiting it; if the await graph contains a cycle, pstree reports an error instead, while ps prints every task regardless.
  4. The commands are available only on supported platforms and may require permission to inspect another process.

Working: what an operator does

  1. Find the process id (from the orchestrator, or pgrep).
  2. Run python -m asyncio ps PID with a Python 3.14 that can read the target: the table of every Task and its awaiter.
  3. Run python -m asyncio pstree PID: the same, as a tree, which shows which branch of a request is stuck.
  4. Only then decide whether to restart.

Permissions

Reading another process's memory is a debugger's privilege, and production systems restrict it.

  • On Linux, some distributions enable ptrace restrictions (Yama); setpriv --ptracer any, from util-linux 2.41, loosens them for one process and is applied to the process being debugged. The program's allow_inspection() makes the same prctl call on itself, which is what lets it run on CI runners.
  • Docker 19.03 or newer and containerd 1.6.7 or newer allow the ptrace system call inside containers on Linux kernel 4.8 or higher; the CAP_SYS_PTRACE capability may also work, but the docs say it is equivalent to superuser access and should only be used in low-security environments.
  • A process can have only one tracer at a time, so a process already attached to strace or gdb cannot be inspected this way at the same time.

The tools need a Python 3.14 on the machine and permission to read the target. A container image built from a slim base often has neither a second Python nor the right to attach, and the first time anyone finds out is during an incident. Gateway v10 therefore also prints its own dump on a signal, which needs no permission at all (rung 3).

Loop lag as a metric: what it sees, and what it cannot

Last part: ps and pstree show where every Task waits, when someone runs them. Still unsolved: a number a dashboard can graph all day, which says whether the loop itself is healthy.

Part 2 measured loop lag once, in a program. Part 4 named it the production metric for blocking calls. A dashboard needs it as a series, sampled continuously, from every process, and the team needs to know which incidents it will catch.

Introduction

Part 2's probe asked "how late does a 100 ms timer fire?". Kept running in an owned Task, the same question gives a metric. This part runs it through four situations, including this page's incident.

Definition

Loop lag is how late a timer fires compared with when it was due. A sampler sleeps for a fixed interval, compares the loop's clock with the expected wake-up time, and records the difference.

Working

  1. Every 50 ms the loop-lag Task records "expected = now + 50 ms" and sleeps.
  2. If the loop is free, the timer fires on time and the lag is about 0.
  3. If something holds the loop, the timer fires late by however long the loop was held after the timer was due.
  4. The sample goes into a histogram, and the worst value since the last scrape is kept as a gauge.

Program

Four phases, one sampler. LagMonitor is in observe.py (rung 3 shows it); here only its numbers matter.

Explanation of the program

  1. Idle: 0 ms over 12 samples.

The sampler's interval is raised from 50 ms to 1 s to save work. A blocking call of 300 ms now happens at a random moment. What does the worst-lag gauge show, on average?

Usually 0. Metrics for every seller call: a latency histogram and outcome counts

Last part: loop lag says whether the loop is free, and nothing about requests. Still unsolved: numbers that say how each seller is behaving and how long requests really take, kept so the tail is visible.

Introduction

Gateway v10 adds two kinds of metric. Counts say how often each outcome happens; a histogram says how long things take, including the slow few. Both are cheap enough to update on every seller call and every request.

Definitions

  1. A counter only goes up; a dashboard shows its rate. Prometheus's instrumentation guide says every failure should increment a counter, and that failures should generally come with another metric counting all attempts.
  2. A histogram counts each value into the range it falls in: how many calls took at most 50 ms, at most 100 ms, and so on.
  3. A percentile such as p99 is the value 99 in 100 measurements are at or under. From a histogram it can only be bounded: "p99 is at most 2,500 ms".

Why a histogram and not an average

Google's SRE book warns against designing monitoring around means, and recommends recording request counts in latency buckets, rendered as a histogram, with roughly exponential bucket boundaries. The same chapter names the four golden signals as latency, traffic, errors and saturation, and says to distinguish the latency of successful requests from the latency of failed ones. Gateway v10's bounds are 50, 100, 250, 500, 1,000 and 2,500 ms: about twice apart, with the 250 ms budget as one of them, so "answered within budget" is read straight off one bucket.

Working: what gateway v10 records

  1. Every seller call (Part 7's fill, the one real call per seller and item): its duration into that seller's histogram, whatever the outcome, and one count of "seller-c timed out", "answered", "failed" or "skipped".
  2. Every request: its duration from the line arriving to the answer, into one histogram; one count of answered, partial, hung up or stopped by shutdown.
  3. The loop: lag samples into a histogram, and the worst value since the last read.
  4. The audit wait: a count of rows not confirmed in time (next parts).

Why each is needed

  • Step 1 records failures with their durations: a seller that hangs for 2 s shows in its histogram, not only as a count.
  • Step 2 starts the clock when the shopper's line arrives, not when compare() starts, so time spent after the answer is computed (the audit wait) is counted.
  • Steps 3 and 4 cover the two failures this page has measured: a busy loop and a stuck dependency.

Solved example: reading a histogram

Given: 1,000 requests: 985 answered at 250 ms and 15 at 2,250 ms (stuck behind the audit store for 2 s).

Step 1. Buckets: 985 in "at most 250", 15 in "at most 2,500".

Step 2. p50: 500 of 1,000 are reached in the 250 bucket, so p50 ≤ 250 ms.

Step 3. p99: 990 values are needed; the 250 bucket has 985, so the answer is the next bucket: p99 ≤ 2,500 ms.

Step 4. Mean: (985 × 250 + 15 × 2,250) ÷ 1,000 = 280 ms.

Controlling time: a loop whose clock jumps to the next timer

Introduction

Every wait in the gateway with stub sellers is a timer: sleep(), timeout(), timeout_at(). Part 2 showed that each loop iteration computes how long until the next timer is due, then waits in the selector for that long. If the loop's clock could jump forward by that amount instead of waiting, every test would run as fast as its code, with exact times.

Definitions

  1. loop.time() returns the current time according to the event loop's internal monotonic clock, and loop.call_at() schedules callbacks using the same time reference as loop.time().
  2. SelectorEventLoop uses the most efficient selector for the platform, and can be given the exact selector to use; the documentation's example passes asyncio.run() a loop_factory that creates a SelectorEventLoop with a chosen selector.
  3. asyncio.run() gained the loop_factory parameter in Python 3.12, and asyncio.Runner, added in 3.11, takes a loop_factory too. The documentation recommends configuring the event loop with loop_factory rather than policies, and says the policy system is deprecated and will be removed in Python 3.16.
  4. A virtual clock moves only when every Task is waiting for a timer, and then by exactly the time until that timer.

Working: one iteration of the virtual-clock loop

  1. The loop runs every ready callback (Part 2).
  2. It computes the time until the next timer, say 0.08 s for seller-a's stub, and asks the selector to wait that long.
  3. VirtualSelector.select() first checks real sockets, including the loop's own wake-up pipe, without waiting. If any is ready, it returns them: real I/O still works.
  4. If none is ready, it adds 0.08 to the loop's now and returns at once. VirtualClockLoop.time() returns now.
  5. The loop then runs every timer due by time(), exactly as it would after a real 80 ms wait.

Why each step is needed

  • Step 3: signals, wake-ups from other threads and real sockets arrive through file descriptors; ignoring them would hang the test.
  • Step 4 changes nothing else in the loop: both pieces it overrides are public, the selector given to the constructor and the time() method every timer reads.

Program

Explanation of the program

  1. sleep(0.9) ends with loop.time() at exactly 0.900 and 0 ms of real time.
  2. asyncio.timeout(0.25) fires at exactly 1.150: the clock jumped to the deadline because nothing else was due.
  3. Two sleeps of 0.2 s and 0.1 s: the 0.1 s one finishes first, at 1.250. Order between timers is preserved.
  4. time.sleep(0.05) on the loop's thread: 50 ms of real time pass, and loop.time() does not move except for the earlier sleeps. A blocking call costs nothing on this clock, which the next block warns about.

What the virtual clock cannot do

  • Threads and processes. Their work takes real time, but the clock may jump past a deadline while they run. Tests on this clock replace pools with InlineExecutor.
  • Real network I/O. A real socket's reply takes real time; if a timer is due meanwhile, the clock jumps to it first. Stub the network.
  • Blocking calls and debug mode. A blocking call is invisible on this clock, and since debug mode times callbacks with the loop's own time() (rung 2), its slow-callback report is blind here too. Keep one real-time test with debug mode on for that trap.
  • uvloop. Its loop is not a SelectorEventLoop and takes no selector, so this technique applies to asyncio's own loop only.

Python 3.11. asyncio.run() has no loop_factory before 3.12; use with asyncio.Runner(loop_factory=VirtualClockLoop) as runner: runner.run(main()), which this page's version probe checks on 3.11. Older test suites change the loop through an event loop policy; the policy system is deprecated and will be removed in Python 3.16, so new tests should not.

Wrong belief: "To test timeouts without waiting, shorten them: a 250 ms budget becomes 2.5 ms in tests."

Why it is wrong: scaled-down times make scheduling noise relatively 100 times larger, so the tests get flakier, not faster, and they test a configuration nobody runs. The virtual clock keeps the real values, 250 ms, 900 ms, 1 s, and makes them cost nothing.

  • VirtualClockLoop: a SelectorEventLoop whose selector jumps the clock to the next timer instead of waiting.
  • Use with asyncio.run(main(), loop_factory=VirtualClockLoop) (3.12+) or asyncio.Runner (3.11+).
  • Only for code whose waits are timers: stub the network and the pools; keep a real-time test for blocking calls.

Failure 1: the call graph on 3.14.0 to 3.14.7

Program

Solved example: what breaks first

Given: the output: 2 lines and 302 bytes per cached request; 8 processes at 2,000 requests a second each (Part 8).

Step 1. Today: 16,000 requests a second × 2 lines = 32,000 lines a second, 4.8 MB a second, 0.42 TB a day.

Prometheus's naming guide warns that every unique combination of label values is a new time series, and says not to use labels for dimensions with high cardinality such as user IDs, email addresses or other unbounded sets of values. Seller × outcome is 20 series per process. An item label with 50,000 items makes it 1,000,000 per process. "Which products are slow" is a log query, not a label.

What to alert on, and what only to graph

Last part: telemetry has a cost. Still unsolved: of all these numbers, which should wake someone at 3 a.m., and which should only be on a dashboard.

Gateway v10 exports loop lag, seller histograms, outcome counts, audit timeouts and requests in progress. The first draft of alerts has 14 rules; in its first week it pages 40 times, mostly for seller-e's timeouts, which happen on every request by design.

Introduction

An alert is a promise that someone must act now. This part separates the gateway's signals into what users feel and why they feel it, and pages only on the first.

Definitions

  1. Google's SRE book frames monitoring as two questions, what is broken (the symptom) and why (the cause), says every page should be actionable, and says it is better to spend much more effort catching symptoms than causes.
  2. An SLO (service level objective) is a target for the share of good events, for example 99.9% of requests answered within 300 ms over 30 days. The 0.1% left is the error budget.
  3. The SRE workbook defines burn rate as how fast, relative to the SLO, the service consumes its error budget, and for a 99.9% SLO over a 30-day window recommends paging when the burn rate is 14.4 over both the last hour and the last 5 minutes, which is 2% of the budget, or 6 over 6 hours and 30 minutes, which is 5%.

Working: sorting gateway v10's signals

  1. Symptom: the SLO. A good request is answered within 300 ms (250 ms budget plus margin). Read it from the request histogram's 250 and 500 buckets, and from busy and stopped counts. Page on burn rate.
  2. Symptom: requests in progress at the front door's limit. Page if it stays at the limit for minutes: requests are not finishing, whatever the cause.
  3. Cause: loop lag. Graph it; open a ticket if its p99 stays above 50 ms. It explains a burning SLO; alone it rarely needs a human at night.
  4. Cause: per-seller timeouts and failures. Graph them against each seller's normal: seller-e times out on most requests by design, so an absolute threshold pages forever.
  5. Cause: audit timeouts. Ticket on any sustained rate: the rows are late, the store needs attention, shoppers are already protected by the limit.

Interview drill: seeing and testing an async service

Last part: the checklist. Still unsolved: explaining it out loud, with mechanisms, numbers and trade-offs, the way an interviewer asks.

"How would you debug it?" and "how do you test it?" are the follow-ups to almost every async design question. A weak answer names tools. A strong one says what each tool can and cannot see, with numbers, and what it costs.

Introduction

Three prompts follow. Each draws on this page and at least one earlier part. Try each before opening the reference answer.

Prompt 1: "p99 jumped from 250 ms to 2 s; CPU is at 5%; nothing in the logs"

An asyncio API on Python 3.14. p99 is 2 s, p50 is unchanged at 120 ms, CPU on the loop's thread is 5%, loop lag is 0 to 1 ms, there are no errors. Diagnose, without restarting.

Low CPU and near-zero lag rule out the loop: no blocking call, no overload (Part 4's trap 2, this page's lag metric). An unchanged p50 with a 2 s p99 means a minority of requests wait on something with a long or missing timeout; with no errors, the wait ends in success or the client gives up. Next, before any restart, dump the Tasks: python -m asyncio pstree PID if permitted, else the in-process dump on a signal, and look for many requests parked at the same frame. Read one chain to the dependency, and check its own Tasks, as the audit writers here. Then confirm with that dependency's duration histogram, if it records every outcome. Fix: a time limit on that wait sized below the client's timeout, so the hang becomes a counted, logged timeout, plus the missing histogram. Trade-off: the limit turns slowness into failures or late writes for that dependency, which must be acceptable for it.

Prompt 2: "Make this test suite fast and stop it flaking"

An async service's 400 tests take 9 minutes and about one run in ten fails a different test. Most use real sockets and asyncio.sleep with short timeouts. What do you change, and in what order?

First stop the flakes, because they hide real failures: run every test on a fresh loop, create asyncio objects inside tests rather than at import, reset module-level state, and fail any test that leaves a Task running; the failures that appear are real leaks. Then take time out of the tests: find the seam where the service calls its dependencies, replace them there with stubs that sleep, run thread and process pools inline, and run on a loop whose selector jumps the clock to the next timer, so the real timeouts, 250 ms or 30 s, run in milliseconds with exact assertions. Restore production values instead of the shortened ones. Keep a thin integration layer on real sockets, on each loop implementation in production, and one real-time test with debug mode for blocking calls. The trade-off: the stubs must keep matching the real dependencies, which the integration layer checks.

Prompt 3: "Design the observability for the price gateway"

You own the gateway from this series. List what you emit, what you page on, and what you would refuse to add, with numbers.

Emit: a request histogram from the line's arrival to the answer, with bounds about twice apart including 250 ms; counts of answered, partial, busy, hung up and stopped by shutdown; requests in progress; per-seller call histograms and counts for every outcome, 5 × 4 series; loop lag as worst-per-scrape plus a histogram; audit timeouts; one JSON line per request end and per seller call with the request id, about 300 bytes per request; named Tasks and an in-process dump on SIGUSR1, plus a rehearsed pstree on 3.14.8+. Page on: SLO burn rate (99.9% within 300 ms; 14.4 over 1 h and 5 min) and requests in progress at the front door's limit for minutes. Dashboard, not pager: loop lag, seller timeouts against their normal (seller-e times out by design), audit timeouts. Refuse: an item or shopper label on metrics (50,000 items turns 20 series into 1,000,000), per-seller-call INFO lines for cache hits, debug mode in production. Trade-off: every signal costs CPU, bytes and money at 10× the load, so each must answer a question someone will ask in an incident.

What separates a senior answer here: it distinguishes a blocked loop from stuck awaits before naming a tool, and knows which tools see which (debug mode and lag for the first, task dumps and call graphs for the second); it measures from the edge, records every outcome, and reads tails, not means; it pages on symptoms and keeps causes on the dashboard; it makes tests exact by controlling the clock rather than shrinking timeouts, and says what that clock cannot see; and it treats telemetry as a cost with a budget.

  • Dump Tasks before restarting; read one chain to the dependency.
  • Exact tests via a controlled clock; a thin real-time layer for the rest.
