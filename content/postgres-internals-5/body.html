One query, many ways to run it

A merchant dashboard query was fast last quarter. Today it is two hundred times slower. Nobody changed the code, the index from Part 4 is still there, and the server is not busy.

Think of a maps app. You ask for one destination; it knows many routes, and it picks one from its traffic estimates. When the estimates are wrong, it sends you down a jammed road, and you still arrive at the same place.

A database works the same way. Your SQL says which rows you want, not how to fetch them. The destination is the query's result. Each route is a plan. The traffic estimate is how many rows each step will produce. Travel time is the plan's estimated cost.

  1. The parser checks the query's syntax and builds a query tree.
  2. The rewriter applies rules stored in the system catalogs; views work this way, with the view replaced by a query on its base tables.
  3. The planner creates the possible paths to the same result, estimates the cost of each, and expands the cheapest into a full plan for the executor. This chooser is the planner.
  4. The executor runs the plan as a demand-pull pipeline: each time a plan node is called, it delivers one more row or reports that it is done.

The important word in step 3 is estimates. The planner does not run the candidates to see which is fastest. It prices them from numbers it gathered earlier. When the data grows or those numbers go stale, a different plan can start to look cheapest, and the same SQL suddenly runs a different way. Engineers call that a plan flip.

This page teaches you to see which plan ran, why the planner picked it, and how to give it better numbers. Part 4 covered which indexes exist; this part covers how the planner decides whether to use them.

The planner picks the plan that looks cheapest from its estimates, so the plan can change while the SQL stays the same.

Put the stages a query passes through in order.

  1. Parser builds a query tree
  2. Rewriter expands views
  3. Planner prices paths and keeps the cheapest
  4. Executor pulls rows through the plan

Syntax first, then rules and views, then the cost-based choice, then execution. Only the planner looks at statistics.

Last week a query used an index. Today, with no code or index change, it reads the whole table. Which stage made the new choice?

  1. The parser
  2. The executor
  3. The planner, because its cost estimates changed

Choosing between paths by estimated cost is the planner's job. Same SQL plus different estimates can mean a different plan.

In your own words: why can the same SQL run fast one week and slowly the next, with no code change?

SQL only describes the result. The planner chooses how to produce it by listing possible plans, estimating each one's cost from statistics, and keeping the cheapest. When the table grows or the statistics change, the estimates change, and a different plan can win. The new plan can be much slower in reality if the estimates behind it are wrong.

How the planner prices a plan

Last part: the planner keeps the cheapest of several plans. Still unsolved: cheapest in what unit, and why does the winner change?

A million payments sit on about sixteen thousand pages. One merchant's rows can come from reading every page in order or from jumping through an index. Which is cheaper depends on how many rows match.

Think of shopping. For three items you walk straight to their aisles. For half the store, walking every aisle once in order beats zig-zagging.

Costs are in arbitrary units set by the planner's cost parameters; by tradition one unit is one sequential page fetch, so seq_page_cost is 1.0 and the other parameters are set relative to it. The defaults are seq_page_cost 1.0, random_page_cost 4.0, cpu_tuple_cost 0.01, cpu_index_tuple_cost 0.005 and cpu_operator_cost 0.0025.

  1. A sequential scan's estimated cost is the pages read times seq_page_cost plus the rows scanned times cpu_tuple_cost, and each operator in a WHERE condition adds cpu_operator_cost for every row it checks.
  2. An index scan fetches table rows in index order, which makes each fetch expensive, so the planner uses it mostly when very few rows match or when an ORDER BY matches the index order.
  3. A bitmap scan first collects the locations of matching rows from the index, sorts them into physical order, and then reads the table pages in that order.

The first cost on an EXPLAIN line is the start-up cost spent before the node can output its first row, such as the time to sort; the second is the total cost if the node runs to completion. A node's cost includes the cost of all its children, and the top node's total cost is the number the planner tries to minimize.

EXPLAIN SELECT * FROM payments;
-- Seq Scan on payments  (cost=0.00..26394.00 rows=1000000 width=95)
--   16394 pages x seq_page_cost 1.0       = 16394
-- + 1000000 rows x cpu_tuple_cost 0.01    = 10000
--                                total    = 26394

The model below is a toy: every matching row sits on a different, uncached page. The real planner also counts caching and physical order, but the shape holds: a flat line, a steep line, and a crossover that moves with the constants.

The docs say random storage reads normally cost much more than four times a sequential read, and the default of 4.0 is lower because most random reads, such as index reads, are assumed to hit cache. Lowering random_page_cost relative to seq_page_cost makes the planner prefer index scans, and setting the two equal makes sense if the database is entirely cached in RAM. Only the relative values of the cost parameters matter, and the docs warn that changing them on the basis of a few experiments is very risky.

Costs are in page-fetch units: a sequential scan's cost barely depends on how many rows match, an index scan's grows with every row, so the row estimate decides which wins.

The team lowers random_page_cost from 4.0 to 1.1 on a server whose data fits in memory. What changes?

  1. Index reads get faster
  2. Some queries that used sequential scans now pick index or bitmap scans
  3. Nothing, because only relative values matter

Lowering random_page_cost relative to seq_page_cost makes index scans look cheaper, so the crossover moves and more queries choose them. Measure the queries that flip before and after.

Where row estimates come from

Last part: the row estimate decides which scan wins. Still unsolved: how does the planner know how many rows match without reading them?

WHERE status = 'failed' on a million payments. Is that fifty rows or a hundred thousand? The answer picks the plan, and the planner must guess before reading anything.

The table's row and page counts come from reltuples and relpages in pg_class, which VACUUM, ANALYZE and a few DDL commands such as CREATE INDEX update. The planner also looks up the table's current number of pages, which is cheap, and scales reltuples to match whenever that differs from relpages.

Next it needs each condition's selectivity. Selectivity is estimated from the pg_statistic catalog, which ANALYZE fills, and the statistics are always approximate, even right after ANALYZE. The pg_stats view shows the statistics per column: null_frac, n_distinct, most_common_vals with most_common_freqs, histogram_bounds, and correlation.

  1. For col = constant, a value in the most-common-values list gets its stored frequency as the selectivity.
  2. For col = constant with a value not in the most-common-values list, the selectivity is an even share of what the list leaves over: one minus the listed frequencies and the null fraction, divided by the number of other distinct values.
  3. For a range such as col < constant, the planner checks the condition directly against the most common values and adds up their frequencies; for the remaining rows it uses the histogram, whose buckets hold equal numbers of rows, counting the whole buckets below the constant plus a straight-line share of the bucket the constant falls in.
  4. For several conditions, the planner normally assumes they are independent and multiplies their selectivities.
  5. A correlation near +1 or -1 makes an index scan on the column look cheaper than one near zero, because rows in value order sit close together on disk.

The model below reproduces the worked examples in the PostgreSQL docs, and its tests check the same numbers the docs print.

For large tables, ANALYZE reads a random sample rather than every row, so the statistics change slightly on each run, and in rare cases a plan changes after ANALYZE even though the data didn't. ANALYZE aims for a sample of 300 rows times the largest statistics target it needs for the table. default_statistics_target is 100, and the target caps both the length of the most-common-values list and the number of histogram buckets. With every target at 100, that is thirty thousand sampled rows, whether the table holds a million rows or a billion.

Every row estimate is arithmetic over a sample: frequencies for common values, an even share for the rest, histogram buckets for ranges, and multiplication across conditions.

payments has a million rows. merchant_id has 5,000 distinct values and no nulls. Its most-common-values list holds 100 merchants whose frequencies add up to 0.30. Merchant 42 is not on the list. Commit to an estimate for WHERE merchant_id = 42.

(1 − 0.30) ÷ (5,000 − 100) ≈ 0.000143, times a million rows ≈ 143 rows. Every merchant outside the list gets the same estimate, whether it really has 3 rows or 30,000.

Which statistic does the planner use for status = 'failed' when status has only five values?

  1. The most-common-values list and its frequencies
  2. The histogram bounds
  3. The correlation

With five values, all of them fit in the list, so the estimate is the stored frequency of 'failed'.

Three ways to join, and who picks the order

Last part: estimates for one table. Still unsolved: what a wrong estimate does to a join.

Joining 50 payments to merchants and joining 5 million need different methods. Pick the one for 50 when the truth is 5 million, and the query crawls.

Seating wedding guests: look up five guests one by one; for five hundred, bucket the chart by surname first; if both lists are alphabetical, walk them together.

  1. Nested loop: in a nested loop join, the right side is scanned once for every row of the left side, which can be a good strategy when the right side can use an index scan keyed by values from the current left row.
  2. Hash join: in a hash join, one side is loaded into a hash table on its join columns, then the other side is scanned and each row probes the table for matches.
  3. Merge join: in a merge join, both sides are sorted on the join key, by a sort step or by an index scan in that order, then read in parallel, so each side is scanned only once.

A nested loop's cost is set from the outer scan's cost plus one repetition of the inner scan for each outer row, plus a little CPU time for join processing. So an outer estimate that is a hundred times too low makes the inner work a hundred times larger than the planner priced. Memoize, on by default, caches the results of parameterized inner scans in a nested loop, so a repeated value whose results are still cached skips the inner scan; when the cache is full it evicts the least recently used entry rather than spilling to disk.

All joins in the executor take two inputs, and the number of possible join orders grows exponentially with the number of tables. From geqo_threshold FROM items on, 12 by default, the planner replaces its exhaustive search with a genetic search that takes less time but won't necessarily find the best plan. The planner merges a subquery into its parent only if the resulting FROM list has at most from_collapse_limit items, 8 by default, and join_collapse_limit, set the same by default, applies that rule to explicit JOINs other than FULL JOIN. Setting join_collapse_limit to 1 makes the planner join tables in the order written with explicit JOIN syntax.

Where the comparison stops: the planner never sees the guests, only estimated counts.

Nested loops win for a few outer rows with an index on the inner side, hash joins for large unsorted inputs, merge joins for inputs already in key order, and a bad outer estimate picks the wrong one.

The planner expects 50 outer rows and picks a nested loop with an index lookup on the inner side. The outer side really returns 500,000 rows and the inner table is small. Which join would correct estimates most likely have chosen?

  1. The same nested loop
  2. A hash join, building the small inner table once
  3. A merge join, because both sides are large

With 500,000 outer rows, loading the small inner table into a hash table once beats half a million index lookups.

Explain to a teammate how one wrong row estimate can turn a fast join into a slow one.

The planner picks plans by estimated cost, and the main input is how many rows each step returns. Those estimates come from sampled statistics and assume conditions are independent. If it believes the outer side returns 50 rows, a nested loop with an index lookup per row looks cheapest. If the outer side really returns 500,000 rows, the inner lookup runs 500,000 times, and a hash join would have been far cheaper.

Reading EXPLAIN ANALYZE without fooling yourself

Last part: a wrong outer estimate picks the wrong join. Still unsolved: how to see the estimates, and the truth, for a real query.

An endpoint joins payments filtered by city and state to orders. It is slow, and EXPLAIN alone looks reasonable.

EXPLAIN ANALYZE executes the query and shows the true row counts and run time of each plan node next to the estimates. The thing usually most important to look for is whether the estimated row counts are reasonably close to the actual ones.

Nested Loop  (cost=0.42..33426.20 rows=128 width=12)
             (actual time=0.021..85.331 rows=2500.00 loops=1)
  Buffers: shared hit=27991 read=5903
  ->  Seq Scan on payments p  (cost=0.00..31394.00 rows=255 width=8)
                             (actual time=0.014..76.228 rows=5000.00 loops=1)
        Filter: ((city = 'c7') AND (state = 's0'))
        Rows Removed by Filter: 995000
  ->  Index Scan using orders_pkey on orders o  (cost=0.42..7.97 rows=1 width=12)
                             (actual time=0.002..0.002 rows=0.50 loops=5000)
        Index Cond: (id = p.id)
        Index Searches: 5000
Planning Time: 0.371 ms
Execution Time: 85.511 ms
  1. Read bottom-up and find the first node where estimate and actual part ways. Here: 255 expected, 5,000 got. Everything above inherits that error.
  2. When a node runs more than once, loops is the number of executions and the actual time and rows are per-execution averages, so multiply by loops for the totals. The inner index scan ran 5,000 times.
  3. Rows Removed by Filter appears when a filter condition rejected at least one scanned row. Here the scan read a million rows to keep five thousand.
  4. BUFFERS counts shared blocks hit, read, dirtied and written; a hit means the block was already in cache, so no read was needed. BUFFERS counts on an upper node include those of all its children.
  5. PostgreSQL 18 added BUFFERS output to EXPLAIN ANALYZE automatically and prints actual row counts as fractions, such as rows=0.50, while estimated rows stay whole numbers. That keeps loops arithmetic honest.

Three traps. Because EXPLAIN ANALYZE runs the statement, an INSERT, UPDATE, DELETE or MERGE really changes data, so wrap it in BEGIN and ROLLBACK. Per-node timing reads the clock repeatedly and can slow a query significantly on some systems; TIMING OFF keeps the row counts without it. A LIMIT can stop a child node early, so actual rows below the estimate there are not an estimation error.

BEGIN;
EXPLAIN (ANALYZE, BUFFERS, SETTINGS)
  UPDATE payments SET status = 'failed' WHERE merchant_id = 42;
ROLLBACK;

The SETTINGS option lists configuration parameters that affect planning and differ from their built-in defaults. The script below automates the first step: it multiplies by loops and flags estimates off by ten times or more, plus the spills you'll meet later.

"This query is fast in staging and slow in production. How do you investigate?" A strong answer gets the production plan, not the staging one, with EXPLAIN (ANALYZE, BUFFERS, SETTINGS) on a replica or inside a rolled-back transaction. It compares row estimates with actuals node by node, then checks why they differ: data volume and skew, statistics freshness, and settings that SETTINGS reveals. It notes that a toy staging table can't predict the production plan.

Find the lowest node where estimated and actual rows diverge, multiply per-loop numbers by loops, and treat everything above that node as a consequence.

A node shows (actual time=0.010..0.012 rows=3.00 loops=20000). How many rows did it return in total?

  1. 3
  2. About 0.012 ms worth
  3. 60,000

Rows and time are per-execution averages. Multiply by loops: 3 × 20,000 = 60,000 rows.

Giving the planner better numbers

Last part: find where estimated and actual rows part ways. Still unsolved: what to change.

A nightly job loads two million rows into events. Dashboards that read the new rows pick nested loops and time out until morning.

After a significant change in a table's data distribution, including a bulk load, running ANALYZE is strongly recommended, because with missing or obsolete statistics the planner can make poor choices. Autovacuum analyzes a table once the rows inserted, updated or deleted since the last ANALYZE exceed autovacuum_analyze_threshold plus autovacuum_analyze_scale_factor times the table's row count. autovacuum_analyze_threshold defaults to 50 rows and autovacuum_analyze_scale_factor to 0.1, that is ten percent of the table.

Autovacuum never runs ANALYZE on partitioned tables themselves, only on their partitions, so the parent's statistics need a manual ANALYZE when it is first populated and whenever its distribution changes much.

ALTER TABLE ... ALTER COLUMN ... SET STATISTICS sets one column's target, which caps its most-common-values list and histogram buckets, and a target of zero turns statistics off for that column. A higher limit might allow more accurate estimates, particularly for irregular distributions, at the price of more space in pg_statistic and slightly more time to compute estimates.

The planner normally assumes conditions on different columns are independent, and per-column statistics cannot capture cross-column correlation. CREATE STATISTICS only records interest in a set of columns; ANALYZE, manual or automatic, collects the data. A statistics object made this way is called extended statistics.

  1. dependencies: functional dependencies are applied only to equality conditions comparing columns to constants and to IN lists of constants, and they assume the conditions are compatible, so a city paired with another city's zip code is estimated as if the pair were valid, although no rows match.
  2. ndistinct: n-distinct statistics improve group-count estimates for GROUP BY on several columns, and the docs advise them only for column groups actually grouped on where misestimates cause bad plans.
  3. mcv: a multivariate most-common-values list stores actual value combinations, so it can decide which combinations are compatible, and it also handles range conditions, unlike functional dependencies.
-- 1. Fresh statistics right after the load, in the same job
ANALYZE events;

-- 2. A skewed column gets a longer list and finer histogram
ALTER TABLE payments ALTER COLUMN merchant_id SET STATISTICS 1000;

-- 3. Columns that move together
CREATE STATISTICS payments_city_state (dependencies, mcv)
  ON city, state FROM payments;
ANALYZE payments;

-- A big, busy table: auto-analyze after 1% changes instead of 10%
ALTER TABLE events SET (autovacuum_analyze_scale_factor = 0.01);

autovacuum_analyze_scale_factor can be overridden for one table with a storage parameter of the same name. Then check the estimate moved.

"The planner estimates one row and gets fifty thousand. Walk me through it." A strong answer checks freshness first (did a load outrun autovacuum?), then conditions on related columns (extended statistics), then skew (a higher target), confirming each step against the actual count. It doesn't reach for hints or global settings first.

Fix estimates in order: fresh statistics, then a higher target for skewed columns, then extended statistics for columns that move together.

GROUP BY city, state is estimated at 20,000 groups but returns 500, and the planner picks a sort-based plan sized for 20,000. Which statistics kind targets this?

  1. dependencies
  2. A higher SET STATISTICS on city
  3. ndistinct on (city, state)

The planner multiplies per-column distinct counts for a multi-column GROUP BY. ndistinct statistics record the real number of combinations.

Sorts, hashes and parallel workers: where memory goes

Last part: better estimates. Still unsolved: a right plan that runs out of memory.

A report sorts half a million rows. One setting decides whether it sorts in memory or spills to temporary files.

work_mem is the base amount of memory one query operation such as a sort or hash table may use before writing to temporary disk files, and its default is 4MB. Sorts serve ORDER BY, DISTINCT and merge joins; hash tables serve hash joins, hash-based aggregation, Memoize and hashed IN subqueries. A hash table's limit is work_mem times hash_mem_multiplier, which defaults to 2.0.

  1. A Sort node in EXPLAIN ANALYZE reports its sort method and the memory or disk it used; methods named external sort or external merge mean the sort spilled to disk.
  2. A Hash node reports its buckets, batches and peak memory, and more than one batch means disk space was used as well. When the inner side doesn't fit, a hash join runs in batches written to temporary files, and the executor doubles the batch count when the hash table grows too large, unless an earlier split moved all or none of a batch's rows, after which it stops growing the count.
  3. Hash aggregation that exceeds its memory limit keeps updating the groups already in memory and writes rows for new groups to disk in partitions, to process in later batches.
  4. When the input is already sorted on a prefix of the sort keys, an Incremental Sort sorts in smaller batches, which returns rows sooner, helps LIMIT, and can lower memory use and spilling.
BEGIN;
SET LOCAL work_mem = '256MB';
SELECT merchant_id, sum(amount)
FROM payments
GROUP BY merchant_id
ORDER BY 2 DESC;
COMMIT;

SET LOCAL lasts only until the current transaction ends, after which the session's setting applies again.

A parallel plan contains a Gather or Gather Merge node; the part below it runs in background worker processes, and the leader runs that part too while collecting the workers' rows. max_parallel_workers_per_gather, 2 by default, caps the workers per Gather node, and work_mem applies to each worker separately, so a query with 4 workers may use up to 5 times the resources of a serial one. No parallel plan is made for a query that writes data or locks rows, apart from the SELECT inside commands such as CREATE TABLE AS, or for a cursor.

Partition pruning drops partitions that cannot contain matching rows, using only the partition bounds, not indexes. Partition pruning can also run during execution for values unknown at planning time, such as prepared-statement parameters; partitions pruned at executor start-up don't appear in EXPLAIN, and a Subplans Removed line counts them.

work_mem is a per-operation, per-process limit: a sort or hash that outgrows it spills to disk, and every parallel worker gets its own.

A Hash node shows Batches: 16 and the query is slower than expected. What does that tell you?

  1. The hash table had 16 buckets
  2. The inner side didn't fit in hash memory, so the join ran in batches through temporary files
  3. 16 parallel workers built the hash

More than one batch means the hash outgrew work_mem × hash_mem_multiplier and spilled. Either the inner side is bigger than estimated or the memory limit is too small for it.

Finding the slow queries in production

Last part: memory and parallelism. Still unsolved: in production you don't know which query to EXPLAIN.

p99 latency doubled after a deploy. The service runs thousands of distinct queries. You need the few that matter, and their real plans, without guessing.

pg_stat_statements tracks planning and execution statistics of all SQL statements on the server; it must be loaded through shared_preload_libraries, which needs a restart, and its view is enabled per database with CREATE EXTENSION. Queries that are the same apart from literal constants are typically combined into one entry, with columns including calls, total_exec_time, mean_exec_time, rows, and shared and temp block counts. pg_stat_statements.max, 5000 by default, caps the statements tracked, and the least-executed ones are discarded beyond it.

SELECT queryid,
       calls,
       round(total_exec_time)              AS total_ms,
       round(mean_exec_time::numeric, 1)   AS mean_ms,
       temp_blks_written,
       left(query, 60)                     AS query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;

Sort by total time to find where the server's time goes; sort by mean time to find individually slow statements; sort by temp blocks written to find spills. Then capture the plan. auto_explain logs the plans of statements that run at least as long as auto_explain.log_min_duration, which is -1, meaning off, by default. With auto_explain.log_analyze on, per-node timing runs for every statement, logged or not, which can hurt performance badly; turning off auto_explain.log_timing reduces that cost.

shared_preload_libraries = 'pg_stat_statements,auto_explain'
auto_explain.log_min_duration = '500ms'
auto_explain.log_analyze = on
auto_explain.log_timing = off
auto_explain.log_buffers = on

auto_explain.log_buffers adds buffer usage to the logged plan and has no effect unless auto_explain.log_analyze is on. log_min_duration_statement logs the duration of every statement that runs at least as long as its value; -1, the default, disables it, and 0 logs every statement. track_io_timing adds I/O wait times to EXPLAIN BUFFERS output and pg_stat_statements, and it is off by default because reading the clock repeatedly may be costly on some platforms.

pg_stat_statements tells you which statements cost the most; auto_explain tells you which plan they ran when they were slow.

Statement A: 2 million calls, mean 3 ms. Statement B: 40 calls, mean 20 s. The database CPU is saturated. Which do you look at first?

  1. A: about 6,000 seconds of total time against B's 800
  2. B, because 20 s is far worse
  3. Whichever has more calls, always

total_exec_time = calls × mean. A costs 2,000,000 × 3 ms ≈ 6,000 s; B costs 40 × 20 s = 800 s. B still deserves a look for its users, but A is where the load is.

A teammate asks how you'd find and diagnose the query behind a latency jump. Explain your process end to end.

I'd rank statements in pg_stat_statements by total time, then by mean time and temp blocks written, and compare with a snapshot from before the jump. For the top suspects I'd get the real plan, from auto_explain logs or EXPLAIN (ANALYZE, BUFFERS) on a replica. In the plan I'd find the lowest node where estimated and actual rows differ by ten times or more, remembering to multiply by loops. Then I'd fix the estimate with ANALYZE, a higher statistics target or extended statistics, and only after that look at memory, indexes or cost settings.

The plan that flips at ten times the data

Last part: tools that find slow statements. Now the failures they find, starting with plans that change by themselves.

A merchant's dashboard uses an index scan. The merchant grows tenfold in a quarter. One morning the same query reads the whole table, and its latency jumps.

Go back to the crossover chart. The planner switches plans when the estimate crosses the line. That is often correct: once a merchant owns a few percent of the table, a sequential scan really is cheaper than thousands of random page reads. A flip is a bug only when the estimate behind it is wrong, or when the cost constants misdescribe your hardware.

So when a plan changes, ask three questions. Did the real row count cross the crossover? Did the estimate move without the data moving? Did the constants or settings change? The first is healthy. The second and third are incidents.

Clerk's postmortem of its February 2026 outage traced it to an automatic ANALYZE whose sample recorded a column as entirely NULL when 99.9996% of its values were NULL, so the planner expected no non-null rows where over 17,000 existed. Clerk's plan flip caused an outage of about 90 minutes, and running ANALYZE again by hand restored the earlier plan. Clerk's follow-ups included alerting on query plan flips and a higher statistics target.

The Clerk case shows the sampling risk from the estimates part: a rare value can be missing from the sample entirely, and one autoanalyze can move the estimate with no change in data. The fix that holds is more detail for that column, not a hint that freezes one plan.

The autovacuum daemon schedules ANALYZE strictly from the number of rows inserted or updated, without knowing whether the statistics changed, and the docs note that a timestamp column whose maximum keeps growing will probably need more frequent statistics updates than one whose distribution changes slowly. How you'd detect a flip: a single queryid's mean time jumps in pg_stat_statements while its call count stays flat; auto_explain shows a new node type at the bottom of the plan; and the jump lines up with an autoanalyze or a bulk load rather than a deploy.

Many enable_* settings only discourage a node type rather than forbid it, and PostgreSQL 18's EXPLAIN marks a disabled node that was used anyway with Disabled: true. Use them in a session to compare plans, as Part 4 did, never as a server-wide fix.

A plan flip is healthy when the real row count crossed the crossover, and an incident when the estimate or the constants moved instead; the cure for the second is better statistics.

In the toy model, the crossover is under one row in a hundred. A merchant grows from a tenth of a percent of the table to three percent. Predict the plan, and whether the change is a bug.

The index scan's cost grows with every matching row while the sequential scan stays flat, so past the crossover the planner should switch to a bitmap or sequential scan. That flip is correct if the estimate matches reality. Check estimated against actual rows before calling it a regression; if they agree, the fix is a better index (Part 4) or accepting the scan, not forcing the old plan.

Correlated columns: the hundredfold underestimate

Last part: flips caused by stale or unlucky statistics. Still unsolved: estimates that are wrong even with perfectly fresh statistics.

An endpoint filters payments by city and state. The planner expects 255 rows, gets 5,000, and drives a nested loop that runs its inner scan 5,000 times.

A city implies its state. The planner doesn't know that. It multiplies the city's selectivity by the state's, as if every city were equally likely in every state, and the product is far too small.

In the docs' example, two columns that always hold the same value, with 100 distinct values each, are estimated at 1 row for a = 1 AND b = 1 when 100 rows match, and a dependencies statistic on the pair brings the estimate to 100. With a dependency of degree f, the planner combines the two selectivities as f times the smaller one plus (1 − f) times their product. The model's dependent_and_sel implements that, and its tests reproduce the docs' numbers.

The damage multiplies upward. The low estimate sits on the outer side of a join, so the nested loop looks cheap. At 5,000 real rows the inner index scan runs 5,000 times, which is what plan_lint flagged in the EXPLAIN part.

GitLab's review of two October 2025 incidents describes a query joining 16 tables whose nested loop joins repeatedly read the same buffer pages, using seconds of CPU per query while one user's automated pipeline sent about 4,000 requests a minute. GitLab's listed fixes include optimizing the query to reduce join complexity and caching member role data.

Detection: estimated rows far below actual on a scan with two or more conditions on related columns. Fix: CREATE STATISTICS (dependencies, mcv) on the pair, ANALYZE, and confirm the estimate moved. Use mcv when conditions are ranges or when impossible pairs appear in queries.

Conditions on related columns get multiplied as if independent, which can underestimate by orders of magnitude; extended statistics are the fix, and the damage shows up in the join above.

Columns a and b move together. The slow query uses a <= 49 AND b > 49, which matches no rows, yet the planner expects many. Which extended statistics kind fixes it?

  1. dependencies
  2. mcv, because it stores real value combinations and handles ranges
  3. ndistinct

A multivariate MCV list stores actual combinations, so it can see that no pair satisfies both ranges.

The sixth execution: when a cached plan goes wrong

Last part: estimates wrong from the start. Still unsolved: fast in psql, slow from the app.

An endpoint turns slow for one huge merchant soon after each deploy. The same query in psql is fast.

The app's driver prepares the statement and reuses it. A prepared statement runs with either a custom plan, made for each execution using that call's parameter values, or a generic plan that is the same for every execution. Prepared statements last only for the current database session.

For a prepared statement with parameters and plan_cache_mode set to auto, the default, the first five executions use custom plans, then a generic plan is created and used whenever its estimated cost is not much higher than the average custom-plan cost. Each custom plan's cost includes a planning charge of 1000 × cpu_operator_cost × (number of relations + 1), which the generic plan doesn't pay, and the average is updated only when a custom plan is made. So once the generic plan wins, the average stops moving. When DDL or a statistics change forces a re-plan, the recorded generic and custom costs are kept rather than reset. So even after an ANALYZE, the old average decides.

The generic plan is priced for a typical value, so it can look cheap yet be disastrous for the value that owns most rows. psql with literals always gets a custom plan.

EXPLAIN EXECUTE shows the plan a prepared statement uses: a generic plan contains parameter symbols such as $1, while a custom plan has the values substituted. The statement is re-planned when objects it uses change definition or their planner statistics are updated. plan_cache_mode also accepts force_custom_plan and force_generic_plan, and it is checked when a cached plan is executed, not when it is prepared.

PL/pgSQL functions generate prepared statements implicitly. The PostgreSQL JDBC driver switches to a named server-side prepared statement once a statement has run prepareThreshold times, 5 by default. Transaction poolers matter because a prepared statement lives in one session. PgBouncer has tracked protocol-level named prepared statements in transaction pooling mode since version 1.21.0, when max_prepared_statements is non-zero.

PREPARE q(int) AS
  SELECT count(*), sum(amount) FROM orders WHERE merchant_id = $1;
-- run it six times, then:
EXPLAIN EXECUTE q(1);   -- "merchant_id = $1" means generic

BEGIN;
SET LOCAL plan_cache_mode = force_custom_plan;
EXECUTE q(1);           -- planned for merchant 1
COMMIT;

"A query is fast in psql and slow from the service. Same SQL, same database." A strong answer suspects the generic-plan switch, confirms it with EXPLAIN EXECUTE showing $1, and picks a fix by trade-off: force_custom_plan for that path (planning on every call), separate queries for the hot tenant, or statistics that make the generic estimate honest.

After five custom plans, a prepared statement can switch to one generic plan priced for a typical value; skewed values make that plan wrong, and the average that decided it stops changing.

The first five calls of a prepared statement happen to be for small merchants. Each custom plan costs about 80. The generic plan's cost is 690. What happens on later calls?

  1. Custom plans continue, because 690 is far above the average custom cost
  2. The generic plan is always used from call six onward
  3. The statement fails over to force_generic_plan

Under auto, the generic plan wins only if its estimated cost is not much higher than the average custom-plan cost. 690 against roughly 80 plus the planning charge keeps custom plans. The trap appears when one expensive custom plan inflates that average.

Explain why a prepared query can be fast in psql and slow in the app, and how you'd prove it.

The app's driver prepares the statement and executes it repeatedly. PostgreSQL plans the first five executions with their actual values, then builds one generic plan without values and uses it if its estimated cost is no worse than the average of the custom ones. That generic plan is sized for a typical value, so for a skewed value, like a merchant owning most rows, it can be badly wrong. psql runs the query with literals, so it always gets a custom plan. EXPLAIN EXECUTE showing $1 in the plan proves it; forcing custom plans for that code path, or fixing statistics, removes it.

work_mem at ten times the connections

Last part: one cached plan for every value. Still unsolved: the memory settings that fix one query and endanger the whole server.

A report spills its hash join to disk. Someone raises work_mem sixty-four times over, for the whole server. During the next traffic spike the database is killed for running out of memory.

A complex query may run several sorts and hashes at once, and several sessions may do so concurrently, so total memory use can be many times work_mem. Parallel workers multiply it again. The model below shows how fast that grows.

Two hundred connections, one sort and two hashes each, two workers per query: the worst case is hundreds of gigabytes from one innocent-looking setting. Real queries rarely hit every limit at once, which is why the failure waits for a traffic spike.

The safer levers. The docs suggest raising hash_mem_multiplier where spilling is a regular occurrence, especially when raising work_mem alone causes memory pressure, which typically shows up as intermittent out-of-memory errors. Raise work_mem per role or per transaction for the reports that need it, and cap concurrent queries with a connection pooler.

Spills also hide in bitmap scans. A bitmap index scan builds its bitmap within work_mem. When the bitmap needs more memory, some pages become lossy: only the fact that the page must be visited is kept, and every row on it is rechecked. EXPLAIN ANALYZE shows this on a Heap Blocks line, which lists exact and lossy page counts when each is non-zero. Rows that a lossy check returned and the recheck rejected are counted on a Rows Removed by Index Recheck line.

How you'd detect each one before users do. log_temp_files logs each temporary file's name and size when it is deleted, where 0 logs all of them and -1, the default, logs none. In pg_stat_statements, a rising temp_blks_written on one statement points at a spill. In plans, look for external merge sorts, hash batches above one and lossy heap blocks.

work_mem is multiplied by operations, workers and connections; raise it narrowly for the queries that spill, and watch temp files to find them.

work_mem is 64MB with the stock hash_mem_multiplier. A query runs one sort and one hash join with two parallel workers. Predict its worst-case memory, then multiply by 50 concurrent copies.

Per process: 64 for the sort plus 64 × 2 for the hash = 192 MB. Three processes (leader plus two workers) = 576 MB. Fifty copies ≈ 28.8 GB. Whether that is safe depends on the server's RAM and everything else running, which is why a global raise is the wrong first move.

Choosing among scans and joins, and a playbook for "it got slow"

Last part: memory multiplies. Now the whole page as decisions you can defend.

In a design review you'll be asked why a plan is right, not only how to read it. You need a short rule per node type and a fixed order for investigating a slow query.

Plan nodeWins whenBreaks when
Seq ScanA large share of the table matches, or the table is tinyFew rows match because the right index is missing or unusable
Index ScanVery few rows match, or ORDER BY ... LIMIT follows the index orderThe estimate is too low and thousands of random fetches follow
Bitmap Heap ScanA middle share of rows, or several indexes combined with AND or ORThe bitmap outgrows work_mem and goes lossy; in a bitmap scan, table rows are visited in physical order, so the index ordering is lost and an ORDER BY needs a separate sort
Index Only ScanEvery needed column is in the index and pages are all-visibleHeap Fetches climb on recently changed pages (Part 4)
Nested LoopFew outer rows and an index on the inner join keyThe outer estimate is far too low
Hash JoinLarge, unsorted inputs joined on equalityThe hashed side outgrows hash memory and runs in batches
Merge JoinBoth inputs already sorted on the key, or needed sorted anywaySorting large unsorted inputs first costs more than hashing

The playbook, in order. Each step is cheaper and safer than the next.

  1. Find it: pg_stat_statements by total time, then mean time and temp blocks.
  2. Get the real plan: auto_explain, or EXPLAIN (ANALYZE, BUFFERS, SETTINGS) with real parameter values; EXPLAIN EXECUTE if the app prepares statements.
  3. Find the lowest node where estimate and actual differ by ten times or more, after multiplying by loops.
  4. Fix the estimate: ANALYZE, a higher target, extended statistics. Then spills: work_mem for that query. Then indexes (Part 4).
  5. Only then cost constants, measured across the whole workload. Never a global enable_* switch.

The draft PostgreSQL 19 release notes add pg_plan_advice, a module to stabilize and control planner decisions, and pg_stash_advice, which applies advice per query ID. The pg_plan_advice docs warn that overriding the planner can backfire when the data distribution changes, because advice can stop the planner from adapting. The draft PostgreSQL 19 notes also add an IO option to EXPLAIN ANALYZE for asynchronous I/O activity, Memoize cache and lookup estimates in EXPLAIN, and conversion of NOT IN to anti-joins when NULLs are not present. PostgreSQL 18 enables JIT compilation by default, where the server is built with it, above a plan cost of 100000, and the draft PostgreSQL 19 notes turn JIT off by default because that cost-based activation proved unreliable. This page follows PostgreSQL 18.

Fleet-wide plan stability, such as a regression gate that compares plans of the top statements before every release, or org-wide rules for cost settings across hundreds of databases, is staff-level work. This page stops at diagnosing and defending plans for one service.

Read plans bottom-up, fix the first wrong estimate before anything else, and change memory, indexes and cost constants only in that order.

A plan's lowest Seq Scan estimates 200 rows and returns 180,000; above it a Hash node shows Batches: 32. What do you fix first?

  1. Raise work_mem so the hash fits
  2. Lower random_page_cost
  3. The scan's row estimate, with ANALYZE or extended statistics

The playbook fixes the lowest bad estimate first. With a correct estimate the planner may pick a different join or size the hash properly, and the spill may disappear.

Interview drill: query plans at the senior bar

Last part: a table and a playbook. Still unsolved: defending a diagnosis under questioning, with the trade-offs said out loud.

Three prompts that come up in product-company rounds. For each, commit to an answer before opening the reference.

For every prompt, say these four things: what evidence you'd collect, the first wrong number you'd look for, the fix, and what that fix costs.

1. Slow merchant dashboard. SELECT ... FROM payments p JOIN refunds r ON r.payment_id = p.id WHERE p.merchant_id = $1 AND p.created_at > now() - interval '30 days'. The plan: Nested Loop, outer Bitmap Heap Scan on payments estimated 40 rows, actual 120,000; inner Index Scan on refunds with loops=120000. Fast for most merchants, slow for the top ten. Diagnose and fix.

The lowest wrong number is the outer estimate: 40 against 120,000. It drove a nested loop with 120,000 inner lookups. Because only big merchants are slow, suspect skew plus a prepared statement: run EXPLAIN EXECUTE and look for $1. If it's generic, the plan is priced for an average merchant. Fixes, with costs: force_custom_plan for this endpoint (planning on every call, small for a two-table join); together with that, a higher statistics target on merchant_id so the top merchants are in the most-common-values list (slightly slower ANALYZE and planning); on its own it doesn't help a generic plan, which ignores the value; keep the index on (merchant_id, created_at) from Part 4. With a right estimate, the planner can choose a hash join for the big merchants and keep the nested loop for the small ones.

2. Fast in staging, slow in production. The same query takes 40 ms in staging and 6 s in production. Staging has a copy of the schema with a tenth of the data, restored last month. What do you compare, and in what order?

Get both real plans with EXPLAIN (ANALYZE, BUFFERS, SETTINGS), production on a replica. Compare node by node: where do the plans first differ, and where do estimate and actual first diverge in production? Then the likely causes: ten times the data crossed a crossover, so a different plan is expected; staging statistics describe old data; different settings (work_mem, random_page_cost, parallel workers) appear in SETTINGS; production buffers show reads where staging shows hits because its data fits in cache. The trade-off to state: you can't make staging predictive without production-like volume and statistics, so the durable fix is checking plans of top statements against production-sized data before release.

3. A monthly finance report scans a 2 TB events table, partitioned by month, grouping by merchant and currency. It runs for hours and fills the temp disk. Design the fix.

First make sure partition pruning keeps it to one month: the WHERE clause must constrain the partition key directly, and EXPLAIN should show only that month's partitions. Then the aggregation: check estimated against actual group counts; merchant and currency are correlated, so ndistinct statistics on the pair can fix the group estimate. Run it with SET LOCAL work_mem sized for this one transaction so the hash aggregate stays in memory, and let parallel workers split the scan, remembering each gets its own work_mem. ANALYZE the parent table by hand, since autovacuum doesn't. The trade-off: more memory for one session, accepted because it runs once a month, at a quiet hour, from a role that ordinary traffic doesn't use. If it still spills, pre-aggregate daily into a summary table.

"Would you pin this plan with a hint?" A strong answer prefers better statistics, because a pinned plan stays fixed while the data keeps changing. It mentions the session-level enable_* switches only for diagnosis, and the draft PostgreSQL 19 plan-advice module as a future, explicitly risky option for stabilizing a known-good plan.

A senior plan diagnosis names the evidence, the first wrong estimate, the fix, and what the fix costs in planning time, memory or flexibility.
