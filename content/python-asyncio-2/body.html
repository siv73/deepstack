Starting tasks is easy; stopping them is the job

Your async order service passes every test. In production, each deploy leaves about 1 in 500 orders half-written, memory climbs from 300 MB to 4 GB during a partner outage, and logs sometimes carry another customer's request id.

cancel() is a request, not a kill

Last part: three edges. Still unsolved: what exactly happens when you stop a task?

An engineer calls task.cancel() on a stuck export job and logs "export stopped". The job writes 12 more rows before it actually stops.

  1. Task.cancel() arranges for a CancelledError to be thrown into the coroutine on the next cycle of the event loop. Until then the task keeps running.
  2. The error appears at the task's current await. Code between awaits always finishes.
  3. The coroutine can clean up, or even deny the request by suppressing the exception, so cancel() does not guarantee the task will be cancelled.
  4. cancelled() returns True only if the coroutine let the CancelledError propagate.

cancel() returns False if the task is already done or cancelled, and True otherwise. Since Python 3.11, the msg passed to cancel() is propagated from the cancelled task to its awaiter. Pass a reason, task.cancel("deploy"), so the log says why.

stubborn returns "finished anyway" and cancelled() is False. The docs call completely suppressing cancellation uncommon and actively discouraged.

cancel() only asks; the task stops at its next await, after its cleanup, and only if it lets the error through.

You call t = asyncio.create_task(polite(log)) and immediately t.cancel(), before any await. Does "rolled back" get logged?

No. The task had not started, so the CancelledError is thrown in before the first line of the body runs. There is no try active yet, so no cleanup runs. The tests confirm the log stays empty.

How a request id follows a request across tasks

Last part: how stopping works. Still unsolved: the "wrong request id in logs" symptom.

A team stores the current request id in a module-level global for logging. Under load, 2% of log lines show another request's id, because 200 requests share one thread and switch at every await.

A global is shared by every task on the loop. What you want is a value that belongs to "this request", wherever its code runs. That is a context variable.

  1. Context variables are natively supported in asyncio with no extra configuration.
  2. If no context is given, a task copies the current context and runs its coroutine in the copy.
  3. So a child task sees the parent's value, but a change in the child stays in the child.
  4. asyncio.to_thread() propagates the current contextvars context to the worker thread.

Two requests run at the same time in the tests. Every line is tagged with its own id, in the child task, after an await, and in the thread. The child's set() does not reach the parent.

Set the value once at the edge, in middleware, and read it in your log formatter. The copy is taken when the task is created, so set the value before you start child tasks.

Per-request data goes in a ContextVar: each task gets a copy at creation, so values follow the request and never leak between requests.

A handler starts a background task, then calls request_id.set("req-9"). What does the background task see?

  1. "req-9", because it shares the parent's context
  2. It raises LookupError because tasks don't support contextvars
  3. Whatever the value was when the task was created

The task copied the context at creation. Set the value first, then create the task.

Keeping a commit alive when the client hangs up

Last part: per-request data. Still unsolved: some work must finish even if the request is cancelled.

A client closes the connection 20 ms into a 50 ms "create order" call. The server framework cancels the handler. The payment row is written but the order row is not: 1 in 500 orders is half-written.

  1. Put the must-finish step in its own task, and await it through asyncio.shield().
  2. From the shielded task's point of view the cancellation did not happen, but the caller's await still raises CancelledError.
  3. The docs say to save a reference to tasks passed to shield(), since the loop keeps only weak references.

The tests cancel create_order after 10 ms. The handler raises CancelledError, as it should, and 40 ms later the order is in the database.

shield() protects against the caller being cancelled, not against the process ending. When asyncio.run() finishes, it cancels every task that is still pending, then finalizes async generators and shuts down the default executor. A test shows a shielded commit that is still running when main() returns is cancelled and never written. At shutdown, wait for _pending before returning.

Better still, make the operation safe to interrupt: one transaction for both rows, so a cancel means "nothing written" instead of "half written". Use shield for the short commit step, not for a long job.

"A client disconnect leaves data half-written. How do you fix it?" A strong answer first makes the write atomic (one transaction, idempotency key), then protects only the commit with a shielded, referenced task, and makes shutdown wait for those tasks. It notes that shield changes nothing for a process kill, so anything that must happen goes through a durable outbox.

shield() lets a referenced task finish when its caller is cancelled, but not when the process exits; atomic writes are the real fix.

A shielded commit is running when the handler is cancelled. What does the handler's await asyncio.shield(task) do?

  1. Raises CancelledError right away, while the commit task keeps running
  2. Waits for the commit to finish, then returns normally
  3. Cancels the commit and raises CancelledError

The caller is cancelled as usual; only the inner task is protected.

Making producers slow down: bounded queues

Last part: protecting one step from cancellation. Still unsolved: the memory that grows during an outage.

A consumer reads 2,000 events per second from a stream and hands each to create_task. The enrichment API slows from 20 ms to 2 s. Tasks pile up: 4,000 new ones every second, each holding its event and buffers.

The fix is backpressure: when consumers fall behind, the producer waits. A queue with a size limit does it for you.

  1. With maxsize above 0, await put() waits when the queue is full until get() removes an item.
  2. A fixed number of worker tasks each loop over get(). That number is your concurrency cap.
  3. join() waits until task_done() has been called once for every item that was put.
  4. Queue.shutdown() was added in Python 3.13; after it, put() raises QueueShutDown and get() raises it once the queue is empty. Workers use that as their signal to exit.

The tests push 200 items through 4 workers with maxsize=10: every item is handled, at most 4 are in flight, and the queue never holds more than 10.

The producer pausing is the point. With a stream such as Kafka, the unread events stay in the broker, which is built to hold them, instead of in your process.

"Your consumer's memory grows when a downstream slows. What do you change?" A strong answer replaces unbounded task creation with a bounded queue and a fixed worker pool, sizes the pool from the downstream's limit, puts a timeout on each call, and lets the producer block so the backlog stays in the broker. It adds a metric for queue depth.

A bounded queue plus a fixed set of workers turns "more work than we can handle" into "the producer waits".

The enrichment API slows down. Put what happens in order.

  1. Each worker takes longer per item
  2. Items are removed from the queue more slowly than they arrive
  3. The queue reaches maxsize
  4. The producer's put() waits
  5. The producer reads from the stream more slowly; the backlog stays in the broker

Slowness flows backward: worker, then queue, then producer, then the broker.

Races on one thread: when you need a lock

Last part: bounded queues. Still unsolved: can two tasks on one thread corrupt shared state?

A flash sale has 1 unit left. 10 requests arrive together. Each checks units > 0, writes an audit row, then decrements. You sell 10 units and stock ends at −9.

"One thread, so no races" is wrong. A task can only be interrupted at an await, but a check and an act with an await between them are two steps. Every other task can run in that gap.

  1. Code with no await between the check and the act is safe: nothing else runs in between.
  2. With an await in between, the check may be stale when you act.
  3. An asyncio.Lock gives exclusive access to a shared resource, and the preferred way to use it is async with.
  4. Acquiring an asyncio.Lock is fair: the first coroutine that started waiting proceeds first.

The tests run 10 reservations at once: reserve_racy gives 10 successes and −9 units; reserve_safe gives exactly 1 and 0 units.

Scope matters. An asyncio lock protects state inside one process. Two pods selling the same stock need the database to decide, for example UPDATE ... SET units = units - 1 WHERE units > 0 and checking the row count. asyncio synchronization primitives are not thread-safe; use the threading module to synchronize OS threads.

Any await between a check and an act is a race window; hold an asyncio.Lock across it, or let the database do the check.

Which function needs a lock when 100 tasks call it at once?

  1. A function that does counter += 1 with no await
  2. A function that reads a cached token, awaits a refresh call if it's expired, then stores the new token
  3. A function that sets results[task_id] = value

Many tasks can see the expired token, all await a refresh, and all overwrite each other. A lock around check-refresh-store makes one refresh.

Shutting down on SIGTERM without losing work

Last part: races between tasks. Still unsolved: the half-finished work at every deploy.

Every deploy, Kubernetes stops your worker pod. Two jobs are mid-flight. The process dies instantly, both jobs are redelivered, and one charge happens twice.

On Pod termination, Kubernetes normally sends SIGTERM to the main process in each container, then SIGKILL to anything still running when the grace period ends. The default grace period is 30 seconds. By default, Python does nothing special with SIGTERM. Python installs only a few default signal handlers: SIGPIPE is ignored and SIGINT becomes KeyboardInterrupt, unless the parent process changed it.

  1. Register a handler. loop.add_signal_handler() is Unix-only; it runs the callback inside the event loop, so unlike signal.signal() handlers it may interact with the loop, and it must be called in the main thread.
  2. The handler only sets an Event. Main code waits on it.
  3. Stop taking new work: queue.shutdown(immediate=True). With immediate=True, shutdown() drains the queue at once and blocked get() callers raise QueueShutDown.
  4. In-flight jobs finish; workers exit; the TaskGroup closes; the process exits 0 well inside 30 s.

The tests run this as a real process and send it SIGTERM. With the handler: jobs 0 and 1 finish, job 2 never starts, exit code 0. Without it: exit code −15, nothing finished, no finally ran.

Dropped jobs must go back to the broker: don't acknowledge a message until its job is done, so the next pod picks it up. Ctrl-C is different: Since Python 3.11, asyncio.Runner, which asyncio.run() uses, handles Ctrl-C (SIGINT) in the main thread by cancelling the main task, so try/finally cleanup runs, then raises KeyboardInterrupt.

Handle SIGTERM with add_signal_handler, stop intake, let in-flight work finish, and acknowledge messages only after the work is done.

Walk through how you'd make an async queue worker safe to deploy 20 times a day.

Workers pull from a bounded queue, so memory stays flat and the backlog stays in the broker. I register a SIGTERM handler with add_signal_handler that sets an event; on it I shut the queue down so no new work starts, let in-flight jobs finish, and exit before the 30-second kill. Messages are acknowledged only after their job completes, so dropped work is redelivered. Writes are atomic or idempotent, so a redelivery can't double-charge, and any shared state touched across an await is behind a lock.

When a thread needs to talk to the loop

Last part: clean shutdown. Still unsolved: sync libraries that call you back on their own threads.

A sync message-queue client delivers messages on its own thread. Its callback calls queue.put_nowait(msg) on an asyncio queue. It works in tests, then once a day a worker never wakes up for a message sitting in the queue.

Almost all asyncio objects are not thread safe. asyncio queues are not thread-safe. Touching them from another thread corrupts their internal state in ways that only show under load. The fix is to hand the work to the loop's own thread.

  1. Fire and forget: call_soon_threadsafe() must be used to schedule callbacks from another thread, because call_soon() is not thread-safe.
  2. Run a coroutine and wait for its result: run_coroutine_threadsafe() submits a coroutine to a given loop from another OS thread and returns a concurrent.futures.Future to wait on.
  3. Pass the loop to the thread up front: get it with asyncio.get_running_loop() while you are on the loop.

The tests confirm every handler ran on the loop's thread, in order, and that a message sent with call_soon_threadsafe reaches a waiting get().

Waiting on fut.result(timeout=5) in the consumer thread is deliberate: the sync client doesn't fetch the next message until the async handler finishes. That is backpressure across the thread boundary.

At shutdown the loop may close while the thread is still delivering. call_soon_threadsafe() raises RuntimeError if the loop has been closed, which can happen on a secondary thread during shutdown. Stop the client's thread first, then let the loop close.

Never touch asyncio objects from another thread; hand work over with call_soon_threadsafe or run_coroutine_threadsafe.

A sync SDK's callback thread must run await save(event) and know if it failed. What should the callback do?

  1. Start a new loop in the thread with asyncio.run()
  2. Schedule save with the loop's call_soon_threadsafe()
  3. Submit it with run_coroutine_threadsafe() and wait on the returned Future with a timeout

It runs the coroutine on the main loop and gives the thread a Future whose result raises if save() failed.

The worker loop that hangs forever

Last part: crossing threads. Still unsolved: what breaks first when a queue-based service meets bad data or 10× load.

A nightly job puts 50,000 rows in a queue, starts 8 workers, and awaits queue.join(). Row 3 has a bad date. The job never finishes and never errors. It is killed at 6 a.m. by the scheduler.

  1. The worker raises on the bad row. task_done() is skipped and the worker task ends.
  2. The unfinished count can never reach zero, so join() waits forever. The test proves it with a timeout.
  3. Nobody awaits the worker, so its error surfaces only as a late "Task exception was never retrieved" log line; the test run shows exactly that.
  4. If all workers die this way, the queue fills and producers block too.

The fix is pipeline.py from part 5: task_done() in a finally, workers owned by a TaskGroup so one failure stops the job with an ExceptionGroup, and shutdown() to end workers instead of cancelling them. A test shows it failing fast instead of hanging. Decide per job whether one bad row should stop the batch or go to a dead-letter list and continue.

At 10× load the first thing to break is an unbounded queue. An asyncio.Queue with maxsize less than or equal to zero has no size limit. The default is 0, so put() never waits and the backlog lives in memory; a test fills one with 100,000 items and full() is still False.

Detect it: export qsize() as a gauge and alert on sustained growth; put a timeout on join(); alert on worker count dropping.

Queue methods have no timeout parameter; the docs point to asyncio.wait_for(). Wrap join() or put() in asyncio.timeout() so a stuck pipeline turns into an error you see, not a job that runs until someone kills it.

task_done() goes in finally, workers belong to a TaskGroup, queues have a maxsize, and join() has a deadline.

3 workers, 30 items, and each worker's loop has task_done() after the handler, not in a finally. Items 4, 9 and 17 raise. What happens to await queue.join()?

It never returns. Each failure kills one worker and skips one task_done(). After three failures no workers are left, the remaining items sit in the queue, and the unfinished count stays above zero. Nothing raises in the caller.

Refusing a cancel: the bookkeeping you break

Last part: queues that hang. Still unsolved: code that catches CancelledError "just this once".

A request handler wraps a slow cache call in except asyncio.CancelledError, logs "cache cancelled, continuing", and carries on. Weeks later, requests where an unrelated TaskGroup fails end with CancelledError instead of the real error, and the 500s show no cause.

Timeouts and TaskGroup need to know whether a cancel was theirs or came from outside. They keep a count on the task.

  1. cancelling() returns the number of cancel() calls minus the number of uncancel() calls.
  2. asyncio.timeout() and TaskGroup use uncancel() so that a cancellation meant for their block does not spill into the code after it.
  3. If you swallow a cancel, the count stays at 1. Later, when a child of some TaskGroup fails, the group sees that count, concludes an outside cancel is still pending, and cancels the task again.
  4. The docs say uncancel() is used by asyncio's internals and isn't expected in end-user code, but code that suppresses CancelledError needs to call it.

Without uncancel(), the task ends with CancelledError even though every error was handled and "done" was about to be returned. With it, the task returns "done". TaskGroup's handling of simultaneous internal and external cancellations changed in Python 3.13. On Python 3.12 this test does not fail the same way, so the test only runs on 3.13 and later. Version-dependent behaviour is another reason not to rely on it.

The rule: don't catch CancelledError to continue. To give up on a slow call and carry on, put the call in its own asyncio.timeout() block and catch TimeoutError outside it. The timeout does the uncancel bookkeeping for you. If you truly must suppress a cancel, call uncancel() in the same except block.

There is no tg.cancel(). The docs show how to stop a TaskGroup early: add a task that raises a custom exception, and catch it with except*.

"When is it OK to catch CancelledError?" A strong answer: to clean up and re-raise, always. To suppress, almost never; use a timeout block and catch TimeoutError instead. If you must suppress, call uncancel() so timeouts and TaskGroups further up still behave. It mentions that the exact behaviour changed across 3.11 to 3.13.

Catching CancelledError to continue leaves a stale cancel count that breaks later TaskGroups; use a timeout block, or uncancel() if you must.

You want "try the cache for 50 ms, else fall back to the DB". Which is correct?

  1. Start a task for the cache call, cancel it after 50 ms, and catch CancelledError in the handler to continue
  2. try: async with asyncio.timeout(0.05): v = await cache.get(k) except TimeoutError: v = await db.get(k)
  3. Wrap the cache call in except BaseException and fall back

asyncio.timeout cancels, then uncancels and converts to TimeoutError, so the rest of the handler is unaffected.

Async generators that clean up too late

Last part: stale cancel counts. Still unsolved: cleanup that is written correctly but runs at the wrong time.

A service streams rows from Postgres with an async generator and stops after the first match. Under load, the connection pool runs dry: cursors stay open well after each request returns.

  1. Leaving an async for early leaves the generator paused at its yield. Its finally has not run.
  2. If an async generator exits early, its async cleanup may run later, after tasks it depends on have finished, or during loop shutdown via the garbage-collection hook.
  3. The docs recommend closing async generators explicitly with aclose() or contextlib.aclosing().

In the tests, right after first_big_leaky returns, the log still says only "cursor opened"; "cursor closed" appears later, from another task. With aclosing(), it is closed before the function returns.

Why it hurts: the late cleanup runs outside your request, after your connection may be back in the pool, and possibly during shutdown when the database client is already closed. The error, if any, lands in a log line far from the cause.

Detect it: pool "connections in use" not returning to baseline between requests; "unhandled exception during asyncio.run() shutdown" in logs.

Any async generator you might leave early goes inside contextlib.aclosing(), so its cleanup runs now, in your task.

An async generator yields rows and closes its cursor in finally. A caller does async for r in rows(): if match(r): break. When does the cursor close?

  1. Later, whenever the paused generator is finalized, possibly in another task or at shutdown
  2. Immediately at the break
  3. Never

Without aclosing() or aclose(), cleanup is deferred to finalization.

Finding a stuck task in production, and testing without flakes

Last part: late cleanup. Still unsolved: how to see these failures when they happen.

A worker pod is "up" but has processed nothing for 20 minutes. CPU is 0%. Restarting it fixes the symptom and destroys the evidence.

Look inside the live process. Python 3.14 adds python -m asyncio ps PID and python -m asyncio pstree PID to inspect the tasks of a running process without modifying or restarting it. pstree shows each task's coroutine stack nested under the task awaiting it. The commands are only available on supported platforms and may require permission to inspect another process. In a container that can mean allowing ptrace for a debug session. A worker stuck in Queue.join, or a TaskGroup waiting on one child blocked in a lock, shows up directly. Name your tasks (create_task(..., name="worker-3")) so the output is readable.

Watch for leaks. asyncio.all_tasks() returns the set of not-yet-finished tasks run by the loop. Export its size as a gauge. A count that climbs between requests means tasks are being started and never finished.

Test with a fresh loop per test. unittest.IsolatedAsyncioTestCase (Python 3.8+) accepts coroutines as test methods and has asyncSetUp() and asyncTearDown(). It needs no plugin and runs under pytest.

The second test asserts no tasks are left running: a cheap guard against the lost-task bugs from Part 1. For timing-sensitive code, test with short real sleeps and generous bounds, as this page's tests do, or inject the slow dependency so the test controls it.

Use python -m asyncio pstree on the live process before restarting it, export the task count, and assert no tasks leak in tests.

A pod is idle but stuck. What gives you the most evidence before a restart?

  1. Restart it with PYTHONASYNCIODEBUG=1 and wait
  2. Take a CPU profile
  3. Run python -m asyncio pstree PID against the running process

It shows every task and the exact await each is stuck at, without touching the process.
