The system so far, and what this page adds to it

Part 1 ended with a gateway that answers in 250 ms with seller-b at 1,199, on one thread. But its five sellers were timers. Not one byte crossed a network. A real seller is a server you reach over a TCP connection, and Part 1's toy loop has no way to wait on one.

Introduction

This is Part 2 of a ten-part series. Every part works on the same system: a price-comparison gateway that asks five sellers for a price and must answer within a budget of 250 ms. Part 1 is the prerequisite for this page. This part recaps it in one screen; if any line below is unfamiliar, read that part of Part 1 first.

What Part 1 built

  1. The gateway asks five sellers: seller-a (80 ms, 1,249), seller-b (120 ms, 1,199), seller-c (150 ms, 1,229), seller-d (200 ms, 1,215) and seller-e (900 ms, 1,149).
  2. Asking them one after another took 1,450 ms (the sum). Giving each call its own thread brought it to about 900 ms, at the cost of one waiting thread per call.
  3. A generator pauses at yield and is resumed with send(). A coroutine (async def) pauses the same way: await passes a yield from the bottom of the await chain up to whoever called send().
  4. The toy loop resumed coroutines from a ready queue, parked sleeping ones in a timer heap, and jumped a virtual clock to the next wake-up. On one thread, the five waits overlapped: 900 ms.
  5. Stopping at the 250 ms budget gave "cheapest: seller-b at 1,199; missed: seller-e".

What was still broken

  • The toy loop fakes the network with timers. It cannot wait on a socket.
  • An exception in one task escapes the loop and fails the whole request.
  • A blocking call stalls every task.
  • Stopping unfinished work is done by hand.

This page fixes the first two. It makes the sellers real servers on your own machine, shows how one thread can wait on many sockets at once, and then opens up asyncio's real event loop to show that it is the same machine as the toy loop, with three pieces added: a selector, Futures and Tasks.

Introduction

Part 1 overlapped five waits by making every wait a timer. A real seller call is not a timer. The gateway sends a request over a network connection and the answer comes back whenever the seller sends it. This part shows what happens when one thread makes such a call the ordinary way, and why that is the problem the rest of the page solves.

Comparison

Think of phoning a shop and being put on hold. While the hold music plays, you hold the phone to your ear. You are not working, but you cannot make another call either. Five shops, one after another, means five holds in a row.

  • You = the thread.
  • The phone line = the socket.
  • Being on hold = the thread blocked inside recv().

The comparison stops working here: on hold you could still read a book. A blocked thread can do nothing at all until the call returns.

Definitions

  1. A socket is one end of a network connection, as seen by a program. The program writes bytes into it with send() and reads bytes out with recv().

  2. A file descriptor (fd) is a small number the operating system gives a process for every open file, socket or pipe. A Python socket's fileno() method returns its file descriptor, a small integer.

  3. A socket in blocking mode makes the calling thread wait inside an operation until the operation can finish. Python's socket docs say sockets are created in blocking mode by default, unless a default timeout was set with setdefaulttimeout(). In blocking mode, operations block until they complete or the system returns an error, such as a connection timeout.

Working

  1. The thread opens a connection to seller-a and sends one line: the item code.
  2. It calls recv(). No answer has arrived yet, so the operating system puts the thread to sleep inside the call.
  3. 80 ms later seller-a's answer arrives. The operating system wakes the thread and recv() returns the bytes.
  4. Only now can the thread connect to seller-b. Steps 1 to 3 repeat for each seller.

Why each step is needed

  • Step 2 is the whole problem: the thread cannot ask the operating system to wait on several sockets at once in a plain recv() call. It waits on exactly one.
  • Step 4 follows from step 2: the next seller cannot even be asked until the previous one has answered, so the waits add up.

A blocking recv() puts the thread to sleep until that one socket has data. While it sleeps, the thread cannot connect to the next seller, so the five waits happen one after another and add up to about 1,450 ms plus connection set-up. The CPU is idle almost the whole time, so a faster CPU changes nothing. What must change is how the thread waits: it needs to wait on all five sockets at once.

A socket that never makes you wait: non-blocking mode and "would block"

Last part: a blocking socket parks its thread inside one call. Still unsolved: how can one thread keep five calls in flight if any call may park it?

We want to send the item code to all five sellers in the first millisecond and then collect the answers as they arrive: 80, 120, 150, 200 and 900 ms. That only works if no call ever puts our one thread to sleep.

Introduction

The operating system offers a second mode for every socket. In this mode an operation that cannot finish now does not wait. It returns at once with an error that means "try later". This part shows that error and the naive way of using it, which works but wastes a whole CPU core.

Comparison

Instead of holding the line, you ask the shop to call you back, and hang up. If you have nothing else to do, the temptation is to keep ringing the shop: "Is it ready yet?" every second.

  • Hanging up at once = a non-blocking call that returns "would block".
  • Ringing again and again = calling recv() in a loop: busy waiting.

Where it stops working: a shop would get annoyed. The operating system answers every one of your thousands of calls, and the cost lands on your own CPU.

Definitions

  1. A socket in non-blocking mode never makes the thread wait. sock.setblocking(False) puts a socket in non-blocking mode; the docs say it is equivalent to sock.settimeout(0.0). In non-blocking mode, an operation that cannot be completed immediately fails, and functions from the select module can be used to know when the socket is ready for reading or writing.

  2. "Would block" is the error a non-blocking operation returns when finishing it would mean waiting. Python raises BlockingIOError when an operation would block on an object set for non-blocking operation; it corresponds to the errno values EAGAIN, EALREADY, EWOULDBLOCK and EINPROGRESS.

  3. Busy waiting means checking something again and again in a loop instead of asking to be woken when it changes. Part 1 met the word for a sleeping task; here it is a socket.

Working

  1. setblocking(False) switches the socket to non-blocking mode.
  2. connect() starts the TCP handshake and returns at once with BlockingIOError, errno EINPROGRESS: "still connecting".
  3. Once connected, send() copies the line into the operating system's send buffer and returns.
  4. recv() finds no data yet and returns at once with BlockingIOError, errno EAGAIN: "no data, try again".
  5. The naive program now calls recv() again and again until the answer arrives.

Why each step is needed

  • Steps 2 and 4: an error instead of a wait is what keeps the thread free to start other calls.
  • Step 5 is the part we will throw away: it keeps the thread free, but it burns the CPU asking.

Program

Explanation of the program

Wrong belief: "BlockingIOError means the connection failed."

Why it is wrong: it means "not yet". EINPROGRESS says the connection is still being made; EAGAIN says no data has arrived yet. Real failures arrive as other errors, such as ConnectionRefusedError, and a closed connection shows up differently again: socket.recv() returns an empty bytes object when the other side has disconnected. Code that treats BlockingIOError as a failure drops healthy calls.

  • setblocking(False) means operations return at once instead of waiting.
  • "Would block" arrives as BlockingIOError: EINPROGRESS for connect, EAGAIN for recv on Linux.
  • Calling again and again (busy waiting) works but keeps a CPU core busy for the whole wait.

Non-blocking mode frees the thread from waiting, but only half solves the problem: something must say when to try again.

  2. No data has arrived yet; try again when the socket is ready to read

Asking the operating system which sockets are ready: selectors

Last part: non-blocking sockets never make the thread wait, but asking again and again keeps a core busy. Still unsolved: how does the thread learn exactly when a socket is worth asking?

Five sockets, five answers due at 80, 120, 150, 200 and 900 ms. We want the thread to sleep, using no CPU, and wake exactly five times: once per answer.

Introduction

The operating system already knows when data arrives on a socket: it is the one that receives the bytes. Every modern operating system lets a program hand over a list of sockets and sleep until at least one of them is ready. Python wraps these system calls in the selectors module. This is the piece Part 1's toy loop was missing.

Comparison

A restaurant pager. You order at five counters, and each gives you a pager. You sit down and do nothing until a pager buzzes; then you collect that one order and sit down again.

  • The pagers on your table = the sockets registered with the selector.
  • Sitting and waiting for a buzz = select().
  • The buzzing pager = a ready event, with a note saying which counter it is from (the data you attached).

Where it stops working: a pager buzzes once and is done. A selector keeps reporting a socket as ready to read for as long as unread data sits in it: every select() call names it again until the program reads the data. (This page's tests check that behaviour.)

Definitions

  1. A socket is ready for reading when a recv() would return at once instead of saying "would block", and ready for writing when a send() would. Readiness notification means the operating system telling a program which of its sockets are ready.

  2. A selector is an object from Python's selectors module that holds registered sockets and waits until some are ready. The selectors module provides high-level, efficient I/O multiplexing built on the select module's primitives, and the docs encourage using it unless you need precise control over the operating-system calls. selectors.DefaultSelector is an alias to the most efficient implementation available on the current platform.

  3. epoll is Linux's readiness notification facility; kqueue is the BSD and macOS one. Python's select module docs list epoll as available on Linux 2.5.44 and later, and kqueue as available on BSD and macOS. In CPython 3.14's selectors.py, DefaultSelector is KqueueSelector when kqueue is available, otherwise EpollSelector, then DevpollSelector, then PollSelector, and SelectSelector last. Hence DefaultSelector is epoll on Linux and kqueue on macOS.

Working

  1. Create a selector: sel = selectors.DefaultSelector().
  2. For each socket, sel.register(sock, EVENT_READ, data=name): "tell me when this can be read, and remind me it is this seller".
  3. Call sel.select(timeout). The thread sleeps inside it, using no CPU, until at least one socket is ready or the timeout passes.
  4. It returns a list of (key, events) pairs. key.fileobj is the socket and key.data is what you attached.
  5. Read from each ready socket. A recv() now returns data at once.
  6. When you are done with a socket, unregister it, then close it.

register() returns a SelectorKey, and raises KeyError if the file object is already registered. For select(timeout): a timeout above 0 is the longest wait in seconds, a timeout of 0 or less does not block and only reports what is ready now, and None waits until some registered file object is ready. The docs say a file object shall be unregistered before it is closed.

Why each step is needed

  • Step 2: the selector only watches what it was told to watch; data saves you a lookup from socket to seller.
  • Step 3: this single sleep replaces five blocked threads (Part 1) and five spinning loops (last part).
  • Step 5: the selector only says "ready"; reading the data is still your job.
  • Step 6: a closed socket left in the selector is a bug; the "When it breaks" rung shows what it does.

One turn of asyncio's loop: ready callbacks, timers and one select() call

Last part: a selector sleeps on many sockets and wakes when one is ready. Still unsolved: a loop also has timers and ready work. How does one thread fit sockets, timers and ready work into a single cycle?

At some moment the gateway has two callbacks ready to run, a timer due in 100 ms and five sockets waiting for answers. If it calls select() with no timeout, the timer fires late. If it runs the callbacks first and never looks at the sockets, answers sit unread. In what order should the loop do these three jobs?

Introduction

Part 1's toy loop had two structures: a ready queue and a timer heap. asyncio's loop keeps both and adds the selector from the last part. This part opens one loop iteration and follows it line by line in CPython's source. Work in asyncio's loop is a callback: a plain function the loop calls later. The next parts show that even a coroutine runs as a series of callbacks.

Comparison

A clerk at a post office counter works in rounds. Each round: look at the clock to see when the next scheduled pickup is due; check the mail slot, but only wait at it until that pickup if the queue at the counter is empty; move any parcels whose pickup time has come to the counter; then serve everyone standing at the counter right now. People who join the queue during the round wait for the next round.

  • The counter queue = the ready queue (_ready).
  • The pickup schedule = the timer heap (_scheduled).
  • Waiting at the mail slot = select(timeout).

Where it stops working: a clerk might serve a late arrival in the same round. asyncio deliberately does not, so that waiting sockets are checked between rounds.

Definition

In CPython 3.14, one iteration is the method BaseEventLoop._run_once(); its own description says it runs all ready callbacks, polls for I/O, schedules the resulting callbacks, and then schedules call_later callbacks. The ready queue is a collections.deque named _ready, and the timers are a heap list named _scheduled. The names start with an underscore: they are private, and the "When it breaks" rung explains why that matters.

Working

  1. Work out the timeout. The timeout for select() is 0 if callbacks are ready or the loop is stopping; otherwise it is the time until the earliest timer, capped at 24 hours; with no timers at all it is None.
  2. Poll for I/O. The loop calls its selector's select() with that timeout, and the callback registered for each ready socket is added to the ready queue.
  3. Move due timers. Every timer whose time has come is popped from the heap and appended to the ready queue.
  4. Run what is ready now. The loop runs only the callbacks that were in the ready queue at this point; callbacks they schedule run in the next iteration, after another I/O poll.

Why each step is needed

  • Step 1: if work is ready, sleeping would delay it, so the poll is only a peek (timeout 0). If nothing is ready, the loop may sleep, but only until the next timer, so timers fire on time.
  • Step 2: one call covers every socket at once; this is the selector from the last part.
  • Step 3: timers are queued after the poll, so a timer that came due during a long sleep runs in this same iteration.
  • Step 4: counting the ready callbacks first means a callback that keeps scheduling more work cannot keep the loop from polling sockets.

Wrong belief: "The loop runs callbacks until the ready queue is empty, then looks at the sockets."

Why it is wrong: the loop runs only the callbacks that were ready when the iteration started its run step. A callback that schedules another callback cannot keep the loop from the next select(). If it emptied the queue first, two callbacks that keep scheduling each other would starve every socket.

  • One iteration: timeout, select(), queue I/O callbacks, queue due timers, run what is ready now.
  • Timeout: 0 if work is ready; time to the earliest timer otherwise; None if there is nothing to wait for but sockets.
  • Callbacks scheduled during a run wait for the next iteration.

Each turn of asyncio's loop sleeps in select() only as long as the next timer allows, then runs exactly the work that is ready at that moment.

Put one iteration of asyncio's loop in order.

  1. Work out the select() timeout from the ready queue and the earliest timer
  2. Call select() and queue the callbacks of ready sockets
  3. Move every due timer from the heap to the ready queue
  4. Run the callbacks that are in the ready queue at this moment

The timeout must be known before select() is called; due timers are collected after the poll, so time spent sleeping is counted; running comes last, and only for what is ready now.

Putting work on the loop: call_soon and call_later

Last part: each iteration runs the ready queue and moves due timers onto it. Still unsolved: how does code put a callback into the ready queue, or onto the timer heap, in the first place?

The gateway must cut the request at 250 ms. In Part 1 the toy loop had run(until=250) built in. In asyncio we need to tell the loop "call this function 0.25 seconds from now", and keep a way to cancel it if every seller answers first.

Introduction

asyncio's loop has two low-level methods that map one to one onto Part 1's structures. call_soon appends to the ready queue. call_later pushes onto the timer heap. Most application code never calls them directly, but every higher-level tool on this page and the next is built from them.

Definitions

  1. loop.call_soon(callback, *args) schedules the callback for the next iteration of the loop and returns an asyncio.Handle; callbacks are called in the order in which they are registered, each exactly once.

  2. loop.call_later(delay, callback, *args) schedules the callback after delay seconds and returns an asyncio.TimerHandle; if two callbacks are scheduled for exactly the same time, the order in which they run is undefined.

  3. A handle is the object these methods return. Handle.cancel() cancels the callback; if it has already been cancelled or has run, it has no effect.

  4. loop.time() returns the current time as a float, according to the event loop's internal monotonic clock. A monotonic clock is one that only moves forward. Python's time.monotonic() returns seconds from a clock that cannot go backwards and is not affected by system clock updates. On CPython, loop.time() reads this same clock, which this page's tests check.

Working

  1. call_soon(f) wraps f in a Handle and appends it to the ready queue.
  2. call_later(0.25, f) wraps f in a TimerHandle due at loop.time() + 0.25 and pushes it onto the timer heap.
  3. handle.cancel() marks the handle as cancelled. The loop skips cancelled handles when it reaches them.
  4. At each iteration, due timers move to the ready queue and every ready handle runs once, in order.

Why each step is needed

  • Steps 1 and 2: these are the only two ways into the loop; everything else (Futures, Tasks, sockets) ends up calling one of them.
  • Step 3: the gateway's budget timer must be cancellable, or it would fire after a request that already finished.
  • Step 4: "each exactly once, in order" is what makes the loop predictable enough to test.

Definition

A Future is an object that starts empty and is later completed exactly once, with a result, an exception, or a cancellation. The docs say a Future represents an eventual result of an asynchronous operation, and that it is not thread-safe. The recommended way to create one is loop.create_future(), and the rule of thumb is never to expose Future objects in user-facing APIs.

Working

A Future is in one of three states. CPython's futures.py names them _PENDING, _CANCELLED and _FINISHED.

  1. Pending. done() is False. Calling result() or exception() before the Future is done raises InvalidStateError.
  2. Finished with a result or an exception. A Future is done if it was cancelled or if a result or an exception was set with set_result() or set_exception(). result() then returns the value, or raises the exception that was set.
  3. Cancelled. cancel() returns False if the Future is already done; otherwise it marks it cancelled, schedules its callbacks and returns True. On a cancelled Future, result() and exception() raise CancelledError.
  4. Only once. set_result() and set_exception() raise InvalidStateError if the Future is already done.
  5. Done callbacks. add_done_callback(fn) arranges for fn to be called with the Future as its only argument when the Future is done; if it is already done, fn is scheduled with call_soon. In CPython's futures.py, completing a Future also schedules each waiting callback with loop.call_soon rather than calling it directly.

Why each step is needed

  • Step 1: asking too early is a programming error, so it raises instead of returning a placeholder such as None.
  • Step 4: "exactly once" means two callbacks racing to fill the same Future cannot silently overwrite each other.
  • Step 5: scheduling callbacks instead of calling them keeps the order of work in the loop's hands, so a callback chain cannot grow deeper and deeper inside one function call.

Definition

A Future is awaitable: coroutines can await it until it has a result or an exception set, or is cancelled, and a Future can be awaited many times with the same result. Working

  1. The coroutine runs await fut. Python calls fut.__await__().
  2. fut is not done, so __await__ yields fut.
  3. That yield travels up through every await in the chain and comes out as the return value of the send(None) that resumed the coroutine.
  4. Later someone calls fut.set_result(1199).
  5. The coroutine is resumed with send(None) again. __await__ continues after its yield and returns fut.result(), so await fut evaluates to 1199.

Why each step is needed

  • Step 2: yielding the Future, not a description of the wait, means the driver does not need to understand timers or sockets: it only needs to know how to be told when a Future is done.
  • Step 5: the result is read only after the resume, so an exception set on the Future is raised at the await line, inside the coroutine, where a try can catch it.

Introduction

Part 1's toy loop had a small Task class: a coroutine plus a done flag and a result. Its scheduler called send(None). asyncio's Task does the same job, but in a different style: it is a Future (so it has a result, an exception or a cancellation), and it drives its coroutine through callbacks on the loop instead of being picked by the scheduler.

Comparison

A personal assistant working through your to-do list. They do the next step, and when a step needs something from someone else, they leave a note on that person's desk: "when this is ready, put me back on the schedule". Then they go and do something else. The note is what brings them back.

  • The assistant = the Task; the to-do list = the coroutine.
  • The note on the desk = the Task's wake-up callback on the Future.
  • "Put me back on the schedule" = call_soon of the next step.

Where it stops working: an assistant can work on two lists at once. A loop runs one Task step at a time, on one thread.

Definitions

  1. A Task is a Future that runs a coroutine. When a Task's coroutine awaits a Future, the Task suspends the coroutine and waits for the Future to complete; when the Future is done, the coroutine resumes. asyncio.Task inherits all the Future APIs except set_result() and set_exception().

  2. A step is one resumption of the coroutine: from a send() until it next yields, returns or raises. Event loops use cooperative scheduling: a loop runs one Task at a time, and while a Task awaits a Future the loop runs other Tasks and callbacks or performs I/O.

Working

The steps below follow CPython 3.14's tasks.py. When the _asyncio C module is available, CPython uses its C versions of Task and Future instead of the Python classes in tasks.py and futures.py. This page reads the Python versions because they are written out in plain Python.

  1. Create. Unless it is started eagerly, a new Task schedules its first step with loop.call_soon. Nothing of the coroutine has run yet.
  2. Step. Each step resumes the coroutine with coro.send(None), or with coro.throw(exc) when an exception must be delivered into it.
  3. Park on a Future. If the coroutine yields a Future, the Task adds its wake-up method to that Future as a done callback. The step ends; the loop goes on with other work.
  4. Wake. When the Future completes, its done callbacks are scheduled with call_soon, so the wake-up runs in a later iteration. The wake-up starts the next step, throwing the Future's exception into the coroutine if it has one.
  5. Finish. When the coroutine returns, the Task sets its result from StopIteration; when it raises any other exception, the Task stores it with set_exception.
  6. Other yields. A bare yield, which is what asyncio.sleep(0) produces, makes the Task schedule its next step with call_soon; yielding anything else is an error, reported as "Task got bad yield".

Why each step is needed

  • Step 1: scheduling instead of running means create_task() returns at once, and the caller keeps running until it awaits.
  • Step 3: the done callback is the "note on the desk". The loop needs no list of waiting tasks; each waiting Task is remembered by the Future it waits on.
  • Step 4: going through call_soon means the coroutine resumes from the loop, not from inside whatever code filled the Future.
  • Step 5: this is the fix for Part 1's second bug. A failure becomes the Task's stored exception instead of escaping the loop.
  • Step 6: this is why Part 1's real_io.py failed. The toy loop did not understand asyncio's yields; an asyncio Task does not understand the toy loop's tuples.

From start to finish: what asyncio.run does

Last part: a Task drives a coroutine step by step. Still unsolved: somebody has to create the loop, create the first Task, and clean up when it ends. What happens to Tasks that are still running when main() returns?

The gateway's main() returns, but a background Task is still waiting, an async generator is paused half-way, and a thread in the loop's executor is busy for another 200 ms. If the program just exits, the Task's clean-up never runs and the generator's finally never runs either.

Introduction

Every program on the next pages starts with one line: asyncio.run(main()). This part opens it. It is short code in CPython's runners.py, and almost every line of it is a clean-up step that a hand-written run_forever() program tends to forget.

Definitions

  1. asyncio.run(coro) runs the coroutine in an asyncio event loop and returns its result, taking care of managing the loop, finalizing asynchronous generators and closing the executor. It cannot be called while another asyncio event loop is running in the same thread, and the docs say it should be the main entry point of an asyncio program, ideally called only once.

  2. An async generator is an async def function that contains yield; it hands out values one at a time to async for. If it is left paused, its finally block has not run yet.

  3. The default executor is the pool of threads the loop uses for loop.run_in_executor(None, f), which runs a blocking function off the loop's thread.

Working

  1. Create. If loop_factory is given it creates the loop; otherwise asyncio.new_event_loop() is used, and the loop is closed at the end.
  2. Run. In CPython 3.14's runners.py, run() wraps the coroutine in a Task with loop.create_task() and runs the loop with run_until_complete() until that Task is done.
  3. Cancel leftovers. When the runner closes, it cancels every task that is still running and runs the loop until all of them have finished, gathering them with return_exceptions=True.
  4. Close async generators. Next it runs loop.shutdown_asyncgens(), which schedules every async generator that is still open to close with aclose().
  5. Shut down the default executor. Then it runs loop.shutdown_default_executor(), which waits for the executor's threads to finish; after that, run_in_executor() with the default executor raises RuntimeError. asyncio.run gives the executor 5 minutes; if it has not finished by then, a warning is emitted and the executor is closed.
  6. Close the loop. loop.close() discards any pending callbacks; it is irreversible, and no other methods should be called on the loop afterwards.

Why each step is needed

  • Step 3: a Task that is never cancelled never runs its except or finally; cancelling gives it the chance to close sockets and files.
  • Step 4: a paused async generator often holds a connection or a cursor; its finally is where that is released.
  • Step 5: a thread still running in the executor may be writing data; waiting lets it finish.
  • Step 6: closing frees the selector and other resources, and makes any later use of the loop fail loudly instead of silently.

  • Then, in order: cancel leftover tasks, close async generators, shut down the default executor, close the loop.

  2. Close async generators that are still open
  3. Wait for threads in the default executor
  4. Close the loop and return main()'s result

Introduction

asyncio offers several layers for network I/O. The highest one, streams, gives a coroutine a reader and a writer and hides the selector, the non-blocking sockets and the callbacks. Underneath, everything from the earlier parts is still at work: a selector waits on the socket, a callback fills a Future, and a Task wakes up. This part writes the gateway on streams, and builds the budget and the "wait for all five" by hand from call_later, Futures and done callbacks, because those are exactly the tools this page has taught. Part 3 of the series replaces both with the proper tools.

Definitions

  1. Streams are asyncio's high-level connection API. The docs describe streams as high-level async/await-ready primitives for network connections that send and receive data without callbacks or low-level protocols and transports. asyncio.open_connection() establishes a connection and returns a (reader, writer) pair of StreamReader and StreamWriter objects; the reader's buffer limit defaults to 64 KiB.

  2. StreamWriter.write() tries to write the data to the socket immediately and, if that fails, queues it in an internal write buffer; it should be used together with await writer.drain(). drain() is a flow-control method: when the write buffer has reached its high watermark, it waits until the buffer drains to the low watermark, and otherwise it returns immediately.

  3. StreamReader.readline() reads one line ending with a newline; at end-of-file without a newline it returns the partial data, and at end-of-file with an empty buffer it returns an empty bytes object. writer.close() closes the stream and the underlying socket, and the docs recommend following it with await writer.wait_closed().

  4. Task.cancel() makes the Task throw a CancelledError into its coroutine; if the coroutine is awaiting a Future at that moment, that Future is cancelled. task.cancelled() returns True if the coroutine did not suppress the CancelledError and was actually cancelled. Task.cancel() only requests cancellation: it arranges for the CancelledError to be thrown into the coroutine on the next cycle of the event loop, and the coroutine may clean up or even suppress it.

Working

  1. ask_seller() opens a connection, writes the item code, drains, and awaits reader.readline(). Its finally closes the connection.
  2. compare() creates one Task per seller with asyncio.create_task(..., name=...).
  3. The budget: loop.call_later(0.25, ...) cancels every Task that is not done yet.
  4. Waiting for all five: one Future, all_done, and a done callback on every Task that counts down; the last one to finish fills all_done.
  5. When all_done is filled, each Task is sorted by its state: cancelled means missed, an exception means failed, otherwise its result is an offer.

Why each step is needed

  • Step 1: finally runs on success, on failure and on cancellation, so no connection is left open.
  • Step 3: a cancelled Task still ends, through its finally, so the budget cut is clean.
  • Step 4: compare() must not await the Tasks one by one: awaiting a cancelled Task raises CancelledError in the awaiting coroutine. Waiting on one Future that is filled from done callbacks avoids that. This is a stand-in, and Part 3 replaces it.
  • Step 5: the Future states from the Future part decide each seller's fate without raising.

Introduction

Closing a socket without unregistering it

Last part: polling keeps the loop awake. Still unsolved: what happens to a selector when a socket's owner forgets to tell it the socket is gone?

A hand-written selector loop (like gateway v2) closes seller-e's socket at the 250 ms budget but forgets to unregister it. The very next request opens a socket, the operating system gives it the same file descriptor number, and register() raises KeyError. Every request after the first budget cut now fails.

Introduction

The selector keeps a table from file objects and file descriptor numbers to keys. Closing a socket does not remove its row. File descriptor numbers are reused, so a stale row can collide with a brand-new socket. This is a bug of hand-written selector code; asyncio's transports unregister for you, which is one reason to use them.

Working

  1. The old socket is registered: the selector's table has one row for its file descriptor.
  2. The socket is closed while still registered. The table still has the row.
  3. A new socket is opened. The old number is free again, so the operating system may hand it out; in the program below, on Linux, it did.
  4. register(new) finds a row for that number and raises KeyError: already registered.
  5. The fix: unregister(old) before old.close(). Then the new socket registers normally.

The selectors docs say a file object shall be unregistered before it is closed, and that unregister() raises KeyError if the file object is not registered.

Program

Explanation of the program

  1. After old.close(), get_map() still has one entry: the dead socket.
  2. The new socket gets the same file descriptor number. (The program prints True instead of the number, which differs between machines.)
  3. Registering it fails with KeyError, "already registered".
  4. Unregistering the old socket, even though it is closed, removes the stale row, and the new socket registers.

Solved example

Many idle sockets: why the choice of selector matters at scale

Last part: a socket closed without unregistering haunts the selector. Still unsolved: what does each registered socket cost the loop, even when nothing happens on it?

At 10 times Part 1's load the gateway holds a few thousand seller connections open at once, nearly all of them idle at any moment, waiting for an answer. Every iteration of the loop calls select() over all of them. If each call cost time in proportion to the number of sockets, the loop would spend its time asking about sockets that have nothing to say.

Introduction

The oldest readiness call, select(), takes the full set of descriptors as arguments on every call; Python's select.select(rlist, wlist, xlist) shows this in its signature. epoll keeps the set inside the kernel. In CPython's selectors.py, SelectSelector passes its whole set of readers and writers to select() on every call, while EpollSelector hands each descriptor to the kernel's epoll object once, in register(), and its select() calls that object's poll(). This part measures the difference on one Linux machine and shows the hard limit that the old call hits first. kqueue plays epoll's role on macOS; it was not measured here.

Working

  1. With SelectSelector, every select() call passes every registered descriptor to the kernel and gets every one back, ready or not. The work grows with the number of sockets.
  2. With EpollSelector, the sockets were handed to the kernel once, at register(). A select() call asks only for the ready ones.
  3. SelectSelector also has a ceiling on the descriptor number: past it, the call fails outright.

Given: 200 requests per second; each request keeps its five seller connections open for 80, 120, 150, 200 and 250 ms (seller-e is cut at the budget). Load grows 10 times.

Wrong belief: "Idle connections are free: they do nothing, so they cost nothing."

  • epoll keeps the set in the kernel; measured, idle sockets add almost nothing per call.

Running out of file descriptors

Last part: at 10 times the load the gateway holds about 1,600 seller connections open. Still unsolved: every one of them is a file descriptor, and a process may only hold so many.

During a sale the gateway starts returning errors for every request, while CPU and memory look normal. The logs say OSError: [Errno 24] Too many open files. The process hit its limit on open file descriptors, so it can neither connect to sellers nor accept new shoppers.

Introduction

The event loop made waiting cheap, which means a single process can now have far more calls in flight than a thread-per-call design ever could. Each one still needs a socket, and each socket is a file descriptor. The operating system caps how many a process may hold. This part hits that cap on purpose.

Definitions

  1. RLIMIT_NOFILE is the maximum number of open file descriptors for the current process. Each resource limit is a pair: a soft limit, which is the current limit and may be lowered or raised by the process, and a hard limit, which the soft limit can never exceed. Python's resource.setrlimit() raises ValueError if the new soft limit exceeds the hard limit, or if a process tries to raise its hard limit; a process running as the super-user may request any valid value.

  2. EMFILE is the errno for "Too many open files".

Working

  1. Every socket() call, connection made or connection accepted takes one more file descriptor.
  2. When the process already holds as many descriptors as its soft limit, the next one fails with EMFILE.
  3. In the gateway, a failed open_connection() fails that seller's Task, and a failed accept in the server means shoppers cannot connect at all.

Program

  3. The 62nd socket call fails with OSError EMFILE, "Too many open files".

Calling the loop from another thread

Last part: too many sockets run into the descriptor limit. Still unsolved: the loop assumes it is the only thread touching its queues. What happens when a second thread, such as a metrics exporter or a callback from a blocking library, hands it work?

A price-feed library runs in its own thread and calls loop.call_soon(update_cache) whenever a seller pushes a new price. In tests it seems to work. In production, cache updates sometimes arrive up to a second late, and once in a while the process misbehaves in ways nobody can reproduce.

Introduction

Everything on this page so far ran on the loop's own thread. The loop's queues are plain Python objects with no locks, and the loop may be asleep inside select(). Work handed in from another thread has to be put in safely and has to wake the loop. One method does both; the one most people reach for does neither.

Definitions

  1. An event loop runs in a thread, typically the main thread, and executes all callbacks and Tasks in that thread. Almost all asyncio objects are not thread-safe; code outside a Task or callback that must call a low-level asyncio API should use loop.call_soon_threadsafe().

  2. loop.call_soon_threadsafe() is the thread-safe variant of call_soon(), and it must be used when scheduling callbacks from another thread, because call_soon() is not thread-safe. To schedule a coroutine from another thread, use asyncio.run_coroutine_threadsafe(), which returns a concurrent.futures.Future for the result.

Working

  1. The loop has nothing ready and its only timer is 1 second away, so it sleeps in select(timeout=1.0).
  2. At 100 ms another thread calls loop.call_soon(cb). The handle is appended to the ready queue, but nothing wakes the sleeping select().
  3. At 1,000 ms the timer's timeout ends the sleep, and only then is cb run: 900 ms late.
  4. With call_soon_threadsafe(cb) instead, the handle is appended and the loop is woken at once. In CPython 3.14, call_soon_threadsafe() appends the handle to the ready queue and then calls the loop's _write_to_self(), which sends a byte on a socket pair whose other end the loop's selector watches, so select() returns.
  5. In debug mode, call_soon from the wrong thread is caught. CPython's check raises RuntimeError("Non-thread-safe operation invoked on an event loop other than the current one").

Why each step matters

  • Step 2: the late callback is the visible half of the bug. The invisible half is that the ready queue was changed from two threads without a lock, which the docs rule out.
  • Step 4: waking the selector is the reason the thread-safe method exists. It is the same trick as the selector part: the loop only wakes for sockets and timers, so the thread-safe method makes a socket ready.

Program

Explanation of the program

  2. With call_soon the callback, handed in at 100 ms, runs at 1,000 ms: when the timer ends the loop's sleep.

  4. With debug mode on, call_soon from the other thread raises RuntimeError in that thread, which turns a silent timing bug into a loud one.

Solved example

  • One loop, one thread: its callbacks and Tasks all run there.
  • From another thread: call_soon_threadsafe for callbacks, run_coroutine_threadsafe for coroutines.
  • Plain call_soon from another thread can wait until the next timer; debug mode turns it into a RuntimeError.

Introduction

Reading CPython's source is the best way to understand the loop, and this page did it on purpose. Using what you read is a different matter. Definition

Python's tutorial states the convention that a name prefixed with an underscore, such as _spam, should be treated as a non-public part of the API, an implementation detail subject to change without notice.

Working: real changes from the release notes

  1. In Python 3.14, asyncio moved native tasks to a new per-thread doubly linked list, which the release notes credit with 10 to 20% better standard benchmark results and lower memory use. The note describes how tasks are stored inside asyncio, not a new API: a change made entirely beneath the underscore names.
  2. The Python 3.13 release notes say that uncancel() may now reset the undocumented _must_cancel flag of a task. Code that read or set that flag directly saw its meaning change.
  3. A new **kwargs argument to create_task() was accidentally added in Python 3.13.3 and broke the API contract for custom task factories; several third-party task factories added workarounds, and 3.13.4 and later honour the old factory contract again until 3.14.

Why it matters

  • Step 1 is a performance improvement; it changed internals that nobody was promised.
  • Step 3 shows that even an extension point (a task factory) close to the internals can break in a patch release, so code at that level needs tests on every Python version it runs on.

Which layer to write I/O at: selectors, threads, streams or protocols

Introduction

Every layer on this page waits the same way underneath: a selector (or, on Windows, a completion port) tells the program when a socket is ready. Definitions

  1. A transport moves the bytes; a protocol decides what they mean. The docs say the transport is concerned with how bytes are transmitted, while the protocol determines which bytes to transmit, and that there is always a one-to-one relationship between a transport and its protocol.

  2. Introduction

Prompt 1: the full path of one readline()

  1. The coroutine waits on a Future. When the StreamReader's buffer has no complete line, it creates a Future with loop.create_future() and awaits it.
  2. The Task parks. The Future is yielded up the await chain to the Task, which adds its wake-up as a done callback. The step ends.
  3. The socket was already registered. The selector transport registered its socket with add_reader(), with its _read_ready method as the callback, when it started reading.
  4. The loop sleeps. Nothing is ready and no timer is due, so the iteration calls select(timeout=None).
  5. Data arrives. The selector returns the socket; the loop queues _read_ready and runs it in the same iteration. That callback calls sock.recv() with a buffer of 256 KiB and passes the bytes to the protocol's data_received().
  6. The bytes reach the reader. The streams protocol's data_received() calls the reader's feed_data(), which appends the bytes to the buffer and wakes the waiter by setting the Future's result.
  7. The wake-up is queued. Completing the Future schedules the Task's wake-up with call_soon. It does not run yet.
  8. Next iteration, your code runs. Something is ready, so select(timeout=0) only peeks. The wake-up runs, the Task calls send(None), readline() finds the line in its buffer and returns it, and your next line runs.

Explanation of the program

  1. The tracing selector from the loop-iteration part prints only while readline() is waiting.
  2. Exactly two iterations separate the call from the resume: one that sleeps (timeout=None) and receives the data (steps 4 to 7), and one that peeks (timeout=0.00) and runs the Task's wake-up (step 8).

  • Gateway v2 (toy loop plus selector) and gateway v3 (asyncio streams): 900 ms, then seller-b at 1,199 in 250 ms with seller-e missed, and seller-c's failure kept inside its own Task.
  • Failure modes: busy loops, forgotten unregister, idle sockets with select(), file descriptor limits, cross-thread calls, private internals; loop lag as the signal.

What is still broken

  • No structured way to run many tasks. "Wait for all five" is a Future, a counter and five done callbacks. A Task that is never referenced or never read can lose its result or its error.
  • No limits. Every request opens five connections at once; at 10 times the load that is about 1,600 open connections on average, against a descriptor limit that may be 1,024.
  • No deadlines. The 250 ms budget is a timer that cancels by hand. Nothing guarantees it is cancelled when the request ends early, and nothing nests: a seller call has no deadline of its own inside the request's.
