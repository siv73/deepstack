Why one GPU stops being enough

Your team must serve Llama 3.1 70B. Part 1 worked out that its BF16 weights alone take 140 GB. One H100 holds 80 GB. No setting makes 140 fit in 80.

NVIDIA lists the H100 SXM with 80 GB of memory, 3.35 TB/s of memory bandwidth, and NVLink at 900 GB/s next to PCIe Gen5 at 128 GB/s. Remember the last two numbers. Once a model spans GPUs, how fast GPUs talk to each other starts to matter as much as how fast each one computes.

There are three ways to put more GPUs to work:

  1. Split every layer's weight matrices across GPUs. All of them work on every token, and they swap partial results inside every layer. That is tensor parallelism (TP).
  2. Give each GPU a run of consecutive layers. A token's activations pass from GPU to GPU, like an assembly line. That is pipeline parallelism (PP).
  3. Run whole copies of the model on separate GPUs, each serving its own requests. Part 2 of this page names these copies.

A translation agency faces the same choice with a book too big for one translator. Four translators can each take a quarter of every sentence and stitch the sentences together (tensor). They can take chapters in turn, passing the draft along (pipeline). Or the agency can hire more teams, each with its own book (copies).

vLLM's guide says: if the model fits on one GPU, distributed inference is probably unnecessary; if it fits on one node, use tensor parallelism across that node's GPUs; if it needs several nodes, use tensor parallelism within each node and pipeline parallelism across nodes.

When the weights do not fit, split each layer (tensor), split the stack of layers (pipeline), and add whole copies for more traffic.

The 70B model in BF16 must run on one 8-GPU H100 node with NVLink. Following vLLM's guide, how should one copy of the model be spread?

  1. Pipeline parallelism over the node's GPUs
  2. Tensor parallelism within the node
  3. Several copies, one per GPU

The weights fit in one node, so the guide says tensor parallelism within that node. Copies come after one copy fits.

Why an LLM copy is not a stateless web server

Last part: split a layer, split the layers, or add copies. Still unsolved: can a load balancer treat the copies like ordinary pods?

Your FastAPI service runs 12 identical pods behind round-robin. Any pod can answer any request, because the state lives in the database. You put four copies of a chat model behind the same balancer, and turn 5 of a long conversation is slower than it was on one copy.

Call each full copy a replica. The weights in every replica are identical and never change while serving, so for the weights, any replica will do.

The KV cache is different. Each replica keeps the cache of the requests it is running, and, with prefix caching, the blocks of prompts it finished recently (Part 4). Prefix caching is on by default in vLLM v0.31.0. vLLM's data-parallel guide notes that each replica has its own independent KV cache, so where a prompt is sent decides how much prefix caching can reuse.

Turn 5 of a chat resends turns 1 to 4 as its prompt. The replica that served turn 4 may still hold those blocks. Round-robin sends turn 5 somewhere else, which recomputes the whole history from scratch.

Backend comparisons, mapped:

Backend ideaLLM serving version
Read replicas: full copies, any one answersReplicas: full copies of the weights, any one can answer
Sharding: each node owns part of the dataTensor and pipeline parallelism: each GPU owns part of the weights

So an LLM replica is stateful in the way a pod with a warm local cache is: the cache is not the source of truth, but routing that ignores it pays for it on every request.

Replicas share identical weights but each holds its own KV cache, so the router's choice of replica changes how much work a request costs.

Four replicas sit behind round-robin. Long chats get slower per turn than on a single replica, even though no replica is busy. Why?

  1. Each replica holds different weights, so later turns run a different model
  2. Replicas must synchronize after every turn
  3. Each turn lands on a replica that does not hold the earlier turns' cached blocks, so the history is recomputed

Each replica's KV cache and prefix cache are its own. Round-robin scatters a conversation, so most turns miss the cache.

Explain to a teammate who runs stateless APIs how you would serve a model too big for one GPU, and why the load balancer in front cannot be plain round-robin.

If the weights do not fit on one GPU, I split each layer across GPUs in a node with tensor parallelism, and add pipeline stages across nodes only if one node is not enough. That makes one replica. For more traffic I add replicas. Every replica has the same weights, but each keeps its own KV cache and prefix cache, so a conversation sent to a different replica each turn recomputes its history. The cache is soft state like a local cache: losing it costs time, not correctness, so the balancer should prefer the replica that holds the prefix.

How four GPUs share one layer

Last part: replicas hold their own caches. Still unsolved: inside one replica of the 70B model, how do four GPUs act as one?

With four GPUs, each H100 holds 35 GB of the 70B model's weights. Yet every token needs every weight in every layer.

vLLM's docs say its tensor parallelism includes Megatron-LM's tensor-parallel algorithm. One layer, step by step:

  1. The first matrix of a block is split by columns. Each GPU computes a quarter of the output from the full input, without talking.
  2. The next matrix is split by rows, to match. Each GPU multiplies its quarter and ends up with a partial sum of the full result.
  3. The GPUs add their partial sums so that each holds the full result. That collective step is an all-reduce.
  4. Attention splits the same way by heads: each GPU runs its share of the query heads and stores its share of the KV cache. Every layer repeats these steps.

A column-parallel layer splits the weight matrix A along its second dimension, A = [A_1, ..., A_p]; a row-parallel layer splits A along its first dimension and the input X along its second. In vLLM's Llama code, each layer's attention output projection (o_proj) and MLP down projection (down_proj) are row-parallel, and a row-parallel layer all-reduces its output across the tensor-parallel GPUs when there is more than one. vLLM splits the key/value heads across the tensor-parallel GPUs when there are at least as many heads as GPUs, and copies them when there are fewer.

Llama 3.1 70B has 80 layers, a model dimension of 8,192, 64 attention heads and 8 key/value heads. That is 160 all-reduces per forward pass, each carrying one 8,192-value BF16 vector (16 KB) per token in the step.

Hugging Face's guide says tensor parallelism needs fast communication inside a node, because GPUs exchange partial results at each layer. NVIDIA's Hopper write-up gives H100 18 fourth-generation NVLink links at 25 GB/s each direction, 900 GB/s in total, and calls that 7 times the bandwidth of PCIe Gen 5. This page therefore counts 450 GB/s each way per GPU.

NCCL's test documentation gives the best-case time of an all-reduce of S bytes over n GPUs as S/B × 2(n−1)/n, where B is each GPU's bandwidth. In this page's tested model, a decode step at TP=4 with 133 requests spends about 1.2 ms in all-reduces out of 18.6 ms. A prefill step of 8,192 tokens spends about 72 ms in them.

Tensor parallelism cuts every GPU's share of weight reads and math, and pays with two all-reduces per layer, which is why it lives on NVLink inside one node.

Same 70B model, decode only. You move from TP=4 to TP=8 on the same NVLink node. Predict what happens to one decode step's time, and to the share of it spent in all-reduces.

The step gets shorter: each GPU now reads one eighth of the weights. The all-reduce share grows: 160 all-reduces still happen per step, the ring factor 2(n−1)/n rises from 1.5 to 1.75, and the compute and reads they sit between shrink by half. More GPUs per replica buy lower ITL at a falling efficiency per GPU.

Splitting the stack of layers, and copying the whole model

Last part: tensor parallelism talks inside every layer. Still unsolved: what the other two options send between GPUs, and what each does to TTFT, ITL and throughput.

A model's BF16 weights come to 800 GB, more than one 8-GPU node's 640 GB. Tensor parallelism across two nodes would run two all-reduces per layer over a link much slower than NVLink. You need a split that talks less.

Pipeline parallelism gives each node a run of layers. Only the activations at the boundary cross between stages, once per stage per step. Hugging Face's parallelism guide describes pipeline parallelism as splitting the model's layers across GPUs and passing micro-batches from one GPU to the next, so that GPUs work at the same time instead of waiting. One request still walks through every stage in order, so pipelining does not shorten its own step. It keeps every stage busy with different batches. vLLM keeps at least as many batches in flight as there are pipeline stages; its code notes that a pipeline needs that many to stay full.

vLLM's guide also suggests pipeline parallelism when the GPU count does not split the model evenly, and for GPUs without NVLink, such as the L40S, where it gives higher throughput and less communication than tensor parallelism.

Replicas are the third option. In vLLM's data parallelism the weights are copied to separate instances that each process their own batches. For dense models the copies never talk. For mixture-of-experts models, --enable-expert-parallel switches the expert layers from tensor to expert parallelism, and data-parallel ranks serving such models must synchronize in every forward pass. This page stays with dense models.

OptionSplitsSends between GPUsTTFT and ITL of one requestThroughput

Pipeline (PP)The stack of layers into stagesActivations at each stage boundaryNot shortened; a little longer from the hand-offsUp, if enough batches keep every stage busy
Replicas (data parallel)Nothing: whole copiesNothing, for dense modelsUnchanged; queueing time fallsUp roughly in proportion to copies

Tensor parallelism cuts each request's latency, pipeline parallelism lets a model span nodes with little talking, and replicas add throughput with no talking at all.

An 8B model fits easily on one H100. Traffic triples. Your ITL is fine; requests wait in the queue. What do you add?

  1. Replicas, each on its own GPU
  2. Tensor parallelism across 4 GPUs for the one copy
  3. Pipeline parallelism across 2 GPUs

The problem is waiting, not step time. Copies serve independent requests with no communication, so throughput rises in proportion.

One request through a production fleet

Last part: what TP, PP and replicas each buy. Still unsolved: how a request finds a replica, and how it moves when prefill and decode run on different machines.

A user sends turn 5 of a chat with a 2,000-token history. Twenty prefill and decode replicas could serve it. Which one gets it, and how does the answer stream back token by token?

Some fleets run prefill and decode on separate replicas, so that long prompts never stall anyone's token stream. That design is disaggregated prefill/decode. vLLM's disaggregated mode runs two instances, one for prefill and one for decode, and a connector moves the prefill's KV cache to the decode instance.

The pieces, backed by sources: vLLM's example proxy sends a request first to a prefill instance with max_tokens set to 1 and a do_remote_decode flag, then to a decode instance, choosing each in round-robin order. With NixlConnector, the decode instance reads the KV blocks from the prefill instance, and the prefill instance holds them for a lease, 30 seconds by default, which heartbeats extend while the request waits on the decoder. Mooncake streams each layer's KV cache to the decoding node while prefill continues, overlapping the transfer with compute. vLLM's chat endpoint streams Server-Sent Events and ends the stream with a data: [DONE] line.

Where the backend comparison breaks: a read replica can lag its primary, but model replicas never diverge, because the weights do not change. And a database shard talks to others once per query, while a tensor-parallel GPU talks to its group 160 times per token.

A production request passes a stateless gateway, a router that chooses by cache and load, and replicas; in a disaggregated fleet its KV cache moves once, from prefill to decode.

Put the disaggregated path in order.

  1. The gateway checks the request and attaches a deadline
  2. The router picks a prefill replica by prefix and load
  3. Prefill computes the prompt's KV cache and reports where it is
  4. A decode replica pulls the KV blocks
  5. Tokens stream back as Server-Sent Events, ending with [DONE]

Prefill must finish before its cache can move, and decoding cannot start until the cache has arrived.

In your own words: what does each of tensor parallelism, pipeline parallelism, replicas and disaggregation split, and what does each have to send?

Tensor parallelism splits every weight matrix, so the GPUs must all-reduce twice per layer on every step; that needs NVLink inside a node, and it cuts both TTFT and ITL. Pipeline parallelism gives stages consecutive layers and only passes activations at the boundaries, so it spans nodes cheaply but does not make one request faster. Replicas copy the whole model and send nothing between copies, so they add throughput. Disaggregation runs prefill and decode on different replicas and sends each request's KV cache once, from the prefill replica to the decode replica.

Setting TP, PP and replicas in vLLM

Last part: the request path end to end. Still unsolved: the exact switches, and how to tell from the logs that a layout has room.

You have one 8-GPU H100 node and the 70B model, which needs at least four of its GPUs. Do you run one TP=8 replica, or two TP=4 replicas, and how do you start them?

In vLLM v0.31.0 the flags are --tensor-parallel-size (-tp), --pipeline-parallel-size (-pp) and --data-parallel-size (-dp), each defaulting to 1. The data-parallel guide's example of --data-parallel-size=4 with --tensor-parallel-size=2 uses 8 GPUs, and it runs behind a single API endpoint.

# one replica over all 8 GPUs: lowest ITL, one KV pool
vllm serve $MODEL --tensor-parallel-size 8

# two replicas of 4 GPUs each, one endpoint: more requests in flight per GPU
vllm serve $MODEL -tp 4 -dp 2

Then read the startup log. vLLM logs the GPU KV cache size in tokens and the maximum concurrency for requests of max_model_len tokens, and its guide says to add GPUs or nodes if these are below what you need.

Two behaviours of the built-in replicas matter in production. The internal data-parallel balancer picks a rank from each engine's running and waiting queues; the docs say it could later add KV-cache-aware logic, which it does not use yet. --max-num-seqs applies per data-parallel rank, but --max-num-queued-reqs and --max-num-queued-tokens apply to the whole server.

Copying a single-replica config to -dp 4 and leaving --max-num-queued-reqs at the old value. The cap now covers four ranks together, so the server starts answering 503 while each rank still has room. Size it as roughly ranks × max-num-seqs plus the queue you want.

"One TP=8 replica or two TP=4 replicas for a 70B model on one node?" A strong answer runs the numbers instead of picking a favourite. In this page's tested model, a TP=4 replica's KV pool holds 188 requests of 2,300 tokens and a TP=8 replica's holds 563, because the fixed weight share shrinks per GPU. TP=8 gives lower ITL per request; two TP=4 replicas avoid the larger all-reduce share and keep serving when one replica restarts. Then name the deciding target: if ITL is already met at TP=4, two replicas usually serve more per GPU.

Choose TP for fit and latency, add replicas with -dp or separate servers for traffic, and check the KV cache size and concurrency lines in the startup log.

You go from one replica to -dp 4 with --max-num-seqs 256 and --max-num-queued-reqs 256. Under load, what happens?

  1. Each rank admits up to 256 queued requests, so 1,024 in total
  2. The server rejects new requests once about 256 are in flight across all ranks, while ranks still have room
  3. Each rank is limited to 64 running requests

max-num-seqs is per rank, but the queued caps count across the whole server.

Running prefill and decode apart in vLLM

Last part: the parallelism flags. Still unsolved: what vLLM actually offers for separate prefill and decode pools, and how mature it is.

A team reads that disaggregation is how large providers serve. They want it on Monday. What will vLLM v0.31.0 give them, and what will it not?

vLLM's docs label disaggregated prefilling experimental and subject to change. They say vLLM relies on third-party connectors for production-level disaggregated prefilling.

The docs give two reasons to use it: tuning TTFT and ITL separately, with different parallel settings for each phase, and controlling tail ITL; they add that it does not improve throughput. They note that chunked prefill with a well-chosen chunk size can reach the same tail-ITL goal, but that the right size is hard to find in practice.

The moving part is a KV connector. Connectors in v0.31.0 include NixlConnector, MooncakeConnector, LMCacheConnectorV1, OffloadingConnector, MultiConnector and ExampleConnector. An instance's kv_role is kv_producer, kv_consumer or kv_both, and kv_load_failure_policy is fail by default, with recompute as the alternative.

vllm serve $MODEL --port 8100 \
  --kv-transfer-config '{"kv_connector":"NixlConnector","kv_role":"kv_producer"}'
vllm serve $MODEL --port 8200 \
  --kv-transfer-config '{"kv_connector":"NixlConnector","kv_role":"kv_consumer"}'
# a proxy then sends each request to :8100 (max_tokens 1), then to :8200

The research behind it: DistServe's authors argue that colocating the two phases causes prefill-decode interference and ties both phases to one resource and parallelism plan. The DistServe paper argues that chunked prefill trades TTFT for TPOT and cannot remove the interference between the two phases. Splitwise splits the phases of LLM inference across different machines. Note the disagreement: DistServe says chunking cannot remove interference; vLLM's docs say a good chunk size can, if you can find it.

In vLLM v0.31.0, disaggregation is two instances joined by an experimental KV connector, sold on latency control, not on throughput.

Which reason for disaggregating does vLLM's own documentation give?

  1. It raises throughput per GPU
  2. It reduces the KV cache each request needs
  3. It lets TTFT and ITL be tuned separately and keeps tail ITL under control

The docs name separate tuning and tail ITL, and state plainly that throughput does not improve.

Sizing the fleet: GPUs per replica, then replicas

Last part: routing and cancellation. Still unsolved: how many GPUs to ask for, colocated or split.

Product asks for 66.7 requests per second of chat, 2,000-token prompts and 300-token answers, TTFT under 1 s and ITL under 100 ms. Finance asks for a GPU count by Friday.

The planner below is Parts 1 to 6 assembled. It never uses GPU utilization:

  1. Fit: for each TP size, weights per GPU = weights ÷ TP; what is left of 92% of memory, minus a reserve, is the KV pool (Part 2). Keep TP sizes that hold at least one request.
  2. Step time: a TP group runs like one GPU with TP times the speed, plus the all-reduces (this page), using Part 5's step model.
  3. Colocated capacity: try chunk budgets and batch sizes; keep the highest request rate whose ITL and TTFT meet the targets (Part 5).
  4. Split capacity: size a prefill pool by prompt tokens per second, a decode pool by the batch that meets ITL, and add the KV transfer to TTFT.
  5. Replicas = target rate ÷ (planned peak utilization × capacity per replica), rounded up. The 20% headroom stands in for queueing, which this model does not simulate.

The hardware figures it uses: NVIDIA lists the H200 SXM with 141 GB of memory at 4.8 TB/s and NVLink at 900 GB/s. NVIDIA lists both the H100 SXM and the H200 SXM at 1,979 teraFLOPS of BF16 and 3,958 teraFLOPS of FP8 Tensor Core throughput, with sparsity. The planner halves those to dense, as Part 1 did. A DGX H100 has 8 GPUs and 8 single-port ConnectX-7 InfiniBand cards at up to 400 Gb/s each. That is about 50 GB/s each way per GPU across nodes, a ninth of NVLink.

For Friday's question the planner says: TP=4 colocated, 9 replicas, 36 GPUs; split pools need 8 prefill and 3 decode replicas, 44 GPUs. TP=2 technically fits but holds one request, so it would need hundreds of replicas. With FP8 weights and cache, TP=2 holds 188 requests and the colocated fleet drops to 18 GPUs.

"How many GPUs for this load?" A strong answer is a chain of stated assumptions: request mix, SLOs, the fit per TP size, per-replica capacity under both SLOs, headroom for queueing, then replicas. It ends with what would change the number most (here, FP8 halves it) and with a load test, because the model is a best case at 100% of peak.

Plan from memory fit to per-replica capacity under the SLOs to replicas with headroom, and treat the result as a lower bound to load-test.

Scaling on the right signal when traffic jumps 10 times

Last part: a planned fleet size. Still unsolved: what tells you, live, that the fleet is too small, and how fast new replicas arrive.

A launch sends 10 times the usual chat traffic within an hour. The autoscaler adds replicas when GPU utilization passes 80%. It already read 95% at normal load, so it scaled out once, early, and then had nothing left to react to.

This is Part 1's trap at fleet scale. NVML reports GPU utilization as the percent of time over the sample period during which one or more kernels was executing on the GPU. A busy decode loop always has a kernel running, so the number sits near 100% whether the replica is coasting or drowning.

Scale on what users feel, or on what predicts it. vLLM exports vllm:num_requests_waiting, vllm:kv_cache_usage_perc, where 1 means 100%, and vllm:request_queue_time_seconds, a histogram of time spent waiting. vLLM's llm-d page describes scaling vLLM pools on queue depth and true demand rather than raw GPU utilization.

Memory. If one request of max_model_len tokens would need more KV memory than is available, vLLM refuses to start and suggests raising gpu_memory_utilization or lowering max_model_len. At runtime it does not crash for lack of KV room. vLLM's tuning guide says it preempts requests to free KV space and recomputes them later, which can hurt end-to-end latency, and lists raising gpu_memory_utilization or tensor_parallel_size among the fixes. vLLM exports vllm:num_preemptions as a running count.

Hot prefix. Mooncake's paper notes that system prompts are used by almost every request, and that the hottest KV blocks should be copied to several nodes to avoid congested fetches. The production-stack loadaware mode scores each replica by its matched share of the prompt minus a weighted relative load, so an idle replica without the cache can win over a busy one with it.

Pure prefix routing has no brake. The production-stack prefixaware mode sends a request to a replica that already matched the prefix, and its code says it does not track eviction. A system prompt shared by every request therefore keeps going to the first replica that saw it, however long its queue grows.

Transfers. NixlConnector exports vllm:nixl_xfer_time_seconds, vllm:nixl_num_failed_transfers and vllm:nixl_num_kv_expired_reqs, the last counted on the prefill instance. Blocks waiting for a stuck decoder also hold prefill KV memory until their lease runs out.

Stragglers. Hugging Face's guide notes that in tensor parallelism each GPU computes its slice and the results are synchronized to rebuild the full result. An all-reduce finishes when its slowest member does, 160 times per step for the 70B model, so one throttled GPU sets the pace of the whole replica. vLLM's guide says that if NCCL's logs show NET/Socket instead of NET/IB/GDRDMA, cross-node traffic is running over plain TCP, which is not efficient for tensor parallelism.

Watch every signal per replica, not averaged: hot prefixes, stuck transfers and slow GPUs each hit one replica while the fleet average looks fine.

In one TP=4 replica, one GPU's clocks drop to 70% because of cooling. The other three are fine. Predict that replica's ITL compared with its siblings.

Its ITL rises for every request on it, roughly as if all four GPUs had slowed: each of the 160 all-reduces per step waits for the slow GPU's share of the layer before anyone continues. Averages across 40 replicas barely move, which is why you compare ITL per replica at equal load and replace the outlier.

Explain what breaks first when an LLM fleet sees 10 times its load, and how you would detect and fix each failure.

First, queues grow: TTFT rises while ITL stays flat. Utilization does not show it, so the autoscaler must watch queue time, waiting requests and KV usage, and start early because new replicas take minutes to load weights and warm up. Then individual replicas fail in ways averages hide: KV memory fills and preemptions start; a hot shared prefix piles onto one replica under prefix-only routing; KV transfers stall and hold prefill memory until the lease expires; and one slow GPU slows every all-reduce in its TP group. Each shows up only when you compare replicas, and each has a fix: more KV room, load-aware routing, a transfer failure policy, and replacing the slow node.

When to split prefill from decode, and when not to

Last part: failures and their signals. Still unsolved: given all of it, when is disaggregation worth its machinery?

An architecture review proposes separate prefill and decode pools for every model the company serves. Your planner says the 70B chat fleet would need 44 GPUs split against 36 colocated.

The planner's verdict is consistent: at every mix it was tested on, a colocated replica with a well-chosen chunk budget never needs more GPUs than split pools. Colocated replicas fill the spare compute of memory-bound decode steps with prefill chunks; split pools give that away. That matches vLLM's own note, quoted earlier on this page, that disaggregation does not improve throughput.

The costs grow as models and prompts shrink. Shipping a token's KV cache over a 50 GB/s network link takes 4.6% of the time its prefill math takes for the 70B model, but 16% for the 8B model, which has more KV bytes per FLOP. At 20 requests per second the 8B model needs 1 GPU colocated but 2 split, because each pool needs at least one replica. Short prompts leave little interference to remove in the first place.

Default to colocated replicas with chunked prefill; split prefill from decode when tail ITL must survive a wide prompt mix or the phases need different hardware, and expect to pay GPUs for it.

Disaggregation buys latency control, not throughput. With short prompts and the target already met, it only adds GPUs and moving parts.

Three prompts. For each, state assumptions, estimate, draw the architecture and name what you give up, before opening the reference. The numbers come from this page's tested planner.

1. Serve a 70B model to 2,000 concurrent chat users at TTFT p95 under 1 s and ITL p99 under 100 ms, on H100 nodes.

Assumptions. Each user sends a message every 30 s, so 66.7 requests per second. Prompts average 2,000 tokens with history, answers 300. BF16 to start.

Estimate. 140 GB of weights: TP=4 is the smallest useful size (188 requests fit; TP=2 fits one). Colocated TP=4 replicas sustain about 9.7 requests per second each under both targets, so 9 replicas at 80% planned peak: 36 GPUs, five 8-GPU nodes with room for a spare replica. FP8 weights and cache cut it to 18 GPUs on TP=2.

Architecture. Stateless gateway with auth, limits and a deadline; router with session affinity on the conversation id and a load-aware fallback; vLLM replicas with chunked prefill; SSE streaming with disconnects passed through; autoscaling on queue time and waiting requests with one spare replica.

Given up. No disaggregation: it would cost 44 GPUs for ITL isolation the target does not need. 20% headroom is paid in idle capacity. FP8 needs an accuracy check on our own tasks before it replaces BF16.

2. Long-document question answering: 16,000-token prompts, 200-token answers, 10 requests per second, TTFT p95 under 3 s, ITL p99 under 50 ms, 70B in FP8.

Assumptions. Prompt lengths vary around 16,000; documents repeat across users. Each KV transfer would be 2.6 GB in FP8.

Estimate. Colocated TP=2 replicas meet both targets only with a small chunk budget (512 tokens), at about 1.2 requests per second each: 22 GPUs. Split pools need 26 GPUs; even over the network the transfer adds about 26 ms against a TTFT budget of 3 s.

Architecture. Start colocated with a small chunk budget and prefix-aware routing by document id, so repeated documents hit the cache. Measure ITL p99 under the real length mix. If the tail breaks on the longest documents, move to split pools with NIXL and a recompute failure policy.

Given up. Colocated: TTFT is spent to protect ITL, and the budget must be re-tuned when lengths shift. Split: about 18% more GPUs, an experimental connector and a second failure path.

3. An 8B support bot at 100 requests per second, 500-token prompts with a shared system prompt, 200-token answers, TTFT under 0.5 s, ITL under 50 ms.

Assumptions. One H100 per replica, BF16, the system prompt is most of each prompt.

Estimate. The model fits on one GPU with a large KV pool. Two single-GPU replicas carry the load in the planner; split pools would need three. Add a third replica as a spare.

Architecture. No TP, no split. Load-aware prefix routing, so the shared system prompt stays cached without piling onto one replica. Scale on queue time.

Given up. Lowest possible ITL from TP, which the target does not need. The router carries more logic than round-robin.

One replica is a memory budget run by a scheduler; a fleet is many of them behind a router that knows where each cache lives.

Part 1. Why does decode at batch 1 leave most of a GPU's arithmetic idle?

  1. Decode runs on the CPU
  2. Each step reads every weight to produce one token per request, so memory bandwidth, not math, sets the pace
  3. Attention is too expensive to batch

Low arithmetic per byte read puts decode on the memory side of the roofline.

Part 2. A replica is memory-capped at 50 concurrent long requests. Which change raises that number without new GPUs?

  1. Storing the KV cache in FP8 instead of BF16
  2. A GPU with faster Tensor Cores and the same memory
  3. Raising the requests' priority

Halving bytes per cached token roughly doubles the requests that fit in the same pool.

Part 3. Under static batching, short answers in a batch with one long answer cause what?

  1. Preemption of the long answer
  2. A larger KV cache per request
  3. Finished slots sit idle until the longest request ends, and new requests wait

Continuous batching fixes this by admitting and retiring requests every step.

Part 4. With vLLM's prefix caching on paged KV blocks, why can two requests with the same system prompt share KV memory?

  1. Because they share the weights
  2. Their identical full leading blocks hash the same, so both block tables point at the same physical blocks
  3. Because the scheduler merges them into one request

Blocks are identified by their content and position, so a shared prefix maps to shared blocks.

Part 5. Raising the chunk budget from 2,048 to 8,192 tokens does what to a colocated replica?

  1. Long prompts finish prefill sooner, and steps that carry a chunk get longer, so the worst ITL rises
  2. The KV cache holds more requests
  3. ITL p99 falls

The budget is the dial between TTFT for long prompts and the largest gap between tokens.

Part 6. Why does speculative decoding help less at high concurrency?

  1. It changes the output distribution at high batch
  2. The draft model stops fitting in memory
  3. Verifying several positions per request uses compute that a large batch already needs, so the step stops being memory-bound

Speculation spends spare compute; a big batch leaves less of it.

Part 7. Which statement is true?

  1. Splitting prefill from decode raises throughput per GPU
  2. Tensor parallelism pays two all-reduces per layer, while dense replicas send nothing to each other but each keep their own KV cache
  3. Replicas share one KV cache, so routing does not matter

Tensor parallelism trades communication for per-step speed; replicas trade cache locality for independence.

Final explain-back: in five minutes, walk an interviewer from one request on one GPU to a fleet serving thousands of users.

A request has two phases: prefill reads the prompt in one compute-bound pass and sets TTFT; decode makes one token per step, limited by reading the weights and KV cache, which sets ITL. The KV cache grows with every token and caps how many requests fit, so servers batch continuously, store the cache in fixed-size blocks, and share prefixes. A scheduler with a chunk budget and queue caps keeps TTFT and ITL inside their targets, and goodput counts only requests that meet them. Quantization and speculation make each token cheaper. When one GPU is not enough, tensor parallelism splits each layer inside a node, pipeline parallelism spans nodes, and replicas add throughput; a router sends each request where its cache lives without overloading one replica, the fleet scales on queue time and KV usage, and prefill and decode are split only when tail ITL demands it.
